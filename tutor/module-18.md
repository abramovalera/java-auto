## Цели модуля и вопросы

Формат: вопрос → **суть правильного ответа** → типичные заблуждения.

### О1. Автотесты, пирамида, что автоматизировать
- «Чем автотест отличается от ручного теста? Что общего?» → **те же шаги и ожидаемый результат тест-кейса, но выполняет и сравнивает программа; технически — JUnit-тест.**
- «Нарисуй пирамиду тестов и объясни, почему она такой формы» → **внизу много быстрых дешёвых юнит-тестов, в середине API, наверху мало медленных хрупких UI-тестов.**
- «Назови две вещи, которые не стоит автоматизировать» → **оценку удобства/дизайна, исследовательское тестирование, разовые проверки, капчу, часто меняющийся функционал.**
- Заблуждение: «автотесты заменят ручных тестировщиков». Нет — забирают рутину, думать о сценариях всё равно человеку.
- Заблуждение: «UI-тестов должно быть больше всех — они самые честные».

### О2. Хороший автотест
- «Четыре свойства хорошего автотеста?» → **независимый, повторяемый, понятный, с проверками.**
- «Что такое flaky-тест? Причины?» → **то проходит, то падает без изменений кода; зависимость от других тестов/общих данных, sleep, хрупкие локаторы, нестабильный стенд.**
- «Тест упал. Твои действия по шагам?» → **прочитать сообщение (ожидали/получили/где), скриншот, воспроизвести руками; решить — баг продукта (баг-репорт) или проблема теста/стенда/данных.**
- Заблуждение: «упал — значит баг» и «упал — перезапущу, пока не позеленеет».

### О3. HTML, DOM, DevTools
- «Что такое тег, элемент, атрибут?» → **тег — слово в угловых скобках, элемент — от открывающего до закрывающего тега, атрибут — `имя="значение"` внутри открывающего тега.**
- «Чем `id` отличается от `class`? Зачем `data-test-id`?» → **id уникален, class для оформления и общий у многих, data-test-id — для тестов, дизайн не трогает, поэтому его не меняют.**
- «Как в DevTools проверить локатор?» → **Elements → Ctrl+F → «1 of 1»; или Console: `$$("css")`, `$x("xpath")`.**
- «Элемент есть в HTML — значит, его видно?» → **нет: hidden, ещё не показан, за экраном; поэтому проверяют visible.**

### О4. Локаторы CSS и XPath
- «`button.green` и `button .green` — в чём разница?» → **без пробела — у кнопки класс green; с пробелом — элемент green внутри кнопки.**
- «Чем `>` отличается от пробела?» → **прямой ребёнок против любой глубины.**
- «Почему `//div[@class='book-card']` не находит `<div class="card book-card">`?» → **XPath сравнивает строку атрибута целиком; нужно `contains(@class,'book-card')` или CSS `.book-card`.**
- «Что умеет XPath, чего не умеет CSS?» → **поиск по тексту (`text()`, `contains`) и движение вверх (`..`, `ancestor::`).**
- «Лестница стабильности?» → **data-test-id → id → name/type → осмысленный класс → текст → путь/индекс.**
- «Почему нельзя брать локатор через "Copy XPath"?» → **браузер выдаёт абсолютный/индексный путь — хрупкий; плюс навык не тренируется.**
- Заблуждение: «чем длиннее локатор, тем точнее, тем лучше».
- Заблуждение: `$("email")` найдёт поле с id email (на самом деле ищет тег `<email>`).

### О5. Selenide и ожидания
- «Чем Selenide отличается от Selenium?» → **обёртка над Selenium: короткий синтаксис, автоматические ожидания, скриншоты при падении.**
- «Как работает `shouldBe(visible)`?» → **повторяет проверку каждые 200 мс до `Configuration.timeout` (по умолчанию 4 с); прошло — дальше, нет — падение с сообщением и скриншотом.**
- «Почему `Thread.sleep` плох?» → **ждёт фиксированное время: если раньше — потеря времени, если позже — всё равно падение.**
- «`text` vs `exactText`?» → **подстрока против полного совпадения; регистр оба по умолчанию не учитывают.**
- «`getText()` ждёт?» → **нет нужного текста не ждёт — просто читает; ждут только `should…`.**
- «Что такое `$` в Java?» → **обычный статический метод класса Selenide; `$` — допустимый символ имени.**
- Заблуждение: «AssertJ + getText — то же самое, что shouldHave».

### О6. Page Object
- «Что такое Page Object и зачем?» → **класс страницы: приватные локаторы + методы-действия; правка в одном месте, тест читается как тест-кейс.**
- «Что вернёт `loginAs` при успехе? А при ожидаемой ошибке?» → **объект следующей страницы (CatalogPage); `this` (LoginPage).**
- «Где наследование, где композиция?» → **`CatalogPage extends BasePage` — is-a; страница хранит `Header` — has-a.**
- «Можно ли проверки в Page Object?» → **методы `should…` можно, но ожидаемое значение передаёт тест.**
- ★ «Почему внутри `LoginPage.open()` пишут `Selenide.open("/login")`?» → **метод класса перекрывает статически импортированный `open`.**
- Заблуждение: «Page Object — это чтобы тесты работали без браузера».

### О7. Структура тестового проекта
- «Какие пакеты и что в каждом?» → **pages, tests, data, config (+ resources/config.properties).**
- «Что в BaseTest?» → **`@BeforeAll` настройка Selenide (static), `@AfterEach` закрытие браузера.**
- «Порядок `@BeforeEach` в родителе и наследнике? `@AfterEach`?» → **до — сначала родитель; после — сначала наследник.**
- «Почему поля тестового класса не переживают тест?» → **JUnit создаёт новый объект на каждый тест.**
- «Класс назвали `LoginChecks` — запустит ли его `gradle test`?» → **да: с `useJUnitPlatform()` Gradle отдаёт JUnit все классы, тесты ищутся по `@Test`. А в Maven-проекте — нет: surefire по умолчанию берёт `*Test`, `*Tests`, `Test*` («в IDEA запускается, а на CI 0 тестов»). Поэтому классы всё равно называют `…Test`.**
- «`gradle test` показал 0 тестов, хотя они есть — что проверить?» → **`useJUnitPlatform()` в `tasks.test { }`.**
- «Где хранить адрес стенда и пароли?» → **адрес — config.properties с переопределением `-D`; секреты — переменные окружения / секреты CI, не в Git.**
- «Запустил `gradle test -Dbrowser=firefox`, а тест всё равно в Chrome — почему?» → **тесты идут в отдельной JVM, `-D` попал в JVM Gradle; нужен проброс в `build.gradle.kts`: `tasks.test { systemProperty("browser", …) }` (в уроке 18.6 — цикл по ключам с `System.getProperty(key)?.let { … }`).**
- «Что такое Allure?» → **отчёт по прогонам: шаги, скриншоты, история.**

### О8. API-тесты
- «Из чего состоит HTTP-запрос и ответ?» → **метод, адрес, заголовки, тело / статус, заголовки, тело.**
- «GET/POST/PUT/DELETE?» → **получить / создать / заменить / удалить.**
- «200, 201, 400, 401, 403, 404, 500?» → **ок, создано, плохой запрос, не представился, нет прав, нет такого, сервер упал (почти всегда баг).**
- «given/when/then?» → **подготовка (заголовки, тело) → действие (метод и адрес) → проверки (статус, тело).**
- «Зачем API-тесты автоматизатору UI?» → **быстрые, стабильные, готовят данные для UI-тестов.**

### О9. Тест-дизайн в автотестах
- «Классы эквивалентности и границы на примере "скидка от 1000"?» → **<1000 и ≥1000; границы 999/1000; плюс невалидные (отрицательное, пусто).**
- «Как понять, что тест хороший, а не просто зелёный?» → **он падает, когда в коде баг (идея мутаций из задачи m18-t07).**
- «Зачем параметризованный тест?» → **одна логика — таблица данных; легко добавить случай.**

## Банк головоломок

Давай по одной. Сначала ответ и «почему», потом разбор. ★★★ — со звёздочкой.

### Какой локатор найдёт? Сколько найдёт?
HTML для задач 1–6:
```html
<div class="cart" data-test-id="cart">
  <ul class="items">
    <li class="item" data-test-id="item-7"><span class="name">Чистый код</span><button class="btn remove">Удалить</button></li>
    <li class="item sale" data-test-id="item-9"><span class="name">Java для тестировщиков</span><button class="btn remove">Удалить</button></li>
  </ul>
  <input id="promo" name="promo" placeholder="Промокод">
  <button class="btn btn-primary" data-test-id="checkout" disabled>Оформить</button>
</div>
```
1. `.items .remove` → **2** кнопки.
2. `.items > .remove` → **0**: кнопки не прямые дети `ul`, они внутри `li`.
3. `li.sale .name` → **1**: «Java для тестировщиков».
4. `//li[@class='item']` → **1**: только первый li (у второго class = "item sale", XPath сравнивает целиком). Ловушка!
5. `//span[text()='Чистый код']/../button` → кнопка «Удалить» у «Чистого кода». Попроси объяснить `..`.
6. `$("promo")` в Selenide → ищет тег `<promo>`, упадёт с ElementNotFound через таймаут. Правильно `#promo` или `[name='promo']`.
7. `[data-test-id='checkout']` и `//*[@data-test-id='checkout']` — оба найдут кнопку; почему `*` в XPath? → **тег не важен, верстальщик может его поменять.**
8. ★ `//span[contains(text(),'java')]` → **0**: XPath различает регистр.

### Хрупкий или стабильный?
9. Отсортируй по стабильности: `(//button)[4]`, `#promo`, `.cart .items li:nth-child(2) .btn`, `[data-test-id='checkout']`, `//button[text()='Оформить']` → **data-test-id, #promo, текст, nth-child-цепочка, индекс** (последние два — хрупкие, обсуди почему).
10. «Дизайнер поменял цвет кнопки и перенёс её в шапку. Какие из локаторов выживут?»

### Что проверяет shouldHave / пройдёт ли тест?
11. Текст «Итого: 2 450 ₽». `shouldHave(text("2 450"))` → **пройдёт** (подстрока). `shouldHave(exactText("2 450"))` → **упадёт**.
12. Счётчик показывает «10», ожидаем 1: `shouldHave(text("1"))` → **ложный зелёный**. Как исправить → `exactText("1")`.
13. `shouldHave(text("итого"))` при тексте «Итого: …» → **пройдёт**: регистр не учитывается.

### Ожидания
14. `click(); Thread.sleep(3000); $(".msg").shouldBe(visible);` — сообщение появляется через 0,2 с. Что не так? → **2,8 с впустую; sleep удалить, shouldBe ждёт сам.**
15. ★★ Блок есть сразу с текстом «Загрузка…», через 3 с — «Готово». `Thread.sleep(2000); assertThat($(".status").getText()).isEqualTo("Готово");` → **упадёт: getText не ждёт, assertThat проверяет один раз.**
16. «Как дождаться элемента, который грузится 20 секунд?» → **`shouldBe(visible, Duration.ofSeconds(25))`, не sleep и не глобальный таймаут на всё.**

### Page Object: что вернёт / скомпилируется ли
17. ```java
    new LoginPage().open().loginAs("anna", "qwerty123").shouldShowError("…");
    ```
    `loginAs` возвращает `CatalogPage`, у которого нет `shouldShowError` → **не скомпилируется**. Отлично: типы не дают написать бессмысленный шаг.
18. ★★★ Внутри `LoginPage` есть метод `open()`, и в нём `open("/login")` при `import static …Selenide.*` → **не скомпилируется**: метод класса перекрывает статический импорт.
19. Метод `public void loginAs(String u, String p)` — что плохо? → **теряется переход: тест не знает, где оказался; нельзя продолжить цепочку.**
20. Найди ошибки: публичное поле `public SelenideElement payButton = $(...)` и в методе `$("[data-test-id='pay']").click()` вместо поля → **локатор торчит наружу и продублирован.**

### Независимость и жизненный цикл JUnit
21. Поле `int counter = 0;`, два теста делают `counter++` и печатают → **`11`**: новый объект на тест.
22. То же с `static int counter` → **`12`** (или в другом порядке тестов — тоже 12) — общее состояние, плохо.
23. BaseTest (`@BeforeEach` печатает B, `@AfterEach` — b) + наследник (L, l) + тест (T) → **`BLTlb`**.
24. `@BeforeAll` без `static` → **компилируется, JUnit при запуске сообщает ошибку, тесты класса не выполняются.**
25. `test2` проверяет корзину, в которую книгу положил `test1`. Почему это бомба? → **порядок не гарантирован; отдельно test2 не проходит; flaky.**
26. Класс `CartChecks` с тестами: `gradle test` → **запустит** (ищет по `@Test`); `mvn test` → **0 тестов** (surefire ищет `*Test`). Вопрос с подвохом про разницу сборщиков.

### API
27. На POST с пустым названием книги сервер ответил 500. Баг? → **да, ожидается 400 с сообщением.**
28. Отличи 401 и 403 на примере → **без токена / с токеном покупателя в админку.**

- **m18-t05 `NookEmailRuleTest`** — «Почему по одному неправильному адресу на каждое нарушение правила?» (иначе не понять, что именно ломается); «Как ты подобрал 59 и 60?» (64 и 65 символов — граница длины). Подвохи: `Math.min(t + poll, timeout)` — последняя проверка ровно в таймаут; появившийся между проверками элемент находится на следующей. Спроси, как это связано с `Configuration.pollingInterval` и `timeout` у Selenide.
- **m18-t07 `NookDiscountBugHunterTest`** (★★★) — «Какую проверку ловит каждый мутант?» (A — 1000 без бонуса; B — 5000 с бонусом = 12; C — <1000 с бонусом = 5; D — отрицательная сумма). Если ученик подглядел мутантов и написал ровно 4 проверки — спроси, какие проверки он добавил бы по требованиям без знания мутантов (4999, 0, 7000 и т.д.). ## Итоговый проект (проверяет наставник, без .task)

Ученик в **отдельном** Gradle-проекте (не в `workspace/` курса — там нет сборщика) пишет UI-автотесты на **Selenide + JUnit 5 + AssertJ** по шаблону **Page Object** для учебного сайта. Пример стенда из урока 18.8 — `https://the-internet.herokuapp.com` (только как площадка для самостоятельной практики; подойдёт любой учебный стенд). Задание описано в уроке `site/lessons/m18/08-final-project.html`.

**Как принимать.** Ученик пишет «Хочу сдать итоговый проект» и даёт путь к папке проекта. Ты читаешь код (файлы в его проекте ты **не правишь** — как и в workspace), просишь запустить тесты у себя (окно Gradle → Tasks → verification → test или `gradle clean test`) и прислать результат, задаёшь вопросы. Формат — как код-ревью у тимлида: 1–2 замечания за раз, вопросами.

**Обязательные требования** (все — для зачёта):
1. Gradle-проект (Kotlin DSL): в `build.gradle.kts` junit-jupiter, selenide, assertj-core через `testImplementation`, `useJUnitPlatform()`; собирается и запускается через Gradle → test (`./gradlew test`). Wrapper (`gradlew`, `gradle/wrapper`) — в репозитории.
2. Пакеты `pages`, `tests`, `data`, `config` (названия могут отличаться, смысл — нет); `config.properties` с адресом сайта/браузером; `BaseTest` с настройкой и закрытием браузера.
3. Минимум **10 тестов** на **4+ страницах**; у каждой страницы — свой Page Object; повторяющиеся куски — компоненты или `BasePage`.
4. **В тестах нет ни одного локатора** (`$(`, `$$(`, `By.` только в `pages`).
5. Локаторы **приватные**, без абсолютных путей и индексов (`/html/...`, `[3]`, `nth-child`), если без них можно обойтись. Про любой локатор ученик объясняет, почему выбрал его (на учебном сайте нет data-test-id — смотри, что выбрано лучшее из доступного: id → name → осмысленный класс → текст).
6. **Нет `Thread.sleep`** — только ожидания Selenide (для Dynamic Loading — `shouldBe(visible, Duration.ofSeconds(…))` или аналог).
7. Методы-переходы возвращают следующую страницу; ожидаемые значения передаёт тест.
8. Есть негативные тесты и хотя бы один **параметризованный** (`@CsvSource`/`@EnumSource`/`@ValueSource`).
9. Независимость: любой тест проходит, если запустить его отдельно; весь набор — **три прогона подряд зелёный**.
10. Git: репозиторий с `.gitignore` (`build/`, `.gradle/`, `.idea/`), README (что тестируется, как запустить, стек), несколько осмысленных коммитов. GitHub — желательно (портфолио), не обязательно.

**Типичные замечания на ревью:** локаторы в тестах; `public` поля-элементы; `void` у методов-переходов; `Thread.sleep` «на всякий случай»; тесты, зависящие друг от друга (выход в одном, вход в другом); копипаст полей между страницами; проверки без ожидания (`getText` + `assertThat` для динамического текста); имена `test1`, `test2`; скопированные из DevTools абсолютные XPath.
