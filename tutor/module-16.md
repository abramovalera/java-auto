## Цели модуля и вопросы

Формат: вопрос → **суть правильного ответа** → типичные заблуждения.

### О1. Процесс, поток, main
- «Чем процесс отличается от потока? Аналогия?» → **процесс — запущенная программа со своей памятью (кухня); поток — исполнитель внутри неё (повар). Потоки делят кучу (объекты), у каждого свой стек (локальные переменные).**
- «В каком потоке выполняется `main`?» → **в потоке с именем main.**
- «Зачем программам многопоточность?» → **скорость: большую работу делят между потоками (файлы, запросы, расчёты); сервер обслуживает многих клиентов сразу; программа не «замерзает», пока что-то долго грузится. Плата — плавающие ошибки из-за общих данных.**
- Заблуждение: «два потока = две копии всех объектов». Нет, объекты общие — отсюда гонки.

### О2. Создание и запуск: Thread, Runnable, start/run, join, sleep
- «Назови способы создать поток» → **наследник Thread с переопределённым run(); Runnable (часто лямбдой) в new Thread; на практике — пул ExecutorService.**
- «Чем `start()` отличается от `run()`?» → **start создаёт новый поток и в нём вызывает run; run — обычный вызов метода в текущем потоке.** Классика собеседований — добиться точного ответа.
- «Что будет при втором `start()`?» → **IllegalThreadStateException; поток одноразовый.**
- «Что делает `join()`? Зачем, если есть `sleep`?» → **join ждёт ровно до конца потока; sleep — гадание на время.**
- «Почему `sleep`/`join` требуют try-catch или throws?» → **бросают проверяемое InterruptedException.**
- «Почему в лямбде нельзя использовать `i` из цикла for?» → **лямбда берёт только effectively final переменные; копия `int n = i;`.**
- «Почему лямбда в потоке не может написать `bowls = 4` в локальную переменную, а `bowls[0] = 4` в ячейку массива — может?» → **локальная переменная должна быть effectively final (лямбда получает копию); у массива не меняется ссылка, а сам массив — общий объект в куче.**
- «Когда завершается программа? Что такое daemon-поток?» → **когда закончились все обычные потоки (не только main); daemon (фоновый) поток программу не держит, JVM его обрывает; setDaemon(true) — только до start().**
- Заблуждение: «потоки печатают в порядке вызова start()». Нет, порядок не гарантирован.

### О3. Гонка данных (race condition)
- «Почему два потока по 100 000 `count++` дают меньше 200 000?» → **count++ = прочитать, увеличить, записать; потоки вклиниваются между шагами, одно обновление перезаписывает другое (lost update).**
- «Data race и race condition — одно и то же?» → **data race — одновременный доступ к переменной без синхронизации, хотя бы один поток пишет; race condition — результат зависит от порядка потоков. `if (a.get() < 10) a.incrementAndGet()` на AtomicInteger — race condition без data race.** Засчитывать, если ученик понимает пример.
- «Почему иногда получается ровно 200 000?» → **потокам повезло не пересечься; ошибка в коде есть всегда, проявляется случайно — отсюда плавающие ошибки.**
- «Поможет ли `join`?» → **нет, join только ждёт окончания, потерю обновлений он не лечит.**
- «Поможет ли `Thread.sleep(1)` в цикле?» → **нет, только меняет тайминги.**

### О4. synchronized и атомики
- «Что делает `synchronized (lock) { … }`? Аналогия?» → **замок/примерочная: внутри одновременно только один поток с этим замком, остальные ждут (BLOCKED).**
- «Что будет замком у `synchronized`-метода? У static synchronized?» → **this; объект-класс.**
- «Почему `synchronized (new Object())` не защищает?» → **каждый раз новый замок, никто не ждёт; замок должен быть общим.**
- «Что такое атомарная операция? Пример» → **неделимая: AtomicInteger.incrementAndGet().**
- «Счётчик — AtomicInteger. Безопасно ли `if (c.get() < 10) c.incrementAndGet();`?» → **нет: связка проверить+изменить не атомарна, нужен synchronized или `updateAndGet(x -> x < 10 ? x + 1 : x)` — метод атомарно применяет лямбду «старое → новое».**
- «Когда AtomicInteger, когда synchronized?» → **одна переменная — атомик; несколько действий вместе — synchronized.**

### О5. ExecutorService, Callable, Future
- «Зачем пул, почему не `new Thread` на каждую задачу?» → **потоки дорогие (память, ОС); пул переиспользует N потоков для любого числа задач; аналогия — смена официантов.**
- «Что делают `submit` и `shutdown`? Что будет без shutdown?» → **submit ставит задачу в очередь и сразу возвращает Future; shutdown закрывает приём; без него программа не завершится.**
- «Runnable и Callable — разница?» → **run() void и без проверяемых исключений; call() возвращает V и может бросать.**
- «Что такое Future, что делает `get()`?» → **«чек» на будущий результат; get блокирует до готовности; ошибку задачи приносит как ExecutionException (причина в getCause).**
- «Как не зависнуть на get навсегда?» → **get(timeout, unit) → TimeoutException.**
- «Как дождаться всех задач пула, если результаты не нужны?» → **shutdown(), затем awaitTermination(10, TimeUnit.SECONDS): ждёт не дольше срока, возвращает true/false, бросает InterruptedException; TimeUnit — enum из java.util.concurrent. Без shutdown прождёт весь срок и вернёт false.**
- Заблуждение: «submit выполняет задачу сразу и ждёт». Нет.

### О6. volatile и видимость
- «Флаг `running` без volatile, второй поток крутится в `while (running)`. Что может случиться?» → **поток может никогда не увидеть false и крутиться вечно: JVM/процессор держат копию значения.**
- «Что гарантирует volatile? Делает ли он count++ безопасным?» → **только видимость; count++ всё равно теряет обновления.**
- Аналогия ученика (доска и блокнот) — засчитывать.

### О7. Deadlock и потокобезопасные коллекции
- «Что такое deadlock? Нарисуй» → **два потока держат по замку и ждут замок друг друга, круг ожидания; программа висит без ошибок.**
- «Как избежать?» → **брать замки всегда в одном порядке; вариант — tryLock с таймаутом.**
- «Как понять, что программа в deadlock?» → **висит, процессор не загружен; thread dump (Dump Threads в IDEA) показывает «Found one Java-level deadlock».**
- «Можно ли пополнять ArrayList из нескольких потоков? Что взять?» → **нет: теряются элементы, бывает исключение; Collections.synchronizedList, CopyOnWriteArrayList; вместо HashMap — ConcurrentHashMap.**
- «`map.put(k, map.get(k) + 1)` на ConcurrentHashMap безопасно?» → **нет, две операции; merge(k, 1, Integer::sum).**
- «Чем synchronized отличается от ReentrantLock?» → **synchronized отпирается сам; ReentrantLock — объект, lock()/unlock() в finally, умеет tryLock и ожидание с таймаутом. По умолчанию — synchronized.**
- «Что такое livelock и starvation?» → **livelock — потоки всё время уступают друг другу и не продвигаются; starvation — одному потоку никогда не достаётся замок/процессор.** Достаточно одной фразы.
- «Производитель — потребитель: как передать работу между потоками?» → **BlockingQueue: put ждёт места, take ждёт элемента; сигнал конца — «ядовитая пилюля». Вручную — wait/notifyAll внутри synchronized, wait в while.**

### О8. Независимые данные и предсказуемый результат
- «Почему код, который правильно работает в одном потоке, ломается в нескольких?» → **общие изменяемые данные: static-поля, общий счёт или счётчик, общий файл; зависимость от порядка выполнения.**
- «Как сделать потоки независимыми?» → **свои данные у каждого потока (локальные переменные, своя ячейка массива, своя часть массива), результат — через Future, общий итог собирает main.**
- «Почему `Thread.sleep` не годится, чтобы дождаться потока? Что вместо?» → **гадание на время: либо слишком долго, либо поток не успеет — плавающая ошибка; `join()`, `Future.get()`, `awaitTermination` ждут ровно до конца работы.**
- «Как сделать вывод многопоточной программы одинаковым при каждом запуске?» → **join / Future.get, собрать результаты, отсортировать, итоги — через atomic/synchronized.**

## Банк головоломок

Давай по одной. Сначала ответ и «почему», потом разбор. ★★★ — со звёздочкой, честно предупреждай, что это сверх уровня модуля.

### Что выведется?
1. ```java
   Thread t = new Thread(() -> System.out.println(Thread.currentThread().getName()));
   t.run();
   ```
   → `main`: run() — обычный вызов.
2. То же с `t.start(); t.join();` → `Thread-0` (если других Thread ещё не создавали).
3. ```java
   Thread t1 = new Thread(r); t1.run();
   Thread t2 = new Thread(r); t2.start();   // r печатает имя потока
   ```
   → `main`, затем `Thread-1`: номер даётся при создании объекта, t1 стал Thread-0.
4. ```java
   Thread t = new Thread(() -> System.out.print("A"));
   t.start(); t.join(); System.out.print("B");
   ```
   → всегда `AB`.
5. То же без `join` → `AB` или `BA`, заранее неизвестно (чаще `BA`).
6. `static int x = 0;` поток делает `x = 5`, main без join печатает `x` → 0 или 5, чаще 0.
7. Два потока по 50 000 `count++` над `static int`, оба join → число ≤ 100 000, каждый раз разное.
8. То же с `AtomicInteger.incrementAndGet()` → ровно 100 000.
9. ```java
   AtomicInteger n = new AtomicInteger(5);
   System.out.println(n.getAndIncrement() + " " + n.incrementAndGet());
   ```
   → `5 7`.
10. ```java
    Future<Integer> f = pool.submit(() -> { Thread.sleep(200); return 10; });
    System.out.print("Ждём "); System.out.print(f.get() * 2);
    ```
    → `Ждём 20`.
11. main печатает «main закончил» и выходит, помощник через 500 мс печатает «Помощник закончил» → обе строки, программа ждёт обычный поток.
12. Задачи пула добавляют "C", "A", "B" в synchronizedList, после awaitTermination — `Collections.sort` и печать → `[A, B, C]` всегда.

### Скомпилируется ли?
13. `for (int i = 0; i < 3; i++) new Thread(() -> System.out.println(i)).start();` → **нет**, i не effectively final.
14. `public static void main(String[] args) { Thread.sleep(1000); }` → **нет**, не обработано InterruptedException.
15. `Runnable r = () -> { return 42; };` → **нет**, run() void. Нужен `Callable<Integer>`.
16. `Callable<Integer> c = () -> { Thread.sleep(100); return 1; };` → **да**: call() объявлен с throws Exception.
17. `Runnable r = () -> Thread.sleep(100);` → **нет**: run() не может бросать проверяемое исключение.

### Скомпилируется, но что будет при запуске?
18. `t.start(); t.start();` → один запуск и `IllegalThreadStateException`.
19. Пул без `shutdown()`, `f.get()` отработал → напечатает и **не завершится**.
20. Флаг `static boolean running` без volatile, помощник в `while (running) {}` → может крутиться вечно.
21. Два метода берут `synchronized (a) { synchronized (b) … }` и `synchronized (b) { synchronized (a) … }` с паузой внутри → зависание (deadlock).
22. ★★ `t.setDaemon(true)` у потока с `while (true) {}`, main печатает «Пока!» → печатает и завершается: daemon не держит JVM.
23. ★★ `t.start(); t.setDaemon(true);` → `IllegalThreadStateException`: daemon задают до start.
24. Задача в пуле делит на ноль, main вызывает `f.get()` → `ExecutionException`, причина — `ArithmeticException`. Без `get()` исключение никто не увидит.

### Найди ошибку
25. `static volatile int count; … count++` из 4 потоков → volatile не даёт атомарности.
26. `synchronized (new Object()) { count++; }` → замок каждый раз новый.
27. Методы `payment()` (wallet → basket) и `refund()` (basket → wallet) → разный порядок замков, deadlock.
28. Интернет-магазин: `static String orderId;` — поток A оформляет заказ, поток B оформляет свой, A отправляет чек по `orderId` → при одновременной работе A отправляет чек по чужому заказу.
29. `payer.start(); Thread.sleep(3000); if (status == "Оплачено") System.out.println("Готово");` (поток `payer` записывает результат оплаты в общее поле `status`) → две проблемы: sleep вместо `join()` (гадание на время) и сравнение строк через `==` (модуль 8).

### Почему здесь ошибка?
30. `java.lang.IllegalThreadStateException at java.lang.Thread.start` → поток запускают второй раз.
31. `error: local variables referenced from a lambda expression must be final or effectively final` → лямбда в потоке берёт меняющуюся переменную.
32. `java.util.concurrent.ExecutionException: java.lang.NullPointerException` → NPE случился внутри задачи пула, а увидели его на `get()`.

### Ожидание и очереди
33. Пул без `shutdown()`, сразу `awaitTermination(3, TimeUnit.SECONDS)` и печать результата → ждёт все 3 секунды, возвращает `false`, программа потом не завершается.
34. Продавец в цикле `shelf.take()`, пекарь положил 5 булочек и не положил «КОНЕЦ» → 5 продаж, потом вечное ожидание в `take()`.
35. `String[] dish = {"суп"}; new Thread(() -> dish[0] = "борщ").start();` — скомпилируется? → **да**: меняется ячейка, ссылка `dish` не меняется. А если ниже есть `dish = new String[1];` → **нет**, `dish` уже не effectively final.
36. `lock.lock(); count++; lock.unlock();` с `ReentrantLock` — что не так? → нет `try/finally`: при исключении замок не отпустится, остальные потоки повиснут.
