## Цели модуля и вопросы

Формат: вопрос → **суть правильного ответа** → типичные заблуждения.

### О1. Отладчик: брейкпоинт и шаги
- «Программа остановилась на строке `int x = 5;`. Чему равна x?» → **переменной ещё нет: отладчик стоит ПЕРЕД строкой.**
- «Чем Step Over отличается от Step Into? Аналогия?» → **F8 выполняет строку целиком (вызов метода «за кадром»), F7 заходит внутрь твоего метода; рецепт «приготовь крем (стр. 40)».** Step Out (Shift+F8) — доделать метод и вернуться. Resume (F9) — до следующего брейкпоинта.
- «Цикл на 5000 кругов, ошибка на одном заказе. Как остановиться на нём?» → **условный брейкпоинт: правый клик по точке → Condition.**
- «Что делает Evaluate Expression? Чем опасен?» → **вычисляет любое выражение в текущем состоянии; выполняет его по-настоящему, `list.remove(0)` удалит элемент.**
- Заблуждение: «для отладчика надо что-то дописать в код». Нет.
- Заблуждение: «F8 перепрыгнет брейкпоинт внутри вызываемого метода». Нет, остановится на нём.

### О2. Frames, стек вызовов, «под капотом println»
- «Что показывает панель Frames?» → **стек вызовов: текущий метод сверху, main внизу; щелчок по фрейму — его переменные.**
- «Как связаны Frames и stack trace?» → **stack trace — снимок того же стека в момент исключения; читаем снизу вверх.**
- «Как зайти отладчиком внутрь `println`?» → **обычный F7 в JDK не заходит; Force Step Into — Alt+Shift+F7.** Увидит `println → writeln → implWriteln` (имена зависят от версии JDK).
- «Когда отладчик не поможет и нужен лог?» → **сервер/CI/ночной прогон, многопоточные гонки (остановка меняет тайминги), история работы во времени.**

### О3. Git: репозиторий, коммит, индекс, история
- «Зачем Git? Аналогия?» → **история изменений, откат, сравнение, ветки, командная работа; сохранения в игре.**
- «Что такое коммит?» → **снимок проекта + сообщение + автор + время + хеш.**
- «Зачем индекс (staging)?» → **выбрать, что войдёт в коммит; можно закоммитить исправление отдельно от недоделанной фичи.**
- «Что будет, если сделать `git commit -m "…"` без `git add`?» → **коммит не создастся: no changes added to commit.**
- «Цвета файлов в IDEA?» → **красный — untracked, зелёный — добавлен, синий — изменён.**
- «Что сделать перед первым коммитом на новом компьютере?» → **`git config --global user.name` и `user.email`; иначе «Author identity unknown» (IDEA спросит сама окном Git User Name Is Not Defined).** На Windows Git ставится отдельно (git-scm.com или Download and Install в IDEA).
- «Revert и удаление коммита — одно и то же?» → **нет: revert создаёт новый коммит, отменяющий изменения; история сохраняется.**
- «amend, reset, revert — когда что?» → **amend — поправить последний коммит (сообщение, забытый файл); reset (`--soft HEAD~1`, в IDEA Undo Commit) — убрать последний неотправленный коммит, правки остаются; revert — отменить новым коммитом, единственный вариант после push.** amend/reset переписывают историю — только до push. `reset --hard` выбрасывает правки безвозвратно.
- «Что такое хорошее сообщение коммита?» → **коротко отвечает «что сделает этот коммит»: «Почини доставку для суммы 2000». Не «fix», «правки».**

### О4. Ветки, merge, .gitignore
- «Зачем ветки? Аналогия?» → **параллельная линия истории для задачи; черновик и чистовик.**
- «`git switch -c имя` vs `git switch имя`?» → **создать и перейти / просто перейти.** `git checkout` — старый аналог.
- «`git merge feature` — что куда сливается?» → **ветка feature вливается в ТЕКУЩУЮ.**
- «Что класть в .gitignore?» → **out/, build/, .gradle/, *.class, личные настройки IDEA, .env и любые секреты.** (wrapper `gradlew` и `gradle/wrapper` — наоборот, коммитят.)
- «Папка уже закоммичена, потом добавлена в .gitignore. Исчезнет?» → **нет; нужно `git rm -r --cached папка` + коммит.**
- «Пароль закоммитили и удалили следующим коммитом. Всё хорошо?» → **нет: он в истории; считать утёкшим, менять.**

### О5. Удалённый репозиторий и командная работа
- «clone, pull, push, fetch — что делает каждая?» → **скачать репо целиком / забрать чужое и влить (fetch+merge) / отправить своё / только скачать без слияния.**
- «Коммит сделан, push нет. Коллега видит?» → **нет.**
- «Путь задачи от ветки до main?» → **pull main → ветка → коммиты → push → merge request → ревью + CI с тестами → merge.**
- «Что такое MR/PR, кто там участвует?» → **запрос на слияние; коллеги ревьюят, CI гоняет тесты; красный тест блокирует слияние.**
- «Хорошие привычки ревью?» → **маленькие MR, описание, комментарии о коде, а не о человеке, вопросы вместо приказов.**
- «Как выложить свой проект на GitHub?» → **☰ → Git → GitHub → Share Project on GitHub (создаст репозиторий, коммит и push); без IDEA — пустой репозиторий на сайте + `git remote add origin адрес` + `git push -u origin main`.** Перед этим — проверить .gitignore.
- Вход: обычный пароль для push не принимают — вход через браузер в IDEA, токен или SSH. Токен в код не коммитят.

### О6. Конфликты
- «Когда возникает конфликт?» → **двое по-разному изменили одни и те же (или соседние) строки.** Разные файлы, разные места, одинаковые правки — без конфликта.
- «Что значат `<<<<<<<`, `=======`, `>>>>>>>`?» → **начало (твой вариант, HEAD), разделитель, конец (вариант вливаемой ветки).**
- «Как решить в IDEA?» → **Conflicts → Merge… → три панели: слева твоё, справа чужое, в центре результат; » « переносят, ✕ отбрасывает; Apply; прогнать тесты; закоммитить.**
- «Не понимаешь, чей вариант правильный?» → **спросить автора; не угадывать.**
- «Аню слили в main на сервере, Боря сразу пишет `git merge main` в своей ветке — что будет?» → **Already up to date: локальный main старый. Сначала `git switch main` + `git pull`, потом merge; или Fetch и merge `origin/main`.**

### О7. Gradle (и Maven обзорно)
- «Зачем сборщик?» → **зависимости (с транзитивными), сборка, запуск тестов; одинаково на всех компьютерах и на CI.** Аналогия: список покупок (build.gradle.kts) — курьер (Gradle) — склад (Maven Central) — холодильник (~/.gradle/caches).
- «Структура проекта?» → **build.gradle.kts, settings.gradle.kts, gradlew/gradlew.bat + gradle/wrapper, src/main/java, src/main/resources, src/test/java, build/.**
- «Что такое wrapper и почему `./gradlew`, а не установленный gradle?» → **wrapper фиксирует версию Gradle в gradle-wrapper.properties и сам её скачивает: у всех и на CI одна версия; ставить Gradle не нужно. Файлы wrapper коммитят.**
- «Откуда Gradle берёт библиотеки?» → **`repositories { mavenCentral() }` — тот же Maven Central, что у Maven; кэш — ~/.gradle/caches.** Координаты — `группа:имя:версия` одной строкой. SNAPSHOT — версия в работе.
- «implementation / testImplementation / testRuntimeOnly?» → **для main-кода (и тестов) / только для тестов / только при запуске тестов, в коде не видна (junit-platform-launcher).** Аналог scope в Maven. JUnit в src/main при testImplementation → **ошибка компиляции package … does not exist.**
- «Зачем `useJUnitPlatform()`?» → **говорит задаче test, что тесты на JUnit 5; без неё Gradle их не находит — 0 тестов (в новых версиях ещё и ошибка).**
- «Что делает `gradle test`? А `gradle build` — прогонит тесты?» → **задача test тянет compileJava и compileTestJava, потом запускает тесты; build включает check → test, так что да.** `clean` — удалить build/. Итог — BUILD SUCCESSFUL / BUILD FAILED, отчёт — build/reports/tests/test/index.html.
- «Добавил зависимость в build.gradle.kts, а импорт красный?» → **Load Gradle Changes (Ctrl+Shift+O или слон со стрелкой).**
- «Как убрать / обновить зависимость?» → **удалить строку (или поменять версию) → Load Gradle Changes → убрать красное, Ctrl+Alt+O → gradle clean test. Обновлять по одной, мажорную версию — после release notes.** Удалить import ≠ убрать зависимость. (`val`-переменная для версии и version catalog — в уроке только «для любопытных», не требовать.)
- *Дальше два пункта — блок «для любопытных» урока 17.4: спрашивай только если ученик сам интересуется, на зачёт не влияют.*
- «Как посмотреть, кто притащил библиотеку?» → **окно Gradle → Dependencies или `gradle dependencies --configuration testRuntimeClasspath`; `+---`/`\---` — ветки дерева.**
- «Две библиотеки хотят разные версии третьей — что выберет Gradle? А Maven?» → **Gradle — самую новую (в дереве `2.11.0 -> 2.16.1`), Maven — ближайшую к проекту.** Почему — `gradle dependencyInsight --dependency commons-io --configuration runtimeClasspath`. Симптом — NoSuchMethodError/ClassNotFoundException при запуске при успешной сборке. Лечение — `exclude(group = …, module = …)` внутри зависимости или `version { strictly("…") }`.
- «Gradle vs Maven?» → **та же идея и тот же склад; pom.xml (XML) вместо build.gradle.kts, scope test вместо testImplementation, target/ вместо build/, mvn test вместо gradle test, Load Maven Changes. Maven (surefire) по умолчанию запускает только классы *Test/*Tests/Test*, Gradle с JUnit 5 — все классы с @Test.**

### О8. JUnit: основы
- «Что такое юнит-тест? Зачем тесты, если можно проверить руками?» → **код, который вызывает маленький кусок кода и сам сравнивает результат; гоняется тысячи раз бесплатно.** Пирамида: юнит → интеграционные → сквозные.
- «Кто запускает тест, если нет main?» → **JUnit: находит методы с @Test, создаёт объект класса, вызывает.**
- «Порядок аргументов assertEquals и почему важен?» → **ожидаемое, фактическое; иначе сообщение врёт.**
- «Как проверить исключение?» → **`assertThrows(Тип.class, () -> …)`; возвращает исключение — можно проверить сообщение.** Если исключения нет — тест красный.
- «Тест без assert — какой?» → **всегда зелёный (если нет исключения) и бесполезен.**
- «AAA?» → **Arrange, Act, Assert; один тест — одно поведение.**
- «Почему `assertEquals(0.3, 0.1 + 0.2)` падает?» → **double неточен; дельта третьим аргументом.**
- «`assertEquals` для двух одинаковых массивов?» → **красный: сравнение ссылок; `assertArrayEquals`.**
- «Первый assertEquals в тесте упал — выполнятся ли проверки ниже?» → **нет: проверка бросает исключение, тест заканчивается. Нужны все расхождения сразу — `assertAll(() -> …, () -> …)`, сообщение Multiple Failures.**
- Методы-тесты в JUnit 5 не обязаны быть public.

### О9. JUnit: жизненный цикл и параметризация
- «Порядок BeforeAll/BeforeEach/AfterEach/AfterAll для двух тестов?» → **BeforeAll, (BeforeEach, тест, AfterEach) × 2, AfterAll.**
- «Почему @BeforeAll static?» → **вызывается до создания объектов; без static — ошибка JUnit при запуске, тесты не выполнятся.**
- «Поле `int count` увеличивается в двух тестах. Что напечатает второй?» → **1: новый объект на каждый тест.**
- «Почему тесты должны быть независимыми?» → **порядок не гарантирован, объект новый; тест должен проходить и один, и в любом порядке.**
- «@ParameterizedTest + @CsvSource — как работает? Сколько запусков?» → **строка = запуск, значения по параметрам по порядку.** `@ValueSource` — один параметр.
- «@Disabled — тест красный?» → **нет, пропущен (skipped); всегда с причиной и номером задачи.** @DisplayName — имя для отчёта.

### О10. AssertJ
- «Чем AssertJ удобнее обычных assertEquals?» → **читается как фраза, фактическое всегда в assertThat — не перепутать, подробные сообщения, сотни проверок, подсказки IDEA после точки.**
- «contains vs containsExactly vs containsExactlyInAnyOrder?» → **есть среди прочих / ровно эти в этом порядке / ровно эти в любом порядке.**
- «`assertThat(list.isEmpty());` что проверяет?» → **ничего.**
- «Как проверить исключение на AssertJ?» → **`assertThatThrownBy(() -> …).isInstanceOf(…).hasMessageContaining(…)`.**
- `.as("описание")` — сообщение; soft assertions — для любопытных, не требовать.

### О11. Тест-дизайн (Мастерская)
- «Откуда брать ожидаемое значение?» → **из требований, не из кода и не из текущего поведения.**
- «Что такое класс эквивалентности? Аналогия?» → **группа входов с одинаковым поведением; ложка из каждой кастрюли.**
- «Почему границы важнее середины?» → **`>` вместо `>=`, «±1» — ошибка видна только на стыке.**
- «Что такое регрессионный тест?» → **тест, закрепляющий исправленный баг; не даст ему вернуться.**
- «Все тесты зелёные — багов нет?» → **нет: тесты показывают наличие ошибок, а не их отсутствие.**
- «Что показывает Run with Coverage? 100% покрытия — значит всё проверено?» → **какие строки тесты выполнили (зелёные/жёлтые/красные); нет: покрытие не знает, есть ли assert и верны ли ожидания.**
- FIRST — назвать хотя бы 3 буквы своими словами.

### О12. Чистый код: стиль, DRY, KISS, YAGNI (урок 17.8)
- «Как в Java называют класс, метод, переменную, константу, пакет?» → **PascalCase; camelCase с глагола у метода; camelCase; UPPER_SNAKE_CASE; маленькими буквами.**
- «Что такое магическое число и как от него избавиться?» → **число без объяснения смысла; именованная константа `static final` (Ctrl+Alt+C) или enum.**
- «Что значат DRY, KISS, YAGNI? Пример нарушения каждого?» → **одно знание — в одном месте; самое простое из рабочих решений; не писать код «на будущее».** Заблуждение: «DRY — склеить всё, что выглядит одинаково» (два разных тарифа по 50 ₽ — два правила, а не одно).
- «Чем помогает Checkstyle?» → **автоматически проверяет стиль при сборке, спор о стиле решает инструмент, а не ревьюер.**

### О13. SOLID (урок 17.9)
- «Расшифруй SOLID, по примеру на каждую букву» → **S — одна причина для изменения; O — новое добавляем новым классом, не правя старый; L — наследник работает везде, где родитель; I — маленькие интерфейсы вместо толстого; D — логика зависит от интерфейса, конкретику передают снаружи.**
- «Single Responsibility — это "один метод в классе"?» → **нет: одна забота, одна причина меняться.**
- «Чем Dependency Inversion отличается от Dependency Injection?» → **первое — принцип (зависеть от абстракций), второе — приём (передать зависимость через конструктор).**
- «Как D помогает тестам?» → **в конструктор можно передать фейк вместо настоящей базы, почты, обогревателя.**

### О14. Паттерны проектирования (уроки 17.10–17.11)
- «Что такое паттерн? Какие три группы?» → **проверенный рецепт для типичной задачи (GoF, 1994); порождающие, структурные, поведенческие.** Заблуждение: «паттерн — готовый код/библиотека».
- «Как сделать Singleton и чем он плох?» → **приватный конструктор + `private static final` поле + `getInstance()` или enum; глобальное состояние, скрытые зависимости, мешает тестам, ленивый вариант небезопасен в потоках.**
- «Зачем Builder, если есть конструктор?» → **читаемый вызов, необязательные параметры без россыпи конструкторов, проверка в `build()`, неизменяемый результат.**
- «Поверхностная и глубокая копия?» → **копия ссылок против копии вложенных объектов; `clone()` у массива поверхностный.**
- «Чем Adapter, Decorator и Proxy похожи и чем отличаются?» → **все — обёртки; адаптер меняет интерфейс, декоратор добавляет способность, заместитель управляет доступом (лень, кеш, права).**
- «Где Strategy и Iterator в JDK?» → **`Comparator` и лямбды в `sort`/`filter`; `Iterator` и for-each через `Iterable`.**
- «Mediator и Observer — в чём разница?» → **посредник — центр, через который общаются все; наблюдатель — подписчики получают уведомление от одного источника.**

## Банк головоломок

Давай по одной. Сначала ответ и «почему», потом разбор. ★★★ — с подвохом.

### Тест зелёный или красный? Что напишет JUnit?
1. `int sum = add(2, 2); assertEquals(sum, 5);` (метод верный) → красный, сообщение `expected: <4> but was: <5>` — врёт из-за перепутанных аргументов.
2. `@Test void t() { int p = shop.price(1000, 10); System.out.println(p); }` — метод с багом → **зелёный**: нет ни одной проверки.
3. `assertEquals(0.3, 0.1 + 0.2)` → красный; нужна дельта.
4. `assertEquals(new int[]{1, 2}, new int[]{1, 2})` → красный: у массивов equals = сравнение ссылок; `assertArrayEquals`.
5. `assertEquals("Аня", new String("Аня"))` → **зелёный**: assertEquals использует equals, а не ==. (А `assertSame` был бы красным.)
6. `assertThrows(IllegalArgumentException.class, () -> feeFor(0))`, а метод вернул 199 → красный: «Expected … to be thrown, but nothing was thrown».
7. `assertThrows(RuntimeException.class, () -> { throw new IllegalArgumentException(); })` → **зелёный**: IllegalArgumentException — подкласс RuntimeException (модуль 12). ★★★
8. `assertThat(list.isEmpty() == false);` при пустом списке → **зелёный**: нет проверки после точки.
9. `assertThat(List.of("a", "b", "c")).contains("c", "a")` → зелёный; `.containsExactly("a", "b")` → красный.
10. `assertTrue(result == true || result == false)` → всегда зелёный, тест бесполезен.
10а. `assertAll(() -> assertEquals(1, a), () -> assertEquals(2, b))`, где a = 5 и b = 7 → красный, и в отчёте **оба** расхождения (Multiple Failures (2 failures)). Без assertAll — только первое.

### Жизненный цикл
11. Два теста, в каждом `count++` и печать поля `count` (изначально 0) → `1` и `1`: новый объект на каждый тест. ★★★
12. Конструктор, `@BeforeAll`, `@BeforeEach` печатают своё имя, тестов два → `BeforeAll, конструктор, BeforeEach, тест, конструктор, BeforeEach, тест`.
13. `@BeforeAll void open()` без static → компилируется; при запуске JUnit сообщает, что метод должен быть static, тесты класса не выполняются.
14. Исключение в `@BeforeEach` → каждый тест класса красный (подготовка упала — тест не начинался). `@AfterEach` при этом всё равно вызовется.
15. `@Disabled` у теста → в отчёте skipped, не красный и не зелёный.
16. `@ParameterizedTest @CsvSource({"1, 2", "3, 4"})` + `@ValueSource(ints = {5, 6, 7})` у другого метода → в отчёте 5 запусков.
