API-тесты кратко

Средний этаж пирамиды. Тест разговаривает с сервером напрямую, без браузера: быстро, стабильно и очень востребовано на собеседованиях. Знакомимся с HTTP, JSON и REST Assured.

⏱ 20 минут🔌 HTTP и JSON📖 код для чтения

Повторение

Клиент, сервер и HTTP

Когда ты жмёшь «В корзину», браузер не сам кладёт книгу в корзину. Он отправляет запрос на сервер — программу на другом компьютере (часто на Java!), — а тот присылает ответ. Правила этого разговора называются HTTP. А набор «вопросов», которые сервер умеет принимать, — его API (Application Programming Interface — «интерфейс для программ»).

Аналогия: ресторан

Ты (клиент) не идёшь на кухню (сервер) — заказываешь через официанта (HTTP) по меню (API): «принесите книгу номер 101». Кухня отвечает блюдом (данные) или вежливым «такого нет» (ошибка 404). API-тест — это ревизор, который делает заказы по меню и проверяет, что принесли, не любуясь интерьером зала (интерфейсом).

Подсмотри запросы любого сайта

F12 → вкладка Network → фильтр Fetch/XHR → поделай что-нибудь на сайте. Ты увидишь все запросы, которые страница отправляет серверу, и ответы на них. Автоматизаторы смотрят сюда постоянно: «что ответил сервер, когда тест упал?»

Из чего состоят запрос и ответ

📤

Запрос

Метод HTTP — что сделать (GET, POST…; не путать с методом в Java). Адрес — с чем (/api/books/101). Заголовки — служебное: формат, токен входа. Тело — данные, если что-то отправляем.

📥

Ответ

Статус-код — получилось или нет (200, 404…). Заголовки. Тело — данные, обычно в формате JSON.

МетодСмыслПример
GETполучить, ничего не меняяGET /api/books/101 — книга 101
POSTсоздать новоеPOST /api/books + книга в теле
PUTзаменить целикомPUT /api/books/101 + новая версия
DELETEудалитьDELETE /api/cart/items/7

Статус-коды — трёхзначные числа, первая цифра говорит главное:

КодЗначитКогда видишь
200 OKвсё хорошополучили данные
201 Createdсозданопосле успешного POST
204 No Contentсделано, тела нетчасто после DELETE
400 Bad Requestты прислал что-то не тоцена «abc», пустое название
401 Unauthorizedне представилсянет токена входа
403 Forbiddenпредставился, но нельзяпокупатель лезет в админку
404 Not Foundтакого неткниги 999999 не существует
500 Internal Server Errorсервер сломалсяэто почти всегда баг!

Запомнить просто: 2xx — успех, 4xx — ошибка клиента («ты не так попросил»), 5xx — ошибка сервера («мы сломались»).

Ты отправил заказ с отрицательным количеством книг (−3), а сервер ответил 500. Это баг?

Да. Неверные данные от клиента сервер должен отклонять вежливо — кодом 400 и понятным сообщением. 500 значит, что сервер не ожидал такого ввода и упал внутри (возможно, с исключением, как в модуле 12). Негативные проверки «прислали ерунду — получили 400» — обязательная часть API-тестов.

JSON — формат данных

Данные в API почти всегда передают в JSON (JavaScript Object Notation). Он похож на то, как мы описываем объекты в Java:

{
  "id": 101,
  "title": "Java для тестировщиков",
  "price": 990,
  "inStock": true,
  "authors": ["Анна Петрова", "Борис Иванов"],
  "publisher": null
}
  • { } — объект: пары «ключ в кавычках: значение» через запятую.
  • Значения: строки в двойных кавычках, числа, true/false, null, массивы [ ] и вложенные объекты.

Такой объект удобно превратить в Java-record из модуля 11 — библиотека (обычно Jackson) сделает это сама:

public record Book(int id, String title, int price, boolean inStock) {
}

JSON → Java-объект называется десериализацией, обратно — сериализацией. Лишние поля (authors, publisher) можно игнорировать, если они не нужны тесту.

REST Assured: given / when / then

REST — самый распространённый стиль API: адреса описывают «вещи» (/books/101), методы — действия с ними. Для тестов таких API в Java есть библиотека REST Assured. Её главная идея — тест как одна цепочка вызовов методов из трёх частей, как фраза (каждый метод возвращает объект, у которого вызывается следующий):

  • given — «дано»: заголовки, тело, токен;
  • when — «когда»: метод и адрес;
  • then — «тогда»: проверки (assertions) статуса и тела ответа.

Это та же схема «подготовка → действие → проверка», что и в любом хорошем JUnit-тесте. Прочитай пример — запускать его негде, наш сайт Nook выдуманный, но устройство настоящее:

import io.restassured.RestAssured;
import io.restassured.http.ContentType;
import org.junit.jupiter.api.BeforeAll;
import org.junit.jupiter.api.Test;

import static io.restassured.RestAssured.given;
import static org.assertj.core.api.Assertions.assertThat;
import static org.hamcrest.Matchers.*;

class BooksApiTest {

    @BeforeAll
    static void setUp() {
        RestAssured.baseURI = "https://nook-shop.test";
    }

    @Test
    void bookCanBeFetchedById() {
        given()
                .accept(ContentType.JSON)
        .when()
                .get("/api/books/{id}", 101)
        .then()
                .statusCode(200)
                .body("title", equalTo("Java для тестировщиков"))
                .body("price", greaterThan(0));
    }

    @Test
    void newBookIsCreated() {
        Book newBook = new Book(0, "Тестирование для всех", 1500, true);

        Book created = given()
                .contentType(ContentType.JSON)
                .body(newBook)
        .when()
                .post("/api/books")
        .then()
                .statusCode(201)
                .extract().as(Book.class);

        assertThat(created.id()).isPositive();
        assertThat(created.title()).isEqualTo("Тестирование для всех");
    }

    @Test
    void unknownBookReturns404() {
        given()
        .when()
                .get("/api/books/{id}", 999999)
        .then()
                .statusCode(404);
    }
}
RestAssured.baseURI

Как Configuration.baseUrl у Selenide: адрес стенда — один раз, в настройке.

.get("/api/books/{id}", 101)

Вызов метода get с двумя аргументами — шаблоном адреса и числом 101: {id} заменится на 101, и отправится GET-запрос.

.body("title", equalTo(…))

Проверка поля в JSON-ответе: первый аргумент — имя поля, второй — «матчер» с ожидаемым значением. equalTo, greaterThan — матчеры (статические методы) из библиотеки Hamcrest, она приходит вместе с REST Assured.

.body(newBook)

Аргумент — объект-record newBook: он превратится в JSON и уйдёт в теле запроса (нужна зависимость Jackson в build.gradle.kts: testImplementation("com.fasterxml.jackson.core:jackson-databind:…")).

.extract().as(Book.class)

Метод as возвращает объект класса Book, собранный из ответа, — дальше проверяем привычным AssertJ: в assertThat передаём фактическое значение, в isEqualTo — ожидаемое.

statusCode(404)

Негативный тест: несуществующая книга — ожидаемое значение статус-кода 404 «нет такой», а не 500 и не 200 с пустым телом.

Запустить этот пример негде, но вот как выглядело бы падение API-теста в IDEA: ожидаемое значение — 201 «создано», а фактическое — 400 «плохой запрос»:

400 — баг или нет?

Сначала посмотри, что ты отправил: может, в тесте не то тело запроса (опечатка в поле, пустое название). Чтобы увидеть запрос и ответ целиком, добавь в цепочку .log().all() после given() и после then() — REST Assured напечатает их в консоль теста.

Зачем автоматизатору API-тесты

⚡

Быстро

Запрос — миллисекунды, а не секунды загрузки страницы. Сотни проверок за минуту.

🧱

Стабильно

Нет вёрстки, анимаций и локаторов — меньше поводов «мигать».

🧰

Подготовка данных

UI-тесту корзины нужен пользователь с тремя книгами? Создай его API-запросами за долю секунды, а через браузер проверь только саму корзину.

Для ручного исследования API пользуются программой Postman: отправляешь запрос кнопкой и смотришь ответ. Хороший порядок работы: сначала «пощупать» запрос в Postman или DevTools, потом записать его автотестом.

Проверь себя

Поговори с наставником

Напиши: «Опиши мне API маленькой библиотеки книг (3–4 запроса), а я придумаю к нему по одному позитивному и негативному тесту: метод, адрес, ожидаемый статус и что проверить в теле».

Коротко

  • Клиент шлёт HTTP-запрос (метод, адрес, заголовки, тело), сервер отвечает (статус, заголовки, тело).
  • GET — получить, POST — создать, PUT — заменить, DELETE — удалить.
  • 2xx — успех, 4xx — ошибка клиента, 5xx — ошибка сервера (почти всегда баг).
  • Данные — JSON; удобно превращать в record.
  • REST Assured: given() → when() → then(). API-тесты быстрые, стабильные и помогают готовить данные для UI-тестов.
