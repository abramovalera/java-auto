До сих пор при вызове метода ты передавал ему аргументами данные: число, строку, список. Но часто методу нужно передать действие: «как сравнивать», «что проверять», «что сделать с каждым элементом».

В программах это на каждом шагу. Вот типичные просьбы к программе магазина — и в каждой спрятано маленькое действие:

🔎

«Оставь товары дешевле 1000 ₽»

Действие: проверить один товар — подходит или нет.

📋

«Отсортируй товары по цене»

Действие: сравнить два товара — кто раньше.

🖨️

«Напечатай каждое имя»

Действие: сделать что-то с одним элементом.

Ты это уже умеешь — через анонимный класс. Помнишь сортировку строк по длине из модуля про коллекции?

List<String> names = new ArrayList<>(List.of("Вика", "Ян", "Борис"));

names.sort(new Comparator<String>() {
    @Override
    public int compare(String a, String b) {
        return a.length() - b.length();
    }
});

System.out.println(names);

Набери это в IDEA и запусти. Заметь: IDEA сама намекает, что анонимный класс тут лишний:

Посчитай: шесть строк, а полезная из них — одна, a.length() - b.length(). Всё остальное — «обёртка», которую компилятор и так мог бы додумать. Вот её мы и выбросим.

Сжимаем анонимный класс в лямбду

Посмотри на обёртку глазами компилятора. Метод sort ждёт Comparator<String> — значит, «new Comparator<String>()» он знает и так. У интерфейса Comparator всего один метод, который надо написать, — значит, и «public int compare» понятно без слов. Типы параметров — тоже: это строки из списка.

Остаётся только то, чего компилятор знать не может: имена параметров и что делать. Это и есть лямбда-выражение (или просто лямбда) — метод без имени, записанный прямо там, где его передают аргументом:

names.sort((a, b) -> a.length() - b.length());
(a, b)

Параметры лямбды a и b — те же, что были у метода compare. Типы не пишем: компилятор берёт их из того, что ждёт sort.

->

Стрелка — читается «переходит в» или «даёт». Слева — что пришло, справа — что сделать.

a.length() - b.length()

Тело лямбды. Если это одно выражение, его значение и есть возвращаемое значение — return писать не нужно.

Аналогия: записка в доставку

Курьерская служба (метод sort) говорит: «Напишите, как сравнивать посылки». Анонимный класс — это заявление на бланке со штампом, ФИО и подписью. Лямбда — стикер «сначала лёгкие». Курьер и так знает, что это за бланк, — ему нужна только суть.

Синтаксис: все формы лямбды

У лямбда-выражения всегда три части: параметры, стрелка -> и тело. Меняется только количество скобок:

Сколько параметровКак выглядитЧто значит
одинx -> x * 2скобки вокруг одного параметра можно не писать
два и больше(a, b) -> a + bскобки обязательны
ноль() -> "Привет"пустые скобки обязательны
с типом(String s) -> s.length()тип можно указать явно — тогда скобки нужны

Если в теле нужно несколько инструкций, бери блок в фигурных скобках. Тогда работают обычные правила метода: точки с запятой и явный return.

// короткая форма: одно выражение, return не пишем
Comparator<String> byLength = (a, b) -> a.length() - b.length();

// блочная форма: несколько строк, return обязателен
Comparator<String> byLengthLoud = (a, b) -> {
    System.out.println("Сравниваю " + a + " и " + b);
    return a.length() - b.length();
};

Заметь: лямбда-выражением можно инициализировать переменную, как числом или строкой. Тип переменной — интерфейс (Comparator<String>), а значение — лямбда.

Скомпилируется ли Comparator<String> c = (a, b) -> { a.length() - b.length() };?

Нет. В фигурных скобках — обычный блок кода, как в методе. Там нужна точка с запятой и return: { return a.length() - b.length(); }. Правило простое: есть фигурные скобки — пиши return, нет скобок — не пиши.

Одинаково ли работают s -> s.isEmpty() и s -> { return s.isEmpty(); }?

Да, это одно и то же: короткая форма — просто сокращение блока с одним return. Короткую пишут почти всегда, блочную — когда действий несколько.

Функциональный интерфейс: куда «вставляется» лямбда

Лямбда не живёт сама по себе: у неё всегда есть тип-интерфейс, и она становится реализацией его метода. Но не любого интерфейса, а только такого, в котором ровно один абстрактный метод. Такой интерфейс называют функциональным интерфейсом.

Почему один? Потому что у лямбды нет имени метода. Если бы в интерфейсе было два нереализованных метода, компилятор не понял бы, какой из них ты пишешь.

Напишем свой функциональный интерфейс — правило проверки цены — и передадим в него разные лямбды:

@FunctionalInterface
interface PriceRule {
    boolean check(int price);
}

public class PriceRules {
    static void report(String title, int price, PriceRule rule) {
        System.out.println(title + ": " + rule.check(price));
    }

    public static void main(String[] args) {
        PriceRule positive = p -> p > 0;
        PriceRule cheap = p -> p < 1000;

        report("Цена больше нуля", 500, positive);
        report("Дешевле 1000", 1500, cheap);
        report("Круглая", 2000, p -> p % 100 == 0);
    }
}
@FunctionalInterface

Аннотация-проверка. Говорит компилятору: «следи, чтобы метод был ровно один». Добавишь второй абстрактный — получишь ошибку сразу в интерфейсе. Без аннотации интерфейс тоже работает, она просто страхует.

PriceRule rule

У метода report есть параметр rule типа PriceRule — правило, и метод не знает, какое именно. Он просто вызывает у объекта rule метод check и передаёт аргумент price.

p -> p % 100 == 0

Лямбда-выражение можно передать аргументом прямо в вызове метода, без переменной. Так делают чаще всего.

Важно: default и static не считаются

В функциональном интерфейсе могут быть default- и static-методы с готовым телом — их сколько угодно. Считаются только абстрактные методы (без тела). Так устроен и Comparator: метод compare один, а готовых помощников вроде reversed() — много.

В interface Calc два абстрактных метода. Что скажет компилятор на Calc c = (a, b) -> a + b;?

Ошибка компиляции: Calc is not a functional interface — multiple non-overriding abstract methods found. Лямбда не знает, какой из двух методов она реализует.

Проверка по ходу

Лямбда и переменные снаружи

Лямбда видит локальные переменные метода, в котором её написали. Это удобно: правило можно настроить.

int limit = 1000;
PriceRule cheap = p -> p < limit;     // лямбда «захватила» limit
System.out.println(cheap.check(700));  // true

Но есть строгое правило: такую переменную нельзя менять — ни внутри лямбды, ни снаружи после её создания. Переменная должна быть final или «фактически final» (effectively final) — то есть её инициализировали один раз и больше ничего ей не присваивали.

int count = 0;
names.forEach(n -> count++);   // ❌ ошибка компиляции

Почему так строго? Лямбда может выполниться позже, в другом месте — а локальная переменная метода живёт на стеке и к тому времени может исчезнуть. Поэтому Java копирует в лямбду её значение. А раз это копия, менять её бессмысленно — и Java запрещает, чтобы ты не обманулся.

Посчитать что-то лямбдами всё равно можно — но правильным способом: вызовом метода count() у стрима. Это будет в уроке 14.5.

🔎 Для любопытных: лямбда — это не анонимный класс (можно пропустить)

Снаружи похоже, но внутри по-разному. Для анонимного класса компилятор создаёт отдельный файл Main$1.class, а лямбда превращается в обычный скрытый метод, и объект для неё JVM собирает на лету (через инструкцию invokedynamic). Отсюда разница: внутри анонимного класса this — это сам анонимный объект, а внутри лямбды this — объект, в методе которого лямбду написали. На собеседовании иногда спрашивают именно это.

Напиши: «Я прошёл урок 14.1. Дай мне анонимный класс, а я перепишу его в лямбду и объясню, что выбросил и почему компилятор это разрешает».

Коротко

  • Лямбда-выражение — короткая запись «кусочка поведения»: (параметры) -> тело. Его передают аргументом в метод или им инициализируют переменную.
  • Один параметр — скобки можно опустить; ноль или несколько — скобки нужны.
  • Если тело лямбды — выражение, его значение и есть возвращаемое значение; тело-блок { } требует return.
  • Лямбда всегда реализует функциональный интерфейс — интерфейс ровно с одним абстрактным методом. @FunctionalInterface это проверяет.
  • Локальные переменные снаружи лямбда читает, но менять их нельзя: они должны быть effectively final.
