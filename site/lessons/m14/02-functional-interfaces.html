Встроенные функциональные интерфейсы

Писать свой интерфейс под каждую лямбду — скучно. В Java уже есть готовый набор «розеток» на все случаи жизни. Выучишь пять — и будешь читать любой код со стримами.

Повторение

Готовые розетки из java.util.function

В прошлом уроке мы написали свой PriceRule с методом boolean check(int price). Но «взять что-то и ответить да/нет» нужно так часто, что в Java давно есть готовый функциональный интерфейс — Predicate. Как и ещё несколько на типовые случаи. Все они лежат в пакете java.util.function.

Чтобы их запомнить, достаточно смотреть на форму: что входит и что выходит.

ИнтерфейсВход → выходМетодПример лямбдыГде пригодится
Predicate<T>T → booleantests -> s.isEmpty()«подходит ли элемент?» — фильтры
Function<T, R>T → Rapplys -> s.length()«превратить элемент в его текст/цену»
Consumer<T>T → ничегоaccepts -> System.out.println(s)«сделать с каждым»: напечатать, сохранить
Supplier<T>ничего → Tget() -> new ArrayList<>()«выдать по требованию»: новый список, случайное число
BiFunction<T, U, R>(T, U) → Rapply(a, b) -> a + b«из двух сделать одно»
Аналогия: кухонные приборы

Predicate — сито: кладёшь ягоду, оно говорит «пропустить» или «нет». Function — соковыжималка: яблоко на входе, сок на выходе. Consumer — мусорное ведро: принимает и ничего не отдаёт. Supplier — холодильник: ничего не кладёшь, а достаёшь продукт. BiFunction — блендер на два ингредиента.

Все пять в коде

Посмотри: объявляем переменную типа интерфейса, инициализируем её лямбда-выражением, а потом вызываем у неё единственный абстрактный метод интерфейса — у каждого он свой. Лямбда задаёт тело этого метода:

import java.util.*;
import java.util.function.*;

public class FiveInterfaces {
    public static void main(String[] args) {
        Predicate<String> isError = text -> text.startsWith("ERROR");
        System.out.println(isError.test("ERROR: нет связи"));  // true

        Function<String, Integer> length = text -> text.length();
        System.out.println(length.apply("Купить"));  // 6

        Consumer<String> log = text -> System.out.println("[LOG] " + text);
        log.accept("Заказ принят");  // [LOG] Заказ принят

        Supplier<String> greeting = () -> "Добро пожаловать!";
        System.out.println(greeting.get());  // Добро пожаловать!

        BiFunction<Integer, Integer, Integer> total =
                (price, count) -> price * count;
        System.out.println(total.apply(250, 4));  // 1000
    }
}
Generics — только классы-обёртки

Как в коллекциях из модуля 13, в угловых скобках нельзя писать int: только Integer, Double, Boolean. Поэтому Function<String, Integer>, а не Function<String, int>.

Есть ещё два «частных случая», их часто встретишь в чужом коде:

UnaryOperator<T>
Это Function<T, T>: тип на входе и выходе одинаковый. Пример: UnaryOperator<String> up = s -> s.toUpperCase();
BinaryOperator<T>
Это BiFunction<T, T, T>: два одинаковых в одно такое же. Пример: BinaryOperator<Integer> sum = (a, b) -> a + b; Пригодится в reduce.
Объявлена переменная Predicate<Integer> even = n -> n % 2 == 0;. Что вернёт вызов even.test(0)?

true: 0 % 2 = 0, значит, ноль — чётное число. Граничный случай, на котором многие спотыкаются.

Склеиваем правила: and, or, negate, andThen

У этих интерфейсов есть готовые default-методы, которые собирают из простых правил сложные. Это как конструктор: каждое правило маленькое и понятное, а вместе — мощные.

Predicate<String> notEmpty = s -> !s.isEmpty();
Predicate<String> shortText = s -> s.length() <= 10;

Predicate<String> validButton = notEmpty.and(shortText);
System.out.println(validButton.test("Купить"));  // true
System.out.println(validButton.test(""));        // false
// true: текст длиннее 10
System.out.println(shortText.negate().test("Оформить заказ"));

Function<String, String> trim = s -> s.trim();
Function<String, Integer> length = s -> s.length();
System.out.println(trim.andThen(length).apply("  OK  "));  // 2
  • Каждый такой метод возвращает новое правило. p1.and(p2) — оба правила (как &&), p1.or(p2) — хотя бы одно (как ||), p.negate() — наоборот (как !).
  • f1.andThen(f2) — сначала f1, потом её возвращаемое значение передаётся аргументом в f2. Как конвейер из двух станков.
Function<Integer, Integer> twice = x -> x * 2; и plus3 = x -> x + 3;. Что даст twice.andThen(plus3).apply(5)?

13. Сначала twice: 5 · 2 = 10, потом plus3: 10 + 3 = 13. Порядок важен: plus3.andThen(twice) дал бы (5 + 3) · 2 = 16.

Коллекции уже умеют принимать лямбды

Эти интерфейсы встроены в коллекции из модуля 13. Три метода, которым лямбда-выражение передают аргументом, — ты будешь вызывать их постоянно:

List<String> buttons = new ArrayList<>(List.of("Купить", "", "Отмена", "  "));

buttons.removeIf(b -> b.isBlank());          // Predicate: убрать пустые
buttons.forEach(b -> System.out.println(b)); // Consumer: напечатать каждую

Map<String, Integer> prices = new HashMap<>();
prices.put("Чай", 200);
prices.put("Кофе", 350);
prices.forEach((name, price) -> System.out.println(name + " — " + price));

removeIf и неизменяемые списки

removeIf меняет список. У списка из List.of(…) он выбросит UnsupportedOperationException — такой список неизменяемый. Поэтому выше мы создали изменяемую копию: новый объект new ArrayList<>(…), которому аргументом передали этот список.

Comparator без анонимных классов: comparing и thenComparing

Самое приятное — сортировка. У Comparator есть статический метод comparing: ты передаёшь ему аргументом Function «как достать ключ сравнения», а он возвращает готовый Comparator.

record Student(String name, int group, int score) { }

List<Student> students = new ArrayList<>(List.of(
        new Student("Вика", 2, 90),
        new Student("Аня", 1, 75),
        new Student("Борис", 2, 90)));

students.sort(Comparator.comparing(s -> s.name()));     // по имени
System.out.println(students.get(0).name());              // Аня

А если нужно по двум полям — «по баллу от большего, при равенстве по имени»? Тут лямбды в длинной цепочке вызовов начинают мешать компилятору (подробности — ниже), поэтому пишут ссылки на методы Student::score — это та же лямбда s -> s.score(), только короче. Подробно разберём их в следующем уроке, а пока просто прочитай:

students.sort(Comparator.comparing(Student::score).reversed()
        .thenComparing(Student::name));

students.forEach(s -> System.out.println(s.name() + " " + s.score()));
Борис 90
Вика 90
Аня 75
Comparator.comparing(Student::score)

Вызов статического метода comparing с аргументом — ссылкой на метод Student::score. Возвращает компаратор «по баллу, по возрастанию».

.reversed()

Вызов reversed() у этого компаратора возвращает новый — по убыванию.

.thenComparing(Student::name)

Вызов thenComparing добавляет второе правило: если баллы равны — сравнить по имени. Работает только как «второй судья».

Ловушка: comparing(лямбда).reversed()

Comparator.comparing(s -> s.score()).reversed() не скомпилируется: cannot find symbol: method score(). Из-за .reversed() в конце компилятор не может понять тип параметра s лямбды и считает его просто Object. Лечится ссылкой на метод Student::score или явным типом (Student s) -> s.score().

Для чисел есть варианты без лишней упаковки: Comparator.comparingInt(Student::score), comparingDouble. А для «естественного» порядка — Comparator.naturalOrder() и Comparator.reverseOrder().

Коротко

  • Predicate — проверить (test), Function — превратить (apply), Consumer — сделать (accept), Supplier — выдать (get), BiFunction — из двух в одно.
  • Правила склеиваются: and, or, negate, andThen.
  • Методы коллекций принимают аргументом лямбда-выражения: forEach, removeIf (только изменяемый список!), map.forEach((k, v) -> …).
  • Сортировка: Comparator.comparing(…), .reversed(), .thenComparing(…).
