Стек вызовов

Метод вызывает метод, тот — ещё один, а тот — ещё… Как Java не теряется и всегда знает, куда вернуться? Знакомься: стек вызовов — одна из самых важных идей в программировании.

Повторение

Выпиши себе: отладчик, часть 2, и прыжки по коду

Сегодня заглянем внутрь своих методов. Базовые клавиши отладчика (точка останова Ctrl+F8, запуск 🐞 Shift+F9, шаг F8, дальше F9, стоп Ctrl+F2) — в шпаргалке урока 6.5. Допиши к ним новые:

Разница F8 и F7 на строке с вызовом метода: F8 выполнит вызов целиком и встанет на следующую строку, F7 провалится внутрь метода.

Метод вызывает метод

В теле метода можно вызывать другие методы — так же, как из main. Настоящие программы так и устроены: большая задача делится на маленькие, а те — на ещё меньшие. Вот касса магазина:

public class Shop {
    public static void main(String[] args) {
        int total = calculateTotal(300, 4);
        System.out.println("К оплате: " + total);
    }

    static int calculateTotal(int price, int count) {
        int sum = price * count;
        int discount = calculateDiscount(sum);
        return sum - discount;
    }

    static int calculateDiscount(int sum) {
        if (sum > 1000) {
            return percentOf(sum, 10);
        }
        return 0;
    }

    static int percentOf(int value, int percent) {
        return value * percent / 100;
    }
}

Цепочка: main → calculateTotal → calculateDiscount → percentOf. Пока percentOf считает, три метода под ним ждут: каждый остановился посреди своей строки и ждёт возвращаемого значения. Как Java помнит, кто кого ждёт и в каком месте?

Предскажи: что напечатает программа?

К оплате: 1080. main вызывает calculateTotal и передаёт аргументы 300 и 4: сумма 300 × 4 = 1200. Она больше 1000, значит calculateDiscount вернёт 10% от 1200 = 120. Итог 1200 − 120 = 1080. Сейчас пройдём это по шагам и посмотрим, что творится в памяти.

Стопка рабочих столов

Помнишь из модуля 2: переменные живут в области памяти под названием стек. Теперь узнаем, почему она так называется.

Каждый раз, когда вызывается метод, Java кладёт на стек новый фрейм (кадр) — «рабочий стол» этого метода. На нём лежат:

  • параметры метода (инициализированные значениями аргументов);
  • его локальные переменные — те, что объявлены в теле метода;
  • закладка: в какое место вернуться, когда метод закончит.

Новый фрейм всегда кладётся сверху. Работает всегда верхний. Когда метод делает return (или доходит до закрывающей скобки), его фрейм снимают, и работа продолжается в фрейме под ним — ровно с той закладки.

Аналогия: стопка тарелок

Тарелку кладут только сверху и берут только сверху. Последней положили — первой взяли. По-английски это LIFO: Last In, First Out. Метод, который вызвали последним, закончится первым — иначе и быть не может: те, кто ниже, ждут его ответа.

Пройди кассу по шагам

Теперь смотри на настоящий стек. Каждый вызов кладёт фрейм, каждый return его снимает. Там, где спросят, впиши значение сам.

Заметь: переменная sum была на двух столах сразу, и они друг другу не мешали. Каждый вызов получает свой фрейм со своими переменными. Это пригодится через три урока — в рекурсии один и тот же метод будет лежать на стеке много раз.

println — тоже метод

Ты сто раз писал System.out.println("Привет"). Это вызов метода println с аргументом "Привет". Метод объявлен не в твоём классе, а в стандартной библиотеке Java — в готовом коде, который пришёл вместе с JDK. Что значат System и out с точками, разберём в модуле 9.

И внутри println — не волшебство, а обычные методы, которые вызывают другие методы: пока буквы добираются до консоли, на стеке над твоим main вырастает целая стопка фреймов JDK. Запоминать их не нужно. Важна идея: Java — это гора готового кода, и каждая твоя «простая» строчка запускает методы, которые вызывают методы…

А почему между System, out и println точки и где «живёт» сам println? Это вопрос про классы и объекты. В модуле 9 мы разберём эту строку по кусочкам и сами построим цепочку из десятка классов — как кофейня, где заказ проходит через баристу, кофемашину, бойлер и насос.

Stack trace: стек, напечатанный при аварии

Когда программа падает с ошибкой, Java печатает stack trace — «след стека»: снимок стопки фреймов в момент аварии. Это лучший друг программиста. Смотри:

public class Report {
    public static void main(String[] args) {
        printReport(0);
    }

    static void printReport(int days) {
        System.out.println("Среднее: " + average(700, days));
    }

    static int average(int total, int count) {
        return total / count;
    }
}

Читаем сверху вниз — это стек от вершины ко дну:

  1. Первая строка — что случилось: ArithmeticException: / by zero, деление на ноль.
  2. at Report.average(Report.java:11) — где именно упало: метод average, строка 11. Это верхний фрейм.
  3. at Report.printReport(Report.java:7) — кто вызвал average: метод printReport, со строки 7 — там average передали аргументы 700 и days.
  4. at Report.main(Report.java:3) — а его вызвал main со строки 3. Дно стека.

Деление сломалось в average, но виноват, скорее всего, тот, кто передал ноль: main вызвал printReport с аргументом 0, им инициализировался параметр days. Stack trace показывает весь путь — и ты идёшь по нему вниз, пока не найдёшь, откуда пришло плохое значение. В IDEA имена файлов со строками в stack trace — синие ссылки: щёлкни, и редактор откроет нужную строку.

Предскажи: успеет ли напечататься слово «Среднее:»?

Нет. Чтобы вызвать println, Java сначала должна вычислить аргумент — всё выражение "Среднее: " + average(700, days). Вычисление упало внутри average, и до println дело не дошло. Аргументы всегда вычисляются до вызова метода.

Где это пригодится

Упавшая программа — это всегда stack trace. В большом проекте сверху могут оказаться десятки строк чужих библиотек, а ниже — твои методы. Умение быстро найти в нём свою строку — ежедневный навык любого программиста.

Стек в отладчике IDEA

Стек вызовов можно увидеть вживую. Набери программу Shop из этого урока и:

  1. Щёлкни слева от номера строки return value * percent / 100; — появится красная точка. Это точка останова (breakpoint): «остановись здесь».
  2. Запусти не ▶, а жука 🐞 рядом (Debug). Программа остановится на красной строке.
  3. Внизу откроется панель Debug. Слева в ней — список Frames: percentOf, calculateDiscount, calculateTotal, main. Это и есть стек! Щёлкай по фреймам — справа будут меняться переменные: у каждого фрейма свои.
  4. Нажимай F8 (Step Over — «шаг через»): программа пойдёт дальше по строчкам, методы будут возвращать значения, а фреймы — сниматься.
  5. В другой раз попробуй F7 (Step Into — «шаг внутрь»): на строке с вызовом метода отладчик зайдёт внутрь твоего метода. В методы JDK вроде println он по умолчанию не заходит, а просто выполняет их — и это удобно.

Отладчик — это тот же трассировщик, что на сайте, только для любой твоей программы. Если не понимаешь, почему код работает не так, — поставь точку останова и пройди по шагам. Так делают все профессионалы.

🔎 Для любопытных: стек внутри println в отладчике (Force Step Into)

Обычный F7 в методы JDK не заходит. Но есть Force Step Into — Alt+Shift+F7, «зайти насильно». Поставь точку останова на строку 4 (System.out.println(…)), запусти 🐞 и несколько раз нажми Alt+Shift+F7. Стопка в Frames начнёт расти — это те самые методы JDK со схемы из шага 5. Вернуться в свой код поможет Shift+F8 (Step Out), нажатый несколько раз, или просто F9.

Коротко

  • Каждый вызов метода кладёт на стек фрейм: параметры, локальные переменные, место возврата.
  • Работает только верхний фрейм; те, кто ниже, ждут ответа. return снимает фрейм, и выполнение продолжается в вызвавшем методе с того же места.
  • Стек — LIFO: последним вызван — первым закончится.
  • println — тоже метод из готового кода JDK, и внутри он вызывает другие методы. Ctrl+клик по имени метода открывает его объявление.
  • Stack trace — снимок стека при аварии: сверху — где упало, ниже — кто вызвал. Отладчик показывает стек в панели Frames.
