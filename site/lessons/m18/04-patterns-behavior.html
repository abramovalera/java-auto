Поведенческие

Как объекты делят работу: кто выбирает алгоритм, кто кого обходит. Стратегия и Итератор (ещё два — в конце, для любопытных).

Не зубри код. Для каждого паттерна запомни три вещи: какую боль он лечит, на что похож в жизни и где ты его уже видел в Java.

Выпиши себе: шесть паттернов одной строкой

Перепиши таблицу в тетрадь и дополняй своими примерами. На собеседовании спрашивают именно так: «что это и где встречал».

Обёртки: Adapter, Decorator, Proxy

Три паттерна устроены одинаково: класс держит в поле другой объект и передаёт ему вызовы. Разница — зачем он это делает.

Adapter — переходник

Проблема. Программа ждёт интерфейс Thermometer с методом celsius(), а датчик из старой библиотеки умеет только fahrenheit(). Чужой код менять нельзя.

Аналогия: переходник для розетки

Вилка плоская, розетка круглая. Ни то, ни другое не переделываешь — берёшь переходник.

Адаптер реализует нужный тебе интерфейс, а внутри держит чужой объект и переводит вызовы на его язык:

// Чужой класс из старой библиотеки — менять нельзя
class OldThermometer {
    double fahrenheit() { return 104; }
}

// Интерфейс, который ждёт наша программа
interface Thermometer {
    double celsius();
}

// Переходник: снаружи Thermometer, внутри — OldThermometer
class ThermometerAdapter implements Thermometer {
    private final OldThermometer old;

    ThermometerAdapter(OldThermometer old) { this.old = old; }

    @Override
    public double celsius() { return (old.fahrenheit() - 32) * 5 / 9; }
}
Thermometer t = new ThermometerAdapter(new OldThermometer());
System.out.println("В комнате " + t.celsius() + " °C");
В комнате 40.0 °C

Где в JDK. InputStreamReader из урока 15.4: снаружи Reader (символы), внутри InputStream (байты). И Arrays.asList(массив) — массив «притворяется» списком, не копируясь:

String[] drinks = {"чай", "кофе"};
List<String> menu = Arrays.asList(drinks);
drinks[0] = "какао";
System.out.println(menu);
menu.add("сок");
Что выведет этот код и что случится на последней строке?

Напечатается [какао, кофе]: адаптер смотрит прямо в массив. А menu.add("сок") бросит UnsupportedOperationException: длина массива фиксирована. Нужен изменяемый список — new ArrayList<>(Arrays.asList(drinks)). Любимая ловушка собеседований.

Decorator — добавляем способность обёрткой

Проблема. К эспрессо можно добавить молоко, сироп, двойное молоко… Наследник на каждую комбинацию (EspressoWithMilkAndSyrup) — и классов больше, чем пунктов в меню.

Декоратор реализует тот же интерфейс, что и объект внутри, и добавляет свою часть работы. Бариста не варит «кофе-с-молоком» отдельно — он добавляет молоко к эспрессо:

interface Beverage {
    String name();
    int price();
}

class Espresso implements Beverage {
    @Override public String name() { return "Эспрессо"; }
    @Override public int price() { return 150; }
}

// Добавка — тоже напиток, а внутри держит другой напиток
class WithMilk implements Beverage {
    private final Beverage inner;
    WithMilk(Beverage inner) { this.inner = inner; }
    @Override public String name() { return inner.name() + " + молоко"; }
    @Override public int price() { return inner.price() + 40; }
}

Сироп устроен так же:

class WithSyrup implements Beverage {
    private final Beverage inner;
    WithSyrup(Beverage inner) { this.inner = inner; }
    @Override public String name() { return inner.name() + " + сироп"; }
    @Override public int price() { return inner.price() + 30; }
}

Собираем заказ, как матрёшку:

Beverage order = new WithSyrup(new WithMilk(new Espresso()));
System.out.println(order.name() + ": " + order.price() + " ₽");
Эспрессо + молоко + сироп: 220 ₽

Двойное молоко — просто две обёртки WithMilk, без нового класса. Где в JDK: new BufferedReader(new FileReader("a.txt")) из урока 15.4 — обёртка добавляет буфер и readLine().

Proxy — заместитель

Проблема. В альбоме сто фото, каждое грузится секунду. Грузить все сразу — долго, а посмотрят, может, три.

Заместитель реализует тот же интерфейс, что и настоящий объект, и стоит перед ним — как секретарь перед начальником. Ленивый заместитель создаёт тяжёлый объект только при первом обращении:

interface Picture {
    void show();
}

class HeavyPicture implements Picture {
    private final String file;
    HeavyPicture(String file) {
        this.file = file;
        System.out.println("Загружаю " + file + " (это долго)");
    }
    @Override public void show() { System.out.println("Показываю " + file); }
}

// Тот же интерфейс, а настоящая картинка — только по требованию
class LazyPicture implements Picture {
    private final String file;
    private HeavyPicture real;   // пока null
    LazyPicture(String file) { this.file = file; }
    @Override public void show() {
        if (real == null) {
            real = new HeavyPicture(file);
        }
        real.show();
    }
}
Picture[] album = {
        new LazyPicture("море.jpg"), new LazyPicture("горы.jpg"), new LazyPicture("лес.jpg")
};
System.out.println("Альбом открыт");
album[1].show();
album[1].show();
Что напечатает этот код? 
Альбом открыт
Загружаю горы.jpg (это долго)
Показываю горы.jpg
Показываю горы.jpg

Заместители создаются мгновенно. Загрузка случилась один раз и только для той картинки, которую попросили.

Бывает и защитный заместитель: Collections.unmodifiableList(список) даёт читать, а на add бросает UnsupportedOperationException и до настоящего списка не пускает.

Facade — одна кнопка вместо десяти

Проблема. Чтобы посмотреть фильм, нужно приглушить свет, включить проектор, запустить фильм — в правильном порядке. Как на пульте с кнопкой «Кино»: техника та же, просто думать о ней не нужно.

Фасад — класс с простым методом, который сам вызывает части сложной системы в нужном порядке:

class Projector {
    void on() { System.out.println("Проектор включён"); }
    void play(String movie) { System.out.println("Показываем: " + movie); }
}

class RoomLights {
    void dim(int percent) { System.out.println("Свет приглушён до " + percent + "%"); }
}

// Фасад: одна кнопка поверх нескольких устройств
class HomeCinema {
    private final Projector projector = new Projector();
    private final RoomLights lights = new RoomLights();

    void watchMovie(String movie) {
        lights.dim(10);
        projector.on();
        projector.play(movie);
    }
}
new HomeCinema().watchMovie("Интерстеллар");
Свет приглушён до 10%
Проектор включён
Показываем: Интерстеллар

Фасад — удобный вход, а не замок: к частям системы можно обращаться и напрямую. Где в JDK: Files.readString(путь) — одна строчка, а под ней поток байтов, кодировка, буфер и закрытие файла из урока 15.4.

Strategy — алгоритм подменяется на лету

Переходим к поведенческим. Проблема. Касса считает итог по-разному: без скидки, −10%, промокод на 300 ₽. Первое, что приходит в голову:

int total = price;
if (type.equals("percent10")) {
    total = price * 90 / 100;
} else if (type.equals("promo300")) {
    total = Math.max(0, price - 300);
}   // …и ещё ветка на каждую новую акцию

Метод растёт, и сломать соседнюю скидку всё проще. Вспомни навигатор: кнопка «Маршрут» одна, а способ — пешком, на машине, на автобусе — ты выбираешь переключателем.

Стратегия: каждый вариант алгоритма — отдельный объект с общим интерфейсом. Касса хранит стратегию в поле и просто вызывает её. Интерфейс с одним методом — функциональный, значит, стратегию можно передать лямбдой (урок 14.1):

interface Discount {
    int apply(int price);
}

class CashDesk {
    private Discount discount = price -> price;   // по умолчанию — без скидки

    void setDiscount(Discount discount) {
        this.discount = discount;
    }

    int total(int price) {
        return discount.apply(price);   // ни одного if: что положили, то и считает
    }
}
CashDesk desk = new CashDesk();
System.out.println(desk.total(1000));
desk.setDiscount(price -> price * 90 / 100);           // скидка 10%
System.out.println(desk.total(1000));
desk.setDiscount(price -> Math.max(0, price - 300));   // промокод на 300 ₽
System.out.println(desk.total(1000));
1000
900
700

Новая акция — новая лямбда, класс CashDesk не меняется. Если стратегию выбирают по слову с клавиатуры, сложи их в словарь Map<String, Discount>: ключ — название, значение — стратегия. Так ты сделаешь в задаче про доставку.

Где в JDK. Comparator из урока 11.4 — стратегия сравнения: sort один, а порядок задаёшь ты, например names.sort(Comparator.comparing(String::length)). Каждая лямбда, которую ты передавал в sort, removeIf или filter, — маленькая стратегия.

Iterator — обход, не зная устройства

Проблема. Список хранит элементы в массиве, множество — в хеш-таблице. Если бы для обхода нужно было знать устройство, цикл ломался бы при замене ArrayList на HashSet. Как контролёр в автобусе из урока 13.3: ему важно только «есть ли кто-то ещё?» и «к следующему».

Итератор — объект, который выдаёт элементы по одному: hasNext() и next(). Коллекция отдаёт его методом iterator() — это интерфейс Iterable. For-each — короткая запись цикла с итератором, поэтому он работает с любым Iterable, и с твоим классом тоже:

import java.util.Iterator;

class Playlist implements Iterable<String> {
    private final String[] songs;   // как устроено внутри — снаружи не видно

    Playlist(String... songs) { this.songs = songs; }

    @Override
    public Iterator<String> iterator() {
        return new Iterator<>() {
            private int pos = 0;
            @Override public boolean hasNext() { return pos < songs.length; }
            @Override public String next() { return songs[pos++]; }
        };
    }
}
for (String song : new Playlist("Утро", "Дорога", "Вечер")) {
    System.out.println("♪ " + song);
}
♪ Утро
♪ Дорога
♪ Вечер

Итератор здесь — анонимный класс (урок 11.4), он видит поле songs. Заменишь массив на ArrayList — ни один цикл по плейлисту не заметит. По правилам next() без элементов бросает NoSuchElementException: в настоящем коде добавь эту проверку. Где в JDK: у каждой коллекции из модуля 13 есть iterator().

🔎 Для любопытных: ещё два поведенческих — Посредник и Наблюдатель

Mediator — посредник

Пять участников общаются каждый с каждым — это 10 связей, у шестерых уже 15. Посредник — центр, через который идёт всё общение: участники знают только его. Как пилоты, которые говорят не друг с другом, а с вышкой.

Пример — чат-комната: участник отдаёт сообщение комнате, а та разносит остальным.

import java.util.ArrayList;
import java.util.List;

class ChatRoom {
    private final List<ChatMember> members = new ArrayList<>();

    void join(ChatMember member) { members.add(member); }

    void send(ChatMember from, String text) {
        for (ChatMember m : members) {
            if (m != from) {
                m.receive(from.name + ": " + text);
            }
        }
    }
}

class ChatMember {
    final String name;
    private final ChatRoom room;   // знает только комнату, а не других участников

    ChatMember(String name, ChatRoom room) { this.name = name; this.room = room; }
    void say(String text) { room.send(this, text); }
    void receive(String message) { System.out.println("[" + name + "] " + message); }
}
ChatRoom room = new ChatRoom();
ChatMember anna = new ChatMember("Анна", room);
room.join(anna);
room.join(new ChatMember("Борис", room));
anna.say("Кто идёт в кино?");
[Борис] Анна: Кто идёт в кино?

Правило «не пересылать брань» появится в одном месте — в ChatRoom. Обратная сторона: посредник легко разрастается в «объект, который знает всё».

Observer — наблюдатель

Посылка поменяла статус — надо сообщить по SMS, в приложении, а завтра добавится ещё канал. Как подписка на блогера: он выкладывает видео, а уведомление получают все подписчики. Наблюдатель хранит список подписчиков и оповещает каждого:

import java.util.ArrayList;
import java.util.List;

interface ParcelListener {
    void statusChanged(String status);
}

class Parcel {
    private final List<ParcelListener> listeners = new ArrayList<>();

    void subscribe(ParcelListener listener) { listeners.add(listener); }

    void setStatus(String status) {
        for (ParcelListener l : listeners) {
            l.statusChanged(status);
        }
    }
}
Parcel parcel = new Parcel();
parcel.subscribe(status -> System.out.println("SMS: " + status));
parcel.subscribe(status -> System.out.println("Push: " + status));
parcel.setStatus("Прибыла в пункт выдачи");
SMS: Прибыла в пункт выдачи
Push: Прибыла в пункт выдачи

Так устроены слушатели событий в программах с окнами: кнопке говорят «когда нажмут — вызови вот это» (addActionListener(…)). Это обратный вызов из урока 11.4, только подписчиков сколько угодно.

Поговори с наставником

Спроси: «Объясни на примере из жизни, чем Декоратор отличается от Заместителя, если у обоих тот же интерфейс». Или: «Дай мне три описания ситуаций, а я угадаю паттерн и объясню почему». После задачи про доставку: «Посмотри мой DeliveryCost: где у меня ещё остался выбор по типу через if?»

Коротко

  • Адаптер — переходник: чужой интерфейс подгоняется под нужный (Arrays.asList, InputStreamReader).
  • Декоратор — обёртка с тем же интерфейсом добавляет способность; обёртки вкладываются (BufferedReader).
  • Заместитель — тот же интерфейс, но управляет доступом: лениво создаёт, кеширует, защищает (Collections.unmodifiableList).
  • Фасад — одна простая кнопка поверх сложной системы (Files.readString).
  • Стратегия — алгоритм в отдельном объекте, подменяется без if; часто это лямбда (Comparator).
  • Итератор — обход без знания устройства; любой Iterable работает в for-each.
  • Для любопытных: Посредник — общение через центр, Наблюдатель — оповещение подписчиков.
