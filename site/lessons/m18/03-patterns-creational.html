Паттерны проектирования: как создавать объекты

«Нужен ровно один такой объект», «у объекта куча необязательных настроек» — такие задачи повторяются из проекта в проект. Для них давно есть проверенные решения с именами. Сегодня — решения о том, как создавать объекты.

Повторение

Что такое паттерн проектирования

Паттерн проектирования (design pattern) — проверенное решение типичной задачи в устройстве программы. Это не кусок кода для копирования, а идея: какие классы завести и кто кого создаёт. Код под неё каждый раз пишут заново.

Аналогия: кулинарные рецепты

«Бисквит», «заварной крем» — повар понимает другого повара с одного слова. Паттерны — такие рецепты для программ: скажешь «здесь строитель» — и коллега сразу представляет, как устроен код.

Паттерн — не цель

Паттерны — это словарь и подсказка, а не украшение. Вставленные «для солидности», они превращают простой код в лабиринт. Помнишь KISS и YAGNI из урока 18.1? Сначала пиши просто, паттерн — когда без него уже больно.

Singleton — одиночка

Иногда объект должен быть ровно один на всю программу: настройки приложения, журнал (лог). Если каждый класс создаст свои «настройки» через new, один включит тёмную тему, а другой об этом не узнает. Одиночка (Singleton) гарантирует: объект один, и все получают именно его.

public class AppSettings {
    private static final AppSettings INSTANCE = new AppSettings();

    private String theme = "светлая";

    private AppSettings() {
    }

    public static AppSettings getInstance() {
        return INSTANCE;
    }

    public String getTheme() {
        return theme;
    }

    public void setTheme(String theme) {
        this.theme = theme;
    }
}
private AppSettings() { }

Приватный конструктор. Снаружи new AppSettings() не скомпилируется — второй объект не создать.

private static final AppSettings INSTANCE

Единственный объект создаётся внутри класса и лежит в static-поле — одном на весь класс.

public static AppSettings getInstance()

Единственный вход: кто бы ни вызвал, получит один и тот же объект.

AppSettings a = AppSettings.getInstance();
AppSettings b = AppSettings.getInstance();
a.setTheme("тёмная");
System.out.println(b.getTheme());
System.out.println(a == b);
Тему меняли через a, а спрашиваем у b. Что выведется?

тёмная и true. Переменных две, а объект один: getInstance() оба раза вернул INSTANCE. Пример из JDK — Runtime.getRuntime().

🔎 Для любопытных: одиночка через enum и «ленивый» вариант

У enum каждое значение существует в одном экземпляре — за этим следит JVM. Значит, enum с одним значением — готовый одиночка, самый короткий и надёжный:

public enum Clipboard {
    INSTANCE;

    private String text = "";

    public void copy(String text) {
        this.text = text;
    }

    public String paste() {
        return text;
    }
}

Пользуются так: Clipboard.INSTANCE.copy("привет");, а в любом другом месте Clipboard.INSTANCE.paste() вернёт "привет".

Иногда объект создают «лениво» — при первом вызове: if (instance == null) instance = new AppSettings();. С несколькими потоками это ловушка из модуля 16: два потока одновременно увидят null и создадут два объекта. Бери вариант со static final-полем или enum — оба безопасны.

Мешает тестам

Один тест включил тёмную тему, следующий ждёт светлую — и падает. Тесты перестают быть независимыми.

Поэтому одиночку иногда зовут антипаттерном. В больших программах объект обычно создают один раз в начале и передают через конструктор тем, кому он нужен: объект по-прежнему один, но зависимость видна.

Factory Method — фабричный метод

Самый частый вариант — статический фабричный метод: обычный static-метод, который создаёт и возвращает объект вместо твоего new. Ты ими давно пользуешься:

List<String> days = List.of("пн", "вт", "ср");   // а не new ArrayList<>()
Integer price = Integer.valueOf(100);             // а не new Integer(100)

Свой такой метод: магазин уведомляет покупателя, а каналы бывают разные.

interface Notifier {
    void send(String text);
}

class SmsNotifier implements Notifier {
    public void send(String text) { System.out.println("SMS: " + text); }
}

class EmailNotifier implements Notifier {
    public void send(String text) { System.out.println("Письмо: " + text); }
}

public class Notifiers {
    static Notifier of(String channel) {
        return switch (channel) {
            case "sms" -> new SmsNotifier();
            case "email" -> new EmailNotifier();
            default -> throw new IllegalArgumentException("Нет канала: " + channel);
        };
    }
}

Пользователь пишет Notifiers.of("sms").send("Заказ готов"); и знает только интерфейс. Чем это лучше new:

  • У метода есть имя. List.of, Notifiers.of — понятно, что получишь. У конструктора имя всегда одно — как у класса.
  • Можно вернуть любой подкласс. Заменят SmsNotifier другим классом — чужой код не изменится.
  • Можно вернуть готовый объект. new всегда создаёт новый, а Integer.valueOf для чисел от −128 до 127 отдаёт объект из кеша — поэтому обёртки сравнивают через equals, а не ==.
🔎 Для любопытных: фабричный метод «по книге» GoF

В книге GoF фабричный метод — шаг дальше: метод создания объявляет родитель, а что именно создать, решают наследники. Служба доставки: порядок у всех одинаковый, а транспорт разный.

abstract class Delivery {
    abstract Transport createTransport();      // фабричный метод

    void deliver(String parcel) {
        Transport t = createTransport();       // что создать — решит наследник
        System.out.println(t.name() + " везёт: " + parcel);
    }
}

class CityDelivery extends Delivery {
    Transport createTransport() { return new Bike(); }
}

class CountryDelivery extends Delivery {
    Transport createTransport() { return new Truck(); }
}
// Transport — интерфейс с методом name(), Bike и Truck его реализуют

Нужна доставка дронами? Новый класс DroneDelivery — и ни строчки правки в Delivery: принцип открытости/закрытости в действии. Пример из JDK — iterator() у коллекций: ArrayList создаёт свой итератор, HashSet — свой.

🔎 Для любопытных: Abstract Factory — абстрактная фабрика

Бывает, что объекты нужны семейством и должны подходить друг к другу: светлая кнопка в тёмном окне — некрасиво. Абстрактная фабрика — интерфейс, который создаёт всё семейство целиком, по сути набор фабричных методов:

interface Button { String draw(); }
interface Window { String draw(); }

class DarkButton implements Button { public String draw() { return "[тёмная кнопка]"; } }
class DarkWindow implements Window { public String draw() { return "тёмное окно"; } }

interface ThemeFactory {                       // абстрактная фабрика
    Button createButton();
    Window createWindow();
}

class DarkTheme implements ThemeFactory {
    public Button createButton() { return new DarkButton(); }
    public Window createWindow() { return new DarkWindow(); }
}
// LightTheme — так же, только создаёт светлые кнопку и окно

public class ThemeDemo {
    public static void main(String[] args) {
        ThemeFactory theme = new DarkTheme();     // сменить тему = передать другую фабрику
        System.out.println(theme.createWindow().draw()
                + " с кнопкой " + theme.createButton().draw());
    }
}

Код, который рисует окно, не знает ни одного конкретного класса кнопки и не может перепутать темы: всё берётся из одной фабрики.

Builder — строитель

Бутербродная: хлеб обязателен, а сыр, число котлет и соус — по желанию. С обычным конструктором вызов выглядит так:

Sandwich s = new Sandwich("ржаной", true, 2, "горчица");

Что значит true? С сыром? С луком? Через месяц не вспомнит никто. А если параметров семь и почти все необязательные, придётся писать кучу конструкторов на все сочетания.

Строитель (Builder) — объект-помощник, который собирает настройки по шагам, а в конце вызовом build() выдаёт готовый объект:

public class Sandwich {
    private final String bread;
    private final boolean cheese;
    private final int cutlets;

    private Sandwich(Builder b) {              // только через строителя
        this.bread = b.bread;
        this.cheese = b.cheese;
        this.cutlets = b.cutlets;
    }

    public static class Builder {
        private final String bread;            // обязательное — в конструкторе
        private boolean cheese = false;        // необязательные — со значениями по умолчанию
        private int cutlets = 1;

        public Builder(String bread) { this.bread = bread; }
        public Builder cheese() { this.cheese = true; return this; }
        public Builder cutlets(int count) { this.cutlets = count; return this; }
        public Sandwich build() {
            if (cutlets < 1 || cutlets > 3) throw new IllegalArgumentException("Котлет от 1 до 3");
            return new Sandwich(this);
        }
    }
}
Sandwich lunch = new Sandwich.Builder("ржаной")
        .cutlets(2)
        .cheese()
        .build();
public static class Builder

Новое: вложенный класс — класс внутри другого, полное имя Sandwich.Builder. static значит, что для него не нужен объект Sandwich. Вложенный и внешний классы видят private-поля друг друга, поэтому конструктор читает b.bread.

return this;

Метод настройки возвращает тот же строитель, поэтому после .cutlets(2) сразу пишут .cheese(). Это цепочка вызовов (fluent interface).

private Sandwich(Builder b)

Недособранный бутерброд снаружи не создать, а поля final — готовый объект не меняется.

build()

Последний шаг: проверить параметры и создать объект. Все проверки — в одном месте.

Что будет, если cheese() объявить как public void cheese() { this.cheese = true; }, а цепочку не трогать?

Не скомпилируется. .cheese() теперь возвращает void — «ничего», и у «ничего» нельзя вызвать .build(). Без return this строитель работает только отдельными строками: b.cheese(); b.cutlets(2);.

Родственник, которого ты знаешь, — StringBuilder: его append тоже возвращает this, поэтому пишут sb.append("Привет, ").append(name). В JDK есть и «настоящие» строители, например HttpRequest.newBuilder()…build().

Когда строитель нужен, а когда нет

Когда параметров много (примерно от четырёх) и большинство необязательные. Для двух-трёх полей хватит конструктора или record — снова KISS.

Задача

В задачах модуля тебя ждёт «Пиццерия»: заказ пиццы со строителем, проверка размера в build() и пицца дня одной цепочкой.

🔎 Для любопытных: Prototype — прототип, или «сделай копию»

Иногда проще не собирать объект заново, а скопировать готовый: плейлист «В дорогу» настроен, нужен такой же плюс пара песен. Помни: Playlist copy = road; — не копия, а вторая ссылка на тот же объект. Настоящую копию обычно делают конструктором копирования:

import java.util.ArrayList;
import java.util.List;

public class Playlist {
    private final String title;
    private final List<String> songs;

    public Playlist(String title, List<String> songs) {
        this.title = title;
        this.songs = new ArrayList<>(songs);
    }

    public Playlist(Playlist other) {                // конструктор копирования
        this.title = other.title;                    // String не меняется
        this.songs = new ArrayList<>(other.songs);   // свой новый список
    }
}

Главное — насколько глубоко копировать. Напиши this.songs = other.songs; — получится поверхностная копия: объекты разные, а список общий, и песня, добавленная «в копию», появится в оригинале. С new ArrayList<>(…) копия глубокая — ни с кем ничего не делит. clone() у массивов тоже поверхностный, а у своих классов он капризный, поэтому в Java обычно пишут конструктор копирования или метод copy().

Коротко

  • Паттерн — проверенный рецепт для типичной задачи и общий словарь разработчиков. 23 паттерна GoF делятся на порождающие, структурные и поведенческие. Применяй, когда без него больно, а не «для красоты».
  • Singleton: приватный конструктор + static final-поле + getInstance(), или enum. Минусы: глобальное состояние, спрятанные зависимости, мешает тестам.
  • Factory Method: статическая фабрика (List.of, Integer.valueOf) прячет new и выбор класса и может вернуть готовый объект.
  • Builder: обязательное — в конструктор строителя, необязательное — методами, которые возвращают this, в конце build() с проверками. Родственник — StringBuilder.
  • Реже встречаются Abstract Factory (создаёт семейство совместимых объектов) и Prototype (копия готового объекта; поверхностная копия делит вложенные объекты, глубокая — нет).
