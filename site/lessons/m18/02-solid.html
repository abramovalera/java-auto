SOLID: пять принципов хорошего дизайна

Программа работает — это половина дела. Вторая половина: через месяц добавить в неё новую фичу и не сломать старые. Пять коротких правил SOLID подсказывают, как разложить код по классам, чтобы изменения были маленькими и безопасными.

Повторение

Что такое SOLID и зачем он нужен

Дизайн кода — это то, как код разложен по классам и кто от кого зависит. Компилятору всё равно, а разница видна, когда код нужно менять: новый способ оплаты, другой вид чека, найденный баг. Хороший дизайн — когда каждое изменение затрагивает одно место и не ломает соседей. Как в хорошей квартире: чтобы поменять люстру, не нужно долбить стену и отключать воду.

SOLID — пять принципов объектно-ориентированного дизайна. Их собрал программист Роберт Мартин («дядя Боб»), а из первых букв сложилось слово solid — «прочный»:

🎯

S — Single Responsibility

Принцип единственной ответственности: одна причина для изменения.

🔌

O — Open/Closed

Открыт для расширения, закрыт для изменения.

🔁

L — Liskov Substitution

Наследник подставляется вместо родителя без сюрпризов.

✂️

I — Interface Segregation

Маленькие интерфейсы лучше одного толстого.

🔃

D — Dependency Inversion

Зависеть от интерфейса, а не от конкретного класса.

Сразу честно: это ориентиры, а не законы, компилятор за их нарушение не ругается. Новичку важнее всего S и D — их разберём подробно. Остальные три — коротко: они часто вырастают из первых двух сами.

S — одна причина для изменения

Принцип единственной ответственности (Single Responsibility Principle, SRP): у класса должна быть одна причина для изменения. Не «один метод», а одна забота — одна группа людей, которая может прийти и попросить его поменять.

Вот класс заказа, который умеет всё:

class Order {                              // ❌ три заботы сразу
    int price;
    int count;
    int total() { return price * count; }  // 1. считает сумму

    void printReceipt() {                  // 2. печатает чек
        System.out.println("Итого: " + total() + " ₽");
    }

    void sendEmail(String to) {            // 3. отправляет письмо
        System.out.println(to + ": заказ оформлен");
    }
}

Кто может попросить его изменить? Маркетологи — подсчёт суммы (скидки, акции). Бухгалтерия — вид чека. Отдел рассылок — текст письма. Три причины — три ответственности, и правка чека может случайно задеть подсчёт денег.

Делим по заботам — каждому классу одна:

class Order {                              // ✅ только заказ и сумма
    int price;
    int count;
    int total() { return price * count; }
}

class ReceiptPrinter {                     // ✅ только вид чека
    void print(Order order) {
        System.out.println("Итого: " + order.total() + " ₽");
    }
}

Письма точно так же уезжают в свой класс OrderMailer.

Бухгалтерия попросила добавить в чек дату. Какие классы из второго варианта придётся открыть?

Только ReceiptPrinter. Order и OrderMailer не трогаем, а значит, и сломать их не можем. В первом варианте правка шла бы в тот же класс, где считаются деньги.

Аналогия: кафе

В кафе повар, кассир и уборщик — разные люди. Поменяли кассовый аппарат — переучивается только кассир, повар готовит как готовил.

Класс пора делить, если его трудно назвать без «и» («заказ, и чек, и письма») или в нём сотни строк.

Как спросят на собеседовании

«Что такое Single Responsibility? Приведи пример нарушения». Ответ: у класса одна причина для изменения. Пример: класс заказа и считает сумму, и печатает чек, и шлёт письма — делим на три класса. Ловушка: SRP не значит «один метод в классе».

O — открыт для расширения, закрыт для изменения

Принцип открытости/закрытости (Open/Closed Principle, OCP): новое поведение добавляют новым кодом, а не правкой старого, уже проверенного.

Магазин считает доставку через switch, и каждый новый способ (дрон, постамат, экспресс) — ещё одна ветка в том же методе:

class DeliveryCalculator {                 // ❌ новая доставка — правка здесь
    int cost(String type, int kg) {
        return switch (type) {
            case "courier" -> 300 + 50 * kg;
            case "pickup" -> 0;
            default -> throw new IllegalArgumentException(type);
        };
    }
}

Решение — полиморфизм из модуля 10: каждый способ доставки сам знает свою цену.

interface Delivery { int cost(int kg); }   // ✅

class Courier implements Delivery {
    @Override public int cost(int kg) { return 300 + 50 * kg; }
}

class Drone implements Delivery {          // новая доставка = новый класс
    @Override public int cost(int kg) { return 500; }
}

Код оформления заказа вызывает delivery.cost(kg) и не знает, какая доставка ему пришла. Дрон добавили — старые классы не открывали. Как сменный объектив: фотоаппарат не разбирают, а прикручивают объектив к стандартному креплению.

switch — не преступление

Если вариантов мало и новых не предвидится (дни недели, «да/нет»), switch проще пачки классов — это KISS и YAGNI из прошлого урока. Интерфейс нужен, когда варианты реально добавляются.

🔎 Для любопытных: после появления Drone совсем ничего не надо менять?

Одно место всё-таки поменяется — то, где по выбору покупателя создают объект: new Drone() кто-то должен написать. Но это одна строчка в одном месте, а не правка логики расчёта. OCP не обещает «ноль изменений», он обещает, что старый проверенный код останется нетронутым.

L — наследник без сюрпризов

Принцип подстановки Лисков (Liskov Substitution Principle, LSP; Барбара Лисков — учёная, которая его сформулировала): объект наследника должен работать везде, где работает объект родителя, и не ломать ожиданий.

Пример с квадратом и прямоугольником ты уже видел в уроке 10.7. Вот ещё один, попроще:

class Bird {
    void fly() { System.out.println("Лечу!"); }
}

class Penguin extends Bird {               // ❌ обещал летать, а не может
    @Override
    void fly() { throw new UnsupportedOperationException("Не летаю"); }
}

Код, который перебирает список птиц и у каждой вызывает fly(), скомпилируется без единого предупреждения — а на пингвине упадёт с исключением. Ошибку увидит пользователь, а не компилятор. Решение — не обещать лишнего: умение летать выносим в отдельный интерфейс.

interface Flying { void fly(); }           // ✅ летает не каждая птица

class Bird { }

class Sparrow extends Bird implements Flying {
    @Override public void fly() { System.out.println("Лечу!"); }
}

class Penguin extends Bird { }             // летать не обещает

Теперь пингвина в List<Flying> не положишь — ошибку поймает компилятор. Тревожные звонки, что L нарушен: наследник бросает «не поддерживается», метод пустой «для галочки», перед вызовом приходится проверять instanceof Penguin.

I — маленькие интерфейсы лучше толстого

Принцип разделения интерфейсов (Interface Segregation Principle, ISP): класс не должен зависеть от методов, которыми не пользуется.

interface OfficeMachine {                  // ❌ один интерфейс на всё
    void print(String doc);
    void scan(String doc);
    void fax(String doc, String number);
}

Обычный принтер, реализуя такой интерфейс, вынужден писать заглушки scan и fax с исключением — тот же тревожный звонок, что в букве L. Режем по умениям:

interface Printer { void print(String doc); }     // ✅ по умению
interface DocScanner { void scan(String doc); }
interface Fax { void fax(String doc, String number); }

class SimplePrinter implements Printer {
    @Override public void print(String doc) { System.out.println(doc); }
}

Комбайн реализует сразу все три: implements Printer, DocScanner, Fax. А бухгалтеру, которому нужна только печать, передают Printer — про факс он ничего не знает. Как пульт для бабушки: пять нужных кнопок вместо шестидесяти. В Java так устроены Comparable и Runnable — по одному методу.

D — зависеть от интерфейса, а не от конкретного класса

Принцип инверсии зависимостей (Dependency Inversion Principle, DIP): классы высокого уровня (главная логика: «оформить заказ») не должны зависеть от классов низкого уровня (детали: «как именно отправить письмо»). Оба должны зависеть от абстракции — интерфейса.

Как обычно пишут в первый раз (EmailSender — класс, который отправляет письмо):

class OrderService {
    // ❌ сам выбрал и сам создал
    private final EmailSender sender = new EmailSender();

    void placeOrder(String customer) {
        // ... оформляем заказ ...
        sender.send(customer, "Заказ оформлен");
    }
}

OrderService намертво приварен к почте. Захотели SMS — переписываем его. Хотим проверить тестом — при каждом запуске «уходит письмо», и что именно ушло, не проверить.

Переворачиваем: OrderService говорит «мне нужен кто-то, кто умеет отправлять уведомления», а кто именно — решают снаружи и передают через конструктор:

interface Notifier {
    void send(String to, String text);
}

class OrderService {
    private final Notifier notifier;

    OrderService(Notifier notifier) {      // ✅ зависимость передают снаружи
        this.notifier = notifier;
    }

    void placeOrder(String customer) {
        notifier.send(customer, "Заказ оформлен");
    }
}

Почта и SMS — классы EmailNotifier и SmsNotifier, оба реализуют Notifier. Какой взять, решают в одном месте, на входе в программу: new OrderService(new SmsNotifier()).

Самый приятный бонус — тесты. В тест можно передать фейк (поддельную реализацию), который никуда ничего не отправляет, а только запоминает, что его попросили отправить.

Можно ли написать такой тест для первой версии OrderService, где внутри new EmailSender()?

Нормально — нет. Объект создаётся внутри класса, и снаружи его не подменить: тест всегда будет работать с настоящим EmailSender. Как только зависимость приходит через конструктор, тест сам решает, что подставить.

🔎 Для любопытных: как выглядит тест с фейком 
import org.junit.jupiter.api.Test;
import java.util.ArrayList;
import java.util.List;
import static org.assertj.core.api.Assertions.assertThat;

class FakeNotifier implements Notifier {
    final List<String> sent = new ArrayList<>();

    @Override
    public void send(String to, String text) {
        sent.add(to + ": " + text);        // ничего не отправляем, только запоминаем
    }
}

class OrderServiceTest {
    @Test
    void notifiesCustomerAfterOrder() {
        FakeNotifier fake = new FakeNotifier();
        new OrderService(fake).placeOrder("anna@example.com");
        assertThat(fake.sent).containsExactly("anna@example.com: Заказ оформлен");
    }
}
Аналогия: розетка

Лампу не припаивают к проводке в стене — у неё вилка, а в стене стандартная розетка. В неё можно включить лампу, зарядку или тестер электрика. Розетка — интерфейс, приборы — реализации, тестер — тот самый фейк.

Заметь: new SmsNotifier() не исчез, а переехал в main — в одно место. Классы с логикой получают готовое через конструктор. Этот приём называют внедрением зависимости через конструктор (constructor injection).

Как спросят на собеседовании

«Чем Dependency Inversion отличается от Dependency Injection?» Ответ: Inversion — принцип: логика зависит от абстракций, а не от конкретных классов. Injection — приём: зависимость передают снаружи, например через конструктор. Приём помогает соблюдать принцип.

Ориентиры, а не законы

SOLID легко довести до абсурда: интерфейс на каждый класс, десять файлов ради «Привет, мир» — это нарушает KISS и YAGNI. Применяй принципы там, где изменения правда случаются:

  • Класс разросся и меняется по разным причинам — дели (S).
  • Класс сам создаёт свои «инструменты» через new, и его не протестировать — передай их через конструктор, тип поля — интерфейс (D).
  • Варианты поведения реально добавляются — интерфейс и новые классы вместо растущего switch (O).
  • Наследник бросает «не поддерживается» — пересмотри иерархию (L), часто вместе с толстым интерфейсом (I).

Если запомнишь из урока только две вещи — пусть это будут S («у класса одна забота») и D («нужные объекты передай через конструктор, тип поля — интерфейс»).

🔎 Для любопытных: как спросят про O, L и I на собеседовании

«Как понимать “открыт для расширения, закрыт для изменения”?» Новое поведение добавляем новым классом, который реализует интерфейс; старый код, который с этим интерфейсом работает, не меняем. Пример: switch по типу доставки заменяем интерфейсом Delivery.

«Что такое принцип подстановки Лисков?» Наследника можно передать везде, где ждут родителя, и программа продолжит работать правильно. Нарушения: квадрат-наследник прямоугольника с сеттерами; пингвин, который бросает исключение в fly(). Аналогия — прокат машин: в любой машине тормоз слева, иначе на неё нельзя «подставиться».

«Чем плох толстый интерфейс?» Реализациям приходится писать заглушки (часто с исключением — привет, L), а клиенты зависят от методов, которыми не пользуются. Лечится разделением на маленькие интерфейсы; один класс может реализовать сразу несколько.

Проверь себя

Поговори с наставником

Напиши: «Я прошёл урок про SOLID. Дай мне три небольших класса с нарушениями разных принципов, а я сам скажу, какая буква нарушена и как это исправить». А потом: «Возьми мою последнюю задачу и скажи, где в ней нарушен S или D — только укажи место, исправлю я сам».

Коротко

  • S — у класса одна причина для изменения: заказ, печать чека и рассылка писем — разные классы.
  • O — новый вариант поведения добавляем новым классом с интерфейсом, а не новой веткой в старом switch.
  • L — наследник работает везде, где родитель; исключение «не поддерживается» в наследнике — тревожный звонок.
  • I — несколько маленьких интерфейсов вместо одного толстого; класс реализует только то, что умеет.
  • D — логика зависит от интерфейса, конкретную реализацию передают через конструктор; в тест — фейк.
  • Это ориентиры, а не законы. Главное для начала — S и D; не плоди интерфейсы «на всякий случай» (KISS, YAGNI).
