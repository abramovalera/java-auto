План по шагам

  1. Каркас. IDEA → New Project → Build system Gradle, DSL Kotlin, JDK 21. В build.gradle.kts — junit-jupiter, selenide, assertj через testImplementation, useJUnitPlatform() и проброс -D (урок 6). Пакеты pages, tests, data, config; config.properties с адресом сайта; BaseTest.
  2. Первый тест. LoginPage с приватными полями-элементами (локаторы внутри) и методами страницы loginAs / loginExpectingError, страница после входа — SecureAreaPage. Тест «успешный вход» зелёный — коммит.
  3. Ещё страницы. Checkboxes, Dropdown, Add/Remove, Dynamic Loading — по классу-странице и тест-классу на каждую.
  4. Данные. Пользователи — record + enum; негативные входы — параметризованный тест с @CsvSource «логин, пароль, ожидаемая ошибка».
  5. Надёжность. Ни одного Thread.sleep. Запусти все тесты три раза подряд через Gradle → test (или gradle clean test): все три раза зелёные? Запусти один тест отдельно — проходит?
  6. Git и README. Репозиторий, .gitignore (build/, .gradle/, .idea/; wrapper gradlew и gradle/wrapper — коммитить), README: что тестируется, как запустить, какие технологии. Выложи на GitHub — это твоё портфолио.

Критерии: проект готов, когда…

Проект сдан наставнику, еслиПроект готов, если

  • минимум 10 тестов на 4+ страницах, все зелёные три прогона подряд;
  • в тестах нет ни одного локатора — только вызовы методов страниц;
  • локаторы — приватные, составлены руками, без абсолютных путей и номеров; про каждый можешь сказать, почему выбрал именно его;
  • нет Thread.sleep; ожидания — проверками состояния Selenide (shouldBe, shouldHave);
  • каждый тест можно запустить отдельно, и в любом порядке;
  • есть негативные тесты (неверный пароль и т.п.) и хотя бы один параметризованный;
  • адрес сайта и браузер — в config.properties, данные — в пакете data;
  • понятные имена тестов: по имени ясно, что проверяется;
  • проект в Git с README; коммиты — небольшие, с понятными сообщениями;
  • ты можешь объяснить любую строку своего кода.

Вопросы с собеседований автоматизатора

Сначала ответь вслух, потом открывай. Ответ «потому что так принято» не засчитывается — только с объяснением «почему».

1. Что такое Page Object и зачем он нужен?

Класс на каждую страницу: приватные поля-элементы с локаторами и публичные методы страницы — действия пользователя. Локаторы правятся в одном месте, тесты читаются как тест-кейсы, повторяющийся код уходит из тестов.

2. CSS или XPath — что выбрать?

По умолчанию CSS: короче и понимает классы. XPath — когда нужен поиск по тексту или движение вверх по дереву (.., ancestor::). Главное не язык, а стабильный атрибут: data-test-id, id.

3. Почему Thread.sleep в тестах — плохо?

Ждёт фиксированное время: если элемент появился раньше — время потеряно, если позже — тест всё равно упал. Нужны ожидания условия: проверка состояния shouldBe(visible) в Selenide, опрос с таймаутом для остального.

4. Что такое flaky-тест и что с ним делать?

Тест, который то проходит, то падает без изменений кода. Причины: зависимость от других тестов и общих данных, sleep вместо ожиданий, нестабильные локаторы, нестабильный стенд. Не перезапускать до победы, а найти причину; пока не починен — пометить и не доверять.

5. Тест упал. Твои действия?

Прочитать сообщение (ожидаемое значение, фактическое значение, где упало), посмотреть скриншот и шаги, воспроизвести руками. Решить: баг продукта (завести баг-репорт с шагами, ожидаемым и фактическим результатом) или проблема теста/стенда/данных (починить тест).

6. Чем отличаются @BeforeEach и @BeforeAll?

Метод с аннотацией @BeforeEach — перед каждым тестовым методом; с @BeforeAll — один раз перед всеми тестами класса, поэтому метод static (объекта класса ещё нет — JUnit создаёт новый объект на каждый тест).

7. Как сделать тесты независимыми?

Каждый тест сам готовит данные (лучше через API) и состояние (@BeforeEach), не использует общие изменяемые static-поля, не рассчитывает на порядок запуска, по возможности убирает за собой. Свежий браузер на тест.

8. Классы эквивалентности и граничные значения — на примере «скидка от 1000 ₽»

Классы: меньше 1000 (скидки нет) и от 1000 (скидка есть) — внутри класса поведение одинаковое, хватает одного значения. Границы: 999 и 1000 — именно там ошибаются (> вместо >=). Плюс невалидные: отрицательная сумма, пусто, не число.

9. Чем 401 отличается от 403? А 500?

401 — не авторизован (не представился, нет токена). 403 — представился, но прав нет. 500 — сервер упал внутри; на неверный ввод правильный ответ — 400, поэтому 500 почти всегда баг.

10. Классика Java: чем == отличается от equals?

== у объектов сравнивает ссылки (один ли это объект), equals — содержимое, если класс его переопределил. Строки сравнивают через equals. Переопределил equals — переопредели и hashCode, иначе HashMap и HashSet сломаются.

11. Checked и unchecked исключения — в чём разница?

Checked (наследники Exception, кроме RuntimeException) компилятор заставляет обработать или объявить в throws — например, IOException. Unchecked (RuntimeException и наследники) — нет: NullPointerException, IllegalArgumentException. Кстати, упавшая проверка (assertion) в тесте — это AssertionError, вообще не Exception, а Error.

12. Что автоматизировать в первую очередь?

Smoke и главный регресс: самые важные пользовательские сценарии, которые проверяются каждый выпуск и стабильны по требованиям. Не автоматизировать то, что меняется каждую неделю, разовые проверки и оценку удобства.
