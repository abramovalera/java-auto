Чистый код: стиль, DRY, KISS, YAGNI

Программа работает — это половина дела. Вторая половина — чтобы её мог прочитать и поправить человек: коллега или ты сам через полгода. Сегодня — правила оформления и три принципа, которые знает каждый разработчик.

⏱ 18 минут🧹 код-стайл🎯 DRY · KISS · YAGNI

Повторение

Код пишут для людей

Компьютеру всё равно, как называются переменные. Оба метода ниже делают одно и то же — прибавляют к сумме заказа доставку, если заказ меньше 2000 ₽:

static int calc(int s) {
    return s >= 2000 ? s : s + 199;
}🚫 так не надо — не набирай
static final int FREE_DELIVERY_FROM = 2000;
static final int DELIVERY_PRICE = 199;

static int addDelivery(int orderSum) {
    if (orderSum >= FREE_DELIVERY_FROM) {
        return orderSum;
    }
    return orderSum + DELIVERY_PRICE;
}👀 просто прочитай

Первый короче, но что такое s? что за 2000 и 199? Второй читается как обычный текст.

Код читают гораздо чаще, чем пишут: ты сам, когда ищешь баг, коллега на код-ревью (просмотр чужого кода перед тем, как его примут в общую ветку), новичок через год. Код, понятный человеку, называют чистым: понятные имена, единый стиль, ничего лишнего.

Аналогия: коробки при переезде

Подписал коробки «1», «2», «3» — через неделю открываешь шесть штук в поисках чайника. Написал «Кухня: чайник, кружки» — нашёл сразу. Хорошие имена — это подписи на коробках с кодом.

🔎 Для любопытных: что об этом говорят классики

Роберт Мартин в книге «Чистый код» прикидывает: на чтение кода уходит больше чем в десять раз больше времени, чем на его написание. Мартин Фаулер говорил примерно так: код, который понимает компьютер, напишет любой, а хороший программист пишет код, который понимают люди. Чистый код — это не про красоту, а про деньги и нервы: его быстрее читать, проще менять, и в нём труднее спрятаться багу.

Хорошая новость: половину работы по чистоте кода сделает IDEA.

Имена: все правила в одном месте

Правила имён из уроков 1.6 и 2.3 — вместе. Это часть код-стайла (code style) — договорённости, как оформлять код. Компилятор её не проверяет, но соблюдает весь мир Java.

Магические числа

Магическое число — число посреди кода без объяснения. Что значит 3 в if (order.status() == 3): «оплачен»? «отменён»? Лекарство — именованная константа (static final int DELIVERY_PRICE = 199;) или enum (Status.DELIVERED): у числа есть имя, а менять его — в одном месте.

В IDEA: курсор на число, Ctrl+Alt+C (Extract Constant). Неудачное имя меняй через Shift+F6 — сразу везде.

А комментарии?

// прибавляем доставку над addDelivery только повторяет имя. Комментарий полезен, когда объясняет почему: // склад закрыт по воскресеньям — переносим отправку. Хочется объяснить «что тут происходит» — сначала попробуй дать имя получше.

Оформление и помощники: IDEA и Checkstyle

Кроме имён код-стайл договаривается о том, как код выглядит:

  • Отступ — каждый уровень вложенности сдвигается вправо (в IDEA — 4 пробела).
  • Открывающая скобка { — на той же строке, что if или метод, закрывающая — на своей строке. else пишется так: } else {.
  • Фигурные скобки — всегда, даже если внутри if одна строка. Иначе легко добавить вторую строку и думать, что она тоже внутри условия.
  • Строка — не длиннее 100–120 символов. В IDEA границу показывает тонкая вертикальная линия справа в редакторе.
if (orderSum >= FREE_DELIVERY_FROM)
{
    return orderSum;
}
else return orderSum + DELIVERY_PRICE;🚫 не по стилю Java
if (orderSum >= FREE_DELIVERY_FROM) {
    return orderSum;
} else {
    return orderSum + DELIVERY_PRICE;
}👀 так принято в Java

Расставлять отступы руками не нужно: Ctrl+Alt+L (Code → Reformat Code) приводит весь файл к стилю проекта. Ты знаешь эту клавишу с модуля 1 — сделай её привычкой перед каждым коммитом.

Красным IDEA показывает ошибки компиляции, а жёлтым и серым — инспекции (inspections): код скомпилируется, но выглядит подозрительно или его можно упростить. Посмотри, сколько всего она нашла в шести строках:

Правило простое: перед коммитом в файле не должно остаться жёлтого и серого. Курсор на подсветку, Alt+Enter — и IDEA предложит исправление. А в командах стиль ещё и проверяют автоматически при каждой сборке — инструментом Checkstyle.

🔎 Для любопытных: Checkstyle, разные стили и перенос длинных строк

Стилей несколько — главное, один на проект. Самые известные своды правил — Google Java Style (отступ 2 пробела, строка до 100 символов) и правила IDEA по умолчанию (отступ 4 пробела, строка до 120). Они совпадают в главном: имена, скобки, переносы. Смешанный стиль хуже любого из двух.

Длинную строку переносят, а продолжение сдвигают дополнительным отступом. Цепочку Stream переносят так, чтобы каждый шаг был на своей строке, — точка в начале строки:

List<String> bigBuyers = orders.stream()
        .filter(order -> order.total() > 10_000)
        .map(Order::customer)
        .distinct()
        .toList();👀 просто прочитай

Ещё одна полезная клавиша: Ctrl+Alt+O убирает неиспользуемые import.

Checkstyle. IDEA подсказывает, но не заставляет: жёлтое можно проигнорировать и закоммитить. Checkstyle читает исходники и сверяет их со списком правил — имена, длина строк, скобки, магические числа и сотни других. В Gradle он подключается плагином checkstyle, правила лежат в config/checkstyle/checkstyle.xml (обычно его уже положил кто-то из команды, часто на основе Google Java Style). Дальше задача check, а значит и build, сама проверяет стиль:

Здесь замечания — предупреждения, и сборка прошла. Многие команды настраивают строже: есть хоть одно замечание — сборка красная, и код «не по стилю» не попадёт в общую ветку. Настраивать Checkstyle самому пока не нужно: если сборка ругается на стиль — открой отчёт и поправь строки. Плагин CheckStyle-IDEA показывает те же замечания прямо в редакторе.

DRY: не повторяйся

DRY — Don't Repeat Yourself, «не повторяйся»: каждое правило программы записано в одном месте. Скидка 10% на заказы от 5000 ₽ нужна в чеке, в SMS и при оплате бонусами — и формулу скопировали:

static void printReceipt(int sum) {
    int toPay = sum >= 5000 ? sum - sum / 10 : sum;
    System.out.println("К оплате: " + toPay);
}

static boolean canPayByBonuses(int sum, int bonuses) {
    int toPay = sum >= 5000 ? sum - sum / 10 : sum;
    return bonuses >= toPay;
}
// … и та же формула ещё раз в sendSms()🚫 так не надо — не набирай
Порог скидки снизили до 3000 ₽. Программист поправил printReceipt и sendSms, а про canPayByBonuses забыл. У покупателя заказ на 4000 ₽ и 3700 бонусов. Что он увидит?

В чеке и в SMS — «к оплате 3600». А при оплате бонусами — отказ: третий метод считает без скидки, нужно 4000. Баг — и никакой ошибки компиляции.

Лечится выносом правила в отдельный метод, а чисел — в константы. Методы больше не считают скидку сами, а спрашивают у одного:

public class DiscountShop {
    static final int DISCOUNT_FROM = 3000;
    static final int DISCOUNT_PERCENT = 10;

    public static void main(String[] args) {
        printReceipt(4000);
        System.out.println(canPayByBonuses(4000, 3700));
    }

    static int priceWithDiscount(int sum) {
        if (sum >= DISCOUNT_FROM) {
            return sum - sum * DISCOUNT_PERCENT / 100;
        }
        return sum;
    }

    static void printReceipt(int sum) {
        System.out.println("К оплате: " + priceWithDiscount(sum));
    }

    static boolean canPayByBonuses(int sum, int bonuses) {
        return bonuses >= priceWithDiscount(sum);
    }
}
К оплате: 3600
true

Теперь порог меняется в одной строке. В IDEA выдели повторяющийся кусок и нажми Ctrl+Alt+M (Extract Method) — она вынесет его в метод и предложит заменить такие же куски. Переделка кода без изменения поведения называется рефакторинг: тесты зелёные до и после — значит, ничего не сломал.

Правило трёх

Написал кусок первый раз — просто пиши. Скопировал второй раз — поморщись. Тянешься скопировать в третий — выноси в метод.

Не перестарайся: похожее ≠ одинаковое

DRY — про одно знание в одном месте, а не про одинаковые буквы. Доставка за килограмм и коробка сейчас обе по 50 ₽, но это разные правила и меняться будут порознь. Дай им разные имена: PRICE_PER_KG и PRICE_PER_BOX.

🔎 Для любопытных: «похоже, но не одно и то же» в коде и имя без глагола 
static int calculateDeliveryPrice(int weightKg) {
    return weightKg * PRICE_PER_KG;      // сейчас 50, но живёт своей жизнью
}

static int calculatePackagingPrice(int boxes) {
    return boxes * PRICE_PER_BOX;        // тоже 50 — совпадение, а не правило
}👀 просто прочитай

Склеишь их в один multiplyBy50(int x) — а после смены тарифа придётся расклеивать обратно.

Заметил, что priceWithDiscount назван не по глаголу? Так можно, когда метод просто вычисляет значение и имя читается как ответ: «цена со скидкой». Главное — чтобы имя объясняло смысл.

KISS: делай проще

KISS — Keep It Simple, Stupid, «делай проще, глупыш». Из двух решений, которые одинаково работают, выбирай то, которое проще прочитать. Хитрый код приятно писать, но читать его будет тот, кто не был у тебя в голове.

Ранний return вместо «лесенки»

Каждый вложенный if сдвигает код вправо, и скоро непонятно, какой else к какому if относится:

static String checkout(String address, int items, boolean paid) {
    if (address != null) {
        if (items > 0) {
            if (paid) {
                return "Отправляем заказ";
            } else {
                return "Заказ не оплачен";
            }
        } else {
            return "Корзина пуста";
        }
    } else {
        return "Нет адреса";
    }
}🚫 так не надо — не набирай

Приём ранний return (guard clause, «условие-охранник»): сначала отсекаем все плохие случаи и сразу выходим из метода. Что осталось в конце — нормальный путь, без вложенности. Набери и проверь, что работает так же:

public class OrderDesk {
    public static void main(String[] args) {
        System.out.println(checkout("Лесная, 5", 0, true));
        System.out.println(checkout("Лесная, 5", 3, true));
    }

    static String checkout(String address, int items, boolean paid) {
        if (address == null) {
            return "Нет адреса";
        }
        if (items <= 0) {
            return "Корзина пуста";
        }
        if (!paid) {
            return "Заказ не оплачен";
        }
        return "Отправляем заказ";
    }
}

Отправляем заказ

Строк даже меньше, а главное — читается сверху вниз, как список правил. Тот же приём спасает от вложенных тернарников: один простой выбор count == 1 ? "товар" : "товаров" — нормально, а тернарник внутри тернарника — уже ребус.

Как записать короче, не меняя смысла?
if (age >= 18) { return true; } else { return false; }

return age >= 18; — сравнение уже даёт boolean. Обёртка из if просто переписывает этот ответ ещё раз. Это та самая серая подсветка «'if' statement can be simplified» со скрина про инспекции — Alt+Enter сделает замену сам.

🔎 Для любопытных: вложенные тернарники, длинные Stream и мысль Кернигана

Метод определяет размер посылки по весу. Чтобы понять, что вернётся для 5 кг, приходится мысленно пройти всю цепочку ? ::

static String findSize(int weightKg) {
    return weightKg > 20 ? "большая"
            : weightKg > 5 ? "средняя"
            : weightKg > 0 ? "маленькая" : "ошибка";
}🚫 так не надо — не набирай

Через if с ранним return — каждая ветка отдельной строкой:

static String findSize(int weightKg) {
    if (weightKg <= 0) {
        return "ошибка";
    }
    if (weightKg <= 5) {
        return "маленькая";
    }
    if (weightKg <= 20) {
        return "средняя";
    }
    return "большая";
}👀 просто прочитай

Если выбор идёт по конкретным значениям (зона 1, 2, 3…), а не по диапазонам, ещё лучше подойдёт switch со стрелками: case 1 -> "центр";.

KISS касается и Stream: цепочка из трёх шагов читается как фраза, а из десяти с лямбдами внутри лямбд — уже нет. Если цепочку трудно прочитать вслух, разбей её на части с понятными именами или напиши обычный цикл. Простой цикл — не позор.

Брайан Керниган, один из авторов языка C, заметил: отлаживать код вдвое труднее, чем писать. Значит, если ты написал код на пределе своей хитрости, отладить его ты уже не сможешь.

YAGNI: тебе это не понадобится

YAGNI — You Aren't Gonna Need It, «тебе это не понадобится». Не пиши код «на будущее»: классы, настройки и параметры, которые никто не просил. Задача: посчитать цену доставки курьером — 300 ₽ плюс 50 ₽ за килограмм. Начитавшийся про интерфейсы программист пишет так:

// вызов: DeliveryFactory.create("courier").calculatePrice(3)

interface DeliveryStrategy {
    int calculatePrice(int weightKg);
}

class CourierDelivery implements DeliveryStrategy {
    public int calculatePrice(int weightKg) {
        return 300 + weightKg * 50;
    }
}

class DeliveryFactory {
    static DeliveryStrategy create(String type) {
        return switch (type) {
            case "courier" -> new CourierDelivery();
            // "drone", "teleport" — на будущее, вдруг пригодится
            default -> throw new IllegalArgumentException(type);
        };
    }
}🚫 так не надо — не набирай

Три типа и фабрика, чтобы умножить и сложить. А вот что действительно нужно по задаче:

static final int BASE_PRICE = 300;
static final int PRICE_PER_KG = 50;

static int calculateDeliveryPrice(int weightKg) {
    return BASE_PRICE + weightKg * PRICE_PER_KG;
}👀 просто прочитай
  • Будущее редко наступает таким, каким его представили: дронов не сделают, а самовывозу заготовка не подойдёт.
  • Лишний код не бесплатный: его читают, поддерживают, в нём живут баги.
  • Простой код легко расширить, когда второй способ доставки появится по-настоящему.
YAGNI — не оправдание для халтуры

YAGNI про новые возможности, которые никто не просил. Проверить входные данные, написать тесты, дать нормальные имена — это нужно уже сейчас.

Поговори с наставником

Возьми любое своё решение задачи из прошлых модулей и напиши: «Вот мой код. Найди в нём нарушения код-стайла, DRY, KISS и YAGNI, но не переписывай — только назови, что не так, а исправлю я сам». Если граница между принципами пока размыта, спроси: «Приведи пример из жизни магазина, где два куска кода похожи, но склеивать их по DRY нельзя».

Коротко

  • Код читают намного чаще, чем пишут. Чистый код — понятный человеку: хорошие имена, единый стиль, ничего лишнего.
  • Имена: классы — PascalCase, переменные и методы — camelCase, методы — с глагола, константы — UPPER_SNAKE_CASE, пакеты — маленькими буквами. Магические числа — в именованные константы.
  • Оформление: скобка открывается на той же строке, закрывается на своей; строки до 100–120 символов; Ctrl+Alt+L перед коммитом.
  • Жёлтое и серое в IDEA — инспекции, их стоит убрать. Checkstyle проверяет стиль автоматически при сборке Gradle.
  • DRY — одно правило в одном месте (но похожий код с разным смыслом не склеивать). KISS — самое простое решение: ранний return вместо лесенки, if вместо вложенных тернарников. YAGNI — не писать «на будущее».
