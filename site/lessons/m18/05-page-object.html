Page Object: страница как класс

Главный шаблон UI-автоматизации. Каждая страница сайта становится Java-классом с локаторами и действиями, а тест читается как тест-кейс. Здесь ООП из модулей 9–11 начинает работать на тебя.

Повторение

Проблема: локаторы везде

Ты написал 30 тестов. В каждом, где нужен вход, повторяются три строки с локаторами:

$("[data-test-id='login']").setValue("anna");
$("[data-test-id='password']").setValue("qwerty123");
$("[data-test-id='login-button']").click();

Разработчики переименовали login-button в sign-in. Красные — все 30 тестов, и чинить надо 30 мест. А ещё тест, где перемешаны локаторы, клики и проверки, трудно читать: за деревьями $("[…]") не видно леса — что, собственно, проверяем?

Аналогия: пульт от телевизора

Ты жмёшь «громче» и не думаешь, какие провода внутри замыкаются. Если производитель переделает плату, кнопка «громче» останется на месте. Page Object — это пульт от страницы: снаружи понятные кнопки «войти», «найти книгу», «положить в корзину», а провода-локаторы спрятаны внутри. Поменялась вёрстка — перепаиваешь один пульт, а не учишь заново всех, кто им пользуется.

Класс страницы

Page Object (объект страницы) — класс, который описывает одну страницу или её часть: где элементы (локаторы — приватные поля) и что с ними можно делать (действия — публичные методы страницы на языке пользователя).

import com.codeborne.selenide.Selenide;
import com.codeborne.selenide.SelenideElement;

import static com.codeborne.selenide.Condition.*;
import static com.codeborne.selenide.Selenide.$;

public class LoginPage {
    private final SelenideElement loginField = $("[data-test-id='login']");
    private final SelenideElement passwordField =
            $("[data-test-id='password']");
    private final SelenideElement loginButton =
            $("[data-test-id='login-button']");
    private final SelenideElement error = $("[data-test-id='error']");

    public LoginPage open() {
        Selenide.open("/login");
        return this;
    }

    public CatalogPage loginAs(String user, String password) {
        fillForm(user, password);
        return new CatalogPage();
    }

    public LoginPage loginExpectingError(String user, String password) {
        fillForm(user, password);
        return this;
    }

    public LoginPage shouldShowError(String expectedText) {
        error.shouldBe(visible).shouldHave(exactText(expectedText));
        return this;
    }

    private void fillForm(String user, String password) {
        loginField.setValue(user);
        passwordField.setValue(password);
        loginButton.click();
    }
}

Элементы страницы, каждый со своим локатором, — приватные поля: инкапсуляция из модуля 10. Снаружи их не видно, тесты не могут завязаться на них напрямую. SelenideElement — «ленивый»: искать элемент он начнёт не при создании объекта страницы, а в момент действия или проверки. Поэтому объявлять поля до открытия страницы безопасно.

LoginPage open()

Метод страницы возвращает this — ссылку на этот же объект страницы. Можно сразу продолжить цепочку: new LoginPage().open().loginAs(…).

CatalogPage loginAs(…)

После успешного входа браузер уходит в каталог — и метод возвращает объект следующей страницы. Тест «переходит» вместе с браузером.

LoginPage loginExpectingError(…)

Когда мы ждём ошибку, остаёмся на странице входа — возвращаем this. Два метода вместо одного: тип результата честно говорит, где мы окажемся.

shouldShowError(expectedText)

Проверка спрятана в страницу, но что ожидать — решает тест: он передаёт ожидаемое значение аргументом expectedText. Страница знает «как проверить», тест — «что должно быть».

private void fillForm(…)

Общий кусок двух методов вынесен в приватный помощник — никакого копипаста.

🔎 Для любопытных: почему Selenide.open, а не просто open?

В классе есть свой метод open(). Если внутри него написать open("/login"), Java будет искать метод open у этого класса — статический импорт Selenide.open перекрыт методом класса с тем же именем. Компилятор скажет, что open() не принимает аргументов. Поэтому вызываем с именем класса: Selenide.open("/login"). Хорошая задачка про области видимости для собеседования.

Тест с Page Object

Сравни. Тест без Page Object:

@Test
void wrongPasswordShowsError() {
    open("/login");
    $("[data-test-id='login']").setValue("anna");
    $("[data-test-id='password']").setValue("12345");
    $("[data-test-id='login-button']").click();
    $("[data-test-id='error']")
            .shouldBe(visible)
            .shouldHave(exactText("Неверный логин или пароль"));
}

Тот же тест с Page Object:

@Test
void wrongPasswordShowsError() {
    new LoginPage().open()
            .loginExpectingError("anna", "12345")
            .shouldShowError("Неверный логин или пароль");
}

@Test
void userCanLogIn() {
    new LoginPage().open()
            .loginAs("anna", "qwerty123")
            .shouldGreet("anna");
}

Второй вариант читается как тест-кейс: «открыть вход → войти с неверным паролем → видна ошибка». Ни одного локатора. Переименовали кнопку — правишь одну строку в LoginPage, и все 30 тестов снова зелёные.

Тесты становятся короче, понятнее и меньше ломаются. А ещё такой тест может прочитать ручной тестировщик или аналитик, не зная Java. Это и есть цель.

Что вернёт new LoginPage().open().loginExpectingError("anna", "1") и какой метод можно вызвать дальше?

Объект LoginPage — ту же страницу (return this). Дальше по цепочке доступны методы страницы входа, например shouldShowError(…). А shouldGreet — нет: его нет в классе LoginPage, компилятор не даст ошибиться. Типы защищают тест от бессмысленных шагов.

BasePage и компоненты: наследование и композиция

У всех страниц магазина одна шапка: поиск, значок корзины, кнопка «Выйти». Описывать её в каждой странице — копипаст. Тут пригодятся оба инструмента ООП.

Композиция (модуль 11): шапка — отдельный класс-компонент, а страницы его имеют:

public class Header {
    private final SelenideElement search = $("[data-test-id='search']");
    private final SelenideElement cartBadge = $("[data-test-id='cart'] .badge");

    public SearchResultsPage search(String query) {
        search.setValue(query).pressEnter();
        return new SearchResultsPage();
    }

    public Header shouldHaveCartCount(int count) {
        cartBadge.shouldHave(exactText(String.valueOf(count)));
        return this;
    }
}

Наследование (модуль 10): общее для всех страниц — в абстрактный BasePage, страницы его расширяют:

public abstract class BasePage {
    // композиция: страница ИМЕЕТ шапку
    private final Header header = new Header();

    public Header header() {
        return header;
    }
}

// наследование: каталог ЯВЛЯЕТСЯ страницей
public class CatalogPage extends BasePage {
    private final SelenideElement greeting = $("[data-test-id='greeting']");

    public CatalogPage shouldGreet(String user) {
        greeting.shouldHave(exactText("Привет, " + user + "!"));
        return this;
    }
}

В тесте: catalog.header().shouldHaveCartCount(1); — вызов header() возвращает компонент-шапку, и у него сразу вызываем метод-проверку с аргументом 1. Работает для любой страницы-наследника.

Композиция чаще лучше

Не тащи в BasePage всё подряд: «у всех страниц есть шапка» — хорошо, «у некоторых есть фильтр» — уже нет. Повторяющиеся куски (шапка, фильтр, карточка товара, модальное окно) оформляй компонентами и подключай туда, где они есть. Это то самое правило «предпочитай композицию наследованию» из модуля 11.

Правила хорошего Page Object

  1. Локаторы — приватные и живут только в своей странице или компоненте.
  2. Методы страницы — действия пользователя: loginAs, addToCart, search. Не clickButton3.
  3. Переход — метод возвращает объект следующей страницы, остался на месте — this.
  4. Ожидаемое решает тест. Страница может иметь методы-проверки should…, но ожидаемые значения тест передаёт в них аргументами.
  5. Никаких Thread.sleep — только ожидания Selenide.
  6. Одна страница — один класс, повторяющиеся куски — компоненты.

Коротко

  • Page Object — класс страницы: приватные поля-элементы с локаторами + публичные методы страницы (действия пользователя).
  • Переход на другую страницу — метод возвращает её объект; остались — return this.
  • Тест без локаторов читается как тест-кейс, а смена вёрстки чинится в одном месте.
  • Общее — в BasePage (наследование), повторяющиеся куски — компоненты вроде Header (композиция).
  • Страница знает «как проверить», тест решает «что ожидать».
