build.gradle.kts: три зависимости

plugins {
    java
}

group = "shop.nook"
version = "1.0"

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)
    }
}

repositories {
    mavenCentral()
}

dependencies {
    testImplementation("org.junit.jupiter:junit-jupiter:5.11.4")
    testImplementation("com.codeborne:selenide:7.5.1")
    testImplementation("org.assertj:assertj-core:3.27.3")
    testRuntimeOnly("org.junit.platform:junit-platform-launcher")
}

tasks.test {
    useJUnitPlatform()
    // передать тестам -D из командной строки: gradle test -Dbrowser=firefox
    listOf("browser", "base.url", "timeout.ms").forEach { key ->
        System.getProperty(key)?.let { systemProperty(key, it) }
    }
}
  • testImplementation — так объявляют зависимость (подключаемую библиотеку), нужную только тестам; в «боевую» программу она не попадёт.
  • Selenide сам подтянет Selenium — отдельно его добавлять не нужно. Такие «зависимости зависимостей» называются транзитивными.
  • useJUnitPlatform() — «тесты на JUnit 5». Без этой строки Gradle не найдёт ни одного теста (урок 17.4). С ней Gradle отдаёт JUnit все классы тестов, и тот находит тестовые методы по аннотации @Test — имя класса неважно. Но классы всё равно называют …Test: так их сразу видно в дереве, а в Maven-проектах класс без такого окончания вообще не запустится.
  • Блок с listOf(…) — проброс настроек, о нём ниже, в разделе про настройки. Похоже на List.of(…).forEach(key -> …) из модуля 14 — вызов forEach с лямбда-выражением: для каждого ключа — «если при запуске передали -Dключ=…, отдай его тестам». ?.let в Kotlin значит «если не null, то сделай».

Версии — актуальные на момент написания курса. Свежие смотри на mvnrepository.com (вкладка Gradle (Kotlin)); IDEA подсвечивает устаревшие сама.

BaseTest: общее для всех тестов

Настроить Selenide и закрыть браузер нужно в каждом тестовом классе. Общее выносим в родителя — наследование из модуля 10, теперь для тестов:

package tests;

import com.codeborne.selenide.Configuration;
import com.codeborne.selenide.Selenide;
import config.TestConfig;
import org.junit.jupiter.api.AfterEach;
import org.junit.jupiter.api.BeforeAll;

public abstract class BaseTest {

    @BeforeAll
    static void configureSelenide() {
        Configuration.baseUrl = TestConfig.baseUrl();
        Configuration.browser = TestConfig.browser();
        Configuration.timeout = TestConfig.timeoutMs();
    }

    @AfterEach
    void closeBrowser() {
        Selenide.closeWebDriver();
    }
}
package tests;

import data.TestUsers;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import pages.LoginPage;

class LoginTest extends BaseTest {
    private LoginPage loginPage;

    @BeforeEach
    void openLoginPage() {
        loginPage = new LoginPage().open();
    }

    @Test
    void userCanLogIn() {
        loginPage.loginAs(TestUsers.ANNA.user())
                .shouldGreet("anna");
    }

    @Test
    void blockedUserSeesError() {
        loginPage.loginExpectingError(TestUsers.BLOCKED.user())
                .shouldShowError("Пользователь заблокирован");
    }
}
Порядок вызовов

@BeforeAll — один раз на класс, до всех тестов (поэтому он static). Перед каждым тестом JUnit создаёт новый объект тестового класса, вызывает методы @BeforeEach — сначала родителя, потом наследника, — затем сам тестовый метод, затем методы @AfterEach — сначала наследника, потом родителя. Новый объект на каждый тест — ещё одна гарантия независимости: поля не переживают тест.

В LoginTest три теста. Сколько раз вызовется configureSelenide, openLoginPage и closeBrowser?

1, 3 и 3. @BeforeAll — однажды на класс, @BeforeEach и @AfterEach — вокруг каждого теста.

Тестовые данные: record и enum

Логины и пароли, раскиданные строками по тестам, — тот же копипаст, что и локаторы. Данные описываем типами из модуля 11:

package data;

public record User(String login, String password) {
}
package data;

public enum TestUsers {
    ANNA("anna", "qwerty123"),
    BORIS("boris", "bookworm"),
    BLOCKED("blocked", "secret");

    private final String login;
    private final String password;

    TestUsers(String login, String password) {
        this.login = login;
        this.password = password;
    }

    public User user() {
        return new User(login, password);
    }
}

А в LoginPage — перегрузка (модуль 7): loginAs(User user) вызывает loginAs(user.login(), user.password()) — передаёт аргументами значения, которые возвращают методы записи, и так же для loginExpectingError(User user). Теперь тест говорит «войти как Анна», а не «ввести anna и qwerty123».

Настоящие пароли — не в коде

Тестовый проект лежит в Git, его видит вся компания. Пароли от общих стендов в код не пишут: их передают через переменные окружения или «секреты» CI и читают вызовом статического метода System.getenv("NOOK_PASSWORD"). В enum — только выдуманные пользователи учебного или локального стенда.

🔎 Для любопытных: данные из таблицы

Параметризованные тесты из модуля 17 отлично дружат с enum: аннотация @EnumSource(TestUsers.class) прогонит тестовый метод для каждого пользователя, а @CsvSource или @CsvFileSource(resources = "/users.csv") возьмёт строки таблицы. Одна логика — много данных: так покрывают формы с десятками вариантов ввода. Попробуешь в задаче «Таблица данных».

Настройки: properties-файл

Адрес стенда, браузер, таймаут меняются чаще, чем код: сегодня тестовый стенд, завтра предрелизный, на CI — другой браузер. Такие вещи держат в файле настроек (чтение файлов — модуль 15):

base.url=https://nook-shop.test
browser=chrome
timeout.ms=4000
package config;

import java.io.IOException;
import java.io.InputStream;
import java.io.UncheckedIOException;
import java.util.Properties;

public final class TestConfig {
    private static final Properties PROPS = load();

    private TestConfig() {
    }

    private static Properties load() {
        Properties props = new Properties();
        try (InputStream in = TestConfig.class.getResourceAsStream(
                "/config.properties")) {
            props.load(in);
        } catch (IOException e) {
            throw new UncheckedIOException(
                    "Не удалось прочитать config.properties", e);
        }
        return props;
    }

    private static String get(String key) {
        return System.getProperty(key, PROPS.getProperty(key));
    }

    public static String baseUrl() { return get("base.url"); }
    public static String browser() { return get("browser"); }
    public static long timeoutMs() { return Long.parseLong(get("timeout.ms")); }
}
getResourceAsStream("/config.properties")

Файлы из src/test/resources Gradle кладёт в classpath тестов вместе со скомпилированными классами, поэтому их читают как «ресурс», а не по пути на диске. Тест одинаково работает на твоём ноутбуке и на CI.

try (…)

try-с-ресурсами (try-with-resources) из модуля 15: поток, объявленный в скобках, закроется сам.

System.getProperty(key, …)

Метод возвращает «системное свойство», а если его нет — свой второй аргумент: значение из файла. Так значение можно подменить при запуске, не трогая код: gradle test -Dbrowser=firefox, на CI — ./gradlew test -Dbase.url=https://stage.nook-shop.test.

Почему -D сам не доходит до тестов

Gradle запускает тесты в отдельной JVM — отдельной «копии» Java. А -Dbrowser=firefox из команды попадает в JVM самого Gradle. Тесты его не увидят, и System.getProperty("browser") вернёт null. Поэтому в build.gradle.kts мы написали проброс: для ключей browser, base.url, timeout.ms — «передали при запуске? отдай тестам через systemProperty». Не передали — ничего не делаем, и TestConfig возьмёт значение из файла.

Где это задать в IDEA. В Gradle-проекте IDEA по умолчанию запускает тесты через Gradle: щелчок по ▶ у теста создаёт конфигурацию запуска Gradle. Открыть её: список конфигураций вверху (рядом с ▶) → Edit Configurations…

🔎 Для любопытных: если тесты запускает сама IDEA

В Settings → Build, Execution, Deployment → Build Tools → Gradle есть пункт Run tests using. Если там выбрано IntelliJ IDEA, ▶ создаёт обычную конфигурацию JUnit, и -Dbrowser=firefox пишут в её поле VM options — тогда свойство попадает в тест напрямую, без Gradle. На CI тесты всегда идут через ./gradlew test, поэтому проброс в build-файле нужен в любом случае.

Ожидания вместо sleep — везде

В модуле 16 ты видел вызов статического метода Thread.sleep: он усыпляет текущий поток на фиксированное время. В автотестах это главный источник медленных и мигающих тестов. Правило одно: ждём условие, а не время.

Чего ждёмКак правильно
Элемент появился, исчез, получил текстshouldBe(visible), shouldNotBe(visible), shouldHave(text(…)) — проверки состояния, Selenide ждёт сам
Долгая операция (загрузка отчёта)та же проверка, вторым аргументом — увеличенный таймаут: shouldBe(visible, Duration.ofSeconds(30))
Не про браузер: письмо пришло, запись в базе появиласьопрос «пока не выполнится или не выйдет время» — как в задаче «Умное ожидание»; есть готовая библиотека Awaitility: await().atMost(10, SECONDS).until(() -> mailbox.hasLetter()) — в until передаём лямбда-выражение без параметров, оно возвращает true, когда условие выполнено
В проекте 300 тестов, в каждом в среднем два Thread.sleep(3000). Сколько времени они тратят впустую за прогон, если элементы обычно появляются за 0,5 с?

Каждый sleep переплачивает ~2,5 с: 300 × 2 × 2,5 = 1500 с — 25 минут каждого прогона уходит на сон. И всё равно, если стенд однажды «задумается» на 4 с, тесты покраснеют. Умные ожидания экономят время и делают тесты стабильнее одновременно.

Запуск и отчёт

  1. Один тест или класс — зелёный треугольник ▶ у метода или класса в IDEA. Так работаешь, пока пишешь тест.
  2. Все тесты пакета — правый клик по пакету tests → Run 'Tests in tests'.
  3. Как на CI — окно Gradle справа в IDEA → Tasks → verification → двойной клик по test. Это та же команда ./gradlew test, которую запускает CI-сервер. HTML-отчёт Gradle кладёт в build/reports/tests/test/index.html, а результаты для CI — в build/test-results/test.

Отчёт. На работе результаты прогона смотрят не в консоли, а в красивом отчёте. Самый популярный — Allure Report: подключается одной зависимостью (для Selenide есть готовый «слушатель» AllureSelenide) и показывает каждый тест по шагам, со скриншотами при падении, историей прогонов и графиками «сколько упало и почему». Глубоко разбираться в Allure пока рано — достаточно знать, что он есть, и уметь читать его отчёт: на собеседованиях о нём часто спрашивают.
