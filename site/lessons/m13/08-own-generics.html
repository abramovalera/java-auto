Свои generics: коробка для чего угодно

Ты уже пользуешься List<T> и Map<K, V>. Теперь заглянем с другой стороны: как написать свой класс и метод с угловыми скобками. Коротко — но так, чтобы чужой код с <T> больше не пугал.

Повторение

Коробка без generics: Object и приведения

Хотим класс-коробку, в которую можно положить одну вещь, а потом достать. Вещь может быть строкой, числом, товаром — чем угодно. Первая мысль — поле типа Object (модуль 10: от него наследуются все классы):

class ObjectBox {
    private Object item;
    void put(Object item) { this.item = item; }
    Object get() { return item; }
}

ObjectBox box = new ObjectBox();
box.put("подарок");
String s = (String) box.get();     // приводить руками
Integer n = (Integer) box.get();   // 💥 ClassCastException — при запуске

Те же проблемы, что у «сырого» списка в уроке 2: компилятор не знает, что внутри, и ошибка всплывает только при запуске. Generics решают это и для твоих классов.

Box<T>: параметр типа

class Box<T> {
    private T item;

    void put(T item) { this.item = item; }
    T get() { return item; }
    boolean isEmpty() { return item == null; }
}

Box<String> gift = new Box<>();
gift.put("книга");
String g = gift.get();        // без приведения
gift.put(42);                 // ❌ ошибка компиляции: int — не String

Box<Integer> coins = new Box<>();
coins.put(42);                // автоупаковка в Integer
int c = coins.get();
class Box<T>

T — параметр типа: «сюда подставят конкретный тип, когда будут создавать коробку». Как параметр метода, только вместо значения — тип.

private T item;

Внутри класса T используется как обычный тип: поле, параметр, результат.

Box<String> gift

Подставили String вместо T. Для этой коробки компилятор «видит» put(String) и String get().

Имена параметров типа по традиции — одна большая буква: T (Type), E (Element — в коллекциях), K и V (Key, Value — в Map). Параметров может быть несколько:

record Pair<K, V>(K key, V value) { }

Pair<String, Integer> p = new Pair<>("хлеб", 45);
System.out.println(p.key() + " = " + p.value());   // хлеб = 45
Где ты это встретишь

Ответ сервера часто описывают как Response<User>, хранилище заказов — как Repository<Order>, кэш товаров — как Cache<String, Product>. А в тестах (модуль 17) assertThat(list) из AssertJ возвращает объект «проверки списка строк» — внутри него generics, поэтому IDEA подсказывает подходящие проверки. Писать такое с нуля джуну приходится редко, а читать — каждый день.

Обобщённый метод: <T> перед типом результата

Параметр типа можно объявить не у класса, а у одного метода. Угловые скобки ставят перед типом результата:

static <T> T lastOf(List<T> list) {
    return list.get(list.size() - 1);
}

String w = lastOf(List.of("а", "б", "в"));  // T = String — Java вывела сама
Integer n = lastOf(List.of(10, 20, 30));    // T = Integer

Указывать T при вызове не нужно: Java выводит тип из аргумента. Один метод работает со списком чего угодно, и при этом результат типизирован: lastOf от списка строк возвращает именно String, а не Object.

Скомпилируется ли: int x = lastOf(List.of("а", "б"));

Нет. T выведен как String, значит метод возвращает String, а его в int не положишь: incompatible types. Generics и тут поймали ошибку до запуска.

Чего нельзя с T
  • Подставить примитив: Box<int> — нельзя, только Box<Integer> (урок 2).
  • Создать объект: new T() — нельзя, Java не знает, какой конструктор вызывать.
  • Вызвать у T методы конкретного класса: про «какой-то тип» известно только то, что он Object — доступны equals, hashCode, toString.

Для любопытных: ограничения и wildcards

Это уже материал «на вырост». Читать стоит, зубрить — нет.

🔎 <T extends Comparable<T>>: «какой-то тип, но сравнимый»

Хотим метод «максимум из списка» для чего угодно. Но сравнивать через compareTo можно не всё. Ограничим T:

static <T extends Comparable<T>> T maxOf(List<T> list) {
    T best = list.get(0);
    for (T x : list) {
        if (x.compareTo(best) > 0) best = x;
    }
    return best;
}

Теперь внутри можно звать compareTo, а вызов maxOf со списком несравнимых объектов не скомпилируется. Так устроен сам Collections.sort.

🔎 Почему List<Integer> — не List<Number>, и что такое ? extends

Integer — наследник Number. Но List<Integer> не наследник List<Number>! Иначе можно было бы сделать так:

List<Integer> ints = new ArrayList<>();
List<Number> nums = ints;   // ❌ не компилируется — и правильно:
nums.add(3.14);             // иначе в список Integer пролез бы Double

Если методу нужно только читать числа из списка любых чисел, пишут wildcard (подстановочный знак) ? extends Number — «список чего-то, что является Number»:

static double sum(List<? extends Number> list) {
    double total = 0;
    for (Number n : list) total += n.doubleValue();
    return total;
}
sum(List.of(1, 2, 3));        // List<Integer> — подходит
sum(List.of(1.5, 2.5));       // List<Double> — тоже

Добавлять в такой список нельзя (кроме null): компилятор не знает, Integer там или Double. Правило-запоминалка с собеседований — PECS: Producer Extends, Consumer Super. Читаешь из коллекции — extends, пишешь в неё — super.

🔎 Стирание типов

Generics существуют только для компилятора. После проверки он «стирает» угловые скобки, и в байт-коде Box<String> и Box<Integer> — один и тот же класс Box с полем Object (приведения компилятор вставляет сам). Поэтому при запуске нельзя спросить «это Box от String?» и нельзя написать new T(). Это называется type erasure — тоже частый вопрос на собеседовании.

Напиши: «Покажи мне 3 строки из настоящей библиотеки с generics (например, из ArrayList или AssertJ), а я объясню, что там значит каждая буква в угловых скобках».

Коротко

  • class Box<T> — класс с параметром типа: при создании подставляют конкретный тип, компилятор проверяет.
  • Без generics — Object, приведения и ClassCastException при запуске.
  • Обобщённый метод: static <T> T lastOf(List<T> list) — тип выводится из аргументов.
  • Нельзя: примитивы в скобках, new T().
  • На вырост: <T extends Comparable<T>>, ? extends Number, стирание типов.
