Сортировка: Comparable и Comparator

Числа и строки Java сортирует сама. А как отсортировать товары по цене, студентов — по баллу, а при равенстве — по имени? Научим объекты сравниваться.

Повторение

Collections.sort: числа и строки

В модуле 6 был Arrays.sort для массивов. Для списков есть класс-помощник Collections (с s на конце — не путай с интерфейсом Collection):

List<Integer> prices = new ArrayList<>(List.of(300, 45, 89, 120));
Collections.sort(prices);                               // [45, 89, 120, 300]
Collections.sort(prices, Collections.reverseOrder());   // [300, 120, 89, 45]

List<String> names = new ArrayList<>(List.of("Вера", "Аня", "Борис"));
Collections.sort(names);                                // [Аня, Борис, Вера]
// просто развернуть, без сортировки:
Collections.reverse(names);                             // [Вера, Борис, Аня]

Сортировка меняет сам список. Поэтому List.of(…) напрямую отсортировать нельзя — он неизменяемый (UnsupportedOperationException), сначала копия в ArrayList.

Как проверить, что список уже отсортирован

Сделай копию (new ArrayList<>(prices)), отсортируй копию и сравни с оригиналом: prices.equals(sortedCopy). Списки сравниваются через equals поэлементно и по порядку — совпали, значит оригинал уже был по порядку.

Почему Collections.sort знает, как сравнивать числа и строки, но не знает, как сравнить два товара?

Потому что Integer и String реализуют интерфейс Comparable — «я умею сравниваться с себе подобным». Это их естественный порядок: числа по возрастанию, строки по кодам символов. Для своего класса порядок придумываешь ты.

Comparable: естественный порядок своего класса

Сначала посмотрим на проблему. Вот товар-record без всякого порядка и попытка отсортировать корзину:

Попробуй отсортировать список своих объектов — компилятор откажется: no suitable method found for sort(List<Product>). Объяснить ему порядок можно, реализовав интерфейс Comparable<T> с одним методом compareTo:

record Product(String name, int price) implements Comparable<Product> {
    @Override
    public int compareTo(Product other) {
        // по цене, по возрастанию
        return Integer.compare(this.price, other.price);
    }
}

List<Product> cart = new ArrayList<>(List.of(
        new Product("сыр", 300),
        new Product("хлеб", 45),
        new Product("молоко", 89)));
Collections.sort(cart);
System.out.println(cart.get(0).name());   // хлеб — самый дешёвый

Правило compareTo — как у строк в модуле 8. a.compareTo(b) возвращает:

Integer.compare и compareTo — готовые судьи

Для чисел — Integer.compare(x, y) (и Double.compare), для строк — s1.compareTo(s2). Не изобретай сравнение через if: готовые методы короче и без ошибок.

🔎 Для любопытных: почему не пишут return this.price - other.price

Вычитание выглядит изящно и в учебниках встречается. Но при больших числах разных знаков оно переполняет int (модуль 3): 2_000_000_000 - (-2_000_000_000) даёт отрицательное число, и сортировка молча становится неправильной. Integer.compare такой проблемы не имеет.

Comparator: сколько угодно порядков

Естественный порядок у класса один. А товары хочется сортировать то по цене, то по названию, то по убыванию цены. Тут нужен Comparator — отдельный объект-судья, который сравнивает двух других: метод compare(a, b) с тем же правилом знаков.

Аналогия: Comparable — рост, Comparator — жюри конкурса

У спортсменов есть «естественный» порядок для построения на физкультуре — по росту (Comparable). А на конкурсе жюри может расставить их по скорости, по прыжкам, по артистизму — каждое жюри со своими правилами (Comparator). Жюри не меняет самих спортсменов, оно просто сравнивает.

Способ 1 — отдельный класс:

class ByNameComparator implements Comparator<Product> {
    @Override
    public int compare(Product a, Product b) {
        return a.name().compareTo(b.name());
    }
}

cart.sort(new ByNameComparator());  // [молоко, сыр, хлеб] — по алфавиту
// то же самое, старая запись:
Collections.sort(cart, new ByNameComparator());

Способ 2 — анонимный класс (модуль 11): класс без имени, объявленный прямо там, где нужен. Удобно для «одноразового» судьи:

cart.sort(new Comparator<Product>() {
    @Override
    public int compare(Product a, Product b) {
        // b и a поменяли местами — по убыванию
        return Integer.compare(b.price(), a.price());
    }
});
Почему Integer.compare(b.price(), a.price()) сортирует по убыванию?

Поменяв аргументы местами, мы переворачиваем знак ответа. Там, где «по возрастанию» судья сказал бы «a раньше» (отрицательное), теперь он говорит «a позже» (положительное). Альтернатива — обернуть готового судью: Collections.reverseOrder(new ByNameComparator()).

Comparator принимают и другие коллекции: new TreeSet<>(new ByNameComparator()), new TreeMap<>(…), new PriorityQueue<>(…) — тогда они упорядочивают элементы по твоему правилу. Так в TreeSet можно положить и класс без Comparable.

Сортировка по нескольким полям

Частая задача: «по цене, а при одинаковой цене — по названию». Идея — сравнивать по очереди, как словарь сравнивает слова по буквам: первое поле решает, если отличается; если равно — слово за вторым полем.

class ByPriceThenName implements Comparator<Product> {
    @Override
    public int compare(Product a, Product b) {
        int byPrice = Integer.compare(a.price(), b.price());
        if (byPrice != 0) {
            return byPrice;  // цены разные — они и решают
        }
        return a.name().compareTo(b.name());  // цены равны — решает название
    }
}

Частая ошибка

Написать два отдельных сравнения подряд без if: Integer.compare(…); return a.name().compareTo(…); — результат первого просто выброшен, сортировка окажется по одному названию. Второе поле должно решать только при равенстве первого.

🔎 Для любопытных: стабильность и Comparator.comparing

Стабильность. Collections.sort и list.sort — стабильные: равные элементы сохраняют исходный взаимный порядок. Поэтому можно сначала отсортировать по названию, потом по цене — и получить «по цене, при равенстве по названию». Но явный двухпольный Comparator понятнее.

Будущее. В модуле 14 этот класс уместится в одну строку: Comparator.comparing(Product::price).thenComparing(Product::name). Чтобы понимать, что делает эта строка внутри, сначала нужно уметь написать её «руками» — как сейчас.

Рецепт: словарь по значению и топ-N

Посчитали частоту слов (урок 5) — и сразу вопрос: «какие три слова встречаются чаще всего?» TreeMap тут не поможет: он сортирует только по ключам. Сам словарь по значениям не отсортировать — зато можно отсортировать список его пар:

  1. Сложить пары словаря в список: new ArrayList<>(counts.entrySet()).
  2. Отсортировать список компаратором по getValue() — по убыванию, а при равенстве по ключу (два поля, как в шаге выше).
  3. Взять первые N элементов — осторожно, если пар меньше N.
Map<String, Integer> counts = new TreeMap<>();
for (String w : List.of("да", "нет", "да", "может", "нет", "да", "ок")) {
    counts.put(w, counts.getOrDefault(w, 0) + 1);
}

List<Map.Entry<String, Integer>> entries = new ArrayList<>(counts.entrySet());
entries.sort(new Comparator<Map.Entry<String, Integer>>() {
    @Override
    public int compare(Map.Entry<String, Integer> a, Map.Entry<String, Integer> b) {
        int byCount = Integer.compare(b.getValue(), a.getValue()); // b и a — по убыванию
        if (byCount != 0) {
            return byCount;
        }
        return a.getKey().compareTo(b.getKey());                 // поровну — по алфавиту
    }
});

int n = 3;
for (int i = 0; i < Math.min(n, entries.size()); i++) {
    Map.Entry<String, Integer> e = entries.get(i);
    System.out.println(e.getKey() + ": " + e.getValue());
}
да: 3
нет: 2
может: 1

Читаем объявление списка: объявляем переменную entries типа «список пар Map.Entry<String, Integer>» и инициализируем её новым ArrayList — копией всех пар словаря. Угловые скобки внутри угловых пугают только с непривычки: это просто «список, в котором лежат пары».

«может» и «ок» встретились по одному разу. Почему в топ-3 попало «может», а не «ок»? И что будет при n = 10?

Количество у них равно, поэтому решает второе поле — ключ: «может» по алфавиту раньше «ок». Без этого второго правила порядок равных зависел бы от исходного порядка пар. При n = 10 программа напечатает все 4 слова и не упадёт: Math.min(n, entries.size()) не даёт выйти за конец списка — без него entries.get(4) бросил бы IndexOutOfBoundsException.

Нужен сам словарь в порядке значений?

Переложи отсортированные пары в LinkedHashMap — он запомнит порядок добавления: for (Map.Entry<String, Integer> e : entries) sorted.put(e.getKey(), e.getValue());. В модуле 14 весь этот рецепт уместится в короткую цепочку стримов — но устроена она внутри так же.

Коротко

  • Collections.sort(list) — естественный порядок; Collections.reverseOrder() — наоборот; сортировка меняет сам список.
  • Comparable<T> + compareTo — «класс сам умеет сравниваться», порядок один.
  • Comparator<T> + compare(a, b) — отдельный судья: классом или анонимным классом. Передаётся в sort, TreeSet, TreeMap, PriorityQueue.
  • Знак ответа: минус — a раньше, ноль — равны, плюс — a позже. Для чисел — Integer.compare.
  • Несколько полей: сравни по первому; если не 0 — верни, иначе сравнивай по второму.
  • Словарь по значению / топ-N: пары в список new ArrayList<>(map.entrySet()) → сортировка по getValue() → первые min(n, size).
