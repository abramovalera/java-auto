Угловые скобки и обёртки

Что значит <String> в List<String>, почему нельзя написать List<int> и почему 127 == 127, а 128 != 128. Последнее спрашивают почти на каждом собеседовании.

Повторение

Зачем угловые скобки

Скобки <…> называются generics (дженерики, «обобщения»). Они говорят компилятору, какого типа элементы лежат в коллекции. Посмотрим, как жилось без них. До Java 5 списки были «просто списками» — туда можно было положить что угодно:

List names = new ArrayList();          // без <…> — «сырой» список
names.add("Аня");
names.add(42);                         // компилятор не возражает
String first = (String) names.get(0);  // каждый раз приводить тип руками
String second = (String) names.get(1); // 💥 ClassCastException при запуске

Ошибка всплывает только при запуске, и далеко от места, где её сделали. С generics компилятор ловит её сразу:

List<String> names = new ArrayList<>();
names.add("Аня");
// ❌ ошибка компиляции: int cannot be converted to String
names.add(42);
// приводить тип не нужно — компилятор знает, что там String
String first = names.get(0);

Компилятор теперь знает тип элементов и при чтении. Попробуй достать из списка строк число — IDEA подчеркнёт это ещё до запуска:

Аналогия: подписанные коробки при переезде

На коробке маркером написано «КНИГИ». Грузчик на входе смотрит на надпись и не даст положить туда кастрюлю. А когда ты открываешь коробку, точно знаешь, что достанешь книгу. Generics — надпись на коробке, компилятор — грузчик. Сырой список — коробка без надписи: сюрприз ждёт при распаковке.

Запомни принцип: ошибка компиляции лучше ошибки при запуске. Компилятор показывает место ошибки ещё до того, как программа сделала что-то не то. Generics переносят целый класс ошибок из «упало у пользователя» в «подчёркнуто красным в IDEA».

List<int> — нельзя. Знакомься: обёртки

Попробуй написать список чисел:

// ❌ unexpected type: required reference, found int
List<int> scores = new ArrayList<>();
List<Integer> scores = new ArrayList<>();  // ✅

Коллекции хранят только объекты — точнее, ссылки на объекты. А int — примитив, не объект. Поэтому для каждого примитива в Java есть класс-обёртка: объект, внутри которого лежит одно число.

ПримитивОбёрткаПример
intIntegerList<Integer>
doubleDoubleList<Double>
booleanBooleanList<Boolean>
charCharacterSet<Character>
longLongList<Long>

Два «неправильных» названия запомни особо: Integer (не Int) и Character (не Char). Остальные — просто с большой буквы.

Автоупаковка: Java заворачивает сама

Писать Integer.valueOf(90) на каждом шагу было бы утомительно. Java делает это сама:

List<Integer> scores = new ArrayList<>();
// упаковка: int 90 → объект Integer (Java пишет за тебя Integer.valueOf(90))
scores.add(90);
// распаковка: Integer → int (Java пишет .intValue())
int first = scores.get(0);
// арифметика с Integer тоже работает — через распаковку
int sum = scores.get(0) + 10;
Автоупаковка (autoboxing)
Примитив сам превращается в объект-обёртку, когда нужен объект: положить в коллекцию, присвоить в Integer.
Распаковка (unboxing)
Обёртка сама превращается в примитив, когда нужен примитив: присвоить в int, сложить, сравнить через <.
Распаковка null — NullPointerException

В отличие от int, переменная Integer может быть null — «объекта нет». Распаковать пустоту нельзя:

Integer age = null;
// 💥 NullPointerException: Java вызывает age.intValue(), а объекта нет
int a = age;

Эта ловушка вернётся в уроке про Map: map.get возвращает null, если ключа нет.

Обёртки — тоже объекты. Что тогда сравнивает == между двумя Integer?

Ссылки, как у строк! А числа внутри сравнивает equals. Но иногда == «случайно» работает правильно — и это самое коварное. Смотри следующий шаг.

Ловушка: 127 == 127, но 128 != 128

Маленькие числа встречаются в программах постоянно: 0, 1, 10, 100. Чтобы не плодить тысячи одинаковых объектов, Java заранее создаёт объекты Integer для чисел от −128 до 127 и хранит их в кэше (запаснике). Упаковка Integer.valueOf(5) не создаёт новый объект, а выдаёт готовый из кэша. Для чисел за пределами кэша каждый раз создаётся новый объект.

IDEA эту ловушку знает и подсвечивает жёлтым — это предупреждение: код скомпилируется, но выглядит как ошибка. А в консоли видно, что подозрение не напрасное:

Правило

Обёртки (Integer, Double, Long…) сравнивай через equals, как строки. == «работает» на маленьких числах только благодаря кэшу — и ломается на 128. Тест на маленьких данных пройдёт, а на реальных — упадёт. Самый неприятный вид бага.

А что напечатает: Integer x = 1000; int y = 1000; System.out.println(x == y);

true. Если с одной стороны == примитив int, Java распаковывает x и сравнивает два числа. Ловушка только когда обе стороны — объекты-обёртки.

Ловушка: remove(1) в списке чисел

У списка два метода remove: remove(int index) — по номеру и remove(Object o) — по значению. Для строк путаницы нет. А для List<Integer>?

List<Integer> nums = new ArrayList<>(List.of(10, 20, 1));
nums.remove(1);  // что удалится: число 1 или элемент номер 1?
System.out.println(nums);
Предскажи вывод

[10, 1]. Аргумент 1 — это int, и Java выбирает перегрузку remove(int index) без всякой упаковки: точное совпадение типа выигрывает (перегрузку методов ты знаешь из модуля 7). Удалился элемент номер 1 — число 20.

Чтобы удалить значение 1, передай объект: nums.remove(Integer.valueOf(1)); → [10, 20].

Поговори с наставником

Коротко

  • <String> — generics: компилятор знает тип элементов, проверяет add и не требует приведения при get.
  • Коллекции хранят только объекты. Для примитивов — обёртки: Integer, Double, Boolean, Character, Long.
  • Автоупаковка и распаковка происходят сами. Распаковка null — NullPointerException.
  • Кэш Integer −128..127: == на маленьких числах «работает», на 128 — нет. Обёртки сравниваем через equals.
  • В List<Integer> remove(1) удаляет по индексу, remove(Integer.valueOf(1)) — по значению.
