Гонка данных (race condition)

Два потока по сто тысяч раз прибавляют единицу к одному счётчику. Должно получиться двести тысяч. Получается… каждый раз по-разному. Разберёмся, куда пропадают единицы и как их спасти.

Повторение

Эксперимент: куда пропали клики?

Кнопка «Нравится» в приложении: два «пользователя» одновременно жмут её по 100 000 раз. Счётчик общий — статическое поле. Для обоих потоков вызываем join — ждём их завершения, так что дело не в нём.

public class LostClicks {
    static int count = 0;

    public static void main(String[] args) throws InterruptedException {
        Runnable clicker = () -> {
            for (int i = 0; i < 100_000; i++) {
                count++;
            }
        };
        Thread a = new Thread(clicker);
        Thread b = new Thread(clicker);
        a.start();
        b.start();
        a.join();
        b.join();
        System.out.println("Кликов: " + count);
    }
}

Набери LostClicks в папке module-16 и запусти раз пять. Числа будут свои, но почти всегда меньше 200 000.

Почему: count++ — это три действия

Для нас count++ (инкремент статического поля count) — одно действие. Для процессора — три: прочитать значение из памяти, увеличить у себя «в руках», записать обратно. Между любыми из этих шагов поток могут прервать и пустить другой.

Когда результат зависит от того, какой поток «прибежит» первым, это называется гонкой данных (race condition). Пройди этот сценарий по шагам и посчитай сам. Код ниже — не настоящая Java, а count++, разобранный на три действия для двух потоков.

А если бы планировщик не переключил потоки посередине — сначала все три шага A, потом все три шага B?

Тогда B прочитал бы уже 6 и записал 7 — всё честно. Поэтому третий запуск в эксперименте и дал 200 000: потокам «повезло» не пересечься. Ошибка в коде есть всегда, а проявляется — как повезёт.

synchronized — замок на двери

Аналогия: примерочная с одним ключом

В примерочную пускают по одному: вошёл — запер дверь, вышел — отпер. Остальные ждут снаружи. Внутри никто не помешает: можно спокойно «прочитать, увеличить, записать».

В Java такая «примерочная» — синхронизированный блок synchronized (…) { … }: участок кода, который в один момент выполняет только один поток. В скобках указывают объект, который служит замком (по-английски lock или monitor). Пока один поток выполняет тело блока, другие потоки с тем же замком ждут у двери.

public class SafeClicks {
    static int count = 0;
    static final Object lock = new Object();

    public static void main(String[] args) throws InterruptedException {
        Runnable clicker = () -> {
            for (int i = 0; i < 100_000; i++) {
                synchronized (lock) {
                    count++;
                }
            }
        };
        Thread a = new Thread(clicker);
        Thread b = new Thread(clicker);
        a.start();
        b.start();
        a.join();
        b.join();
        System.out.println("Кликов: " + count);   // всегда 200000
    }
}
static final Object lock

Объявляем статическое поле lock и инициализируем его новым объектом (new Object()) — это замок. Подойдёт любой объект — важно, чтобы все потоки брали один и тот же.

synchronized (lock) { … }

Вход в синхронизированный блок: поток захватывает замок lock — вошёл и запер. Пока поток выполняет тело блока, другой поток на этой строке ждёт (состояние BLOCKED).

}

Выход из блока: поток отпускает замок — вышел и отпер, даже если внутри вылетело исключение. Следующий ожидающий заходит.

Можно объявить с модификатором synchronized целый метод (синхронизированный метод) — тогда замком будет сам объект (this), а у static-метода — класс:

class ClickCounter {
    private int count = 0;

    public synchronized void click() {   // замок — этот объект
        count++;
    }

    public synchronized int get() {
        return count;
    }
}
Замок должен быть общим

Если каждый поток запирает свою дверь (например, synchronized (new Object())), никто никого не ждёт — защиты нет. Ещё запомни цену: потоки у замка стоят в очереди, значит, внутри synchronized держи только то, что действительно нужно защитить.

AtomicInteger — счётчик, который не теряет

Для простых счётчиков есть готовые классы из пакета java.util.concurrent.atomic. Атомарный значит «неделимый»: прочитать-увеличить-записать происходит как одно действие, разорвать его посередине нельзя.

import java.util.concurrent.atomic.AtomicInteger;

public class AtomicClicks {
    static AtomicInteger count = new AtomicInteger(0);

    public static void main(String[] args) throws InterruptedException {
        Runnable clicker = () -> {
            for (int i = 0; i < 100_000; i++) {
                count.incrementAndGet();     // атомарный count++
            }
        };
        Thread a = new Thread(clicker);
        Thread b = new Thread(clicker);
        a.start();
        b.start();
        a.join();
        b.join();
        System.out.println("Кликов: " + count.get());
    }
}
Метод AtomicIntegerЧто делает
incrementAndGet()увеличивает на 1, возвращаемое значение — новое (как ++count)
getAndIncrement()возвращает старое значение и увеличивает (как count++)
addAndGet(5)прибавляет аргумент 5 и возвращает результат
get() / set(0)прочитать / записать

Есть и AtomicLong, AtomicBoolean. Что выбрать?

⚛️

AtomicInteger

Одна переменная-счётчик или флаг. Просто и быстро.

🔒

synchronized

Несколько действий, которые должны пройти вместе: «проверить баланс и списать», «добавить в список и увеличить счётчик».

Счётчик — AtomicInteger, но код такой: if (count.get() < 10) count.incrementAndGet(); Может ли счётчик стать больше 10?

Да! Каждое действие по отдельности атомарно, а пара «проверить, потом увеличить» — нет. Два потока могут оба увидеть 9, оба пройти проверку и оба прибавить — получится 11. Связку действий защищают синхронизированным блоком synchronized (или специальными методами атомиков вроде updateAndGet).

🧾

Общий файл журнала

Несколько потоков дописывают в один файл без синхронизации — строки перемешиваются или теряются.

Лучшее лекарство часто не synchronized, а независимость: у каждого потока свои данные (свой заказ, свой счётчик, уникальное имя файла), а общий итог собирают в конце. Нет общих данных — нет гонки. Так устроена и Мастерская в следующем уроке.

Коротко

  • Гонка данных: несколько потоков меняют общие данные, и результат зависит от того, кто успел первым.
  • count++ — три действия (прочитать, увеличить, записать), поэтому из нескольких потоков теряет обновления.
  • synchronized (lock) { … } — синхронизированный блок с замком lock: его тело одновременно выполняет только один поток. Замок должен быть общим.
  • Вызов incrementAndGet() у объекта AtomicInteger — неделимое увеличение без явного замка, метод возвращает новое значение. Но связка «проверить и изменить» всё равно требует synchronized.
  • Лучшее лекарство от гонок — независимость: у каждого потока свои данные, а итог собирают в конце.
