Многопоточность в автотестах

Зачем всё это автоматизатору? Тесты гоняют параллельно, браузер грузит страницу в своём темпе, а флаки-тесты съедают нервы всей команде. Собираем модуль в практические правила.

⏱ 20 минут🏎 параллельный запуск⏳ ожидания вместо sleep🎤 вопросы с собеседований

Повторение

Параллельный запуск тестов

UI-тест в основном ждёт: пока откроется браузер, загрузится страница, ответит сервер. Процессор при этом почти свободен. Значит, несколько тестов можно гнать одновременно, каждый в своём потоке и со своим браузером.

Создавать объекты потоков (new Thread) в тестах не придётся: параллельность включают настройкой, а потоки создаёт и запускает сам фреймворк. Например, в JUnit 5 (модуль 17) — файлом src/test/resources/junit-platform.properties:

junit.jupiter.execution.parallel.enabled = true
junit.jupiter.execution.parallel.mode.default = concurrent

Одна строчка — и тесты побежали в несколько потоков. А вот сделать так, чтобы они при этом не ломались, — уже работа автоматизатора.

Что ломается при параллельном запуске

По одному все тесты зелёные, вместе — то один красный, то другой. Почти всегда причина — общие данные. Это та же гонка из урока 2, только «общий счётчик» здесь — пользователь, заказ или поле класса.

// ПЛОХО: одно поле на все тесты, а тесты идут в разных потоках
static String orderId;

// поток 1 записал свой заказ…
void createOrder() { orderId = api.createOrder(); }
// …а прочитал — заказ потока 2
void checkOrder() { assertPaid(api.getOrder(orderId)); }

// ХОРОШО: всё нужное тест создаёт себе сам, в локальных переменных
void orderIsPaid() {
    String login = "user_" + UUID.randomUUID();   // уникальный пользователь
    String orderId = api.createOrder(login);
    assertPaid(api.getOrder(orderId));
}
🧍

Свои данные

Каждый тест создаёт своего пользователя, свой заказ, файл с уникальным именем. UUID.randomUUID() — случайный уникальный кусок для имён.

🚫

Без static-состояния

Изменяемые static-поля в тестах — главный источник гонок. Общими могут быть только неизменяемые настройки: адрес стенда, таймауты.

🔀

Без порядка

Тест B не должен рассчитывать, что тест A уже отработал. При параллельном запуске порядка нет — как с выводом потоков в уроке 1.

🔎 Для любопытных: ThreadLocal — «у каждого потока своя копия»

Как Selenide даёт каждому параллельному тесту свой браузер, если в коде просто open("/login") без всякого драйвера? Через ThreadLocal: это «переменная с отдельной ячейкой для каждого потока». Поток 1 кладёт туда свой браузер, поток 2 — свой, и они не пересекаются. Похожий приём используют для своих фреймворков: ThreadLocal<WebDriver> driver = new ThreadLocal<>();, потом driver.set(...) и driver.get() — каждый поток видит своё. Не забывай вызывать driver.remove() в конце: потоки пула живут долго, а данные прошлого теста могут достаться следующему.

Ожидания: почему Thread.sleep — плохо

Ты нажал «Оплатить», а надпись «Оплачено» появится, когда ответит сервер — через 0,3 секунды или через 3. Сам браузер — отдельная программа со своими потоками, твой тест не знает, когда она закончит. Первое, что приходит в голову:

payButton.click();
Thread.sleep(5000);  // подождём 5 секунд «на всякий случай»
assertEquals("Оплачено", status.getText());
🐢

Слишком долго

Обычно ответ за 0,5 секунды, а тест всегда спит 5. Двести таких мест — 16 минут чистого сна в каждом прогоне.

🎲

Слишком коротко

Стенд под нагрузкой ответил за 6 секунд — тест упал, хотя приложение работает. Флаки. Увеличишь до 10 — станет ещё медленнее.

Правильно — явное ожидание (explicit wait): проверять условие часто, например каждые 100 мс, и идти дальше, как только оно выполнилось. А если не выполнилось за таймаут — падать с понятной ошибкой.

Самодельное явное ожидание — это просто цикл, который ты уже умеешь написать:

static void waitUntil(BooleanSupplier condition, long timeoutMs)
        throws InterruptedException {
    long deadline = System.currentTimeMillis() + timeoutMs;
    while (!condition.getAsBoolean()) {
        if (System.currentTimeMillis() > deadline) {
            throw new AssertionError("Не дождались за " + timeoutMs + " мс");
        }
        Thread.sleep(100);                // короткая пауза между проверками
    }
}

// в тесте:
waitUntil(() -> status.getText().equals("Оплачено"), 10_000);
BooleanSupplier condition

Параметр condition имеет тип функционального интерфейса из модуля 14: его метод getAsBoolean() без параметров возвращает boolean. При вызове waitUntil условие передаём аргументом — лямбда-выражением, чтобы его можно было проверять снова и снова.

Thread.sleep(100)

Вызов статического метода sleep с аргументом 100 здесь уместен: это не «гадание на время», а пауза между проверками, чтобы не нагружать процессор.

В настоящих проектах такой цикл уже написан за тебя:

// Selenide: каждая проверка сама ждёт до 4 секунд (Configuration.timeout)
$("#status").shouldHave(text("Оплачено"));

// Selenium без Selenide: ожидание приходится писать явно
new WebDriverWait(driver, Duration.ofSeconds(10))
        .until(ExpectedConditions.textToBe(By.id("status"), "Оплачено"));

Вот почему в модуле 18 мы возьмём Selenide: он ждёт сам, и Thread.sleep в тестах тебе почти никогда не понадобится. Увидишь sleep в чужом тесте — это повод задать вопрос на код-ревью.

Тест с явным ожиданием (таймаут 10 с) упал по таймауту. Это лучше или хуже, чем падение теста со sleep(5000)?

Лучше. Явное ожидание падает, только когда условие не выполнилось за 10 секунд — значит, приложение действительно тормозит или сломано, это настоящий баг. А тест со sleep падает и тогда, когда всё работает, просто на секунду медленнее обычного.

Шпаргалка к собеседованию

Вопросы, которые задают джуну-автоматизатору по многопоточности. Сначала ответь вслух, потом открой.

Чем процесс отличается от потока?

Процесс — запущенная программа со своей памятью. Поток — исполнитель внутри процесса. Потоки одного процесса делят общую кучу (объекты), но у каждого свой стек (локальные переменные).

Как создать поток? Чем start() отличается от run()?

Наследник Thread или создание объекта потока new Thread(...) с задачей Runnable (лямбда-выражением) в аргументе конструктора; в реальном коде — пул ExecutorService. Вызов start() запускает новый поток, run() — обычный вызов метода в текущем потоке. Повторный start() — IllegalThreadStateException.

Что такое race condition и как её избежать?

Результат зависит от того, какой поток успел первым, когда несколько потоков меняют общие данные. Лечение: синхронизированный блок synchronized, атомики (AtomicInteger), потокобезопасные коллекции, а лучше — не делить изменяемые данные вовсе.

Что делает volatile? Делает ли он count++ безопасным?

Гарантирует видимость: каждое чтение — свежее значение из общей памяти. Атомарности не даёт: count++ на volatile всё равно теряет обновления.

Что такое deadlock и как его избежать?

Потоки держат по замку и ждут замки друг друга — круг ожидания, программа висит. Избежать — брать замки всегда в одном порядке (или ждать с таймаутом через tryLock).

Runnable и Callable — разница? Что такое Future?

Задача Runnable: метод run() ничего не возвращает и не бросает проверяемых исключений; задача Callable: метод call() возвращает значение и может бросать. Future — «чек» на будущий результат: вызов get() ждёт и возвращает его.

Почему Thread.sleep в UI-тестах — плохо?

Фиксированная пауза либо слишком длинная (медленные тесты), либо слишком короткая (флаки). Нужны явные ожидания условия с таймаутом; Selenide делает их сам.

🔎 Для любопытных: CompletableFuture одним абзацем

CompletableFuture — «прокачанный Future»: к результату можно прицепить следующие шаги, как в стримах, не блокируя поток на get(). CompletableFuture.supplyAsync(() -> api.getUser(id)) запускает задачу в общем пуле, .thenApply(user -> user.getName()) обработает результат, когда он появится, а .join() в конце дождётся всего (как get(), но без проверяемых исключений). Можно запустить три запроса сразу и дождаться всех: CompletableFuture.allOf(a, b, c).join(). В автотестах встречается редко — например, чтобы параллельно подготовить тестовые данные через API.

Коротко

  • Тесты гоняют параллельно ради скорости; потоки создаёт фреймворк, а не ты.
  • Параллельные тесты ломаются от общих изменяемых данных. Лечение — независимость: свои данные, локальные переменные, никакого порядка.
  • Thread.sleep в тестах — либо медленно, либо флаки. Нужно явное ожидание условия с таймаутом.
  • Selenide ждёт сам (до 4 секунд по умолчанию); в Selenium — WebDriverWait.
  • На собеседовании: процесс и поток, start и run, гонка, synchronized, volatile, deadlock, ExecutorService, Callable и Future.
