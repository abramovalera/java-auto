volatile, deadlock и потокобезопасные коллекции

Повторение

Видимость и volatile

Главный поток хочет остановить помощника флагом — статическим полем running типа boolean. Выглядит безобидно:

public class StopFlag {
    static boolean running = true;          // без volatile!

    public static void main(String[] args) throws InterruptedException {
        Thread worker = new Thread(() -> {
            long laps = 0;
            while (running) {
                laps++;
            }
            System.out.println("Остановился после " + laps + " кругов");
        });
        worker.start();
        Thread.sleep(1000);
        running = false;
        System.out.println("Главный: стоп!");
    }
}

…и программа не завершается. Помощник крутится вечно, хотя флаг давно false. Почему?

Аналогия: доска и блокнот

Меню дня написано мелом на доске в зале. Повар переписал его в свой блокнот, чтобы не бегать, и дальше смотрит только в блокнот. Администратор стёр блюдо с доски — а повар продолжает его готовить. Ради скорости процессор и JVM разрешают потоку держать копию переменной «у себя» (в кеше процессора, в регистре) и не перечитывать её из общей памяти. Без особых указаний изменения одного потока другой может не увидеть никогда.

Модификатор volatile («изменчивый») в объявлении поля запрещает такие копии: каждое чтение — с доски, каждая запись — сразу на доску.

static volatile boolean running = true;   // теперь помощник увидит false
volatile ≠ атомарность

volatile решает только видимость. count++ на volatile int по-прежнему три действия и по-прежнему теряет обновления. Флаг «стоп/работай», который пишет один поток, а читают другие, — работа для volatile. Счётчик — для AtomicInteger или synchronized.

Нужен ли volatile полю, которое читают и пишут только внутри синхронизированных блоков?

Нет. Вход в синхронизированный блок и выход из него тоже «сверяются с доской»: всё, что поток записал до выхода из замка, увидит следующий поток, вошедший в тот же замок. Атомики (AtomicInteger) тоже гарантируют видимость. А «голое» поле без всего — не гарантирует.

Deadlock на пальцах: два повара и две ложки

Для супа нужны ложка и половник. Аня взяла ложку и тянется за половником. Борис в тот же момент взял половник и тянется за ложкой. Каждый держит своё и ждёт, когда другой отдаст. Не отдаст никто — суп не будет готов никогда.

В коде ложка и половник — два объекта-замка, а «взял» — это вход в синхронизированный блок synchronized (spoon):

// поток Ани
synchronized (spoon) {
    synchronized (ladle) {
        cookSoup();
    }
}

// поток Бориса — порядок другой!
synchronized (ladle) {
    synchronized (spoon) {
        cookSoup();
    }
}

Что видно снаружи: программа зависает, процессор не загружен, ничего не печатается, ошибок нет. Тест с таким кодом просто висит, пока его не убьют по таймауту.

Лекарство: один порядок для всех

Договорись, что замки всегда берут в одном порядке: сначала ложку, потом половник. Тогда круга не будет: кто первым взял ложку, тот возьмёт и половник, а второй подождёт у ложки, ничего не держа. Это и есть задача m16-t06.

🔎 Для любопытных: как найти deadlock и четыре условия

Как найти. Пока программа висит, сделай снимок потоков (thread dump): в панели Run в IDEA есть действие Dump Threads (в новом интерфейсе — в меню ⋮). Внизу снимка JVM сама пишет Found one Java-level deadlock и показывает, кто какой замок держит и чего ждёт.

Четыре условия Коффмана — deadlock возможен, только если выполнены все сразу: ресурс может держать только один (взаимное исключение); держат одно и ждут другое; отобрать нельзя; есть круг ожидания. Сломай любое — и deadlock невозможен. Одинаковый порядок замков ломает круг. Ещё вариант — ReentrantLock.tryLock(1, TimeUnit.SECONDS): «не дали за секунду — отпускаю своё и пробую заново».

Потокобезопасные коллекции

ArrayList и HashMap из модуля 13 рассчитаны на один поток. Внутри list.add(x) — несколько действий («положить в ячейку size, увеличить size»), и с потоками случается та же гонка: элементы теряются, в списке появляются null, а иногда вылетает ArrayIndexOutOfBoundsException.

List<Integer> results = new ArrayList<>();
// 4 потока по 10 000 раз делают results.add(i)
System.out.println(results.size());   // 31877? 38205? иногда исключение

Что брать вместо них:

ВместоБериКогда
ArrayListCollections.synchronizedList(new ArrayList<>())несколько потоков добавляют в общий список
ArrayListCopyOnWriteArrayListпишут редко, читают часто (список подписчиков, настроек)
HashMapConcurrentHashMapобщий словарь: кеш, счётчики по ключам
LinkedList как очередьConcurrentLinkedQueueодни потоки кладут задачи, другие забирают

Пример: потоки разбирают заказы интернет-магазина и считают, сколько заказов в каждом статусе. Вызываем у ConcurrentHashMap метод merge и передаём три аргумента: ключ, значение 1 и ссылку на метод Integer::sum — «если ключа нет, положи 1; если есть, прибавь 1» — одним неделимым действием:

Map<String, Integer> stats = new ConcurrentHashMap<>();

// в каждом потоке-воркере, для каждого заказа:
stats.merge(status, 1, Integer::sum);

// после того как все воркеры закончили:
System.out.println(new TreeMap<>(stats));   // {CANCELLED=3, DELIVERED=17, NEW=2}
Безопасная коллекция — не волшебство

Каждый метод ConcurrentHashMap по отдельности безопасен, а связка — нет. stats.put(s, stats.get(s) + 1) — это «прочитать», потом «записать», и между ними вклинится другой поток. Та же гонка, что с count++. Поэтому — merge.

Почему в примере печатаем new TreeMap<>(stats), а не просто stats?

Порядок ключей в ConcurrentHashMap, как и в HashMap, не определён. TreeMap сортирует ключи — вывод одинаковый при каждом запуске. Тот же приём в задачах модуля: сортируй результаты перед выводом.

Безопасно или опасно?

Разложи: что можно спокойно делать из нескольких потоков одновременно, а что приведёт к гонке.

Заметил закономерность? Безопасно то, что не меняется (String), то, что своё у каждого потока (локальные переменные), и специальные потокобезопасные классы. Опасно — когда несколько потоков меняют общее без защиты.

Коротко

  • Без volatile (или synchronized, или атомиков) поток может не увидеть изменения другого потока. volatile — про видимость, не про атомарность.
  • Deadlock — круг ожидания: каждый держит один замок и ждёт другой. Признак — программа висит без ошибок. Лечение — брать замки в одном порядке.
  • ArrayList и HashMap — только для одного потока. Для нескольких: Collections.synchronizedList, CopyOnWriteArrayList, ConcurrentHashMap.
  • Связка «прочитать и записать» небезопасна даже в потокобезопасной коллекции — используй merge и подобные методы.
  • Безопасно: неизменяемое, локальное, специальные классы. Опасно: общее изменяемое без защиты.
