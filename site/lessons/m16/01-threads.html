Что такое поток (thread)

До сих пор твоя программа делала всё строго по очереди: строка за строкой. Сегодня на кухне появится второй повар — и программа начнёт делать два дела одновременно.

Повторение: лямбды и исключения

Сегодня понадобятся две вещи из прошлых модулей: лямбда-выражения (модуль 14) и проверяемые исключения (модуль 12). Освежим.

Несколько поваров на одной кухне

Представь кухню ресторана. Один повар варит суп, потом режет салат, потом жарит котлеты — строго по очереди. Если суп варится 20 минут, салат ждёт. Наймём ещё двух поваров — и три блюда готовятся одновременно. Кухня та же, холодильник общий, плита общая.

Аналогия: кухня

Программа (процесс) — это кухня: своё помещение, свои продукты (память). Поток — это повар: он выполняет свой рецепт шаг за шагом. Поваров на кухне может быть несколько, и все они берут продукты из одного холодильника. Отсюда и вся польза, и все проблемы многопоточности.

Процесс
Запущенная программа. Операционная система выдаёт ей собственную память. Две программы — два процесса, в чужую память они не залезают.
Поток (thread)
«Исполнитель» внутри процесса: идёт по коду строка за строкой. У каждого потока свой стек вызовов (свои локальные переменные), а объекты в куче — общие для всех потоков процесса.
Многопоточность
Когда в одной программе работают несколько потоков одновременно.

Сюрприз: потоком ты пользовался с первого урока. Метод main выполняет поток, который так и называется — main. Спросим его имя:

public class WhoAmI {
    public static void main(String[] args) {
        System.out.println(Thread.currentThread().getName());
    }
}
Зачем это в настоящих программах

Обработать 300 фотографий по очереди — 40 минут. Если раздать их 8 потокам — около 6 минут. Поэтому почти любая серьёзная программа работает параллельно: сервер банка обслуживает тысячи клиентов сразу, игра одновременно рисует кадр и загружает уровень. И почти в каждой команде встречаются «плавающие» ошибки — то есть, то нет, — которые рождаются из-за многопоточности. Этот модуль — про то, как их понимать.

Создаём второй поток

Поток в Java — объект класса Thread. При создании объекта потока (new Thread(…)) конструктору передаётся аргументом задача — объект, реализующий интерфейс Runnable: что поток должен сделать. У этого функционального интерфейса один абстрактный метод void run() (ничего не возвращает), значит, задачу удобно записать лямбда-выражением без параметров:

public class TwoCooks {
    public static void main(String[] args) {
        Runnable soup = () -> {
            for (int i = 1; i <= 3; i++) {
                System.out.println("Помощник: суп, шаг " + i);
            }
        };
        Thread helper = new Thread(soup);
        helper.start();

        for (int i = 1; i <= 3; i++) {
            System.out.println("Главный: салат, шаг " + i);
        }
    }
}
Runnable soup = () -> { … };

Объявляем переменную soup типа Runnable и инициализируем её лямбда-выражением — это рецепт, что делать. Пока это просто объект, тело лямбды не выполняется.

new Thread(soup)

Создание объекта потока: вызываем конструктор Thread и передаём ему аргументом задачу soup — наняли повара и дали ему рецепт. Поток создан, но ещё не работает.

helper.start();

Запуск потока: вызываем метод start() у объекта helper — команда «начинай!». Java запускает новый поток, и уже он вызывает soup.run(). А главный поток, не дожидаясь, идёт дальше — к своему циклу.

Сколько всего строк напечатает программа и в каком порядке?

Строк точно шесть: три от помощника, три от главного. А вот порядок заранее неизвестен! Внутри каждого потока порядок соблюдается (шаг 1 → 2 → 3), но как строки двух потоков перемешаются — решает операционная система. Смотри следующий шаг.

🔎 Для любопытных: второй способ — наследник Thread

Можно унаследоваться от Thread и переопределить run():

class SoupCook extends Thread {
    @Override
    public void run() {
        System.out.println("Варю суп в потоке " + getName());
    }
}
// где-то в main:
new SoupCook().start();

Так тоже работает, но обычно предпочитают Runnable: задача отдельно, исполнитель отдельно, и класс не тратит свою единственную возможность наследования. На собеседовании спрашивают «назови способы создать поток» — ответ: наследник Thread, Runnable (часто лямбдой), а в реальных проектах — пул потоков ExecutorService (урок 3).

Порядок вывода непредсказуем

start() или run()? Вопрос с собеседования

У потока есть метод run() — он выполняет задачу, которую мы описали лямбда-выражением. Почему бы не вызвать его напрямую? Проверим, какой поток выполняет задачу:

Runnable task = () -> System.out.println(
        "Работает: " + Thread.currentThread().getName());

Thread t1 = new Thread(task);
t1.run();      // просто вызов метода

Thread t2 = new Thread(task);
t2.start();    // запуск нового потока
start()run()
Новый потоксоздаётся, задача выполняется в нёмне создаётся
Кто выполняетновый поток (Thread-1)тот, кто вызвал (main)
Главный потоксразу идёт дальшеждёт, пока run() закончится
Вызвать дваждывторой раз — IllegalThreadStateExceptionможно сколько угодно: это обычный метод
Ловушка

run() компилируется и даже работает — только без всякой многопоточности. Ошибку не видно, пока не заметишь, что «параллельные» задачи почему-то идут по очереди. Запускай потоки только через start(), и только один раз: отработавший поток заново не запустить, нужен новый объект Thread.

Почему второй поток в выводе называется Thread-1, а не Thread-0?

Номер получает каждый созданный объект Thread, по порядку. t1 стал Thread-0 — хоть мы его и не запустили, а лишь вызвали run(). Поэтому t2 — Thread-1.

sleep и join: подождать

Вызов статического метода Thread.sleep(500) с аргументом 500 усыпляет текущий поток на 500 миллисекунд. Вызов helper.join() — ожидание завершения потока: текущий поток говорит «я подожду, пока helper закончит работу». Оба метода могут выбросить проверяемое InterruptedException — «тебя разбудили раньше времени», поэтому main объявляет throws.

Забудешь про это — IDEA сразу подчеркнёт вызов красным, а программа не скомпилируется:

А внутри лямбды — только try-catch

Если тот же sleep вызвать в теле лямбды-Runnable, IDEA покажет ту же ошибку, но throws там не допишешь: метод run() у Runnable не разрешает бросать проверяемые исключения. Поэтому в примере ниже sleep обёрнут в try-catch прямо в лямбде.

public class JoinDemo {
    static int soupBowls = 0;

    public static void main(String[] args) throws InterruptedException {
        Thread helper = new Thread(() -> {
            try {
                Thread.sleep(500);          // суп варится полсекунды
            } catch (InterruptedException e) {
                return;
            }
            soupBowls = 4;
        });
        helper.start();
        helper.join();                      // главный ждёт помощника
        System.out.println("Тарелок супа: " + soupBowls);
    }
}

Пройди программу по шагам. Обрати внимание, что делает главный поток, пока работает помощник.

Что напечатает программа, если убрать строку helper.join()?

Почти наверняка Тарелок супа: 0. Главный поток не ждёт и печатает сразу, а помощник ещё спит. Ошибки нет — просто ответ неправильный. Именно так рождаются «плавающие» ошибки: программа прочитала результат раньше, чем данные успели появиться.

Почему soupBowls — поле, а не локальная переменная

Вспомни правило из повторения: лямбда-выражение может использовать только «фактически final» локальные переменные — те, которым после инициализации больше ничего не присваивают. Попробуем объявить счётчик тарелок прямо в main:

int bowls = 0;
Thread helper = new Thread(() -> bowls = 4);   // ошибка компиляции

Компилятор не пропустит: local variables referenced from a lambda expression must be final or effectively final. Причина: лямбда получает копию значения локальной переменной, и запись в эту копию никто бы не увидел. Поэтому Java запрещает присваивание совсем. Законных выходов два:

  • статическое поле класса, как soupBowls выше: оно живёт не в стеке метода, а в общей памяти, и его видят все потоки;
  • ячейка массива: объявляем int[] bowls = new int[1];, а в теле лямбды присваиваем bowls[0] = 4;

Почему с массивом можно? Переменная bowls хранит ссылку на массив (модуль 6), и сама ссылка не меняется — значит, переменная «фактически final». А массив — объект в куче, общий для всех потоков, и менять его ячейки разрешено. Аналогия: бумажку с адресом коробки переписывать нельзя, а класть вещи в коробку — можно. Этим приёмом пользуется задача m16-t01: у каждого помощника своя ячейка массива.

Скомпилируется ли? String[] dish = {"суп"}; new Thread(() -> dish[0] = "борщ").start(); dish = new String[1];

Нет. Последняя строка присваивает переменной dish новый массив — значит, dish больше не «фактически final», и лямбда не может её использовать. Менять ячейки массива можно, а переприсваивать саму переменную — нет.

Когда программа завершается: обычные и фоновые (daemon) потоки

Программа на Java работает, пока жив хоть один обычный поток — не только main. Если main дошёл до конца, а помощник ещё варит суп, программа дождётся помощника и только потом завершится. (join() нужен для другого: чтобы main дождался результата помощника, прежде чем читать его.)

Бывают и фоновые потоки — daemon-потоки (daemon — «служба в фоне»). Они программу не держат: как только закончились все обычные потоки, JVM завершается и обрывает фоновые на полуслове. Поток делают фоновым вызовом setDaemon(true) — обязательно до start(), иначе IllegalThreadStateException.

public class BackgroundMusic {
    public static void main(String[] args) throws InterruptedException {
        Thread music = new Thread(() -> {
            while (true) {
                System.out.println("играет музыка");
                try {
                    Thread.sleep(300);
                } catch (InterruptedException e) {
                    return;
                }
            }
        });
        music.setDaemon(true);      // фоновый: программу не держит
        music.start();
        Thread.sleep(1000);         // main работает секунду
        System.out.println("main закончил");
    }
}

Программа напечатает «играет музыка» примерно четыре раза, потом «main закончил» — и завершится, хотя в потоке music бесконечный цикл: последний обычный поток закончился, фоновый оборвали.

Что будет, если убрать строку music.setDaemon(true)?

Программа не завершится никогда: music станет обычным потоком с бесконечным циклом, и JVM будет его ждать. «main закончил» напечатается, а музыка продолжит играть, пока не нажмёшь красный ■ Stop.

Фоновыми делают служебные потоки, которые не жалко оборвать: автосохранение, проверку обновлений. Сама JVM держит в фоне свои служебные потоки — например, сборщик мусора. А важную работу (запись файла, перевод денег) в daemon-поток не отдают: её оборвут на середине.

🔎 Для любопытных: состояния потока и interrupt()

У потока есть состояния (t.getState()): NEW — создан, не запущен; RUNNABLE — работает или готов работать; BLOCKED — ждёт замок (урок 2); WAITING / TIMED_WAITING — ждёт в join() или sleep(); TERMINATED — закончил.

Остановить поток силой в Java нельзя (старый метод stop() давно запрещён). Можно только вежливо попросить: t.interrupt(). Если поток спит в sleep или ждёт в join, он получит InterruptedException и сам решит, как закончить работу. Если просто считает — пусть сам проверяет Thread.currentThread().isInterrupted().

Проверь себя

Поговори с наставником

Напиши: «Я прошёл урок 16.1. Спроси меня, чем start() отличается от run(), как на собеседовании, и поправь, если я отвечу неточно».

Коротко

  • Процесс — кухня, поток — повар. Потоки одной программы делят общие объекты в куче, а локальные переменные у каждого свои.
  • main — тоже поток. Создание объекта потока: new Thread(runnable) — задача (Runnable) передаётся аргументом конструктора, удобно — лямбда-выражением.
  • start() запускает новый поток, run() — просто вызов метода в текущем. Повторный start() — IllegalThreadStateException.
  • Порядок работы потоков не гарантирован. Нужен порядок — обеспечь его сам.
  • join() — дождаться потока, Thread.sleep(ms) — поспать. Оба бросают InterruptedException.
  • Лямбда не может присвоить новое значение локальной переменной, но может менять статическое поле или ячейку массива: ссылка на массив при этом не меняется.
  • Программа живёт, пока работает хоть один обычный поток. Фоновый (daemon) поток — setDaemon(true) до start() — программу не держит.
