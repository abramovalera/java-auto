Как читать stack trace

Двадцать красных строк выглядят страшно, но устроены всегда одинаково. Разберём настоящий stack trace по частям и научимся за минуту находить в нём главное: что случилось и в какой строке твоего кода.

Повторение

Stack trace — снимок стека в момент аварии

Stack trace (по-русски «трассировка стека», в разговоре — «стектрейс») — это текст, который Java печатает о неперехваченном (непойманном) исключении. Ты видел короткие в уроке 1 и в модуле 7. Сегодня — настоящий, со строками из кода самой Java. Программа читает настройку подключения к серверу timeout=10s, но ждёт там число:

public class SettingsLoader {
    public static void main(String[] args) {
        startApp();
    }

    static void startApp() {
        int timeout = readTimeout("timeout=10s");
        System.out.println("Таймаут: " + timeout);
    }

    static int readTimeout(String line) {
        String value = line.substring(line.indexOf('=') + 1);
        return Integer.parseInt(value);
    }
}

Метод readTimeout отрезает всё после знака = (методы indexOf и substring из модуля 8) и превращает остаток в число. Остаток — «10s», а это не число. Запускаем:

Разбор по частям

Тот же trace, раскрашенный по смыслу. Номера в кружках — ниже в разборе.

① Exception in thread "main" …

Заголовок: что случилось. В каком потоке выполнения (main — главный; другие потоки появятся только в модуле 16, пока просто пропускай это слово), полное имя класса исключения (java.lang. — пакет, где он живёт) и после двоеточия — сообщение. Это самая полезная строка, читай её первой и целиком.

② at java.base/java.lang.Integer.parseInt(…)

Код JDK. Каждая строка at — один фрейм стека: Класс.метод(Файл.java:строка). Префикс java.base/ — это стандартная библиотека Java. Верхние строки — самые глубокие вызовы: исключение выбросили внутри parseInt. Ошибки в JDK почти никогда нет: она просто честно сообщает, что ей дали плохие данные. Эти строки пропускай.

③ at SettingsLoader.readTimeout(SettingsLoader.java:13)

Первая строка нашего кода. Место, где наша программа вызвала метод JDK и передала ему плохие данные: строка 13, Integer.parseInt(value). С неё и начинают поиск.

④ at SettingsLoader.main(SettingsLoader.java:3)

Откуда всё началось. Нижняя строка — дно стека. Читая снизу вверх, видишь историю: main на строке 3 вызвал startApp, тот на строке 7 вызвал readTimeout, тот на строке 13 — parseInt.

Предскажи: если в main вызвать readTimeout("timeout=") напрямую, без startApp, — что изменится в trace?

Заголовок станет For input string: "" — после = пустая строка. Строки JDK останутся те же. А наших строк будет две: readTimeout (строка 13) и сразу под ней main — фрейма startApp в стеке уже нет.

Caused by: исключение с причиной

Иногда в trace несколько «этажей». Так бывает, когда программа перехватила одно исключение и выбросила вместо него другое, с более понятным сообщением, а старое приложила к нему как причину. Как это делается в коде, разберём в уроке 6, а читать такой trace нужно уметь уже сейчас:

Exception in thread "main" java.lang.IllegalStateException: Не прочитать настройку: timeout=10s
	at SettingsLoader.readTimeout(SettingsLoader.java:16)
	at SettingsLoader.startApp(SettingsLoader.java:7)
	at SettingsLoader.main(SettingsLoader.java:3)
Caused by: java.lang.NumberFormatException: For input string: "10s"
	at java.base/java.lang.NumberFormatException.forInputString(NumberFormatException.java:67)
	at java.base/java.lang.Integer.parseInt(Integer.java:662)
	at java.base/java.lang.Integer.parseInt(Integer.java:778)
	at SettingsLoader.readTimeout(SettingsLoader.java:14)
	... 2 more
IllegalStateException: Не прочитать настройку…

Верхний этаж — новое исключение с понятным человеку сообщением. Под ним, как обычно, строки at: где его выбросили (строка 16) и кто кого вызвал.

Caused by: …NumberFormatException…

Причина. «Caused by» — «вызвано тем, что». Это исходное исключение, с которого всё началось: строка "10s" — не число. Под ним — его собственные строки at: снова JDK, а первая наша — строка 14, где вызван parseInt.

... 2 more

Сокращение. «Ещё 2 строки, такие же, как в конце trace выше» — это startApp и main. Java не повторяет одно и то же дважды.

Этажей с Caused by может быть несколько. Правило простое: корень проблемы — в последнем Caused by. Всё, что выше, — её последствия.

Сверху вниз или снизу вверх?

И так, и так — смотря что ищешь.

⬇️

Сверху вниз: где сломалось

Первая строка — что случилось. Первая своя строка at — где именно. Дальше вниз — кто кого вызвал, вплоть до main.

⬆️

Снизу вверх: как мы туда попали

Читаешь историю по порядку: main вызвал startApp, тот — readTimeout… Помогает понять, откуда пришли плохие данные.

На практике работает такой алгоритм — запомни его, он пригодится каждый день:

  1. Прочитай первую строку целиком. Тип исключения и сообщение. Часто ответ уже здесь: «For input string: "10s"».
  2. Есть «Caused by»? Спустись к последнему Caused by — это корень цепочки, первая беда. Всё, что выше, — её последствия.
  3. Найди первую строку at со своим классом. Пропускай строки java.base/ и jdk.internal — это код JDK, чужой. Первая своя строка — то место, где твоя программа попала в беду.
  4. Щёлкни по ней в IDEA. SettingsLoader.java:13 в панели Run — синяя ссылка, она открывает файл прямо на этой строке.
  5. Подумай, откуда пришли данные. Строка, где упало, часто не виновата. Виноват тот, кто передал туда "10s". Иди по trace вниз.

Главное правило: не ищи ошибку в JDK. Если trace начинается с java.base/ — это не Java сломалась. Это твой код дал ей что-то не то. Ищи свою строку.

Где тут наш код?

Тренируемся на коротком trace. Программа складывает цены, но одна из них набрана с опечаткой — буква O вместо нуля:

public class Prices {
    public static void main(String[] args) {
        String[] prices = {"100", "250", "9O"};
        System.out.println("Сумма: " + sum(prices));
    }

    static int sum(String[] prices) {
        int total = 0;
        for (String p : prices) {
            total += Integer.parseInt(p);
        }
        return total;
    }
}
Предскажи: на какую строку Prices.java ты посмотришь первой? И где на самом деле ошибка?

Первая своя строка в trace — Prices.sum, строка 10: там вызывается parseInt с аргументом "9O". Но сама строка 10 написана правильно. Плохие данные пришли снизу: main (строка 4) передал массив, а создан он на строке 3 — там и опечатка. Trace привёл к месту аварии, а дальше думаешь ты.

Номер строки JDK тебе не нужен

Integer.java:662 — номер строки в исходнике JDK. В другой версии Java он будет другим. Не пытайся его запоминать или искать в нём смысл.

Мой код или JDK?

Главный навык этого урока — с первого взгляда отличать строки своего кода от чужих. Потренируйся: разложи строки из trace этого урока по корзинам.

🔎 Для любопытных: trace настоящего сервера

На работе trace бывает длиннее раз в десять: кроме JDK в нём строки библиотек — чужого готового кода, который подключают к проекту. Вот упрощённый trace сервера интернет-магазина. Приложение прислало заказ в формате JSON, а в поле «количество» вместо числа оказалось "2 шт". JSON разбирает библиотека Jackson:

Алгоритм тот же. Первая строка: поле типа int не удалось заполнить строкой "2 шт". Строки com.fasterxml… (Jackson) и org.springframework… (Spring — библиотека для серверов) — чужие, пропускаем. Первая своя строка — shop.OrderReader.java:25. Всё остальное — тот же навык, что ты тренируешь сейчас.

Проверь себя

Поговори с наставником

Напиши: «Я прошёл урок 12.2. Покажи мне длинный stack trace с Caused by из трёх уровней, а я найду корень проблемы и свою строку кода».

Коротко

  • Stack trace = заголовок (тип + сообщение) + строки at Класс.метод(Файл:строка) от вершины стека к дну (+ иногда цепочка Caused by).
  • Сверху вниз — где сломалось; снизу вверх — как мы туда попали.
  • Алгоритм: прочитай первую строку → спустись к последнему Caused by → найди первую строку своего кода → щёлкни по ней в IDEA → подумай, откуда пришли данные.
  • Строки java.base/ — код JDK, их пропускаем. Ищи свои классы среди чужих строк.
  • Caused by — причина исключения над ним; корень — в последнем Caused by; ... N more — «ещё N строк, как выше».
