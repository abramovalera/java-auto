Как читать stack trace

Двадцать красных строк выглядят страшно, но устроены всегда одинаково. Разберём настоящий stack trace по частям и научимся за минуту находить в нём главное: что случилось и в какой строке твоего кода.

Повторение

Stack trace — снимок стека в момент аварии

Stack trace (по-русски «трассировка стека», в разговоре — «стектрейс») — это текст, который Java печатает о неперехваченном (непойманном) исключении. Ты видел короткие в модуле 7. Сегодня — настоящий, со всеми частями. Программа читает настройку подключения к серверу timeout=10s, но ждёт там число:

public class SettingsLoader {
    public static void main(String[] args) {
        startApp();
    }

    static void startApp() {
        int timeout = readTimeout("timeout=10s");
        System.out.println("Таймаут: " + timeout);
    }

    static int readTimeout(String line) {
        String value = line.substring(line.indexOf('=') + 1);
        try {
            return Integer.parseInt(value);
        } catch (NumberFormatException e) {
            throw new IllegalStateException(
                    "Не прочитать настройку: " + line, e);
        }
    }
}

Слова try, catch и throw ещё впереди (уроки 3 и 6). Пока достаточно знать: на строке 14 parseInt споткнулся о «10s» и выбросил NumberFormatException, а строка 16 создала и выбросила новое исключение с понятным сообщением, «завернув» в него старое как причину. Вот что получилось:

Разбор по частям

Тот же trace, раскрашенный по смыслу. Номера в кружках — ниже в разборе.

① Exception in thread "main" …

Заголовок: что случилось. В каком потоке (main — главный, других у нас пока нет), полное имя класса исключения (java.lang. — пакет, где он живёт) и после двоеточия — сообщение. Это самая полезная строка, читай её первой и целиком.

② at SettingsLoader.readTimeout(SettingsLoader.java:16)

Где упало. Каждая строка at — один фрейм: Класс.метод(Файл.java:строка). Верхняя строка — верхний фрейм, место, где исключение выбросили.

③ at SettingsLoader.main(SettingsLoader.java:3)

Откуда всё началось. Нижняя строка — дно стека. Читая снизу вверх, видишь историю: main на строке 3 вызвал startApp, тот на строке 7 вызвал readTimeout.

④ Caused by: …NumberFormatException…

Причина. Исключение ① выбросили не на пустом месте: при создании ему передали другое исключение как причину — «завернули» вокруг него. «Caused by» — «вызвано тем, что». Здесь настоящий корень проблемы: строка "10s" — не число.

⑤ at java.base/java.lang.Integer.parseInt(…)

Код JDK. Префикс java.base/ — это стандартная библиотека Java. Ошибки в ней почти никогда нет: она просто честно сообщает, что ей дали плохие данные. Эти строки пропускай.

⑥ at SettingsLoader.readTimeout(SettingsLoader.java:14)

Наш код в причине. Первая строка с нашим классом под Caused by — место, где мы вызвали метод JDK и передали ему плохие данные. Строка 14: Integer.parseInt(value).

⑦ ... 2 more

Сокращение. «Ещё 2 строки, такие же, как в конце trace выше» — это startApp и main. Java не повторяет одно и то же дважды.

Сверху вниз или снизу вверх?

И так, и так — смотря что ищешь.

⬇️

Сверху вниз: где сломалось

Первая строка — что случилось. Первая at — где именно. Дальше вниз — кто кого вызвал, вплоть до main.

⬆️

Снизу вверх: как мы туда попали

Читаешь историю по порядку: main вызвал startApp, тот — readTimeout… Помогает понять, откуда пришли плохие данные.

На практике работает такой алгоритм — запомни его, он пригодится каждый день:

  1. Прочитай первую строку целиком. Тип исключения и сообщение. Часто ответ уже здесь: «For input string: "10s"».
  2. Есть «Caused by»? Спустись к последнему Caused by — это корень цепочки, первая беда. Всё, что выше, — её последствия.
  3. Найди первую строку at со своим классом. Пропускай java.base/, jdk.internal, org.junit, com.fasterxml — это чужой код. Первая своя строка — то место, где твоя программа попала в беду.
  4. Щёлкни по ней в IDEA. SettingsLoader.java:14 в панели Run — синяя ссылка, она открывает файл прямо на этой строке.
  5. Подумай, откуда пришли данные. Строка, где упало, часто не виновата. Виноват тот, кто передал туда "10s". Иди по trace вниз.

Главное правило: не ищи ошибку в JDK. Если trace начинается с java.base/ — это не Java сломалась. Это твой код дал ей что-то не то. Ищи свою строку.

Где тут наш код?

Тренируемся на коротком trace. Программа складывает цены, но одна из них набрана с опечаткой — буква O вместо нуля:

public class Prices {
    public static void main(String[] args) {
        String[] prices = {"100", "250", "9O"};
        System.out.println("Сумма: " + sum(prices));
    }

    static int sum(String[] prices) {
        int total = 0;
        for (String p : prices) {
            total += Integer.parseInt(p);
        }
        return total;
    }
}
Предскажи: на какую строку Prices.java ты посмотришь первой? И где на самом деле ошибка?

Первая своя строка в trace — Prices.sum, строка 10: там вызывается parseInt с аргументом "9O". Но сама строка 10 написана правильно. Плохие данные пришли снизу: main (строка 4) передал массив, а создан он на строке 3 — там и опечатка. Trace привёл к месту аварии, а дальше думаешь ты.

Номер строки JDK тебе не нужен

Integer.java:662 — номер строки в исходнике JDK. В другой версии Java он будет другим. Не пытайся его запоминать или искать в нём смысл.

Stack trace настоящего проекта

Вот так примерно выглядит trace на сервере интернет-магазина (упрощено: настоящий длиннее раза в три, номера строк библиотек условные). Мобильное приложение прислало заказ в формате JSON, а в поле «количество» вместо числа оказалось "2 шт". Разбирает JSON библиотека Jackson — она превращает текст в объекты Java, и на этом поле она споткнулась:

Применяем алгоритм. Первая строка: поле типа int не удалось заполнить строкой "2 шт". Caused by здесь нет — корень виден сразу. Первая своя строка: OrderReader.java:25 — метод, который разбирает заказ, а под ней OrderController.java:18 — место, где сервер принял заказ. Дальше думаем: приложение шлёт не тот формат? Наш класс ждёт не то поле? Где лучше проверять такие данные?

Проверь себя

Поговори с наставником

Напиши: «Я прошёл урок 12.2. Покажи мне длинный stack trace с Caused by из трёх уровней, а я найду корень проблемы и свою строку кода».

Коротко

  • Stack trace = заголовок (тип + сообщение) + строки at Класс.метод(Файл:строка) от вершины стека к дну + цепочка Caused by.
  • Сверху вниз — где сломалось; снизу вверх — как мы туда попали.
  • Алгоритм: прочитай первую строку → спустись к последнему Caused by → найди первую строку своего кода → щёлкни по ней в IDEA → подумай, откуда пришли данные.
  • Строки java.base/, org.junit, com.fasterxml, org.springframework — чужой код, их пропускаем.
  • Trace настоящего проекта с библиотеками читается так же: ищи свои классы среди чужих строк.
