Хорошие практики и отладка исключений

Перехватить (поймать) исключение просто. Сложнее — не навредить: не спрятать настоящую ошибку и не потерять причину. Соберём правила, по которым пишут профессионалы, и научим отладчик останавливаться ровно в момент исключения.

⏱ 20 минут✅ правила🐞 Exception Breakpoint

Повторение

Правило 1. Не глотай исключения

Самая вредная привычка — пустой catch: «перехватил и ничего не сделал». Это называют «проглотить исключение»:

static int readTimeout(String text) {
    try {
        return Integer.parseInt(text);
    } catch (NumberFormatException e) {
        // ничего, авось обойдётся
    }
    return 0;
}

Кто-то написал в настройках timeout=10s. Программа не упала — она молча решила, что таймаут 0 секунд. Дальше каждый запрос к серверу обрывается мгновенно, заказы падают с SocketTimeoutException в совершенно другом месте, и ты час ищешь, почему. А настоящая причина — одна опечатка, о которой никто не сообщил.

Аналогия: батарейка из пожарной сигнализации

Сигнализация пищит — раздражает. Вынул батарейку — стало тихо. Но пожар от этого не исчез, ты просто узнаешь о нём позже и в худший момент. Пустой catch — вынутая батарейка.

Правило 2. Не перехватывай Exception без нужды

catch (Exception e) выглядит надёжно: «поймаю всё». Но «всё» — это и твои баги:

try {
    int age = Integer.parseInt(text.trim());
    System.out.println("Возраст: " + age);
} catch (Exception e) {
    System.out.println("Это не число, попробуй ещё раз");
}
Предскажи: что напечатает программа, если из-за бага в другом месте text оказался null?

«Это не число, попробуй ещё раз». На самом деле вызов text.trim() выбросил NullPointerException — баг в коде, а не ошибка пользователя. Общий catch перехватил его и выдал за «не число». Пользователь будет вводить правильные числа снова и снова, а программа будет отвечать одно и то же. С catch (NumberFormatException e) NPE пролетел бы мимо со stack trace — и ты сразу увидел бы настоящую причину.

Перехватывай конкретный тип — тот, который ожидаешь и знаешь, как обработать. Общий catch (Exception e) уместен в одном месте — на самом верху программы, как «последний рубеж»: чтобы сервер не упал из-за одного плохого запроса. И даже там исключение обязательно записывают в лог целиком.

Правило 3. Сохраняй информацию

Перехватил — не теряй, что именно случилось и где.

Правило 4. Исключения — не для обычной логики

Если проблему легко проверить заранее — проверь через if. Не надо перехватывать ArrayIndexOutOfBoundsException, когда можно написать if (index >= 0 && index < arr.length), или ArithmeticException, когда можно проверить делитель. Исключения — для исключительных ситуаций.

А с числами из текста так: у самого Integer.parseInt метода «можно ли превратить?» нет, поэтому для строки, уже прочитанной из файла или настройки, try/catch — нормальный путь. Но если читаешь с клавиатуры через Scanner, проверка есть: scanner.hasNextInt() смотрит, целое ли число дальше во вводе, не забирая его.

Scanner scanner = new Scanner(System.in);
while (!scanner.hasNextInt()) {
    String bad = scanner.next();      // «доедаем» плохое слово
    System.out.println("«" + bad + "» — не целое число, попробуй ещё раз");
}
int n = scanner.nextInt();
System.out.println("Принято: " + n);
Предскажи: что будет, если убрать строку scanner.next() и ввести «abc»?

Бесконечный цикл: hasNextInt() только смотрит и ничего не забирает. «abc» так и останется первым во вводе, и цикл будет вечно печатать сообщение. Поэтому плохое слово обязательно «доедают» через next(). Оба способа — hasNextInt() и nextLine() + parseInt в try — честные; в задачах модуля мы тренируем второй. (С hasNextInt() есть тонкость: он работает по словам, поэтому «3 4» в одной строке — это два числа.)

Остановиться в момент исключения: Exception Breakpoint

Stack trace показывает, где упало. Но не показывает, какие значения были у переменных в этот момент. Для этого есть отладчик (ты знаком с ним по модулям 6 и 7). Обычная точка останова стоит на строке. А Exception Breakpoint («точка останова на исключение») срабатывает в тот миг, когда выбрасывается исключение нужного типа, — где бы это ни случилось. Не надо гадать, на какую строку ставить красную точку.

Когда это особенно выручает

Когда исключение вылетает внутри цикла на сотом круге, или когда его перехватывают и ты видишь только «что-то пошло не так». Поставил точку на исключение — и сразу видишь все переменные в момент аварии. Закончил — сними точку (сними галочку или удали её в том же окне), иначе отладчик будет останавливаться и дальше.

Предскажи: в программе с вводом числа с повтором (Мастерская урока 3) стоит точка на NumberFormatException с галочкой Caught. Пользователь ввёл «abc». Остановится ли отладчик, хотя исключение перехватывает catch?

Да. Галочка Caught exception означает «останавливаться и на перехваченных». Сними её и оставь только Uncaught — тогда отладчик будет замирать лишь на тех исключениях, которые никто не перехватил и которые уронят программу.

И одна фраза на будущее: в модуле 17 ты увидишь, что упавший тест на JUnit — тоже исключение со stack trace, так что всё, чему ты научился здесь, пригодится и там.

Проверь себя

Поговори с наставником

Напиши: «Я прошёл урок 12.7. Покажи мне кусок кода с плохой обработкой исключений, а я найду все проблемы и объясню, как исправить». Потом реши задачу m12-t07 «Почини обработку ошибок датчиков».

Коротко

  • Пустой catch — никогда. Либо обработай по-настоящему, либо заверни с причиной, либо не перехватывай — пусть летит дальше.
  • Перехватывай конкретный тип. catch (Exception e) — только «последний рубеж» на самом верху и с логом.
  • Не теряй информацию: printStackTrace, лог, new X("контекст", e).
  • Что легко проверить заранее — проверяй if-ом; исключения — для исключительного. Для ввода с клавиатуры есть scanner.hasNextInt().
  • Exception Breakpoint (Ctrl+Shift+F8 → «+» → Java Exception Breakpoints) останавливает отладчик в момент выброса исключения — видно все переменные.
