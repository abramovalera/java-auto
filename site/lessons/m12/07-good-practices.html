Хорошие практики и исключения в тестах

Перехватить (поймать) исключение просто. Сложнее — не навредить: не спрятать настоящую ошибку, не потерять причину, не сделать тест, который зелёный всегда. Соберём правила, по которым пишут профессионалы, и заглянем, как JUnit превращает исключения в красные и зелёные галочки.

Повторение

Правило 1. Не глотай исключения

Самая вредная привычка — пустой catch: «перехватил и ничего не сделал». Это называют «проглотить исключение»:

static int readTimeout(String text) {
    try {
        return Integer.parseInt(text);
    } catch (NumberFormatException e) {
        // ничего, авось обойдётся
    }
    return 0;
}

Кто-то написал в настройках timeout=10s. Программа не упала — она молча решила, что таймаут 0 секунд. Дальше каждый запрос к серверу обрывается мгновенно, заказы падают с SocketTimeoutException в совершенно другом месте, и ты час ищешь, почему. А настоящая причина — одна опечатка, о которой никто не сообщил.

Аналогия: батарейка из пожарной сигнализации

Сигнализация пищит — раздражает. Вынул батарейку — стало тихо. Но пожар от этого не исчез, ты просто узнаешь о нём позже и в худший момент. Пустой catch — вынутая батарейка.

Правило 2. Не перехватывай Exception без нужды

catch (Exception e) выглядит надёжно: «поймаю всё». Но «всё» — это и твои баги:

try {
    int age = Integer.parseInt(text.trim());
    System.out.println("Возраст: " + age);
} catch (Exception e) {
    System.out.println("Это не число, попробуй ещё раз");
}
Предскажи: что напечатает программа, если из-за бага в другом месте text оказался null?

«Это не число, попробуй ещё раз». На самом деле вызов text.trim() выбросил NullPointerException — баг в коде, а не ошибка пользователя. Общий catch перехватил его и выдал за «не число». Пользователь будет вводить правильные числа снова и снова, а программа будет отвечать одно и то же. С catch (NumberFormatException e) NPE пролетел бы мимо со stack trace — и ты сразу увидел бы настоящую причину.

Перехватывай конкретный тип — тот, который ожидаешь и знаешь, как обработать. Общий catch (Exception e) уместен в одном месте — на самом верху программы, как «последний рубеж»: чтобы сервер не упал из-за одного плохого запроса или чтобы прогон тестов продолжился после одного сломанного. И даже там исключение обязательно записывают в лог целиком.

Правило 3. Сохраняй информацию

Перехватил — не теряй, что именно случилось и где.

В настоящих проектах вместо println и printStackTrace пишут в лог — журнал работы программы, через библиотеки вроде Logback или Log4j. Правило 4. Исключения — не для обычной логики

Если проблему легко проверить заранее — проверь через if. Не надо перехватывать ArrayIndexOutOfBoundsException, когда можно написать if (index >= 0 && index < arr.length). Исключения — для исключительных ситуаций. А вот у parseInt нет удобного «можно ли превратить?», поэтому там try/catch — нормальный путь.

Как JUnit видит исключения

Заглянем вперёд, в модуль 17. JUnit — программа, которая запускает твои тесты. Тест — обычный метод с аннотацией @Test. JUnit вызывает его внутри своего try/catch — примерно как ты в уроке 3 — и смотрит, не выбросил ли тест исключение:

Отсюда опасный антипаттерн — вечнозелёный тест. Новичок «защищает» тест от падений:

@Test
void readsTimeout() {
    try {
        int timeout = SettingsLoader.readTimeout("timeout=10s");
        assertEquals(10, timeout);
    } catch (Exception e) {
        System.out.println("что-то пошло не так");
    }
}

readTimeout выбрасывает IllegalStateException — catch его перехватывает и проглатывает — до JUnit ничего не долетает — тест зелёный. Баг в программе есть, а тест говорит «всё отлично». Такой тест хуже, чем никакого: он врёт. В тестах исключения не перехватывают — пусть летят в JUnit, для этого он и нужен.

Тизер: assertThrows

А как проверить, что метод правильно выбрасывает исключение? Например, что validateAge(-5) из задачи m12-t04 отказывается? В JUnit для этого есть assertThrows:

@Test
void negativeAgeIsRejected() {
    IllegalArgumentException e = assertThrows(IllegalArgumentException.class,
            () -> AgeValidationGate.validateAge(-5));
    assertEquals("возраст не может быть отрицательным: -5", e.getMessage());
}
  • () -> … — «кусок кода, который JUnit запустит сам» (это лямбда, подробно — модуль 14). JUnit выполнит его внутри своего try/catch.
  • Код выбросил IllegalArgumentException — assertThrows вернёт ссылку на этот объект исключения, и можно проверить сообщение. Не вылетело ничего или вылетело другое — тест упадёт.
  • IllegalArgumentException.class — сам класс как значение: «ожидаю исключение вот этого типа».

Этим займёмся по-настоящему в модуле 17 — там ты будешь писать тесты сам. А пока важно понять идею: исключения — не враги тестов, а их основной язык. Тест сообщает о проблеме исключением, а ты читаешь его stack trace.

Что ты теперь понимаешь в отчётах

AssertionFailedError: expected: <10> but was: <0> — проверка ожидала 10, получила 0 (это потомок AssertionError из JUnit). IllegalStateException с понятным сообщением — твоя программа сама сообщила, что пошло не так. NullPointerException в своём классе — баг в твоём коде. По первой строке ты уже знаешь, куда смотреть.

Проверь себя

Поговори с наставником

Напиши: «Я прошёл урок 12.7. Покажи мне кусок кода с плохой обработкой исключений, а я найду все проблемы и объясню, как исправить». Потом реши задачу m12-t07 «Почини обработку ошибок датчиков».

Коротко

  • Пустой catch — никогда. Либо обработай по-настоящему, либо заверни с причиной, либо не перехватывай — пусть летит дальше.
  • Перехватывай конкретный тип. catch (Exception e) — только «последний рубеж» на самом верху и с логом.
  • Не теряй информацию: printStackTrace, лог, new X("контекст", e).
  • Что легко проверить заранее — проверяй if-ом; исключения — для исключительного.
  • JUnit: тест упал = из него вылетело исключение. В тестах исключения не перехватывают. assertThrows проверяет, что исключение было (модуль 17).
