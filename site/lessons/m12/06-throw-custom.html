throw и свои исключения

До сих пор исключения выбрасывала Java. Теперь выбрасывать будешь ты: метод, которому дали плохие данные, должен громко отказаться, а не молча посчитать ерунду. И научимся создавать свои классы исключений с сообщениями, которые реально помогают.

Повторение

throw: выбросить исключение самому

В модуле 9 ты прятал поля за private и менял их через методы. А что делать методу, если ему передали ерунду? Уровень игрока −3, возраст 500, цена −100. Молча сохранить нельзя — ошибка всплывёт потом, в неожиданном месте. Правильно — отказаться сразу и громко:

public class Player {
    private int level;

    void setLevel(int level) {
        if (level < 1 || level > 100) {
            throw new IllegalArgumentException(
                    "уровень должен быть от 1 до 100, а пришло: " + level);
        }
        this.level = level;
    }
}
new IllegalArgumentException("…")

Создаём объект исключения — как любой другой объект, оператором new с вызовом конструктора. Конструктору передаём аргументом сообщение: оно попадёт в getMessage() и в первую строку stack trace.

throw …;

Выбрасываем этот объект оператором throw. Метод немедленно прерывается, как при return, только вместо результата наружу летит исключение — и всплывает по стеку, как в уроке 1. Строка this.level = level не выполнится.

Аналогия: досмотр в аэропорту

Опасные вещи ищут на входе, до посадки, а не когда самолёт уже в воздухе. Проверка аргументов в начале метода — тот же досмотр: плохие данные не проходят внутрь. По-английски этот принцип называют fail fast — «падай быстро».

Предскажи: скомпилируется ли строка сразу после throw в том же блоке, например throw new IllegalStateException("x"); System.out.println("y");?

Нет: unreachable statement — недостижимый код. После throw управление никогда не дойдёт до следующей строки, как и после return.

Какое исключение выбрасывать

Для большинства случаев в JDK уже есть подходящий класс. Выбирай по смыслу:

ИсключениеКогда выбрасыватьПример сообщения
IllegalArgumentExceptionпередали плохой аргумент«возраст не может быть отрицательным: -5»
IllegalStateExceptionаргумент нормальный, но объект сейчас не в том состоянии«нельзя пополнить закрытый счёт №42»
UnsupportedOperationExceptionоперация в принципе не поддерживается«этот список только для чтения»

Эти три — unchecked, поэтому throws писать не нужно: они сообщают об ошибке того, кто вызвал метод. Вызывающий должен не перехватывать их, а не передавать плохие данные.

🔎 Для любопытных: проверка в record

В модуле 11 ты делал record. Проверять данные удобно прямо в его компактном конструкторе (без скобок с параметрами) — тогда неправильный объект просто невозможно создать:

record Temperature(int celsius) {
    Temperature {
        if (celsius < -273) {
            throw new IllegalArgumentException(
                    "ниже абсолютного нуля: " + celsius);
        }
    }
}

Свой класс исключения

Иногда стандартного мало: ситуация — часть правил твоей программы, и вызывающий должен уметь её отличить и обработать. Например, в кинотеатре кончились места. Это не баг, а нормальная жизненная ситуация, на которую нужен план Б. Объявляем собственный класс исключения — обычным наследованием от Exception:

public class Cinema {
    public static void main(String[] args) {
        CinemaHall hall = new CinemaHall(3);
        try {
            hall.buy(2);
            hall.buy(2);
            System.out.println("Приятного просмотра!");
        } catch (SoldOutException e) {
            System.out.println("Не получилось: " + e.getMessage());
            System.out.println("Можно купить не больше " + e.getFreeSeats());
        }
    }
}

class SoldOutException extends Exception {
    private final int freeSeats;

    SoldOutException(int requested, int freeSeats) {
        super("мест не хватает: запрошено " + requested
                + ", свободно " + freeSeats);
        this.freeSeats = freeSeats;
    }

    int getFreeSeats() {
        return freeSeats;
    }
}

class CinemaHall {
    private int freeSeats;

    CinemaHall(int seats) {
        this.freeSeats = seats;
    }

    void buy(int count) throws SoldOutException {
        if (count <= 0) {
            throw new IllegalArgumentException(
                    "билетов должно быть больше нуля, а пришло: " + count);
        }
        if (count > freeSeats) {
            throw new SoldOutException(count, freeSeats);
        }
        freeSeats -= count;
        System.out.println("Куплено: " + count + ", свободно: " + freeSeats);
    }
}
Куплено: 2, свободно: 1
Не получилось: мест не хватает: запрошено 2, свободно 1
Можно купить не больше 1
class SoldOutException extends Exception

Свой класс — наследник Exception, значит, checked. Имя по традиции заканчивается на Exception и описывает ситуацию. Три класса в одном файле — можно, если public только один (тот, чьё имя совпадает с файлом).

super("мест не хватает: …")

Вызываем конструктор родителя через super (модуль 10) и передаём ему аргументом сообщение. Именно его потом вернёт getMessage() — свой метод для этого писать не нужно.

private final int freeSeats;

Исключение — обычный класс, ему можно дать поля и геттеры. Блок catch получает из него данные вызовом геттера: «сколько всё-таки можно купить».

void buy(int count) throws SoldOutException

Раз исключение checked, метод обязан объявить его в сигнатуре через throws. А main обязан перехватить его (или тоже объявить throws) — иначе не скомпилируется. Компилятор не даст забыть про «мест нет».

Проверь, как компилятор следит за своим checked-исключением: убери из main try/catch и оставь голый вызов.

Посмотри, что происходит в памяти, когда второй buy выбрасывает исключение:

extends Exception или RuntimeException?

Свой класс можно сделать checked или unchecked — смотря от кого наследуешь:

В современных библиотеках чаще встречается RuntimeException: checked-исключения заставляют писать catch или throws в каждом методе по пути, и код быстро обрастает ими. Например, все исключения Spring, Jackson и JUnit — unchecked. Но для учебной копилки в задаче m12-t06 мы сделаем именно checked: пусть компилятор следит, чтобы «недостаточно денег» всегда обрабатывали.

Сообщения, которые помогают

Сообщение исключения читает человек — часто ночью, в отчёте упавших тестов. Сравни:

ПлохоХорошо
"Ошибка""возраст не может быть отрицательным: -5"
"Неверные данные""строка 3 в config.txt: нет знака '=' в «timeout 30»"
"Недостаточно средств""нельзя снять 500: на счёте 300"

Хорошее сообщение отвечает на три вопроса: что не так, какое значение пришло и где (какая строка, какой объект). Пиши его по-русски или по-английски, но обязательно с конкретным значением.

И ещё один приём из урока 2. Если перехватил «низкоуровневое» исключение и выбрасываешь своё, передай перехваченное как причину вторым аргументом конструктора:

try {
    return Integer.parseInt(value);
} catch (NumberFormatException e) {
    throw new IllegalStateException("Не прочитать настройку: " + line, e);
}

Тогда в stack trace появится Caused by: java.lang.NumberFormatException…, и корень проблемы не потеряется. У своих исключений для этого делают конструктор (String message, Throwable cause), который вызывает super(message, cause). Достать причину в коде — e.getCause(). Это задача m12-t08 «Исключение с причиной».

Проверь себя

Поговори с наставником

Напиши: «Я прошёл урок 12.6. Посмотри мой класс PiggyInsufficientFundsException из задачи m12-t06: хорошее ли у него сообщение и правильно ли я выбрал checked?»

Коротко

  • throw new Тип("сообщение") — создать объект исключения и выбросить его; метод прерывается сразу.
  • Плохие аргументы — IllegalArgumentException, неподходящее состояние — IllegalStateException. Проверяй в начале метода (fail fast).
  • Свой класс: class XxxException extends Exception (checked) или extends RuntimeException (unchecked), сообщение — через super(message), можно добавить поля.
  • Хорошее сообщение: что не так + какое значение + где.
  • Заворачивая исключение в своё, передай его как причину: new X("…", e) → «Caused by» в stack trace.
