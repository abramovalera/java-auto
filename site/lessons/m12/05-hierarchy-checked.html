Иерархия исключений, checked и throws

Исключения — обычные классы, и у них есть родословная, как у классов из модуля 10. Она объясняет всё: почему catch перехватывает «родственников», почему одни исключения компилятор заставляет обрабатывать, а другие нет, и зачем в сигнатуре метода слово throws.

Повторение

Родословная исключений

Каждое исключение — объект какого-то класса. А классы исключений связаны наследованием (extends), как классы из модуля 10. Например, в JDK написано примерно так: class NumberFormatException extends IllegalArgumentException. Всё дерево начинается с класса Throwable — «то, что можно выбросить».

Throwable
Корень. Выбросить через throw и перехватить в catch можно только объекты класса Throwable и его потомков.
Error
Серьёзный сбой самой JVM или окружения: кончилась память, переполнился стек. Программа обычно ничего не может с этим сделать — такие не перехватывают.
Exception
Проблемы, с которыми программа может и должна справляться.
RuntimeException
Ветка Exception для ошибок в логике программы: деление на ноль, null, выход за массив. Все знакомые тебе исключения — отсюда.

catch перехватывает и всех потомков

Помнишь полиморфизм: там, где ждут Animal, может прийти Cat. С исключениями то же самое. catch (IllegalArgumentException e) перехватит и само IllegalArgumentException, и любого его потомка — например, NumberFormatException:

try {
    int n = Integer.parseInt("пять");
} catch (IllegalArgumentException e) {
    System.out.println("Поймали: " + e.getClass().getSimpleName());
}
Поймали: NumberFormatException

Вызов e.getClass().getSimpleName() возвращает короткое имя настоящего класса объекта (метод getClass() есть у любого объекта, он из класса Object). Переменная e объявлена с типом IllegalArgumentException, а ссылается на объект NumberFormatException.

Теперь понятно правило из урока 3. catch (RuntimeException e) перехватывает всю жёлтую ветку дерева. Если он стоит выше catch (NumberFormatException e), второму ничего не достанется — отсюда «has already been caught». А catch (Exception e) перехватывает вообще почти всё.

Предскажи: перехватит ли catch (Exception e) ошибку StackOverflowError?

Нет. StackOverflowError — потомок Error, а не Exception. Это соседние ветки, у них общий только Throwable. Так что catch (Exception) перехватывает «почти всё» — кроме Error.

То же касается AssertionError со схемы — «проверка не прошла». Он потомок Error, поэтому catch (Exception e) его не перехватит: проваленную проверку нельзя «случайно» проглотить (в модуле 17 так честно краснеют упавшие тесты).

Error: когда ломается сама машина

Самый простой способ увидеть Error — бесконечная рекурсия из модуля 7. Метод вызывает себя без условия остановки, фреймы копятся, пока стек не переполнится:

public class Forever {
    public static void main(String[] args) {
        countDown(10);
    }

    static void countDown(int n) {
        countDown(n - 1);   // забыли условие остановки
    }
}
Exception in thread "main" java.lang.StackOverflowError
	at Forever.countDown(Forever.java:7)
	at Forever.countDown(Forever.java:7)
	at Forever.countDown(Forever.java:7)
	… (ещё около тысячи одинаковых строк)

Stack trace из тысячи одинаковых строк — верный признак бесконечной рекурсии. Перехватывать такую ошибку бессмысленно: надо чинить код. С OutOfMemoryError (кончилась память в куче) то же самое. Правило: Error не перехватываем.

checked и unchecked

Теперь главное деление. Попробуй сделать паузу в программе — метод Thread.sleep «усыпляет» её на заданное число миллисекунд. (Thread — класс для потоков выполнения, им посвящён модуль 16; сейчас нам нужен только его метод sleep.)

public class Pause {
    public static void main(String[] args) {
        System.out.println("Ждём секунду…");
        Thread.sleep(1000);
        System.out.println("Готово");
    }
}
Pause.java:4: error: unreported exception InterruptedException; must be caught or declared to be thrown
        Thread.sleep(1000);
                    ^

Это текст javac. В IDEA ты увидишь ошибку раньше, прямо в редакторе, и сформулирована она короче:

Код даже не компилируется! Thread.sleep может выбросить InterruptedException («сон прервали» — другая часть программы попросила проснуться раньше; как это бывает, увидишь в модуле 16), а это исключение — checked («проверяемое»). Компилятор проверяет: «ты подумал, что делать, если это случится?» — и не пропустит код, пока ты не ответишь.

Аналогия: прогноз погоды

Checked — это прогноз «возможен дождь». Дождь от тебя не зависит, но выходя из дома, ты обязан решить: беру зонт (catch) или пусть решает тот, кто меня послал (throws). Unchecked — это «наступил в лужу, потому что смотрел в телефон». Такое не планируют — от такого отучаются.

Но в уроке 3 мы перехватывали NumberFormatException! Это не противоречие?

Нет. «Unchecked — исправляй код» относится к ошибкам программиста: NPE, выход за массив, деление на переменную, которую забыли проверить. А NumberFormatException на вводе — это не ошибка в коде, а плохие данные от пользователя: заранее их не исправишь. Поэтому такое unchecked-исключение перехватывают и переспрашивают — как в задачах t01–t05. Вопрос всегда один: кто виноват — мой код или данные снаружи? Код — чиню. Данные — перехватываю и делаю план Б.

throws: «не перехватываю — пробрасываю дальше»

На checked-исключение у тебя два ответа компилятору. Первый — перехватить в catch:

try {
    Thread.sleep(1000);
} catch (InterruptedException e) {
    System.out.println("Сон прервали");
}

Второй — объявить исключение в сигнатуре метода: «я могу выбросить это исключение, пусть разбирается тот, кто меня вызвал». Для этого после скобок с параметрами пишут throws и тип:

public class Pause {
    public static void main(String[] args) throws InterruptedException {
        System.out.println("Ждём…");
        pause(2);
        System.out.println("Готово");
    }

    static void pause(int seconds) throws InterruptedException {
        Thread.sleep(seconds * 1000);
    }
}

pause не перехватывает исключение, а объявляет его в throws — пробрасывает дальше тому, кто её вызвал. Теперь вызывающий main сам должен решить: перехватывать или тоже объявить throws. main объявил — значит, если сон прервут, исключение вылетит из main и уронит программу, как в уроке 1. Для учебных программ это нормально.

Оба ответа IDEA напишет за тебя. Поставь курсор на красное и нажми Alt+Enter — первые два пункта меню и есть «перехватить» и «пробросить дальше»:

throws при переопределении метода

В модулях 10 и 11 ты переопределял методы родителя и реализовывал методы интерфейса. Если у исходного метода есть throws, для переопределения действует правило: новых или более общих checked-исключений добавлять нельзя. Меньше — можно:

import java.io.IOException;

interface ReportSource {
    String load() throws IOException;
}

class MemoryReport implements ReportSource {
    @Override
    public String load() {                     // можно: без throws вообще
        return "Отчёт из памяти";
    }
}

class GreedyReport implements ReportSource {
    @Override
    public String load() throws Exception {    // нельзя: Exception шире IOException
        return "Отчёт";
    }
}
ReportSource.java:16: error: load() in GreedyReport cannot implement load() in ReportSource
    public String load() throws Exception {
                  ^
  overridden method does not throw Exception

Почему так? Вспомни полиморфизм. Кто-то пишет ReportSource source = …; и оборачивает source.load() в catch (IOException e) — он готов только к тому, что обещано в интерфейсе. Если бы наследник мог выбросить что-то шире, это исключение проскочило бы мимо проверки компилятора. Можно: не писать throws, написать тот же тип или его потомка, добавить любые unchecked. Нельзя: новый checked-тип или более общий.

Предскажи: скомпилируется ли в MemoryReport заголовок public String load() throws FileNotFoundException? (FileNotFoundException — потомок IOException.)

Да. Потомок — это более узкое обещание: «могу выбросить только вот эту разновидность IOException». Код, который ловит IOException, перехватит и его.

throw и throws — разные слова

throws (с «s») пишется в сигнатуре метода и предупреждает: «могу выбросить». throw (без «s») пишется в теле метода и выбрасывает исключение прямо сейчас. Его разберём в следующем уроке. Путают их постоянно — на собеседовании это любимый вопрос.

🔎 Для любопытных: а можно throws у unchecked?

Можно: void setAge(int age) throws IllegalArgumentException скомпилируется. Но компилятор этого не требует, и вызывающему перехватывать его необязательно. Иногда так пишут как документацию — «имей в виду». Обратное правило тоже есть: перехватить checked-исключение, которое код в try выбросить не может, нельзя: catch (IOException e) вокруг println даст ошибку exception IOException is never thrown in body of corresponding try statement. С unchecked такой проверки нет.

Мини-игра: к какой ветке дерева относится исключение?

Проверь себя

Поговори с наставником

Напиши: «Я прошёл урок 12.5. Спроси меня, чем checked отличается от unchecked, и придумай пример, где я должен решить: catch или throws».

Коротко

  • Throwable → Error (сбои JVM, не перехватываем) и Exception → RuntimeException (ошибки в коде) + checked-исключения.
  • catch перехватывает свой тип и всех потомков. Поэтому частные catch — выше общих.
  • Checked (Exception, но не RuntimeException) компилятор заставляет перехватить или объявить в throws. Unchecked — нет.
  • throws в сигнатуре — «объявляю и пробрасываю дальше»; throw в теле — «выбрасываю сейчас».
  • Unchecked из-за ошибки в коде — чиним код; плохие данные снаружи (NumberFormatException на вводе) — перехватываем и переспрашиваем.
  • Переопределяя метод, нельзя добавить в throws новое или более общее checked-исключение; меньше или уже — можно.
  • Error (StackOverflowError, AssertionError) — не Exception, catch (Exception) его не перехватит.
