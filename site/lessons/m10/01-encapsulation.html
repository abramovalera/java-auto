Инкапсуляция: прячем данные

Объект — не мешок с полями, куда любой может залезть руками. Хороший объект сам охраняет свои данные и пускает к ним только через «окошки» с проверкой. Учимся писать такие классы на примере банковского счёта.

Три кита ООП

Классы и объекты ты уже умеешь писать. Но в Java есть три идеи, которые превращают «просто классы» в объектно-ориентированное программирование (ООП). Их спрашивают на каждом собеседовании, и на них держится весь этот модуль.

Где набирать примеры из уроков

Создай внутри module-10 пакет для экспериментов: правый клик по папке → New → Package → lesson10. Классы из уроков (Cat, Animal…) клади туда — тогда они не столкнутся с одноимёнными классами из других модулей. А вот файлы задач клади прямо в module-10, без пакета, иначе проверка их не найдёт.

Что не так с открытыми полями

Представь банковский счёт, у которого поле баланса открыто всем:

public class OpenBank {
    public static void main(String[] args) {
        OpenAccount acc = new OpenAccount();
        acc.balance = 100;
        acc.balance = acc.balance - 5000;   // сняли больше, чем было
        acc.balance = -999999;              // или просто так
        System.out.println("Баланс: " + acc.balance);
    }
}

class OpenAccount {
    public int balance;
}
Предскажи: скомпилируется ли этот код? Что напечатает?

Скомпилируется и напечатает «Баланс: -999999». Java не знает, что у счёта баланс не бывает отрицательным. Это знаем только мы — а охранять правило некому: любая строчка любого класса может присвоить полю что угодно.

В маленькой программе ошибку легко найти. А в проекте на сто тысяч строк, где баланс меняют из двадцати мест? Какое из них увело счёт в минус — ищи до вечера.

Аналогия: банкомат и сейф

Деньги банка лежат в сейфе, и клиенту туда залезть нельзя. Клиент говорит банкомату: «сними 500». Банкомат проверяет, хватает ли денег, и только потом выдаёт. Если не хватает — вежливо отказывает.

Открытое поле — это сейф без двери: каждый берёт сколько хочет. Инкапсуляция — это сейф (private-поле) плюс банкомат (публичные методы с проверками).

Прячем поле, даём методы

Инкапсуляция (от «капсула») — приём, при котором данные объекта — его поля — спрятаны внутри с модификатором доступа private, а снаружи доступны только методы, и эти методы следят за правилами. Перепишем счёт:

public class Bank {
    public static void main(String[] args) {
        BankAccount acc = new BankAccount();
        acc.deposit(100);
        boolean ok = acc.withdraw(5000);
        System.out.println("Сняли? " + ok);
        System.out.println("Баланс: " + acc.getBalance());
    }
}

class BankAccount {
    private int balance;                      // сейф: снаружи не достать

    boolean deposit(int amount) {             // окошко «положить»
        if (amount <= 0) {
            return false;
        }
        balance += amount;
        return true;
    }

    boolean withdraw(int amount) {            // окошко «снять»
        if (amount <= 0 || amount > balance) {
            return false;                     // отказ: баланс не трогаем
        }
        balance -= amount;
        return true;
    }

    int getBalance() {                        // окошко «посмотреть»
        return balance;
    }
}
private int balance;

Объявляем поле balance с модификатором private — оно спрятано. Присваивание acc.balance = -999999; в main теперь не скомпилируется: balance has private access.

if (amount <= 0 || amount > balance)

Правило «нельзя снять больше, чем есть» записано в одном месте — внутри класса. Обойти его снаружи невозможно.

return false;

Метод не молчит: он возвращает false или true — сообщает, получилось или нет. Вызывающий код решает, что делать с отказом. (Позже, в модуле 12, научимся сообщать об ошибке исключением.)

int getBalance()

Геттер — метод, который возвращает значение поля; сеттер — метод, который присваивает полю новое значение. Геттер есть, а сеттера нет. Баланс можно прочитать, но поменять — только через deposit и withdraw.

Инвариант
Правило, которое всегда верно для объекта. У счёта: «баланс ≥ 0». Инкапсуляция нужна, чтобы инвариант нельзя было нарушить снаружи.
Интерфейс объекта
Набор методов, которые видны снаружи (здесь — deposit, withdraw, getBalance). Это «пульт» объекта. Не путай со словом interface из модуля 11 — это родственная, но отдельная штука.

Что даёт инкапсуляция

🛡️

Проверки

Каждое изменение проходит через метод, а метод может сказать «нет». Объект не попадёт в бессмысленное состояние.

👀

Только чтение

Геттер без сеттера — поле можно смотреть, но не менять. С открытым полем так не выйдет.

🔧

Свобода переделать

Захотел хранить баланс в копейках (long) — меняешь класс внутри, а весь код снаружи, который вызывает методы, остаётся прежним.

📍

Одно место правды

Правило записано один раз — в классе. Ошибку ищешь в одном месте, а не по всему проекту.

Детали прячем, действия показываем

Возьмём кофемашину. Внутри у неё куча настроек: до скольких градусов греть воду, сколько грамм зёрен молоть, сколько налить молока (это детали, они часто меняются). Снаружи видна только понятная кнопка: «сделать латте». Это инкапсуляция в чистом виде:

class CoffeeMachine {
    // как именно варить — секрет машины
    private int waterTemperature = 92;
    private int coffeeGrams = 18;
    private int milkMl = 150;

    void makeLatte(String guest) { // что умеет машина — открыто
        System.out.println("Грею воду до " + waterTemperature + "°");
        System.out.println("Мелю " + coffeeGrams + " г зёрен");
        System.out.println("Добавляю " + milkMl + " мл молока — латте для " + guest);
    }
}

Купили другие зёрна — теперь их нужно 20 г? Правишь одну строку внутри CoffeeMachine, а сотня мест в программе, которые вызывают makeLatte(...), даже не замечает. Так устроены и большие программы: каждый класс прячет свои детали и показывает наружу только действия.

Ловушки: «геттер и сеттер на всё»

Новички часто делают так: все поля private, а к каждому — геттер и сеттер, сгенерированные IDEA. Выглядит «по правилам», но посмотри:

class FakeAccount {
    private int balance;

    int getBalance() { return balance; }
    void setBalance(int balance) { this.balance = balance; }   // любое число!
}
Предскажи: чем такой счёт лучше счёта с открытым полем?

Почти ничем. acc.setBalance(-999999) делает то же самое, что acc.balance = -999999. Поле формально закрыто, но дверь в сейф по-прежнему распахнута. Инкапсуляция — не слово private, а защита правил. Сеттер имеет смысл, только если в нём есть проверка или если любое значение поля действительно допустимо.

Правило

Сначала подумай, какие действия нужны объекту снаружи («положить», «снять»), и сделай методы под них. Геттеры — только для того, что действительно нужно читать. Сеттеры — только там, где менять поле напрямую не опасно.

🔎 Для любопытных: геттер, который выдаёт секрет

Помнишь из модулей 6–7: переменная-массив хранит ссылку. Если геттер вернёт ссылку на внутренний массив, снаружи смогут менять его содержимое — в обход всех проверок:

class History {
    private int[] operations = {100, -50, 200};

    int[] getOperations() {
        return operations;                    // отдали ключ от сейфа!
    }
}

// снаружи:
history.getOperations()[0] = 1_000_000;      // поменяли «чужую» историю

Защита — отдавать копию: return Arrays.copyOf(operations, operations.length);. Это называется «защитная копия». Со строками (String) такой проблемы нет: строки неизменяемы, их нельзя испортить через ссылку.

Напиши: «Я прошёл урок 10.1. Придумай класс из жизни (например, термостат или лифт), а я скажу, какие у него поля, какие правила-инварианты и какие методы должны быть открыты».

Коротко

  • Три кита ООП: инкапсуляция, наследование, полиморфизм.
  • Инкапсуляция: поля private, работа с ними — через методы, которые проверяют правила.
  • Публичное поле может испортить кто угодно; правило объекта (инвариант) должен охранять сам объект.
  • Геттер без сеттера — поле только для чтения. Сеттер без проверки — почти то же, что открытое поле.
  • Хороший класс как кофемашина: детали спрятаны, наружу — действия.
