Класс Object: toString, equals, hashCode

У всех классов Java есть общий прародитель — Object. От него каждый класс наследует несколько методов. Три из них ты будешь переопределять постоянно: чтобы объект красиво печатался, честно сравнивался и правильно работал в коллекциях.

Повторение

Object — прародитель всех классов

Если у класса не написано extends, Java молча добавляет extends Object. Значит, любой класс — твой Cat, String, массивы — наследник java.lang.Object. Прямо или через цепочку родителей.

Поэтому у каждого объекта есть унаследованные методы, которых ты не писал. Главные:

МетодЧто делает по умолчаниюПереопределять?

Есть и другие (clone, wait, notify…), но в этом уроке они не нужны. Главная линия урока — toString, equals и hashCode.

toString: как объект выглядит в тексте

Где набирать

Примеры урока — в новом пакете lesson10.l5, кусочки без класса — в main класса Main этого пакета (как — в уроке 10.1). Cat здесь свой, не наследник Animal: с именем и возрастом. Второй пример с Point ниже — не новый класс, а продолжение первого: дописывай hashCode в тот же файл.

Cat cat = new Cat("Мурка", 3);
System.out.println(cat);
Предскажи: что напечатается, если toString не переопределён?

Что-то вроде Cat@1b6d3586: имя класса, @ и шестнадцатеричное число (из hashCode). Для человека — бесполезно. Число каждый раз может быть разным.

println(объект) и склейка "Кот: " + cat сами вызывают у объекта toString(). Переопределим:

class Cat {
    private final String name;
    private final int age;

    Cat(String name, int age) {
        this.name = name;
        this.age = age;
    }

    @Override
    public String toString() {
        return "Cat{name=" + name + ", age=" + age + "}";
    }
}
Cat{name=Мурка, age=3}
public обязательно

В Object метод объявлен как public String toString(). Правило из урока 3: доступ при переопределении нельзя сужать. Напишешь String toString() без public — ошибка attempting to assign weaker access privileges. То же для equals и hashCode.

Для поиска ошибок хороший toString — подарок. Программа повела себя странно, ты печатаешь объекты, чтобы понять, что внутри. Видишь User{name=Ann, role=ADMIN}, хотя ждал User{name=Ann, role=GUEST}, — и сразу понятно, что сломалось. А видишь User@5e2de80c — идёшь в отладчик.

equals: «одинаковые» или «тот же самый»?

Два разных объекта с одинаковыми данными:

Point a = new Point(1, 2);
Point b = new Point(1, 2);
System.out.println(a == b);
System.out.println(a.equals(b));
Предскажи вывод, если в Point нет своего equals

false и false. == сравнивает ссылки — объектов два. А equals из Object устроен так же, как ==. Чтобы точки с одинаковыми координатами считались равными, equals надо переопределить.

Аналогия: две одинаковые книги

У тебя и у друга по экземпляру «Гарри Поттера» одного издания. «Это одна и та же книга?» — нет, два физических экземпляра (== → false). «Это одинаковые книги?» — да, текст тот же (equals → true). Что считать «одинаковым», решаешь ты, когда пишешь equals: для книги — название и издание, а не цвет закладки.

Рецепт equals, который пишут почти все (и генерирует IDEA):

class Point {
    private final int x;
    private final int y;

    Point(int x, int y) { this.x = x; this.y = y; }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;                              // 1
        if (o == null || getClass() != o.getClass()) return false; // 2
        Point other = (Point) o;                                 // 3
        return x == other.x && y == other.y;                   // 4
    }
}
equals(Object o)

Параметр — именно Object, иначе получится перегрузка, а не переопределение (это классическая ловушка, есть в головоломках). @Override её поймает.

1: this == o

Ссылки равны — значит, объект сравнивают сам с собой: сразу «да», дальше можно не смотреть.

2: null или другой класс

С null и с объектом другого класса (например, строкой) точка не равна никогда. Проверка на null обязательна — иначе на шаге 3–4 будет NullPointerException.

3: (Point) o

Приведение типа ссылки: параметр o имеет тип Object, а мы уже уверены, что он ссылается на точку, и хотим читать её поля. Подробно — в уроке 6.

4: сравнение полей

Примитивы — через ==, поля-объекты (строки и т.п.) — через их equals. Удобно: Objects.equals(name, other.name) — он ещё и с null справляется.

Контракт equals

Контракт — обещания, которые должен выполнять любой equals. На них полагаются коллекции и библиотеки:

  • Рефлексивность: x.equals(x) — всегда true.
  • Симметричность: если x.equals(y), то и y.equals(x).
  • Транзитивность: x равен y, y равен z → x равен z.
  • Постоянство: пока объекты не менялись, ответ один и тот же.
  • С null: x.equals(null) — всегда false, без исключений.

Кому переопределять, а кому нет

Частый вопрос: «А для String тоже надо писать equals?» Нет. Авторы JDK уже переопределили его в String, Integer и других классах-«значениях». Писать equals нужно только в своих классах, если их объекты надо сравнивать по содержимому. Две ловушки запомни сразу: у массивов и у StringBuilder equals не переопределён и сравнивает ссылки.

new StringBuilder("ок").equals(new StringBuilder("ок")) — false, а Arrays.equals(new int[]{1}, new int[]{1}) — true. Обе ловушки любят на собеседованиях.

Где equals вызывают за тебя. Списки (модуль 13) внутри вызывают equals: list.contains(x), list.indexOf(x), list.remove(x). Ищешь в корзине свой объект new Product("Хлеб", 50), а у Product нет переопределённого equals — contains вернёт false, даже если такой товар в корзине лежит. Решения: переопределить equals или сделать класс record.

hashCode: номер полки

Самая важная и самая непонятная часть. Разберём медленно.

hashCode — это целое число, которое метод hashCode() вычисляет из полей объекта («считает про себя»). Зачем? Ради скорости поиска. В модуле 13 будут HashMap и HashSet — коллекции, которые находят элемент среди миллиона почти мгновенно. Они делают это в два шага:

  1. Вызывают у объекта метод hashCode() и по возвращённому числу выбирают полку (по-научному — «корзину», bucket).
  2. На этой полке перебирают немногих соседей и сравнивают их через equals.
Аналогия: гардероб в театре

Ты сдаёшь куртку, тебе дают номерок 42. После спектакля гардеробщик не перебирает все 500 курток — он идёт сразу к крючку 42 и смотрит там. Номерок — это hashCode, а «да, это моя куртка» — это equals.

Теперь представь: ты приходишь с правильной курткой в руках (equals скажет «та же»), но номерок тебе выдали случайный — 17. Гардеробщик идёт к крючку 17, там пусто: «Нет вашей куртки». Хотя она висит на 42. Вот что бывает, когда равные объекты дают разный hashCode.

Контракт hashCode

  1. Равные объекты → равные hashCode. Если a.equals(b), то a.hashCode() == b.hashCode(). Это главное правило, его нарушение и ломает поиск.
  2. Обратное не обязано. Разные объекты могут случайно получить одинаковый hashCode — это называется коллизия. Ничего страшного: просто на одной полке окажутся двое, и equals их различит. Плохо только, если коллизий очень много — поиск станет медленным.
  3. Постоянство. Пока объект не менялся, hashCode у него один и тот же.

Отсюда железное правило: переопределил equals — переопредели hashCode, по тем же полям. Самый простой способ:

import java.util.Objects;

class Point {
    // ... поля, конструктор, equals как выше

    @Override
    public int hashCode() {
        return Objects.hash(x, y);    // считает число из всех переданных полей
    }
}
Предскажи: return 42; в hashCode — это нарушение контракта?

Нет, контракт соблюдён: у равных объектов hashCode равны (у всех 42). Но все объекты лягут на одну полку, и быстрый поиск превратится в перебор всего подряд. Корректно, но медленно. А вот return (int) (Math.random() * 100); — нарушение: у одного и того же объекта число меняется.

IDEA напишет за тебя

В классе нажми Alt+Insert → equals() and hashCode(), отметь поля — IDEA сгенерирует оба метода согласованно. Там же есть toString(). Но сначала напиши руками пару раз, чтобы понимать, что там происходит: на собеседовании IDEA не будет.

Коротко: getClass и record

getClass() возвращает сведения о реальном классе объекта — не о типе переменной. Имя класса без пакета даёт getClass().getSimpleName(). Проверим на нашем Cat: он без extends, а значит, наследует Object — и ссылку на кота можно положить в переменную типа Object:

Object o = new Cat("Мурка", 3);   // ярлык Object, объект — кот
System.out.println(o.getClass().getSimpleName());   // Cat, а не Object

Мы уже встречали getClass() в рецепте equals: getClass() != o.getClass() — «объекты одного и того же класса?».

🔎 Для любопытных: getClass в toString родителя и getClass против instanceof в equals

Один toString на всю иерархию. Если дописать в Shop из урока 3 такой метод, он напечатает правильное имя каждого наследника:

class Shop {
    @Override
    public String toString() {
        // Bakery открыт, FlowerShop открыт…
        return getClass().getSimpleName() + " открыт";
    }
}

getClass() или instanceof в equals? Иногда в equals вместо getClass() != o.getClass() пишут if (!(o instanceof Point)) return false; (instanceof — проверка «является ли объект точкой», урок 6). Разница — в наследниках. Если есть ColorPoint extends Point со своим полем цвета, то с instanceof легко нарушить симметричность: point.equals(colorPoint) — true (цветная точка является точкой), а colorPoint.equals(point) — false. С getClass() объекты разных классов просто не равны. Для начала используй вариант с getClass() — его же генерирует IDEA по умолчанию.

record делает всё сам

Помнишь record из модуля 9? Для него компилятор сам генерирует equals, hashCode и toString по всем полям. Для «классов-значений» (точка, деньги, пара логин–пароль) это самый короткий и безопасный путь. Назовём запись PointRec, чтобы она не столкнулась с классом Point выше:

record PointRec(int x, int y) {}   // запись можно объявить прямо внутри main

PointRec a = new PointRec(1, 2);
PointRec b = new PointRec(1, 2);
System.out.println(a);                              // PointRec[x=1, y=2]
System.out.println(a.equals(b));                    // true
System.out.println(a.hashCode() == b.hashCode());   // true
🔎 Для любопытных: присваивание не копирует объект, а clone() — копирует (но лучше без него)

Ещё с модулей 6–7 знаешь: Cat c2 = c1; не создаёт второй объект — переменной c2 присваивается копия ссылки, и обе переменные ссылаются на один объект. Чтобы получить настоящую копию, в Object есть метод clone(). Но он капризный: класс должен «разрешить» копирование (реализовать Cloneable, модуль 11), а копия по умолчанию поверхностная — поля-ссылки (массивы, другие объекты) остаются общими у оригинала и копии.

На практике чаще делают конструктор копирования: Cat(Cat other) { this.name = other.name; this.age = other.age; } — понятно, явно и без сюрпризов. Неизменяемые объекты (record, String) копировать вообще не нужно: их нельзя испортить через общую ссылку.

Проверь себя

Поговори с наставником

Напиши: «Я прошёл урок 10.5. Спроси меня про контракт equals и hashCode так, как спрашивают на собеседовании, и попроси привести пример, что сломается, если переопределить только equals».

Коротко

  • Все классы наследуют Object; от него — toString, equals, hashCode, getClass.
  • toString — для печати; переопределяй, это сильно помогает в отладке и в сообщениях об ошибках.
  • == — тот же объект; equals — равен по смыслу. По умолчанию equals = ==.
  • equals: параметр Object, проверка this, null и класса, приведение, сравнение полей.
  • hashCode выбирает полку, equals сравнивает на полке. Равные объекты → равные hashCode. Переопределяй их только вместе.
  • record генерирует всё сам. Присваивание копирует ссылку, а не объект.
