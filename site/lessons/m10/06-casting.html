Приведение типов и instanceof

В коробке с ярлыком «животное» лежит кот. Как его оттуда достать и попросить помяукать? И что будет, если в коробке окажется собака? Разбираемся с приведением типа ссылок на объекты, проверкой instanceof и исключением ClassCastException.

⏱ 25 минут↕️ upcast / downcast🛠 Мастерская

Повторение

Вверх — само, вниз — явно

Где набирать: классы для этого урока

Создай пакет lesson10.l6 (как — в уроке 10.1) и набери в нём файл Animals.java с классами ниже — на них работают все примеры урока. Кусочки кода набирай в main класса Main этого же пакета.

class Animal {
    void speak() { System.out.println("..."); }
}

class Cat extends Animal {
    @Override
    void speak() { System.out.println("Мяу"); }
    void meow()  { System.out.println("Мур-мяу!"); }
}

class Kitten extends Cat { }

class Dog extends Animal {
    private boolean guard;
    Dog() { }
    Dog(boolean guard) { this.guard = guard; }
    @Override
    void speak() { System.out.println("Гав"); }
    boolean isGuard() { return guard; }
}

class Parrot extends Animal {
    @Override
    void speak() { System.out.println("Привет!"); }
}

В модуле 3 ты приводил числа: int → long само (безопасно), double → int только явно, со скобками (можно потерять данные). С объектами похожая история, только двигаемся по иерархии наследования:

Cat cat = new Cat();
Animal a = cat;          // восходящее (upcasting): кот → животное, само
Cat back = (Cat) a;      // нисходящее (downcasting): животное → кот, явно
back.meow();             // ✔ теперь можно
Аналогия: переноска для животных

Ты сажаешь кота в переноску с надписью «Животное» — никаких проблем (вверх). Потом ты открываешь переноску и говоришь: «Я точно знаю, тут кот — сейчас поглажу его за ушком» — это (Cat) a (вниз). Если там правда кот — всё хорошо. Если там собака… в Java на этот случай есть специальное исключение.

Важно: приведение не превращает объект в другой. Кот остаётся котом. Меняется только ярлык — тип ссылки (переменной), через которую ты на него смотришь, а значит, и список методов, которые компилятор разрешит вызвать.

ClassCastException

Компилятор верит тебе на слово: (Cat) a он пропустит, раз переменная типа Animal вообще может ссылаться на кота. А проверяет JVM — во время работы:

public class Oops {
    public static void main(String[] args) {
        Animal a = new Dog();
        Cat c = (Cat) a;
        c.meow();
    }
}
Предскажи: скомпилируется? Что будет при запуске?

Скомпилируется, но при запуске программа упадёт на строке 4 — переменная ссылается на собаку, а мы пообещали кота. До meow() дело не дойдёт.

Читаем stack trace, как в модуле 9: исключение ClassCastException («ошибка приведения класса»), причина — «Dog нельзя привести к Cat», место — Oops.java, строка 4. Хвост про «unnamed module» — служебные подробности, его можно пропустить.

А если классы вообще не родственники, ошибку поймает уже компилятор:

Cat cat = new Cat();
// ✗ incompatible types: Cat cannot be converted to Dog
Dog dog = (Dog) cat;
// ✗ тоже: кот никогда не бывает строкой
String s = (String) cat;

Переменная типа Cat никогда не может ссылаться на собаку — компилятор это знает и не даёт даже попробовать. Приведение имеет смысл только вдоль одной ветки иерархии.

instanceof: сначала посмотри, потом бери

Чтобы не падать, перед приведением спрашивают: «этот объект — кот?». Оператор instanceof («является экземпляром» класса) возвращает true или false:

Animal a = new Dog();           // поменяй на new Cat() и запусти ещё раз
if (a instanceof Cat) {
    Cat c = (Cat) a;            // теперь приведение безопасно
    c.meow();
} else {
    System.out.println("Это не кот");
}

В настоящей программе объект приходит «откуда-то»: из массива, из параметра метода, из файла — и заранее не знаешь, кто там. Тут-то проверка и нужна.

Три правила instanceof, которые спрашивают на собеседованиях:

  • Наследники тоже подходят. Если Kitten extends Cat, то для котёнка a instanceof Cat — true. Котёнок является котом. И a instanceof Animal — тоже true.
  • null — никогда. null instanceof Cat — false, без исключения. Отдельно проверять на null перед instanceof не нужно.
  • Неродственные типы — ошибка компиляции. cat instanceof Dog, где cat типа Cat, не скомпилируется: ответ и так всегда false.
Предскажи: Animal a = new Kitten(); Что даст a instanceof Dog, a instanceof Cat, a instanceof Kitten?

false, true, true. Котёнок — не собака; котёнок является котом (через наследование); и, конечно, котёнком. instanceof проверяет «является», а не «в точности этот класс». Для точного совпадения есть a.getClass() == Cat.class — для котёнка это false.

Что за Cat.class? Так в коде записывают сам класс Cat — его «паспорт», тот же объект-описание, который getClass() (урок 5) возвращает у любого кота. a.getClass() у котёнка вернёт паспорт Kitten, а он не равен паспорту Cat.

Pattern matching: проверка и приведение за раз

Писать Cat три раза подряд (в instanceof, в типе переменной, в скобках) утомительно. С Java 16 можно короче — сопоставление с образцом (pattern matching):

// проверили И сразу получили переменную c типа Cat
if (a instanceof Cat c) {
    c.meow();
}
a instanceof Cat c

Если a ссылается на кота, Java сама объявляет переменную c типа Cat и инициализирует её уже приведённой ссылкой. Если нет — условие false, и c не появляется.

{ c.meow(); }

Переменная c видна только там, где проверка точно прошла, — внутри if. За его пределами её нет (область видимости из модуля 7).

Её можно сразу использовать дальше в условии через && — ленивое «и» из модуля 3 гарантирует, что правая часть выполнится только для собаки:

if (a instanceof Dog d && d.isGuard()) {
    System.out.println("Пёс охраняет двор");
}
Предскажи: скомпилируется ли if (a instanceof Dog d || d.isGuard())?

Нет. С || правая часть выполняется как раз тогда, когда левая ложна — то есть когда a не собака, и переменной d нет. Компилятор это видит: cannot find symbol: variable d.

🛠 Мастерская: перепись зоопарка

Задача (почти как m10-t05): есть массив Animal[] zoo. Посчитать кошачьих (котята тоже коты!), собак и среди собак — сторожевых. Пройдём по шаблону Мастерской.

  1. Пойми задачу. Вход: массив животных разных классов. Выход: три числа. Пример: [Кот Мурка, Собака Шарик (сторож), Котёнок Пушок, Собака Бобик (домашняя)] → 2 кошачьих, 2 собаки, 1 сторож. Граничный случай: пустой массив → 0 0 0.
  2. Реши руками. Беру каждого по очереди: Мурка — кот, кошачьих 1. Шарик — собака, собак 1, сторож — сторожей 1. Пушок — котёнок, но котёнок является котом: кошачьих 2. Бобик — собака, собак 2, не сторож.
  3. Роли переменных. i — шагающая по массиву; cats, dogs, guards — три счётчика, все начинаются с 0.
  4. Псевдокод. «Для каждого животного: если оно кот — cats + 1; иначе если оно собака — dogs + 1, и если она сторож — guards + 1».
  5. Код — перевод псевдокода строка в строку. Проверь трассировкой ниже.

Когда instanceof — тревожный знак

instanceof полезен, но если код превращается в цепочку «если кот — делай так, если собака — эдак, если попугай — вот так», это почти всегда значит, что полиморфизм не использован:

// ✗ плохо: каждый новый зверь — правка этого метода
if (a instanceof Cat) System.out.println("Мяу");
else if (a instanceof Dog) System.out.println("Гав");
else if (a instanceof Parrot) System.out.println("Привет!");

// ✔ хорошо: каждый зверь сам знает свой голос (урок 4)
a.speak();
Правило большого пальца

Поведение, которое различается по типам, — переноси в переопределённый метод. instanceof оставь для случаев, когда нужно отобрать объекты одного вида (посчитать собак, найти все электромобили в гараже) или когда класс чужой и добавить в него метод нельзя. Ещё одно законное место — equals.

Коротко

  • Вверх по иерархии (кот → животное) — автоматически и безопасно.
  • Вниз (животное → кот) — только явно (Cat) a; если объект не тот — ClassCastException при запуске.
  • Приведение между неродственными типами — ошибка компиляции.
  • instanceof проверяет «является» по всей цепочке; для null — false.
  • Java 16+: if (a instanceof Cat c) — проверка и приведение за раз.
  • Цепочка instanceof вместо переопределённого метода — повод использовать полиморфизм.
