Композиция против наследования

Наследование — мощный инструмент, и поэтому им легко злоупотребить. Есть второй способ переиспользовать код: не «быть» другим классом, а «иметь» его внутри. Учимся выбирать между «является» и «имеет» — и заглядываем в модуль 11.

⏱ 20 минут🧩 has-a и is-a🌉 мостик к интерфейсам

Повторение

«Является» и «имеет»

В уроке 2 был тест: «A является B?» Если ответ «нет, A имеет B» — наследование не подходит. Для «имеет» (по-английски has-a) используют композицию: один объект хранит в поле ссылку на другой объект и поручает ему работу — вызывает его методы.

Где набирать

Пакет lesson10.l7; проверять машину — в main класса Main рядом (как — в уроке 10.1). Например: Car car = new Car(); car.start(); car.drive();

class Engine {
    private boolean running;

    void start() { running = true;  System.out.println("Двигатель: врум!"); }
    void stop()  { running = false; System.out.println("Двигатель заглушен"); }
    boolean isRunning() { return running; }
}

class Car {
    private final Engine engine = new Engine();   // машина ИМЕЕТ двигатель

    void start() {
        System.out.println("Поворачиваю ключ");
        engine.start();                           // поручаем работу детали
    }

    void drive() {
        if (engine.isRunning()) System.out.println("Едем!");
        else System.out.println("Сначала заведи двигатель");
    }
}
Композиция
Объект собран из других объектов: ссылки на них хранятся в его полях. «Машина состоит из двигателя, колёс, руля».
Делегирование
Объект не делает работу сам, а поручает её своей части: car.start() вызывает engine.start().
Предскажи: а что было бы, если написать class Car extends Engine?

Скомпилируется! И даже заведётся. Но у машины появятся все методы двигателя: car.isRunning() ещё куда ни шло, а если у Engine есть setRpm(), replaceSparkPlug() — их сможет вызвать любой водитель прямо у машины. И главное — машину можно будет передать туда, где ждут двигатель (в переменную или параметр типа Engine): Engine e = new Car();. Смысл сломан: машина — не двигатель.

Почему наследованием легко навредить

🔗

Жёсткая связь

Наследник зависит от внутренностей родителя. Поменял родитель свой метод — у наследников может тихо сломаться поведение. Это называют проблемой «хрупкого базового класса».

🎒

Берёшь всё

Наследник получает все публичные методы родителя, даже ненужные и опасные. Отказаться от части нельзя.

☝️

Только один родитель

Унаследовал от Engine — от Radio уже не получится. Композицией можно собрать сколько угодно частей.

🔒

Навсегда

Родитель выбирается при написании кода. А часть в поле можно заменить: передать конструктору аргументом другой двигатель — бензиновый или электрический.

Аналогия: гены и LEGO

Наследование — как гены. Ребёнок получает от родителей всё сразу, выбрать «только глаза мамы» нельзя, и поменять потом тоже нельзя.

Композиция — как LEGO. Собираешь модель из нужных деталей, а надоело колесо — снял и поставил другое. Модель не «является» колесом, она его «имеет».

🔎 Для любопытных: подвох «квадрат — это прямоугольник»

В геометрии квадрат является прямоугольником. Но если у класса Rectangle есть методы setWidth и setHeight, начинаются странности: код, который получил «прямоугольник», ставит ширину 5 и высоту 10 и ждёт площадь 50, а квадрат при смене высоты меняет и ширину — площадь 100. Наследник нельзя подставить вместо родителя, не сломав ожиданий. Правило «наследник должен работать везде, где работает родитель» называется принцип подстановки Лисков (буква L в SOLID — спросят на собеседовании). Поэтому в задаче m10-t02 фигуры неизменяемые: размеры задаются только в конструкторе, и проблема не возникает.

Как выбирать

Опытные разработчики говорят: «Предпочитай композицию наследованию». Это не запрет наследования, а порядок вопросов:

  1. Честно ли «A является B» — всегда, в любой ситуации? Если хоть иногда нет — композиция.
  2. Можно ли подставить A везде, где ждут B, и ничего не сломается? Если нет — композиция.
  3. Нужны ли A все методы B? Если половина лишняя или опасная — композиция.
  4. Все ответы «да» — наследуй смело. Классика: иерархии «животные», «фигуры», «транспорт», «сотрудники».

Частая ошибка в больших проектах — «божественный» родитель GameObject на 2000 строк, от которого наследуется всё подряд, потому что «так проще достать нужный метод». Через год никто не понимает, что в нём происходит. Помощников лучше держать отдельными классами и подключать полями — композицией.

Мостик в модуль 11: «умеет»

Последняя загадка модуля. Утка умеет летать и плавать. Самолёт умеет летать. Рыба умеет плавать. Какого общего родителя им дать?

Наследование («является») тут не работает: у класса один родитель, а у утки умений два, и самолёт с уткой — совсем не родня. Нужно третье отношение — «умеет» (can-do). В Java для него есть интерфейсы: class Duck implements Flyer, Swimmer — класс реализует интерфейсы, и их у класса может быть сколько угодно. Это тема модуля 11, вместе с абстрактными классами: «полуготовыми» родителями, у которых часть методов только объявлена, без тела (абстрактные методы).

Три отношения — три инструмента

является → наследование (extends), этот модуль. имеет → композиция (поле), этот урок. умеет → интерфейс (implements), модуль 11. Полиморфизм работает и с интерфейсами: переменная типа Flyer сможет хранить ссылку и на утку, и на самолёт.

Проверь себя

Поговори с наставником

Напиши: «Я прошёл урок 10.7. Давай спроектируем вместе классы для интернет-магазина: я предложу, где наследование, а где композиция, а ты покритикуй».

Коротко

  • «Является» → наследование. «Имеет» → композиция: объект в поле + делегирование.
  • Наследование связывает жёстко: берёшь всё, один родитель, навсегда.
  • Композиция гибче: сколько угодно частей, части можно заменять.
  • Наследуй, только если «является» честно и наследника можно подставить вместо родителя.
  • «Умеет» → интерфейсы, модуль 11.
