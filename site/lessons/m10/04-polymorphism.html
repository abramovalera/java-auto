Полиморфизм: одна команда — разное поведение

Самая мощная идея ООП. В переменную типа «животное» можно положить ссылку на кота или собаку, вызвать метод «подай голос» — и каждый ответит по-своему. Код, который знает только про «животное», вдруг начинает работать с любыми зверями, даже придуманными завтра.

Повторение

Животное в переменной — кот в объекте

До сих пор тип переменной и тип объекта совпадали: Cat c = new Cat();. Но раз класс Cat наследует Animal (кот является животным), Java разрешает и так:

Animal a = new Cat();    // переменная типа Animal, объект — Cat
a.speak();

Тут легко запутаться, поэтому разделим два понятия:

Тип переменной (Animal)
Что написано слева. Это «ярлык на коробке». Компилятор смотрит только на него и решает, какие методы вообще можно вызвать.
Тип объекта (Cat)
Класс объекта, который создан оператором new справа; переменная хранит ссылку на этот объект. Это то, что реально лежит в коробке. Во время работы программы JVM смотрит на него и решает, чья версия метода выполнится.
Предскажи: что напечатает a.speak() — «...» от Animal или «Мяу» от Cat?

«Мяу». Ярлык на коробке — «животное», но внутри кот, и голос подаёт кот. Java выбирает версию метода по реальному объекту, а не по типу переменной.

Компилятор смотрит на ярлык

Обратная сторона: через переменную типа Animal можно вызвать только то, что есть у любого животного.

Animal a = new Cat();
a.speak();      // ✔ speak есть у Animal
a.meow();       // ✗ cannot find symbol: method meow() — у Animal такого нет

Почему так строго? Компилятор не запускает программу и не знает, что a будет ссылаться именно на кота: строчкой ниже переменной могут присвоить ссылку на собаку (a = new Dog();). Он гарантирует только то, что верно для всех возможных животных. Как «достать кота из коробки» и вызвать meow(), разберём в уроке 6.

Аналогия: оркестр

Дирижёр не знает, кто как играет. Он поднимает палочку и показывает всем одно: «играй!». Скрипка играет свою партию, барабан — свою, флейта — свою. Команда одна, исполнение — у каждого своё. Дирижёру (коду) достаточно знать, что перед ним «музыкант» (родительский тип). Так работает полиморфизм — «много форм» по-гречески: вызов метода один, а выполняется версия того объекта, на который указывает ссылка.

Массив разных зверей

Вот где полиморфизм раскрывается. Массив типа Animal[] может хранить ссылки и на котов, и на собак. Один цикл — и каждый подаст свой голос:

public class Choir {
    public static void main(String[] args) {
        Animal[] zoo = { new Cat(), new Dog(), new Cat() };
        for (int i = 0; i < zoo.length; i++) {
            zoo[i].speak();
        }
    }
}
// Animal, Cat и Dog — из урока 3: "...", "Мяу", "Гав"
Предскажи вывод

«Мяу», «Гав», «Мяу». В коде цикла написано одно и то же zoo[i].speak(), а выполняются разные версии метода — по объекту, на который ссылается ячейка.

Пройди цикл по шагам и на каждом витке впиши, из какого класса возьмётся метод speak().

Динамическая диспетчеризация
Выбор версии переопределённого метода во время работы программы по реальному объекту. «Динамическая» — потому что решается на ходу, а не при компиляции. Иногда говорят «позднее связывание».

Зачем это нужно: код, который не надо переписывать

Метод с параметром родительского типа принимает в качестве аргумента объект любого наследника:

static void examine(Animal a) {
    System.out.println("Осмотр:");
    a.speak();
}

// вызовы:
examine(new Cat());     // Осмотр: Мяу
examine(new Dog());     // Осмотр: Гав
// Parrot написали через год, а examine не менялся:
examine(new Parrot());  // Осмотр: Привет!

Завтра появится попугай — достаточно объявить класс Parrot extends Animal и переопределить в нём speak(). Ни examine, ни цикл с хором менять не придётся. Без полиморфизма пришлось бы писать цепочку if: «если кот — мяукай, если собака — лай…» и дописывать её с каждым новым зверем.

В магазине и в играх — на каждом шагу

Касса магазина принимает оплату методом checkout(Payment p) — значит, подходит любой способ: CardPayment, CashPayment, QrPayment. Каждый способ по-своему считает комиссию, а касса написана один раз. А игра держит все уровни как «просто уровни» и вызывает у каждого один и тот же метод — выполняется код конкретного уровня. В задаче m10-t08 ты соберёшь такую мини-игру сам.

Что НЕ полиморфно

Полиморфно работают только переопределённые методы объекта. Три вещи ведут себя иначе — и это любимые вопросы собеседований (подробно — на странице головоломок):

📦

Поля

Если и у родителя, и у наследника есть поле name, то a.name берётся по типу переменной, а не объекта. Поля не переопределяются — ещё одна причина держать их private и работать через методы.

🏛️

static-методы

Принадлежат классу, а не объекту. Одноимённый static-метод наследника прячет родительский, но не переопределяет: вызов выбирается по типу переменной при компиляции.

🔒

private-методы

Наследник их не видит, поэтому его метод с тем же именем — просто другой метод. Родитель внутри себя по-прежнему вызывает свой private-метод.

🔎 Для любопытных: перегрузка выбирается по ярлыку, переопределение — по объекту

Есть два метода: static void feed(Animal a) и static void feed(Cat c). Вызов Animal a = new Cat(); feed(a); выберет feed(Animal)! Перегрузку компилятор выбирает заранее, по типу переменной. А вот внутри, если вызвать a.speak(), выполнится кошачья версия — переопределение решается при запуске. Две разные системы выбора в одной строчке — классика собеседований.

Коротко

  • Переменная родительского типа может хранить ссылку на объект наследника: Animal a = new Cat();
  • Компилятор смотрит на тип переменной: что можно вызвать.
  • JVM смотрит на объект: чья версия переопределённого метода выполнится (динамическая диспетчеризация).
  • Массив Animal[] + цикл + переопределённый метод = каждый объект ведёт себя по-своему без всяких if.
  • Поля, static- и private-методы не полиморфны.
