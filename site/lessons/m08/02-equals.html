Сравнение строк: == против equals

Самый популярный вопрос на собеседовании по Java. Пользователь ввёл «да», а программа уверена, что это не «да». Разберёмся почему — до последней стрелки в памяти.

⏱ 20 минут🎯 классика собеседований🧠 память по шагам

Повторение

Загадка: «да» — это не «да»

Программа спрашивает, продолжать ли. Запусти её в IDEA, введи да — и удивись:

import java.util.Scanner;

public class AskUser {
    public static void main(String[] args) {
        Scanner sc = new Scanner(System.in);
        System.out.print("Продолжить? ");
        String answer = sc.nextLine();
        if (answer == "да") {
            System.out.println("Продолжаем!");
        } else {
            System.out.println("Стоп.");
        }
    }
}

Ты ввёл ровно «да», без пробелов. Строки одинаковые. Почему == говорит «нет»?

Подсказка — в повторении. Для массивов a == b давал false, хотя внутри одно и то же. Строка — тоже объект. Значит…

== сравнивает номерки, equals — содержимое

Для объектов оператор == — это сравнение по ссылке: «это один и тот же объект?» — то есть смотрят ли две стрелки в одно место. Вызов метода equals — сравнение по содержимому, ответ на другой вопрос: «одинаковое ли у них содержимое?» — те же ли символы в том же порядке.

Аналогия: две одинаковые книги

У тебя и у друга по экземпляру «Гарри Поттера». Это одна и та же книга? Нет: два разных экземпляра на разных полках (== → false). А текст в них одинаковый? Да (equals → true). Если же друг держит в руках твой экземпляр — тогда и == → true.

Исправление — одно слово: вызываем метод equals у объекта answer и передаём аргументом литерал "да":

if (answer.equals("да")) {         // сравниваем буквы, а не номерки
    System.out.println("Продолжаем!");
}
Правило на всю жизнь

Строки (и любые объекты) сравнивай по содержимому — через equals. == — только для примитивов (int, char, boolean…) и в редком случае, когда тебе нужно именно «тот же самый объект».

Почему == иногда «работает»: пул строк

Самое коварное: вот этот код печатает true. Из-за этого многие новички думают, что == для строк годится.

String a = "Java";
String b = "Java";
System.out.println(a == b);   // true (?!)

Дело в пуле строк (string pool). Все строки-литералы — то, что написано в коде в кавычках, — JVM кладёт в особое место кучи и хранит по одному экземпляру. Встретила "Java" второй раз — не создаёт новый объект, а отдаёт ссылку (номерок) на уже существующий. Это безопасно, потому что строки неизменяемы: никто не испортит общую строку.

Аналогия: доска объявлений

В подъезде висит одно объявление «Не курить». Жильцам не печатают по личной копии — все смотрят на одну бумажку. Пул строк — такая доска для литералов. А new String("Не курить") — это кто-то отксерил объявление себе домой: текст тот же, бумажка другая.

Строки, которые появились во время работы программы — ввод через Scanner, склейка переменных, строки, которые вернули вызовы substring, toUpperCase и т. п., — в пул не попадают. Это новые объекты в обычной части кучи. Пройди по шагам:

new String("Java") в живом коде почти не пишут — он нужен как раз для таких демонстраций и вопросов на собеседовании. В реальности «разные объекты с одинаковым текстом» получаются сами: из Scanner, из файла, из ответа сервера.

String a = "Java"; String part = "Ja"; String b = part + "va"; — что даст a == b? А a.equals(b)?

a == b → false: выражение со склейкой переменной вычисляется во время работы программы и создаёт новый объект вне пула. a.equals(b) → true: содержимое то же. А вот "Ja" + "va" == "Java" даст true: склейку двух литералов компилятор делает заранее, ещё при компиляции, и в байт-коде остаётся готовый литерал «Java» из пула. Вот почему == для строк — лотерея.

🔎 Для любопытных: intern() — положить строку в пул вручную

Метод intern() возвращает «пуловую» версию строки: если такой текст в пуле есть — ссылку оттуда, если нет — кладёт строку в пул. Поэтому (part + "va").intern() == "Java" → true. В обычном коде это не нужно, но на собеседовании иногда спрашивают «что такое intern».

И ещё тонкость: если переменная объявлена как final String part = "Ja";, она становится константой, и part + "va" тоже вычисляется при компиляции — тогда == снова даст true. Ещё одна причина не полагаться на ==.

Без учёта регистра и без NullPointerException

equalsIgnoreCase — «Да», «ДА» и «да» — одно и то же

String answer = "ДА";
System.out.println(answer.equals("да"));            // false — регистр важен
System.out.println(answer.equalsIgnoreCase("да"));  // true
System.out.println(answer.toLowerCase().equals("да")); // true — тот же эффект

Если в переменной может оказаться null

equals — метод объекта: его вызывают у объекта и передают аргумент. Если объекта нет, вызвать метод не у кого:

String answer = null;
System.out.println("да".equals(answer));   // false — спокойно
System.out.println(answer.equals("да"));   // 💥 NullPointerException
"да".equals(answer)

Метод вызываем у строкового литерала — он точно существует, а answer передаём аргументом. Если answer окажется null, метод просто вернёт false. Такой порядок иногда называют «условия Йоды»: «да равно ли ответу?» — звучит странно, зато безопасно.

answer.equals("да")

Если answer — null, вызвать метод не у кого — это всё равно что прийти в гардероб без номерка и требовать пальто: NullPointerException.

Что будет: String s = null; System.out.println(s == null); ?

true, и никакого исключения. Проверять «есть ли объект» как раз нужно сравнением по ссылке ==: null — это не объект, у него нет «содержимого», есть только «номерка нет». Так что правило «строки — через equals» не мешает писать if (s == null).

Где это встретится в тестах

В тестах сравнение строк — каждая вторая строчка. И там то же разделение: сравнение по ссылке («тот же объект») и по содержимому («то же содержимое»):

Проверка в JUnit / AssertJЧто сравнивает внутри
assertEquals("Корзина", title)equals — содержимое ✅
assertThat(title).isEqualTo("Корзина")equals — содержимое ✅
assertThat(title).isEqualToIgnoringCase("корзина")equalsIgnoreCase
assertSame(expected, actual)== — тот же объект (нужно редко)

JUnit и AssertJ мы разберём в модуле 17. Сейчас важно: когда тест пишет «ожидали Корзина, получили Корзина» и всё равно падает — первое, что проверяешь, это невидимые пробелы и регистр. Об этом — в следующем уроке (trim, strip).

🔎 Для любопытных: а как сравнить «больше-меньше»? compareTo

Для сортировки по алфавиту есть вызов a.compareTo(b). Метод возвращает число: отрицательное, если a по алфавиту раньше, ноль — если строки равны, положительное — если позже. "apple".compareTo("banana") → −1. Знаки < и > к строкам не применяются вообще — не скомпилируется. Пригодится в модуле 13, когда будем сортировать списки.

Проверь себя

Тренировка к собеседованию

Напиши наставнику: «Спроси меня, как на собеседовании: чем == отличается от equals для строк и почему "Java" == "Java" иногда true. Я отвечу своими словами, а ты придирайся».

Коротко

  • == для объектов — сравнение по ссылке (тот же ли объект), equals — сравнение по содержимому.
  • Строки сравнивай по содержимому — вызовом equals. Всегда.
  • Литералы хранятся в пуле по одному экземпляру — поэтому "a" == "a" бывает true. Строки из Scanner, склейки с переменными и new String — новые объекты.
  • equalsIgnoreCase — без учёта регистра. "да".equals(x) не упадёт, даже если x — null.
  • Проверка «объекта нет» — x == null.
