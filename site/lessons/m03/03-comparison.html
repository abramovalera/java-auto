Сравнения и boolean

Программы постоянно задают вопросы: «хватает ли денег?», «совпал ли пароль?», «есть ли товар на складе?». Ответ на такой вопрос — true или false. Учимся задавать вопросы правильно — и узнаём, почему 0.1 + 0.2 не равно 0.3.

Повторение

Вопрос, на который ответ — да или нет

В модуле 2 ты познакомился с типом boolean: у него всего два значения, true (истина, «да») и false (ложь, «нет»). Откуда они берутся в программах? Чаще всего — из сравнений: выражений с операторами сравнения.

ОператорВопросПримерРезультат
==равно?5 == 5true
!=не равно?5 != 5false
>больше?7 > 3true
<меньше?7 < 3false
>=больше или равно?18 >= 18true
<=меньше или равно?20 <= 18false

Сравнение — тоже выражение, просто его значение имеет тип boolean. Значит, его можно напечатать или присвоить переменной типа boolean — положить ответ в коробку:

int age = 20;
boolean isAdult = age >= 18;
System.out.println(isAdult);           // true
System.out.println(age < 14);          // false
System.out.println("Взрослый: " + isAdult);   // Взрослый: true
Это сердце любой проверки

«Пароль совпал с сохранённым?», «баланс не меньше суммы перевода?» — за каждой такой проверкой стоит сравнение. Даже тесты на JUnit из модуля 17 в конце задают вопрос «то, что получилось, равно тому, что ожидали?»: assertEquals(391, result) внутри сравнивает два значения. Тест зелёный — ответ true, красный — false. Сравнения ты будешь писать каждый день.

= и == — не перепутай

Самая частая ошибка новичков (и не только):

📥

x = 5

Присваивание: переменной x присваивается 5 — «положи 5 в x». Это команда.

❓

x == 5

Сравнение: выражение «в x лежит 5?». Это вопрос, ответ — true или false.

int x = 7;
boolean isFive = x = 5;    // ошибка компиляции!

IDEA подчеркнёт ошибку ещё до запуска:

А javac (и проверка на сайте) напишет так:

Oops.java:2: error: incompatible types: int cannot be converted to boolean
        boolean isFive = x = 5;
                           ^

Компилятор спасает: x = 5 — это присваивание, и его значение — число 5, а переменную boolean числом не инициализируешь. Правильно: boolean isFive = x == 5;

Запоминалка: одно = — «положи», два == — «спроси». Вопросу нужно больше знаков, чем ответу 🙂

Что с чем можно сравнивать

  • Числа разных типов — можно: 5 == 5.0 → true. Java расширит int до double, как в арифметике.
  • Символы — тоже, по их кодам: 'a' < 'b' → true (97 < 98). Но осторожно: 'a' < 'B' → false, потому что у больших латинских букв коды меньше (B — 66). А 'A' == 65 → true.
  • boolean — только на равенство: true == false → false. А «больше-меньше» у true и false не бывает — true > false не скомпилируется.
Хотим проверить, что x от 1 до 10. Скомпилируется ли boolean ok = 1 < x < 10; ?

Нет! В математике так пишут, а в Java сравнения выполняются по одному, слева направо. Сначала вычисляется выражение 1 < x → получается значение типа boolean, например true. Потом true < 10 — сравнить «да» с числом нельзя. javac скажет bad operand types for binary operator '<', а IDEA — так:

Ловушка: 0.1 + 0.2 != 0.3

System.out.println(0.1 + 0.2);           // 0.30000000000000004
System.out.println(0.1 + 0.2 == 0.3);    // false (!)

Это не ошибка Java — так ведут себя дробные числа почти во всех языках. Компьютер хранит числа в двоичной системе (из нулей и единиц), а в ней 0.1 нельзя записать точно — получается бесконечная дробь, которую приходится обрезать.

Аналогия: треть торта

Попробуй записать 1/3 десятичной дробью: 0.3333… — бесконечно. На бумажке хватит места, скажем, для 0.3333. Сложи три таких: 0.9999, а не 1. Так и компьютер: 0.1 для него — «бесконечная дробь», и крошечная погрешность вылезает при сложении.

Правило: дробные числа не сравнивают через ==. Вместо этого проверяют, что они «достаточно близки» — разница меньше крошечного допуска:

double sum = 0.1 + 0.2;
boolean almostEqual = Math.abs(sum - 0.3) < 0.000001;   // true

Math.abs — метод, который возвращает модуль числа (отбрасывает минус); класс Math разберём в уроке 3.6. Кстати, в JUnit для дробей так и пишут: assertEquals(0.3, sum, 0.000001) — третий аргумент и есть допуск.

А деньги?

Из-за таких погрешностей деньги в настоящих программах не хранят в double: используют копейки в long или специальный класс BigDecimal. В учебных задачах double для цен — нормально.

Строки через == — пока только предупреждение

Хочется сравнить строки так же, как числа: answer == "да". Иногда это даже работает… и именно поэтому опасно.

Scanner scanner = new Scanner(System.in);
String answer = scanner.next();             // ввели: да
System.out.println(answer == "да");         // false (!!)
System.out.println(answer.equals("да"));    // true

Запусти, введи в консоли да и нажми Enter:

Вспомни стек и кучу из модуля 2: строка — это объект в куче, а в переменной лежит только ссылка на него. Оператор == для объектов сравнивает ссылки — «это один и тот же объект?», а не «одинаковый ли текст?». Строка, которую ввели с клавиатуры, — новый объект, поэтому ответ false, хотя буквы те же.

Запомни на будущее

Текст строк сравнивают методом .equals(): answer.equals("да") — вызываем метод equals у объекта answer и передаём аргумент "да". Почему так и когда == «случайно» работает — подробно разберём в модуле 8 «Строки».

Коротко

  • Шесть операторов сравнения: == != > < >= <=. Результат — boolean: true или false.
  • = — оператор присваивания (кладёт), == — оператор сравнения (спрашивает).
  • Цепочка 1 < x < 10 не работает — сравнения по одному.
  • double не сравнивают через ==: проверяют, что разница меньше допуска.
  • Строки сравнивают через .equals(), а не == (подробно — модуль 8).
