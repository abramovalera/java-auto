SOLID: пять принципов хорошего дизайна

Программа работает — это половина дела. Вторая половина: через месяц в неё нужно добавить новую фичу, и не сломать старые. Пять коротких правил SOLID помогают раскладывать код по классам так, чтобы изменения были маленькими и безопасными.

Повторение

Что такое SOLID и зачем он нужен

Дизайн кода (или архитектура в малом) — это то, как код разложен по классам и кто из них от кого зависит. Компилятору всё равно: программа из одного огромного класса работает так же, как из десяти маленьких. Разница видна позже — когда код нужно менять.

А менять его нужно всегда. Заказчик просит новый способ оплаты, бухгалтерия — другой формат чека, тестировщик находит баг. Хороший дизайн — это когда каждое такое изменение затрагивает одно место и не ломает соседей.

Аналогия: ремонт в квартире

В хорошо сделанной квартире, чтобы поменять люстру, не нужно долбить стену и отключать воду. Электрика отдельно, сантехника отдельно, люстра вкручивается в стандартный патрон. В плохо сделанной всё замуровано вместе: тронешь розетку — потечёт кран.

SOLID — это пять принципов объектно-ориентированного дизайна. Их собрал программист Роберт Мартин (его все зовут «дядя Боб»), а из первых букв сложилось слово solid — «прочный»:

🎯

S — Single Responsibility

Принцип единственной ответственности: одна причина для изменения.

🔌

O — Open/Closed

Открыт для расширения, закрыт для изменения.

🔁

L — Liskov Substitution

Наследник подставляется вместо родителя без сюрпризов.

✂️

I — Interface Segregation

Маленькие интерфейсы лучше одного толстого.

🔃

D — Dependency Inversion

Зависеть от интерфейса, а не от конкретного класса.

Сразу честно: это ориентиры, а не законы. Компилятор за нарушение SOLID не ругается, и опытные программисты иногда сознательно их нарушают. Новичку важнее всего две буквы — S и D: они дают больше всего пользы каждый день. Остальные три чаще всего вырастают из них сами.

S — одна причина для изменения

Принцип единственной ответственности (Single Responsibility Principle, SRP): у класса должна быть одна причина для изменения. Не «один метод», а одна забота, одна группа людей, которая может прийти и попросить его поменять.

Вот класс заказа в интернет-магазине. Он умеет всё:

import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.ArrayList;
import java.util.List;

record Item(String name, int price) { }

class Order {
    private final List<Item> items = new ArrayList<>();

    void add(Item item) {
        items.add(item);
    }

    int total() {                                   // 1. считает сумму
        int sum = 0;
        for (Item item : items) {
            sum += item.price();
        }
        return sum;
    }

    void printReceipt() {                           // 2. печатает чек
        for (Item item : items) {
            System.out.println(item.name() + " — " + item.price() + " ₽");
        }
        System.out.println("Итого: " + total() + " ₽");
    }

    void saveToFile(Path file) throws IOException { // 3. сохраняет в файл
        Files.writeString(file, "Итого: " + total());
    }
}

Посчитаем, кто может попросить изменить этот класс. Маркетологи — правила подсчёта (скидки, акции). Бухгалтерия — вид чека. Тот, кто отвечает за хранение, — формат файла или переезд в базу данных. Три разных причины — три ответственности в одном классе. Правка чека может случайно сломать подсчёт суммы, а для теста подсчёта придётся тащить за собой файлы.

Делим по заботам:

import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.ArrayList;
import java.util.List;

record Item(String name, int price) { }

class Order {                          // только данные заказа и сумма
    private final List<Item> items = new ArrayList<>();

    void add(Item item) {
        items.add(item);
    }

    List<Item> items() {
        return List.copyOf(items);     // наружу — копия только для чтения
    }

    int total() {
        int sum = 0;
        for (Item item : items) {
            sum += item.price();
        }
        return sum;
    }
}

class ReceiptPrinter {                 // только вид чека
    void print(Order order) {
        for (Item item : order.items()) {
            System.out.println(item.name() + " — " + item.price() + " ₽");
        }
        System.out.println("Итого: " + order.total() + " ₽");
    }
}

class OrderStorage {                   // только сохранение
    void save(Order order, Path file) throws IOException {
        Files.writeString(file, "Итого: " + order.total());
    }
}
Бухгалтерия попросила добавить в чек дату. Какие классы из второго варианта придётся открыть?

Только ReceiptPrinter. Order и OrderStorage не трогаем, а значит, и сломать их не можем. В первом варианте правка шла бы в тот же класс, где считаются деньги.

Аналогия: кафе

В маленьком кафе повар, кассир и уборщик — разные люди. Поменяли кассовый аппарат — переучивается только кассир, повар готовит как готовил. Если всё делает один человек, любая новинка выбивает из колеи всё кафе.

Как понять, что класс пора делить: его трудно назвать без «и» («заказ, и печать, и сохранение»), в нём сотни строк, а в импортах соседствуют файлы, консоль и сеть.

Как спросят на собеседовании

«Что такое Single Responsibility? Приведи пример нарушения». Ответ: у класса должна быть одна причина для изменения. Пример: класс заказа и считает сумму, и печатает чек, и сохраняет в файл — делим на три класса. Ловушка: SRP не значит «один метод в классе» — у Order их несколько, но все про одно.

O — открыт для расширения, закрыт для изменения

Принцип открытости/закрытости (Open/Closed Principle, OCP): новое поведение добавляют новым кодом, а не правкой старого, уже проверенного. Класс «открыт» для расширения и «закрыт» для изменений.

Магазин считает стоимость доставки:

class DeliveryCalculator {
    int cost(String type, int weightKg) {
        return switch (type) {
            case "courier" -> 300 + 50 * weightKg;
            case "pickup" -> 0;
            case "post" -> 150 + 30 * weightKg;
            default -> throw new IllegalArgumentException("Неизвестная доставка: " + type);
        };
    }
}

Пока способов три — терпимо. Но вот добавили доставку дроном, потом в постамат, потом экспресс. Каждый раз мы лезем в один и тот же switch, рискуем задеть соседние ветки, а если такой же switch по типу есть ещё в двух местах (срок доставки, иконка в приложении) — правим все три и одно забываем.

Решение — полиморфизм, который ты знаешь с модуля 10. Каждый способ доставки сам знает свою цену:

interface Delivery {
    int cost(int weightKg);
}

class Courier implements Delivery {
    @Override
    public int cost(int weightKg) {
        return 300 + 50 * weightKg;
    }
}

class Pickup implements Delivery {
    @Override
    public int cost(int weightKg) {
        return 0;
    }
}

class Post implements Delivery {
    @Override
    public int cost(int weightKg) {
        return 150 + 30 * weightKg;
    }
}

class Checkout {
    int total(int goodsPrice, Delivery delivery, int weightKg) {
        return goodsPrice + delivery.cost(weightKg);   // не знает, какая именно доставка
    }
}

Доставка дроном — это просто новый класс. Ни Checkout, ни другие доставки мы не открываем:

class Drone implements Delivery {
    @Override
    public int cost(int weightKg) {
        if (weightKg > 5) {
            throw new IllegalArgumentException("Дрон не поднимет больше 5 кг");
        }
        return 500;
    }
}
Совсем честно: после появления Drone в программе точно ничего не надо менять?

Одно место всё-таки поменяется — то, где по выбору покупателя создают объект: new Drone() кто-то должен написать. Но это одна строчка в одном месте, а не правка логики расчёта. OCP не обещает «ноль изменений», он обещает, что старый проверенный код останется нетронутым.

Аналогия: фотоаппарат со сменными объективами

Чтобы снимать издалека, ты не разбираешь фотоаппарат и не перепаиваешь матрицу. Ты прикручиваешь новый объектив к стандартному креплению. Крепление — это интерфейс, объективы — реализации.

switch — не преступление

Если вариантов три и новых не предвидится (дни недели, «да/нет/не знаю»), switch проще и понятнее пачки классов. Это KISS и YAGNI из прошлого урока. Делать интерфейс стоит, когда варианты реально добавляются или когда один и тот же switch по типу повторяется в нескольких местах.

Как спросят на собеседовании

«Как понимать “открыт для расширения, закрыт для изменения”?» Ответ: новое поведение добавляем новым классом, который реализует интерфейс; старый код, который с этим интерфейсом работает, не меняем. Работает это благодаря полиморфизму. Пример: длинный switch по типу доставки заменяем интерфейсом Delivery.

L — наследник без сюрпризов

Принцип подстановки Лисков (Liskov Substitution Principle, LSP; Барбара Лисков — учёная, которая его сформулировала): объект наследника должен работать везде, где работает объект родителя, и не ломать ожиданий кода, который с родителем работает.

Классический пример с квадратом и прямоугольником ты уже видел в уроке 10.7: квадрат «является» прямоугольником в геометрии, но в коде с методами setWidth/setHeight подставить его вместо прямоугольника нельзя. Вот ещё один, попроще:

import java.util.List;

class Bird {
    void fly() {
        System.out.println("Лечу!");
    }
}

class Penguin extends Bird {
    @Override
    void fly() {
        throw new UnsupportedOperationException("Пингвины не летают");
    }
}

public class Birds {
    public static void main(String[] args) {
        List<Bird> birds = List.of(new Bird(), new Penguin());
        for (Bird bird : birds) {
            bird.fly();
        }
    }
}
Скомпилируется? Что будет при запуске?

Скомпилируется без единого предупреждения. При запуске напечатается Лечу!, а на втором элементе вылетит UnsupportedOperationException: Пингвины не летают. Код цикла честно работал с «птицами» и имел право ожидать, что любая птица летает. Пингвин это обещание нарушил — и ошибку увидит пользователь, а не компилятор.

Решение — не обещать лишнего. Умение летать выносим в отдельный интерфейс, и его реализует только тот, кто действительно летает:

import java.util.List;

interface Flying {
    void fly();
}

abstract class Bird {
    abstract String name();
}

class Sparrow extends Bird implements Flying {
    @Override
    String name() {
        return "Воробей";
    }

    @Override
    public void fly() {
        System.out.println("Воробей летит");
    }
}

class Penguin extends Bird {
    @Override
    String name() {
        return "Пингвин";
    }
}

public class Birds {
    public static void main(String[] args) {
        List<Flying> flyers = List.of(new Sparrow());   // new Penguin() сюда не положить
        for (Flying f : flyers) {
            f.fly();
        }
    }
}

Теперь пингвина в список летающих не положишь: ошибку поймает компилятор, а не пользователь посреди работы программы.

Аналогия: прокат машин

Берёшь в прокате «какую-нибудь машину» — и спокойно едешь: газ справа, тормоз слева, руль крутится. Если бы в одной из машин тормоз был справа, на неё нельзя было бы «подставиться» вместо любой другой, даже если по документам это тоже «легковой автомобиль».

Тревожные звонки, что L нарушен: наследник бросает UnsupportedOperationException в методе родителя; метод наследника пустой «для галочки»; перед вызовом приходится проверять if (bird instanceof Penguin).

Как спросят на собеседовании

«Что такое принцип подстановки Лисков? Пример нарушения». Ответ: наследника можно передать везде, где ждут родителя, и программа продолжит работать правильно. Примеры нарушения: квадрат-наследник прямоугольника с сеттерами; пингвин-наследник птицы, который бросает исключение в fly(). Лечится тем, что не обещаем в родителе того, что умеют не все наследники.

Проверка на полпути

I — маленькие интерфейсы лучше толстого

Принцип разделения интерфейсов (Interface Segregation Principle, ISP): класс не должен зависеть от методов, которыми не пользуется. Лучше несколько маленьких интерфейсов, чем один «на все случаи жизни».

В офисе есть устройство «принтер-сканер-факс». Кто-то описал его одним интерфейсом:

interface OfficeMachine {
    void print(String doc);
    void scan(String doc);
    void fax(String doc, String number);
}

class SimplePrinter implements OfficeMachine {
    @Override
    public void print(String doc) {
        System.out.println("Печатаю: " + doc);
    }

    @Override
    public void scan(String doc) {
        throw new UnsupportedOperationException("Я не умею сканировать");
    }

    @Override
    public void fax(String doc, String number) {
        throw new UnsupportedOperationException("Я не умею отправлять факс");
    }
}

Обычный принтер вынужден «реализовать» сканер и факс заглушками — узнаёшь тревожный звонок из буквы L? Это не случайно: толстый интерфейс толкает к нарушению подстановки. А ещё бухгалтер, которому нужна только печать, теперь зависит от метода fax: поменяют его параметры — перекомпилировать и проверять придётся и бухгалтерию.

Режем по умениям:

interface Printer {
    void print(String doc);
}

interface DocScanner {
    void scan(String doc);
}

interface Fax {
    void fax(String doc, String number);
}

class SimplePrinter implements Printer {
    @Override
    public void print(String doc) {
        System.out.println("Печатаю: " + doc);
    }
}

class OfficeCombo implements Printer, DocScanner, Fax {   // умеет всё — реализует всё
    @Override
    public void print(String doc) { System.out.println("Печатаю: " + doc); }

    @Override
    public void scan(String doc) { System.out.println("Сканирую: " + doc); }

    @Override
    public void fax(String doc, String number) { System.out.println("Факс на " + number); }
}

class Accountant {
    private final Printer printer;            // бухгалтеру нужна только печать

    Accountant(Printer printer) {
        this.printer = printer;
    }

    void printReport() {
        printer.print("Отчёт за месяц");
    }
}

Бухгалтеру можно дать и простой принтер, и комбайн — оба умеют Printer. А интерфейс из одного метода — функциональный, поэтому для пробы хватит даже лямбды из модуля 14: new Accountant(doc -> System.out.println(doc)).

Аналогия: пульт от телевизора

Бабушке, которая смотрит три канала, не нужен пульт с шестьюдесятью кнопками. Дай ей пульт на пять кнопок — ей проще, и она не нажмёт случайно «сброс настроек». Маленький интерфейс — это пульт ровно с теми кнопками, которые нужны.

В самой Java много таких «маленьких пультов»: Comparable (один метод compareTo), Runnable (run), Iterable (iterator). Класс берёт только те, что ему подходят.

Как спросят на собеседовании

«Чем плох толстый интерфейс?» Ответ: реализациям приходится писать заглушки для ненужных методов (часто с исключением — привет, L), а клиенты зависят от методов, которыми не пользуются, и страдают от их изменений. Лечится разделением на несколько маленьких интерфейсов; один класс может реализовать сразу несколько.

D — зависеть от интерфейса, а не от конкретного класса

Принцип инверсии зависимостей (Dependency Inversion Principle, DIP): классы высокого уровня (главная логика: «оформить заказ») не должны зависеть от классов низкого уровня (детали: «как именно отправить письмо»). Оба должны зависеть от абстракции — интерфейса.

Посмотри, как обычно пишут в первый раз:

class EmailSender {
    void send(String to, String text) {
        System.out.println("Письмо для " + to + ": " + text);
    }
}

class OrderService {
    private final EmailSender sender = new EmailSender();   // сам выбрал и сам создал

    void placeOrder(String customer) {
        // ... оформляем заказ ...
        sender.send(customer, "Заказ оформлен");
    }
}

Что тут плохо? OrderService намертво приварен к почте. Захотели SMS — переписываем OrderService. Хотим проверить его тестом — при каждом запуске теста «уходит письмо», и проверить, что именно ушло, нечем.

Переворачиваем: OrderService говорит «мне нужен кто-то, кто умеет отправлять уведомления», а кто именно — решают снаружи и передают через конструктор:

interface Notifier {
    void send(String to, String text);
}

class EmailNotifier implements Notifier {
    @Override
    public void send(String to, String text) {
        System.out.println("Письмо для " + to + ": " + text);
    }
}

class SmsNotifier implements Notifier {
    @Override
    public void send(String to, String text) {
        System.out.println("SMS на " + to + ": " + text);
    }
}

class OrderService {
    private final Notifier notifier;

    OrderService(Notifier notifier) {          // зависимость передают снаружи
        this.notifier = notifier;
    }

    void placeOrder(String customer) {
        // ... оформляем заказ ...
        notifier.send(customer, "Заказ оформлен");
    }
}

public class Shop {
    public static void main(String[] args) {
        OrderService service = new OrderService(new SmsNotifier());   // выбор — здесь
        service.placeOrder("+7 900 000-00-00");
    }
}
SMS на +7 900 000-00-00: Заказ оформлен

Самый приятный бонус — тесты. В тест можно передать фейк (поддельную реализацию), который никуда ничего не отправляет, а просто запоминает, что его попросили отправить:

import org.junit.jupiter.api.Test;

import java.util.ArrayList;
import java.util.List;

import static org.assertj.core.api.Assertions.assertThat;

class FakeNotifier implements Notifier {
    final List<String> sent = new ArrayList<>();

    @Override
    public void send(String to, String text) {
        sent.add(to + ": " + text);            // ничего не отправляем, только запоминаем
    }
}

class OrderServiceTest {
    @Test
    void notifiesCustomerAfterOrder() {
        FakeNotifier fake = new FakeNotifier();
        OrderService service = new OrderService(fake);

        service.placeOrder("anna@example.com");

        assertThat(fake.sent).containsExactly("anna@example.com: Заказ оформлен");
    }
}
Можно ли написать такой тест для первой версии OrderService, где внутри new EmailSender()?

Нормально — нет. Объект создаётся внутри класса, и снаружи его не подменить: тест всегда будет работать с настоящим EmailSender. Проверить можно разве что «не упало». Как только зависимость приходит через конструктор, тест сам решает, что подставить.

Аналогия: розетка

Настольную лампу не припаивают к проводке в стене — у неё вилка, а в стене розетка стандартного вида. В розетку можно включить лампу, зарядку или тестер электрика. Розетка — это интерфейс, приборы — реализации, а тестер — тот самый фейк для проверки.

Обрати внимание: new SmsNotifier() никуда не исчез — он переехал в main. Объекты всё равно кто-то создаёт. Идея в том, чтобы делать это в одном месте, «на входе» в программу, а классы с логикой получали готовое через конструктор. Такой приём называют внедрением зависимости через конструктор (constructor injection).

Как спросят на собеседовании

«Чем Dependency Inversion отличается от Dependency Injection?» Ответ: Inversion — принцип: модули высокого уровня зависят от абстракций, а не от конкретных классов. Injection — приём: зависимость не создают внутри, а передают снаружи, например через конструктор. Внедрение помогает соблюдать инверсию, и заодно в тесты можно подставить фейк.

Ориентиры, а не законы

SOLID легко довести до абсурда: интерфейс на каждый класс, по классу на каждую строчку, десять файлов ради «Привет, мир». Это нарушает KISS и YAGNI — и так тоже нельзя. Принципы отвечают на вопрос «как сделать изменения дешёвыми», поэтому применяй их там, где изменения правда случаются:

  • Класс разросся и меняется по разным причинам — дели (S).
  • Класс сам создаёт свои «инструменты» через new, и из-за этого его не протестировать — передай их через конструктор и поставь интерфейс (D).
  • Варианты поведения реально добавляются — интерфейс и новые классы вместо растущего switch (O).
  • Наследник бросает «не поддерживается» — пересмотри иерархию (L), часто вместе с толстым интерфейсом (I).

Если запомнишь из урока только две вещи — пусть это будут S («у класса одна забота») и D («нужные объекты передай через конструктор, тип поля — интерфейс»). С ними твой код уже будет легко тестировать и легко менять.

Проверь себя

Поговори с наставником

Напиши: «Я прошёл урок про SOLID. Дай мне три небольших класса с нарушениями разных принципов, а я сам скажу, какая буква нарушена и как это исправить». А потом: «Возьми мою последнюю задачу и скажи, где в ней нарушен S или D — только укажи место, исправлю я сам».

Коротко

  • S — у класса одна причина для изменения: заказ, печать чека и сохранение — три разных класса.
  • O — новый вариант поведения добавляем новым классом с интерфейсом, а не новой веткой в старом switch.
  • L — наследник работает везде, где родитель; исключение «не поддерживается» в наследнике — тревожный звонок.
  • I — несколько маленьких интерфейсов вместо одного толстого; класс реализует только то, что умеет.
  • D — логика зависит от интерфейса, конкретную реализацию передают через конструктор; в тест — фейк.
  • Это ориентиры, а не законы. Главное для начала — S и D; не плоди интерфейсы «на всякий случай» (KISS, YAGNI).
