Сборка проекта: Gradle

Настоящий проект — это десятки чужих библиотек: JUnit, AssertJ, библиотеки для работы с JSON, базами данных и сетью, логгер. Скачивать их руками и следить за версиями — ад. Этим занимается сборщик. В нашем курсе это Gradle.

Зачем нужен сборщик

До сих пор у тебя были только классы JDK — String, ArrayList, Scanner. Но в работе ты будешь пользоваться чужим кодом: JUnit для тестов, AssertJ для проверок, Jackson для JSON, драйвер базы данных, логгер. Такой готовый чужой код, упакованный в файл .jar, называется библиотекой, а библиотека, которая нужна проекту, — зависимостью (dependency).

Без сборщика пришлось бы: найти сайт библиотеки, скачать .jar нужной версии, скачать ещё пять .jar, без которых она не работает, подключить всё в IDEA — и повторить это на компьютере каждого коллеги и на сервере CI. Через месяц никто не помнит, какие версии где лежат.

Аналогия: список покупок и курьер

Ты не ездишь по складам сам. Ты пишешь список покупок — «молоко 3,2%, 1 л; хлеб бородинский» — и отдаёшь курьеру. Курьер знает, где склад, привезёт ровно это и сложит в холодильник. Список — это файл build.gradle.kts, курьер — Gradle, склад — Maven Central, холодильник — папка ~/.gradle/caches на твоём компьютере.

Gradle — один из двух главных сборщиков Java-проектов (второй — Maven, о нём в конце урока). Он умеет три главные вещи:

📦

Зависимости

Читает список библиотек и сам скачивает их нужных версий — вместе с зависимостями зависимостей.

🏗️

Сборка

Компилирует код, собирает его в один .jar, который можно запустить где угодно.

🧪

Запуск тестов

Одна команда ./gradlew test прогоняет все тесты проекта — так их и запускает сервер CI.

Почему склад называется Maven Central, если сборщик у нас Gradle? Склад исторически завёл Maven, и теперь им пользуются все: Gradle, Maven и даже сама IDEA. Библиотеки одни и те же — меняется только «курьер».

Структура Gradle-проекта

У Gradle есть правила, где что лежит. Это удобно: открыл любой Java-проект на Gradle — и сразу знаешь, где код, а где тесты. Принцип называется «соглашения вместо настройки».

build.gradle.kts
Главный файл: какие библиотеки нужны, под какую Java собирать, как запускать тесты. Разберём его по строчкам в следующем шаге.
settings.gradle.kts
Настройки всего проекта. Главная строка там — rootProject.name = "shop-app", имя проекта. IDEA может добавить туда и служебный плагин — трогать его не нужно.
build/
Сюда Gradle складывает скомпилированные классы, jar и отчёты о тестах. Папку можно удалить в любой момент (./gradlew clean), Gradle соберёт её заново. Поэтому она — в .gitignore, как и служебная папка .gradle/ в корне проекта.

Wrapper: почему ./gradlew, а не просто gradle

У Gradle много версий, и build-файл, написанный под одну, может не заработать на другой. Чтобы у всех — у тебя, у коллеги, у сервера CI — сборка шла одной и той же версией, в проект кладут wrapper («обёртку»):

  • gradlew (для Linux и macOS) и gradlew.bat (для Windows) — маленькие скрипты запуска;
  • gradle/wrapper/gradle-wrapper.properties — в нём записано, какая версия Gradle нужна проекту, например gradle-8.12-bin.zip;
  • gradle/wrapper/gradle-wrapper.jar — программа, которая эту версию скачает.

Запускаешь ./gradlew test — wrapper смотрит, какая версия нужна, при первом запуске скачивает её в ~/.gradle/wrapper и дальше работает ею. Устанавливать Gradle на компьютер вообще не нужно. Все эти файлы коммитят в Git вместе с кодом.

Аналогия: шкаф из IKEA

В коробке со шкафом лежит свой шестигранник — ровно того размера, который нужен. Не надо искать у себя подходящий ключ и надеяться, что подойдёт. Wrapper — такой же «ключ в коробке»: инструмент нужной версии едет вместе с проектом.

Правило простое: код программы живёт в src/main/java, а тесты к нему — в src/test/java, рядом, но отдельно. В готовую программу тесты не попадают — они нужны только команде.

build.gradle.kts по частям

Сердце проекта — файл build.gradle.kts. Окончание .kts значит «скрипт на Kotlin» (Kotlin DSL). Kotlin — другой язык, который тоже работает на JVM, но учить его не нужно: build-файл читается как список настроек. Скобки и строки в кавычках — как в Java, только без точек с запятой. Вот файл проекта с тестами:

plugins {
    java
}

group = "ru.shop"
version = "1.0-SNAPSHOT"

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)
    }
}

repositories {
    mavenCentral()
}

dependencies {
    testImplementation("org.junit.jupiter:junit-jupiter:5.11.4")
    testImplementation("org.assertj:assertj-core:3.27.3")
    testRuntimeOnly("org.junit.platform:junit-platform-launcher")
}

tasks.test {
    useJUnitPlatform()
}
plugins { java }

Блок plugins подключает плагин java. Плагин учит Gradle собирать Java: появляются задачи compileJava, test, jar, build и папки src/main/java, src/test/java. Без него Gradle не знает, что делать с .java-файлами.

group / version

Свойствам group и version присваиваем строки — «адрес» самого проекта: group — организация (обычно перевёрнутый домен, как пакеты в Java), version — версия. Имя проекта лежит в settings.gradle.kts. SNAPSHOT — «версия в работе, ещё меняется». Готовые релизы — без этого слова: 1.0, 5.11.4.

java { toolchain { … } }

Собирать и запускать тесты на Java 21. Если такого JDK на компьютере нет, Gradle сообщит об этом (или скачает сам, если настроено). Кодировку обычно отдельно не указывают: начиная с Java 18 кодировка по умолчанию — UTF-8, и русские буквы в строках не ломаются.

repositories { mavenCentral() }

Откуда брать библиотеки: вызов функции mavenCentral() внутри блока repositories подключает склад Maven Central. Да, Gradle берёт библиотеки оттуда же, откуда Maven: склад общий. Скачанное хранится в ~/.gradle/caches.

testImplementation("…")

Список покупок. Каждая строка — объявление зависимости: вызываем функцию testImplementation и передаём ей аргумент — строку с координатами библиотеки группа:имя:версия через двоеточие: org.assertj — группа, assertj-core — имя, 3.27.3 — версия. Имя функции перед скобками — конфигурация: кому и когда нужна библиотека (таблица ниже).

testRuntimeOnly(launcher)

Ещё одна зависимость, в конфигурации testRuntimeOnly, — «пусковой механизм» JUnit: нужен только в момент запуска тестов, в коде ты его не используешь. Версию писать не надо — её подскажет сам JUnit. В новых версиях Gradle без этой строки тесты не запускаются.

tasks.test { useJUnitPlatform() }

Обязательно! Вызов useJUnitPlatform() в настройках задачи test говорит ей: «тесты написаны на JUnit 5». Без этой строки Gradle ищет тесты старого JUnit 4, а твои тестовые методы с аннотацией @Test из JUnit 5 просто не видит — и пишет 0 тестов.

Конфигурации — главное, что надо понять в блоке dependencies:

КонфигурацияГде видна библиотекаПример
implementationв коде программы src/main/java (и в тестах тоже)библиотека для работы с JSON в самой программе
testImplementationтолько в тестах src/test/java; в итоговую программу не попадётJUnit, AssertJ
testRuntimeOnlyтолько при запуске тестов; в коде её классы не видныjunit-platform-launcher
JUnit подключён через testImplementation. Ты написал import org.junit.jupiter.api.Test; в классе из src/main/java. Что будет при сборке?

Ошибка компиляции: package org.junit.jupiter.api does not exist. Для main-кода этой библиотеки не существует — она видна только тестам. Это защита: тестовые библиотеки не должны попадать в рабочую программу.

Из build-файла случайно удалили useJUnitPlatform(). Тесты есть, код компилируется. Что покажет ./gradlew test?

Ни одного запущенного теста. Gradle по умолчанию ищет тесты JUnit 4, а аннотации JUnit 5 ему незнакомы. В старых версиях Gradle это выглядит как «всё зелёное», хотя проверено ноль тестов; в новых сборка ещё и падает с ошибкой. Увидел «0 тестов» — первым делом проверь useJUnitPlatform().

Откуда берутся библиотеки

Maven Central
Главное общедоступное хранилище Java-библиотек. Искать удобно на mvnrepository.com или central.sonatype.com: находишь библиотеку, выбираешь версию, открываешь вкладку Gradle (Kotlin) — и сайт показывает готовую строку для build-файла.
Транзитивные зависимости
«Зависимости зависимостей». AssertJ сам использует библиотеку byte-buddy — Gradle скачает её автоматически, тебе писать её в build-файл не нужно.
Локальный кэш
Папка .gradle/caches в твоей домашней папке. Там лежат все скачанные jar для всех Gradle-проектов.

Задачи и gradle test

Всё, что умеет Gradle, разложено на задачи (tasks). Задача — одно действие: скомпилировать, прогнать тесты, упаковать jar. Задачи зависят друг от друга: попросишь test — Gradle сам сначала выполнит компиляцию кода и тестов. Главные:

ЗадачаЧто делает
cleanудаляет папку build, чтобы собрать всё с нуля
compileJavaкомпилирует src/main/java в build/classes/java/main
testкомпилирует src/test/java (и сперва main) и запускает все тесты
buildвсё вместе: компиляция, тесты и jar в build/libs

В IDEA задачи — это строчки в окне Gradle. Двойной щелчок по test — запустить тесты. А чтобы собрать с нуля, удобнее Run Anything: Ctrl, Ctrl → gradle clean test → Enter. Внизу откроется панель Run с выводом Gradle:

А вот что будет, если один тест красный:

Ты запустил ./gradlew build. Прогонятся ли тесты?

Убрать и обновить зависимость

Добавлять библиотеки научились. Но в живом проекте их ещё убирают (больше не нужна) и обновляют (вышла версия с исправлениями). Оба действия — правка одной строки build-файла.

Как убрать зависимость

  1. Открой build.gradle.kts и удали строку testImplementation(…) с этой библиотекой. Удобно так: курсор на строку и Ctrl+Y — удалить строку целиком.
  2. Нажми Ctrl+Shift+O — Load Gradle Changes. Библиотека исчезнет из External Libraries.
  3. Пройдись по коду: всё, что использовало библиотеку, станет красным — Cannot resolve symbol, как на скрине выше. Перепиши эти места или удали. Лишние import уберёт Ctrl+Alt+O.
  4. Запусти gradle clean test — убедись, что всё собирается и тесты зелёные.
import — это не зависимость

Частая путаница. Строка import org.assertj… в Java-файле — только сокращение имени (урок 9.5), она ничего не подключает и не скачивает. Подключает библиотеку только build-файл. Удалил import — библиотека осталась в проекте. Удалил зависимость из build.gradle.kts — import стал красным.

Как обновить версию

Поменяй число версии в координатах зависимости и снова Load Gradle Changes. Свежую версию смотри на mvnrepository.com.

Правила безопасного обновления

Обновляй по одной библиотеке и после каждой прогоняй gradle clean test — тогда понятно, кто что сломал. Смотри на первую цифру версии: 5.11 → 5.12 — обычно безопасно, 5 → 6 — «большая» версия, может менять методы и ломать код. Перед таким обновлением читают release notes — список изменений на сайте библиотеки.

🔎 Для любопытных: версия в одном месте, дерево зависимостей и конфликт версий

Это пригодится, когда библиотек в проекте станет много. Для учебных проектов хватает того, что выше.

Версия в одном месте

Когда одна версия встречается в нескольких строках, её выносят в одно место. Самый простой способ — переменная прямо в build-файле:

val junitVersion = "5.11.4"

dependencies {
    testImplementation("org.junit.jupiter:junit-jupiter:$junitVersion")
}

val объявляет переменную в Kotlin и сразу инициализирует её; присвоить новое значение потом нельзя (как final var в Java). А $junitVersion внутри строкового литерала подставляет значение этой переменной. В больших проектах версии держат в отдельном файле — version catalog («каталог версий») gradle/libs.versions.toml:

[versions]
junit = "5.11.4"
assertj = "3.27.3"

[libraries]
junit = { module = "org.junit.jupiter:junit-jupiter", version.ref = "junit" }
assertj = { module = "org.assertj:assertj-core", version.ref = "assertj" }
dependencies {
    testImplementation(libs.junit)
    testImplementation(libs.assertj)
}

В [versions] — номера версий, в [libraries] — библиотеки со ссылкой на версию, а в build-файле к ним обращаются коротко: libs.имя. Встретишь такой файл в проекте — обновляй версию в нём, а не в build.gradle.kts.

Дерево зависимостей: кто кого притащил

Помнишь транзитивные зависимости? Их бывают десятки. Посмотреть, откуда взялась каждая, можно двумя способами: в окне Gradle раскрыть узел Dependencies — или запустить задачу gradle dependencies --configuration testRuntimeClasspath (в IDEA: Ctrl, Ctrl → набери её → Enter). testRuntimeClasspath — «всё, что окажется рядом с тестами при запуске»; без этого уточнения Gradle напечатает деревья для всех конфигураций подряд.

Конфликт версий

Бывает, что две библиотеки тянут одну и ту же третью, но разных версий: условная библиотека A хочет commons-io 2.11.0, а B — commons-io 2.16.1. Две версии одного класса в проекте жить не могут, и Gradle выбирает одну. Правило у Gradle простое: побеждает самая новая из запрошенных версий. (У Maven правило другое — об этом в конце урока.)

Опасность в том, что компиляция проходит, а падает уже во время запуска: библиотеке A досталась версия новее, чем она ждала, а в новой версии какой-то старый метод убрали или переименовали. В консоли тогда NoSuchMethodError или ClassNotFoundException — это почти всегда конфликт версий. Найти его помогает то же дерево:

Как лечат — два способа:

✂️

Исключить лишнюю

Внутри зависимости напиши exclude(…) — «не тащи с собой commons-io». Тогда останется версия от другой библиотеки.

📌

Зафиксировать версию

Объяви commons-io сам и скажи «строго эта версия»: strictly. Выбирай версию, с которой работают обе библиотеки, и проверяй тестами.

dependencies {
    // способ 1: не брать commons-io вместе с library-b
    implementation("ru.example:library-b:3.2") {
        exclude(group = "commons-io", module = "commons-io")
    }

    // способ 2: строго эта версия, «самая новая» не победит
    implementation("commons-io:commons-io") {
        version { strictly("2.11.0") }
    }
}

Это два разных способа — в проекте выбирают один. Исключение подходит, когда «лишняя» версия просто не нужна; strictly — когда точно знаешь, какая версия правильная.

Встретишь и такое: Maven

Maven — второй популярный сборщик и старший брат Gradle. Во многих компаниях проекты собирают именно им, так что прочитать его файл ты должен уметь. Идея та же: зависимости, сборка, тесты, тот же склад Maven Central, те же папки src/main/java и src/test/java. Отличается форма: вместо скрипта — файл pom.xml на XML, языке разметки, где данные лежат внутри парных тегов <тег>значение</тег>, как коробки в коробках.

<dependencies>
    <dependency>
        <groupId>org.junit.jupiter</groupId>
        <artifactId>junit-jupiter</artifactId>
        <version>5.11.4</version>
        <scope>test</scope>
    </dependency>
</dependencies>

Те же координаты, только каждая часть в своём теге: groupId — группа, artifactId — имя, version — версия. <scope>test</scope> — то же, что наш testImplementation. Тесты запускает команда mvn test (в IDEA — окно Maven справа → Lifecycle → test).

🔎 Для любопытных: ещё два отличия Maven

Какие классы считаются тестами. Gradle с JUnit 5 запускает все классы, где есть @Test. Maven по умолчанию — только классы с именами *Test, *Tests, Test*: назовёшь класс LoginChecks — mvn test его не заметит.

Конфликт версий. Gradle при конфликте берёт самую новую версию (подробнее — в блоке «для любопытных» выше). Maven берёт не самую новую, а ту, что ближе к твоему проекту в дереве зависимостей: чем короче путь от pom.xml до библиотеки, тем она главнее; при равной длине — та, что объявлена в pom раньше. Поэтому один и тот же набор библиотек в Maven и Gradle может дать разные версии. Дерево в Maven смотрят командой mvn dependency:tree, а лечат так же: исключением (<exclusions>) или явной версией в своём pom.

Зная один сборщик, второй читаешь за вечер: координаты библиотек, структура папок и смысл «тестовой» зависимости одинаковые.

Проверь себя

Практика с наставником

Напиши: «Я прошёл урок 17.4. Хочу создать в IDEA свой Gradle-проект, подключить JUnit и AssertJ и запустить gradle test — проверь меня по шагам».

Коротко

  • Gradle управляет зависимостями, собирает проект и запускает тесты. Запускают его через wrapper: ./gradlew — у всех одна версия.
  • Структура: build.gradle.kts, settings.gradle.kts, код в src/main/java, тесты в src/test/java, сборка в build.
  • Библиотека = координаты группа:имя:версия; берётся из Maven Central и кешируется в ~/.gradle/caches.
  • testImplementation — библиотека только для тестов; useJUnitPlatform() обязателен для JUnit 5.
  • gradle test = компиляция + все тесты; красный тест → BUILD FAILED, отчёт — build/reports/tests/test/index.html.
  • Убрать или обновить библиотеку — поправить строку в dependencies → Load Gradle Changes → gradle clean test. Обновлять по одной.
  • Maven — то же самое в pom.xml: scope test, target/, mvn test.
