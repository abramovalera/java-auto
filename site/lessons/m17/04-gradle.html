Зачем нужен сборщик

До сих пор у тебя были только классы JDK — String, ArrayList, Scanner. В работе понадобится чужой код: JUnit, AssertJ, драйвер базы данных. Готовый чужой код в файле .jar называется библиотекой, а библиотека, которая нужна проекту, — зависимостью (dependency).

Без сборщика пришлось бы искать и скачивать .jar нужной версии, плюс ещё пять, без которых он не работает, — и повторять это у каждого коллеги и на сервере CI.

Аналогия: список покупок и курьер

Ты пишешь список покупок и отдаёшь курьеру — он знает, где склад, привезёт ровно это и сложит в холодильник. Список — файл build.gradle.kts, курьер — Gradle, склад — Maven Central, холодильник — папка ~/.gradle/caches на твоём компьютере.

Gradle — один из двух главных сборщиков Java (второй — Maven, о нём в конце урока). Он умеет три вещи:

📦

Зависимости

Сам скачивает библиотеки нужных версий — вместе с зависимостями зависимостей.

🏗️

Сборка

Компилирует код и собирает его в один .jar.

🧪

Запуск тестов

Команда ./gradlew test прогоняет все тесты — так их запускает и сервер CI.

Структура Gradle-проекта

У Gradle есть правила, где что лежит: открыл любой Gradle-проект — и сразу знаешь, где код, а где тесты.

build.gradle.kts
Главный файл: какие библиотеки нужны и как собирать. Разберём его в следующем шаге.
settings.gradle.kts
Главная строка там — rootProject.name = "shop-app", имя проекта.
build/
Скомпилированные классы, jar и отчёты о тестах. Папку можно удалить в любой момент (./gradlew clean) — Gradle соберёт её заново. Поэтому она в .gitignore, как и служебная .gradle/.

Wrapper: почему ./gradlew, а не просто gradle

Build-файл, написанный под одну версию Gradle, может не заработать на другой. Чтобы у тебя, у коллеги и у сервера CI сборка шла одной версией, в проект кладут wrapper («обёртку»): скрипты gradlew и gradlew.bat и папку gradle/wrapper, где записано, какая версия нужна. При первом запуске wrapper сам скачает эту версию — устанавливать Gradle не надо. Эти файлы коммитят в Git.

Аналогия: шкаф из IKEA

В коробке со шкафом лежит свой шестигранник ровно нужного размера. Wrapper — такой же «ключ в коробке»: Gradle нужной версии едет вместе с проектом.

build.gradle.kts по частям

Окончание .kts значит «скрипт на Kotlin». Учить Kotlin не нужно: build-файл читается как список настроек, скобки и кавычки — как в Java, только без точек с запятой. Вот файл проекта с тестами:

plugins {
    java
}

group = "ru.shop"
version = "1.0-SNAPSHOT"

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)
    }
}

repositories {
    mavenCentral()
}
dependencies {
    testImplementation("org.junit.jupiter:junit-jupiter:5.11.4")
    testImplementation("org.assertj:assertj-core:3.27.3")
    testRuntimeOnly("org.junit.platform:junit-platform-launcher")
}

tasks.test {
    useJUnitPlatform()
}
plugins { java }

Плагин java учит Gradle собирать Java: появляются задачи compileJava, test, build и папки src/main/java, src/test/java.

group / version

«Адрес» самого проекта: group — организация (перевёрнутый домен, как пакеты), version — версия. SNAPSHOT — «версия в работе», готовые релизы пишут без него: 1.0.

java { toolchain { … } }

Собирать и запускать тесты на Java 21.

repositories { mavenCentral() }

Откуда брать библиотеки: склад Maven Central. Он общий для Gradle и Maven.

testImplementation("…")

Список покупок. Каждая строка — зависимость: координаты библиотеки группа:имя:версия через двоеточие (org.assertj — группа, assertj-core — имя, 3.27.3 — версия). Слово перед скобками — конфигурация: кому и когда нужна библиотека (таблица ниже).

testRuntimeOnly(launcher)

«Пусковой механизм» JUnit: нужен только при запуске тестов. Версию подскажет сам JUnit. Без этой строки новые версии Gradle тесты не запускают.

tasks.test { useJUnitPlatform() }

Обязательно! Говорит задаче test: «тесты на JUnit 5». Без этой строки Gradle ищет тесты старого JUnit 4, не видит твои @Test и пишет 0 тестов.

Конфигурации — главное в блоке dependencies:

КонфигурацияГде видна библиотекаПример
implementationв коде программы src/main/java (и в тестах тоже)библиотека для работы с JSON в самой программе
testImplementationтолько в тестах src/test/java; в итоговую программу не попадётJUnit, AssertJ
testRuntimeOnlyтолько при запуске тестов; в коде её классы не видныjunit-platform-launcher
JUnit подключён через testImplementation. Ты написал import org.junit.jupiter.api.Test; в классе из src/main/java. Что будет при сборке?

Ошибка компиляции: package org.junit.jupiter.api does not exist. Для main-кода этой библиотеки нет — она видна только тестам. Так тестовые библиотеки не попадают в рабочую программу.

Откуда берутся библиотеки

Maven Central
Главный общий склад Java-библиотек. Искать удобно на mvnrepository.com: выбираешь библиотеку и версию, на вкладке Gradle (Kotlin) — готовая строка для build-файла.
Транзитивные зависимости
«Зависимости зависимостей». AssertJ использует byte-buddy — Gradle скачает её сам, писать её в build-файл не нужно.

Задачи и gradle test

Всё, что умеет Gradle, разложено на задачи (tasks): скомпилировать, прогнать тесты, упаковать jar. Попросишь test — Gradle сам сначала скомпилирует код и тесты. Главные задачи:

ЗадачаЧто делает
cleanудаляет папку build, чтобы собрать всё с нуля
compileJavaкомпилирует src/main/java в build/classes/java/main
testкомпилирует src/test/java (и сперва main) и запускает все тесты
buildвсё вместе: компиляция, тесты и jar в build/libs

В IDEA задачи — строчки в окне Gradle (значок слона справа): двойной щелчок по test запускает тесты. Собрать с нуля удобнее через Run Anything: Ctrl, Ctrl → gradle clean test → Enter:

А вот что будет, если один тест красный:

Ты запустил ./gradlew build. Прогонятся ли тесты?

Да. build включает test. Упадёт тест — сборка остановится с BUILD FAILED.

Убрать и обновить зависимость

Библиотеки ещё убирают (больше не нужна) и обновляют (вышла версия с исправлениями). Оба действия — правка одной строки build-файла.

Как убрать зависимость

  1. Удали строку с библиотекой в dependencies { }: курсор на строку и Ctrl+Y.
  2. Load Gradle Changes (Ctrl+Shift+O).
  3. Всё, что использовало библиотеку, станет красным — перепиши или удали. Лишние import уберёт Ctrl+Alt+O.
  4. gradle clean test — проверь, что всё зелёное.
import — это не зависимость

import в Java-файле — только сокращение имени (урок 9.5), он ничего не подключает. Библиотеку подключает и убирает только build-файл.

Как обновить версию

Поменяй число версии в строке зависимости (свежую смотри на mvnrepository.com) → Load Gradle Changes → gradle clean test. Обновляй по одной библиотеке — тогда понятно, кто что сломал. Смена первой цифры (5 → 6) может ломать код: перед ней читают release notes — список изменений.

🔎 Для любопытных: версия в одном месте, дерево зависимостей и конфликт версий

Пригодится, когда библиотек станет много.

Версия в одном месте

Повторяющуюся версию выносят в переменную:

val junitVersion = "5.11.4"

dependencies {
    testImplementation("org.junit.jupiter:junit-jupiter:$junitVersion")
}

val — переменная Kotlin, которую нельзя переприсвоить (как final var в Java); $junitVersion подставляет её значение в строку. В больших проектах версии держат в version catalog — файле gradle/libs.versions.toml:

[versions]
junit = "5.11.4"
assertj = "3.27.3"

[libraries]
junit = { module = "org.junit.jupiter:junit-jupiter", version.ref = "junit" }
assertj = { module = "org.assertj:assertj-core", version.ref = "assertj" }
dependencies {
    testImplementation(libs.junit)
    testImplementation(libs.assertj)
}

В build-файле к библиотекам обращаются коротко: libs.имя. Есть такой файл — обновляй версию в нём.

Дерево зависимостей: кто кого притащил

Откуда взялась каждая транзитивная зависимость, видно в окне Gradle → Dependencies или в выводе задачи gradle dependencies --configuration testRuntimeClasspath (через Run Anything). testRuntimeClasspath — «всё, что будет рядом с тестами при запуске»; без уточнения Gradle напечатает все конфигурации подряд.

Конфликт версий

Бывает, что две библиотеки тянут одну третью разных версий: A хочет commons-io 2.11.0, B — 2.16.1. В проекте останется одна, и у Gradle побеждает самая новая (у Maven правило другое — в конце урока).

Компиляция проходит, а падает при запуске: в новой версии убрали метод, который нужен A. NoSuchMethodError или ClassNotFoundException в консоли — почти всегда конфликт версий. Найти его помогает то же дерево:

Как лечат — два способа:

✂️

Исключить лишнюю

exclude(…) внутри зависимости — «не тащи с собой commons-io».

📌

Зафиксировать версию

strictly — «строго эта версия». Выбирай ту, с которой работают обе библиотеки.

dependencies {
    // способ 1: не брать commons-io вместе с library-b
    implementation("ru.example:library-b:3.2") {
        exclude(group = "commons-io", module = "commons-io")
    }

    // способ 2: строго эта версия, «самая новая» не победит
    implementation("commons-io:commons-io") {
        version { strictly("2.11.0") }
    }
}

В проекте выбирают один из двух способов.

Встретишь и такое: Maven

Maven — второй популярный сборщик, старший брат Gradle; во многих компаниях собирают им. Идея та же: тот же склад Maven Central, те же папки src/main/java и src/test/java. Отличается форма: файл pom.xml на XML — данные внутри парных тегов <тег>значение</тег>, как коробки в коробках.

<dependencies>
    <dependency>
        <groupId>org.junit.jupiter</groupId>
        <artifactId>junit-jupiter</artifactId>
        <version>5.11.4</version>
        <scope>test</scope>
    </dependency>
</dependencies>

Те же координаты, каждая часть в своём теге. <scope>test</scope> — то же, что testImplementation. Тесты запускает mvn test (в IDEA — окно Maven справа → Lifecycle → test).

Жизненный цикл Maven

Maven собирает проект по жизненному циклу — цепочке фаз в строгом порядке. Попросишь фазу — Maven выполнит и все предыдущие: mvn package скомпилирует код, прогонит тесты и только потом упакует. Это любят спрашивать на собеседованиях.

ФазаЧто делает
validateпроверяет, что проект описан правильно
compileкомпилирует src/main/java: .java → .class
testкомпилирует и запускает тесты из src/test/java
packageупаковывает классы в .jar (у веб-приложений бывает .war) в папку target/
verifyдополнительные проверки готовой сборки
installкладёт jar в локальный склад ~/.m2/repository — для других твоих проектов
deployотправляет jar в удалённое хранилище компании — для коллег

Отдельно от цепочки есть clean — удалить target/. Самая частая команда — «удали старое и собери заново, прогнав тесты» (у Gradle — ./gradlew clean build):

mvn clean package
🔎 Для любопытных: что внутри jar и ещё два отличия Maven

Что внутри .jar. jar — обычный zip-архив (можно открыть архиватором). Внутри — .class-файлы по папкам пакетов, ресурсы и файл META-INF/MANIFEST.MF: версия, автор и, если jar запускаемый, строка Main-Class с классом, где лежит main. Такой jar запускается командой java -jar имя.jar.

Какие классы считаются тестами. Gradle с JUnit 5 запускает все классы, где есть @Test. Maven по умолчанию — только классы с именами *Test, *Tests, Test*: назовёшь класс LoginChecks — mvn test его не заметит.

Конфликт версий. Gradle берёт самую новую версию, а Maven — ту, что ближе к проекту в дереве (при равной длине пути — объявленную в pom раньше). Поэтому одни и те же библиотеки в Maven и Gradle могут дать разные версии. Дерево в Maven — mvn dependency:tree, лечат так же: <exclusions> или явной версией в pom.

Зная один сборщик, второй читаешь за вечер: координаты, папки и «тестовые» зависимости одинаковые.

Проверь себя

Практика с наставником

Напиши: «Я прошёл урок 17.4. Хочу создать в IDEA свой Gradle-проект, подключить JUnit и AssertJ и запустить gradle test — проверь меня по шагам».

Коротко

  • Gradle управляет зависимостями, собирает проект и запускает тесты. Запускают его через wrapper: ./gradlew — у всех одна версия.
  • Структура: build.gradle.kts, settings.gradle.kts, код в src/main/java, тесты в src/test/java, сборка в build.
  • Библиотека = координаты группа:имя:версия; берётся из Maven Central и кешируется в ~/.gradle/caches.
  • testImplementation — библиотека только для тестов; useJUnitPlatform() обязателен для JUnit 5.
  • gradle test = компиляция + все тесты; красный тест → BUILD FAILED, отчёт — build/reports/tests/test/index.html.
  • Убрать или обновить библиотеку — поправить строку в dependencies → Load Gradle Changes → gradle clean test. Обновлять по одной.
  • Maven — то же самое в pom.xml: scope test, target/, mvn test.
