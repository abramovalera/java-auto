Что такое тест

Как ты проверял свои программы до сих пор? Запускал main, смотрел вывод глазами, сравнивал с ожидаемым в голове. Поменял код — повторил. А если проверок сто? Если код поменял коллега, а ты даже не знаешь, что проверять?

Тест (автоматический тест) — маленький метод (тестовый метод), который вызывает твой код, передаёт ему известные аргументы и сам сравнивает возвращаемое значение с ожидаемым. Человек нужен только чтобы написать тест один раз. Дальше его гоняют тысячи раз: после каждой правки, на каждом merge request, каждую ночь.

Аналогия: краш-тест

Автозавод не ждёт, пока машина попадёт в аварию у покупателя. Он заранее разбивает её о стену с датчиками и сравнивает показания с нормой. Тест — это стена с датчиками для кода: ошибка обнаруживается у тебя, а не у пользователя.

Юнит-тест (unit test, модульный)
Проверяет одну маленькую единицу кода — обычно один метод одного класса — отдельно от всего остального. Быстрый: тысячи за секунды.
JUnit 5
Главная библиотека для тестов на Java. Находит тестовые методы, запускает их и показывает, какие прошли. Ею же пользуются и для более крупных тестов — интеграционных и сквозных.
Assertion (проверка, ассерт)
Вызов метода-проверки, «убедись, что…»: assertEquals(199, fee) — вызываем метод assertEquals и передаём два аргумента: ожидаемое значение (expected) 199 и фактическое (actual) — значение переменной fee. Не равны — тест падает.

Подключаем JUnit и AssertJ к проекту курса

Папка курса — обычный проект IDEA без Gradle. Библиотеки подключим через настройки проекта — по тем же координатам, что в build.gradle.kts (пункт меню называется From Maven…: IDEA качает с того же склада Maven Central). Сделай это до того, как создавать файлы с тестами: пока библиотеки нет, файл с import org.junit… не компилируется, а с ним не запустится и ни одна другая программа проекта.

  1. Открой File → Project Structure (Ctrl+Alt+Shift+S) → слева Libraries.
  2. Нажми + → From Maven… и впиши координаты org.junit.jupiter:junit-jupiter:5.11.4. Галочку Transitive dependencies оставь — нужны и зависимости. OK.
  3. IDEA спросит, к какому модулю подключить, — выбери свой модуль (он один) → OK.
  4. Ещё раз + → From Maven…: org.assertj:assertj-core:3.27.3 — понадобится в следующем уроке.
  5. Apply → OK. В дереве проекта внизу, в External Libraries, появятся jar-файлы JUnit и AssertJ.
Быстрый путь

Если написать @Test в классе без библиотеки, слово подчеркнётся красным. Alt+Enter → Add 'JUnit5.x' to classpath — IDEA подключит JUnit сама. Для AssertJ так не получится — его добавляй через Project Structure.

Сайт курса проверяет задачи модуля 17 на тех же версиях: JUnit 5.11 и AssertJ 3.27. Если при первом запуске теста IDEA предложит докачать junit-platform-launcher — соглашайся: это «пульт», которым IDEA запускает тесты.

Первый тест

Тестировать будем расчёт доставки: заказ от 2000 ₽ — бесплатно, иначе 199 ₽, сумма 0 и меньше — ошибка. В задачах курса тестируемый класс лежит в том же файле, что и тесты, — без public, ведь public-класс в файле может быть только один:

import org.junit.jupiter.api.Test;

import static org.junit.jupiter.api.Assertions.assertEquals;

class DeliveryFee {
    static int feeFor(int orderSum) {
        if (orderSum <= 0) {
            throw new IllegalArgumentException(
                    "Сумма заказа должна быть больше нуля");
        }
        if (orderSum >= 2000) {
            return 0;
        }
        return 199;
    }
}

public class DeliveryFeeTest {

    @Test
    void smallOrderPaysFee() {
        // Arrange — подготовка
        int orderSum = 500;
        // Act — действие
        int fee = DeliveryFee.feeFor(orderSum);
        // Assert — проверка
        assertEquals(199, fee);
    }

    @Test
    void bigOrderIsFree() {
        assertEquals(0, DeliveryFee.feeFor(2500),
                "от 2000 ₽ доставка бесплатная");
    }
}
import static org.junit.jupiter.api.Assertions.assertEquals;

Статический импорт: можно писать просто assertEquals(…) вместо Assertions.assertEquals(…). Все проверки JUnit — статические методы класса Assertions.

@Test

Аннотация — метка со знаком @ перед объявлением метода. @Test помечает метод как тестовый: «JUnit, это тест, запусти его». Без аннотации метод — просто метод, и JUnit его не тронет.

void smallOrderPaysFee()

Объявление тестового метода: тип возвращаемого значения void (ничего не возвращает), параметров нет. public в JUnit 5 не нужен. Имя — описание проверки: «маленький заказ платит за доставку».

assertEquals(199, fee);

Вызов проверки assertEquals: первый аргумент — ожидаемое значение (expected), второй — фактическое (actual). Равны — молча идём дальше. Не равны — тест падает с сообщением.

"от 2000 ₽ доставка бесплатная"

Необязательное сообщение — третий аргумент, строковый литерал. Его покажут, если проверка упадёт: сразу понятно, какое правило нарушено.

Заметь: main здесь нет! Тест запускает не JVM по точке входа, а JUnit: он сам находит класс, создаёт его объект и вызывает каждый метод с @Test. Причём для каждого теста — новый объект тестового класса. Это важно, вернёмся к этому в следующем уроке.

Запуск: зелёная и красная полоса

Слева от объявления класса public class DeliveryFeeTest и от каждого тестового метода появились зелёные ▶. У класса — запустить все тесты, у метода — только этот. Или Ctrl+Shift+F10, стоя в файле. Внизу откроется окно с результатами. Вот его схема для наших двух тестов — представим, что в DeliveryFee закралась ошибка и smallOrderPaysFee упал:

А вот то же в настоящей IDEA. Ошибка — опечатка в DeliveryFee: в строке 10 написано 200 вместо 2000, поэтому заказ на 500 ₽ тоже стал «бесплатным»:

  • Зелёный ✓ — все проверки в тесте прошли. Красный ✕ — проверка не совпала или вылетело исключение.
  • Сообщение expected: <199> but was: <0> — «ждали 199, а было 0». Это главное, что читают у упавшего теста.
  • Кнопка Rerun Failed Tests перезапускает только упавшие. А через жучок 🐞 у теста — запустить его под отладчиком, с брейкпоинтом внутри тестируемого метода.
Ты по ошибке поменял аргументы местами: assertEquals(fee, 199), а метод вернул 0. Что напишет JUnit?

expected: <0> but was: <199> — наоборот! Тест упадёт правильно, но сообщение будет врать: «ждали 0», хотя ждали мы 199. Через полгода коллега будет чинить не то. Порядок важен: сначала ожидаемое, потом фактическое.

Набор проверок

ПроверкаТест проходит, если…
assertEquals(ожид, факт)значения равны (для объектов — через equals)
assertNotEquals(a, b)значения не равны
assertTrue(условие) / assertFalse(условие)условие истинно / ложно
assertNull(x) / assertNotNull(x)x равен / не равен null
assertThrows(Тип.class, () -> …)код в лямбде бросил исключение этого типа
assertArrayEquals(ожид, факт)массивы равны поэлементно
assertAll(() -> …, () -> …)прошли все проверки внутри; упавшие показываются все сразу (пример ниже)

Проверка исключения — частый гость в тестах. Код, который должен бросить исключение, передаём вторым аргументом — лямбда-выражением без параметров () -> … (модуль 14): JUnit сам вызовет её и перехватит исключение. А ещё assertThrows возвращает пойманный объект исключения — им инициализируем переменную e и проверяем сообщение:

@Test
void zeroSumIsRejected() {
    IllegalArgumentException e = assertThrows(IllegalArgumentException.class,
            () -> DeliveryFee.feeFor(0));
    assertEquals("Сумма заказа должна быть больше нуля", e.getMessage());
}
Что будет, если метод feeFor(0) не бросит исключение, а вернёт 199?

Тест упадёт: Expected java.lang.IllegalArgumentException to be thrown, but nothing was thrown. assertThrows требует, чтобы исключение было. Нет исключения — это тоже ошибка.

Ловушка с дробными числами

assertEquals(0.3, 0.1 + 0.2) упадёт: 0.1 + 0.2 в double — это 0.30000000000000004. Для дробных чисел есть третий аргумент — допустимая погрешность: assertEquals(0.3, 0.1 + 0.2, 0.0001).

Несколько проверок сразу: assertAll

Проверка, которая не прошла, бросает исключение — и тест на ней заканчивается. Проверки ниже уже не выполняются, и ты узнаёшь только о первом расхождении. Когда у одного результата несколько частей, удобнее увидеть все ошибки разом. Для этого есть assertAll: ему передают несколько лямбда-выражений с проверками, он выполняет все и сообщает обо всех упавших вместе.

import org.junit.jupiter.api.Test;

import static org.junit.jupiter.api.Assertions.assertAll;
import static org.junit.jupiter.api.Assertions.assertEquals;

public class FullNameTest {
    @Test
    void fullNameSplitsIntoThreeParts() {
        String[] parts = "Иванова Анна Сергеевна".split(" ");
        assertAll(
                () -> assertEquals(3, parts.length),
                () -> assertEquals("Иванова", parts[0]),
                () -> assertEquals("Анна", parts[1]),
                () -> assertEquals("Сергеевна", parts[2])
        );
    }
}

Если упадут две проверки, JUnit напишет Multiple Failures (2 failures) и ниже — оба сообщения expected … but was …. Это всё ещё один тест про одно поведение («ФИО делится на три части»), просто с подробным отчётом.

Тот же тест без assertAll: четыре assertEquals подряд. В строке две опечатки — "Иванова Ана Сергевна". Сколько расхождений покажет JUnit?

Одно — про «Анна». Проверка длины пройдёт (частей всё равно три), проверка parts[1] упадёт и бросит исключение, до parts[2] дело не дойдёт. Исправишь первое, запустишь — и только тогда узнаешь про «Сергеевна». С assertAll оба расхождения видны сразу.

AAA и хорошие имена

Почти любой тест состоит из трёх частей — Arrange, Act, Assert («подготовь, сделай, проверь»):

🧰

Arrange

Подготовить данные и объекты: сумму заказа, корзину, пользователя.

▶️

Act

Одно действие, которое проверяем: вызвать тестируемый метод и сохранить возвращаемое значение.

✅

Assert

Проверка (assertion): сравнить фактическое значение с ожидаемым.

Аналогия: опыт в школьной лаборатории

Налил в пробирку раствор (arrange), капнул реактив (act), посмотрел, посинело ли (assert). Если делать три опыта в одной пробирке подряд — непонятно, какой реактив что сделал. Так и тест: один тест — одно поведение.

Имена тестов читают чаще, чем код: в отчёте о прогоне видны только они. Имя должно говорить, что проверяется и что ожидается:

Вот тест без единой проверки. Он зелёный или красный? @Test void feeWorks() { DeliveryFee.feeFor(500); }

Всегда зелёный — если метод не бросил исключение. Тест без assert ничего не проверяет: метод может вернуть хоть −1000, тест промолчит. Это самая коварная ошибка новичков в тестах: «тесты зелёные» не значит «всё работает».

Проверь себя

Покажи наставнику

Реши задачи «Первые тесты: скидка в магазине» и «Тесты для правил пароля». Потом напиши: «/check m17-t03 — и спроси меня, почему порядок аргументов в assertEquals важен».

Коротко

  • Тест — тестовый метод с аннотацией @Test: вызывает код и проверяет возвращаемое значение; запускает его JUnit, main не нужен.
  • JUnit и AssertJ в проект курса — через Project Structure → Libraries → From Maven.
  • Проверка assertEquals(ожидаемое, фактическое, "сообщение") — порядок аргументов важен; ещё assertTrue/False, assertNull, assertThrows.
  • assertAll(() -> …, () -> …) выполняет все проверки внутри и показывает все расхождения сразу.
  • Зелёный — прошёл, красный — читай expected … but was …; под отладчиком тест тоже можно запустить.
  • AAA, одно поведение на тест, имя = что проверяем. Тест без assert всегда зелёный — и бесполезен.
