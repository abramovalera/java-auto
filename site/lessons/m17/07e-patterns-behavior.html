Паттерны: структурные и поведенческие

В прошлом уроке паттерны отвечали на вопрос «как создать объект». Сегодня — два других вопроса: как соединить объекты между собой и как им договориться, кто что делает. Восемь паттернов, и почти каждый ты уже встречал в Java, просто не знал его имени.

Повторение

Две новые группы

Напомню: паттерн (шаблон проектирования) — проверенная идея, как решить частую задачу в устройстве программы. Не готовый код, а рецепт: «если у тебя вот такая проблема — сделай вот так».

🧱

Структурные

Как собрать объекты в конструкцию: подключить чужой класс, нарастить способность, спрятать сложность за простой кнопкой. Адаптер, Декоратор, Фасад, Заместитель.

🤝

Поведенческие

Как объекты общаются и делят работу: кто выбирает алгоритм, кто кого оповещает, кто кого обходит. Стратегия, Итератор, Посредник, Наблюдатель.

Не пытайся вызубрить все восемь сразу. Для каждого запомни три вещи: какую боль он лечит, на что похож в жизни и где ты его уже видел в Java. Код запомнится сам.

Выпиши себе: восемь паттернов одной строкой

Перепиши таблицу в тетрадь руками и дополняй её по ходу урока своими примерами. На собеседовании про паттерны спрашивают именно так: «что это и где встречал».

Adapter — переходник

Проблема. Твоя программа работает с интерфейсом Thermometer: метод celsius() отдаёт градусы Цельсия. А датчик достался от старой библиотеки: класс OldThermometer умеет только fahrenheit(). Чужой код менять нельзя, свой переписывать не хочется.

Аналогия: переходник для розетки

Привёз из поездки зарядку с плоской вилкой, а розетка дома круглая. Ни зарядку, ни розетку не переделываешь — покупаешь переходник. С одной стороны он выглядит как то, что ждёт розетка, с другой — принимает то, что у тебя есть.

Адаптер — класс, который реализует нужный тебе интерфейс, а внутри держит чужой объект и переводит вызовы на его язык:

// Чужой класс из старой библиотеки — менять нельзя
class OldThermometer {
    double fahrenheit() {
        return 104;
    }
}

// Интерфейс, который ждёт наша программа
interface Thermometer {
    double celsius();
}

// Переходник: снаружи Thermometer, внутри — OldThermometer
class ThermometerAdapter implements Thermometer {
    private final OldThermometer old;

    ThermometerAdapter(OldThermometer old) {
        this.old = old;
    }

    @Override
    public double celsius() {
        return (old.fahrenheit() - 32) * 5 / 9;
    }
}
Thermometer t = new ThermometerAdapter(new OldThermometer());
System.out.println("В комнате " + t.celsius() + " °C");
В комнате 40.0 °C

Остальная программа знать не знает про Фаренгейты: она видит обычный Thermometer.

Где в JDK. Ты уже пользовался двумя адаптерами:

  • Arrays.asList(массив) — массив «притворяется» списком List. Копии не делается: список смотрит прямо в массив.
  • InputStreamReader — переходник «байты → символы» из урока 15.4: снаружи он Reader (читает символы), внутри держит InputStream (байты).
String[] drinks = {"чай", "кофе"};
List<String> menu = Arrays.asList(drinks);
drinks[0] = "какао";
System.out.println(menu);
menu.add("сок");
Что выведет этот код и что случится на последней строке?

Напечатается [какао, кофе]: адаптер не копирует массив, а смотрит в него, поэтому замена в массиве видна и в списке. А menu.add("сок") бросит UnsupportedOperationException: у массива фиксированная длина, и переходник честно отказывается её менять. Нужен настоящий изменяемый список — new ArrayList<>(Arrays.asList(drinks)). Любимая ловушка собеседований.

Decorator — добавляем способность обёрткой

Проблема. Кофейня продаёт эспрессо. К нему можно добавить молоко, сироп, двойное молоко, молоко и сироп… Если на каждую комбинацию делать наследника (EspressoWithMilk, EspressoWithMilkAndSyrup, …), классов станет больше, чем пунктов в меню.

Аналогия: стаканчик кофе

Бариста не варит отдельный «кофе-с-молоком-и-сиропом». Он берёт эспрессо и добавляет к нему молоко, потом сироп. Каждая добавка знает только свою цену и спрашивает остальное у того, что уже в стаканчике.

Декоратор реализует тот же интерфейс, что и оборачиваемый объект, держит его внутри и добавляет свою часть работы. Сам класс эспрессо при этом не меняется:

interface Beverage {
    String name();
    int price();
}

class Espresso implements Beverage {
    @Override public String name() { return "Эспрессо"; }
    @Override public int price() { return 150; }
}

// Общая часть всех добавок: держим внутри другой напиток
abstract class BeverageAddon implements Beverage {
    protected final Beverage inner;

    BeverageAddon(Beverage inner) {
        this.inner = inner;
    }
}

class WithMilk extends BeverageAddon {
    WithMilk(Beverage inner) { super(inner); }
    @Override public String name() { return inner.name() + " + молоко"; }
    @Override public int price() { return inner.price() + 40; }
}

class WithSyrup extends BeverageAddon {
    WithSyrup(Beverage inner) { super(inner); }
    @Override public String name() { return inner.name() + " + сироп"; }
    @Override public int price() { return inner.price() + 30; }
}
Beverage order = new WithSyrup(new WithMilk(new Espresso()));
System.out.println(order.name() + ": " + order.price() + " ₽");
Эспрессо + молоко + сироп: 220 ₽

Где в JDK. Ровно так устроены потоки чтения из урока 15.4: new BufferedReader(new FileReader("a.txt")). FileReader умеет читать символы из файла, а обёртка BufferedReader добавляет буфер и метод readLine(). Тогда мы назвали это «трубой с насадками» — теперь ты знаешь официальное имя.

Что напечатает Beverage x = new WithMilk(new WithMilk(new Espresso())); и System.out.println(x.name() + ": " + x.price() + " ₽");?

Эспрессо + молоко + молоко: 230 ₽. Одну и ту же обёртку можно надеть дважды — двойное молоко без нового класса. С наследованием для этого понадобился бы ещё один класс EspressoWithDoubleMilk.

Facade — одна кнопка вместо десяти

Проблема. Чтобы посмотреть фильм дома, нужно приглушить свет, включить проектор, настроить звук, запустить фильм. Каждый раз — четыре объекта и правильный порядок вызовов. Ошибся в порядке — смотришь в темноте на выключенную стену.

Аналогия: кнопка «Кинотеатр» на пульте

Умный пульт с одной кнопкой «Кино» сам делает всё по списку. Сложная техника никуда не делась, просто тебе не нужно про неё думать. Захочешь — по-прежнему можешь крутить громкость отдельно.

Фасад — класс с простым методом, который сам вызывает нужные части сложной системы в правильном порядке:

class Projector {
    void on() { System.out.println("Проектор включён"); }
    void play(String movie) { System.out.println("Показываем: " + movie); }
}

class SoundSystem {
    void setVolume(int level) { System.out.println("Громкость " + level); }
}

class RoomLights {
    void dim(int percent) { System.out.println("Свет приглушён до " + percent + "%"); }
}

// Фасад: одна кнопка поверх трёх устройств
class HomeCinema {
    private final Projector projector = new Projector();
    private final SoundSystem sound = new SoundSystem();
    private final RoomLights lights = new RoomLights();

    void watchMovie(String movie) {
        lights.dim(10);
        projector.on();
        sound.setVolume(30);
        projector.play(movie);
    }
}
new HomeCinema().watchMovie("Интерстеллар");
Свет приглушён до 10%
Проектор включён
Громкость 30
Показываем: Интерстеллар

Где в JDK. Files.readString(путь) из модуля 15 — фасад: одна строчка, а под ней открытие файла, поток байтов, перевод в символы по кодировке, буфер и закрытие. Всё это ты разбирал в уроке 15.4, а пользуешься одной кнопкой.

Фасад не запрещает «сложный путь»

Фасад — удобный вход, а не замок. Части системы остаются доступными: если нужен необычный сценарий, работай с ними напрямую.

Proxy — заместитель

Проблема. В фотоальбоме сто снимков, каждый грузится секунду. Если загружать все при открытии альбома, человек будет ждать почти две минуты, хотя посмотрит, может, три фотографии.

Аналогия: секретарь начальника

Ты звонишь в компанию и попадаешь на секретаря. Он выглядит для тебя как «вход к начальнику»: принимает те же просьбы. Но сам решает — соединить сейчас, ответить по памяти («он уже говорил, что совещание в 15:00») или не пустить вовсе.

Заместитель (proxy) реализует тот же интерфейс, что и настоящий объект, и стоит перед ним. Код, который им пользуется, разницы не замечает. Ленивый заместитель создаёт тяжёлый объект только при первом обращении:

interface Picture {
    void show();
}

class HeavyPicture implements Picture {
    private final String file;

    HeavyPicture(String file) {
        this.file = file;
        System.out.println("Загружаю " + file + " (это долго)");
    }

    @Override
    public void show() {
        System.out.println("Показываю " + file);
    }
}

// Заместитель: тот же интерфейс, а настоящая картинка — только по требованию
class LazyPicture implements Picture {
    private final String file;
    private HeavyPicture real;   // пока null

    LazyPicture(String file) {
        this.file = file;
    }

    @Override
    public void show() {
        if (real == null) {
            real = new HeavyPicture(file);
        }
        real.show();
    }
}
Picture[] album = {
        new LazyPicture("море.jpg"),
        new LazyPicture("горы.jpg"),
        new LazyPicture("лес.jpg")
};
System.out.println("Альбом открыт");
album[1].show();
album[1].show();

Три заместителя создаются мгновенно — ничего не грузят. Загрузка случилась один раз и только для той картинки, которую попросили. Второй show() берёт уже загруженную.

Бывают и другие заместители: кеширующий запоминает ответ и не спрашивает настоящий объект второй раз; защитный проверяет права, прежде чем пропустить вызов. Где в JDK: Collections.unmodifiableList(список) возвращает защитного заместителя. Читать через него можно, а на add или remove он бросает UnsupportedOperationException и до настоящего списка не пускает.

Strategy — алгоритм подменяется на лету

Переходим к поведенческим. Проблема. Касса считает итог по-разному: без скидки, со скидкой 10%, с промокодом на 300 ₽. Первое, что приходит в голову, — цепочка if:

int total;
if (discountType.equals("none")) {
    total = price;
} else if (discountType.equals("percent10")) {
    total = price * 90 / 100;
} else if (discountType.equals("promo300")) {
    total = Math.max(0, price - 300);
} else {
    total = price;
}

Каждая новая акция — ещё одна ветка в том же методе. Метод растёт, а случайно сломать соседнюю скидку всё проще.

Аналогия: навигатор

В навигаторе одна кнопка «Проложить маршрут», а способ — пешком, на машине, на автобусе — ты выбираешь переключателем. Навигатор не переписывают под каждый вид транспорта: он просто берёт выбранный способ и просит его посчитать путь.

Стратегия: каждый вариант алгоритма — отдельный объект с общим интерфейсом. Тот, кто им пользуется, хранит стратегию в поле и просто вызывает её. Интерфейс с одним методом — функциональный, значит, стратегию можно передать лямбдой (урок 14.1):

interface Discount {
    int apply(int price);
}

class CashDesk {
    private Discount discount = price -> price;   // по умолчанию — без скидки

    void setDiscount(Discount discount) {
        this.discount = discount;
    }

    int total(int price) {
        return discount.apply(price);   // ни одного if: что положили, то и считает
    }
}
CashDesk desk = new CashDesk();
System.out.println(desk.total(1000));

desk.setDiscount(price -> price * 90 / 100);           // скидка 10%
System.out.println(desk.total(1000));

desk.setDiscount(price -> Math.max(0, price - 300));   // промокод на 300 ₽
System.out.println(desk.total(1000));
1000
900
700

Новая акция — новая лямбда, класс CashDesk не меняется. Если стратегия выбирается по слову с клавиатуры, удобно сложить их в словарь Map<String, Discount>: ключ — название, значение — стратегия. Так ты сделаешь в задаче про доставку.

Где в JDK. Ты пользуешься стратегией с урока 11.4: Comparator — это стратегия сравнения. Метод sort один и тот же, а порядок задаёшь ты:

List<String> names = new ArrayList<>(List.of("Анна", "Ян", "Борис"));
names.sort(Comparator.comparing(String::length));   // стратегия «по длине»
System.out.println(names);
names.sort((a, b) -> b.compareTo(a));               // стратегия «по алфавиту наоборот»
System.out.println(names);
[Ян, Анна, Борис]
[Ян, Борис, Анна]

Выходит, каждая лямбда, которую ты передавал в sort, removeIf или filter, — маленькая стратегия. Ты пользовался паттерном задолго до того, как узнал его имя.

Iterator — обход, не зная устройства

Проблема. Список хранит элементы в массиве, множество — в хеш-таблице, очередь — цепочкой узлов. Если бы для обхода каждой коллекции нужно было знать её устройство, любой цикл ломался бы при замене ArrayList на HashSet.

Аналогия: контролёр в автобусе

Помнишь контролёра из урока 13.3? Ему всё равно, как стоят пассажиры — рядами, кучкой или по одному. Он знает только «есть ещё кто-то впереди?» и «подойти к следующему».

Итератор — отдельный объект, который знает, как ходить по коллекции, и выдаёт элементы по одному: hasNext() и next(). Коллекция только выдаёт итератор методом iterator() — это и есть интерфейс Iterable. А for-each — просто короткая запись цикла с итератором. Значит, for-each работает с любым классом, который реализует Iterable, в том числе с твоим:

import java.util.Iterator;
import java.util.NoSuchElementException;

class Playlist implements Iterable<String> {
    private final String[] songs;   // как устроено внутри — снаружи не видно

    Playlist(String... songs) {
        this.songs = songs;
    }

    @Override
    public Iterator<String> iterator() {
        return new Iterator<>() {
            private int pos = 0;

            @Override
            public boolean hasNext() {
                return pos < songs.length;
            }

            @Override
            public String next() {
                if (!hasNext()) {
                    throw new NoSuchElementException();
                }
                return songs[pos++];
            }
        };
    }
}
Playlist playlist = new Playlist("Утро", "Дорога", "Вечер");
for (String song : playlist) {
    System.out.println("♪ " + song);
}
♪ Утро
♪ Дорога
♪ Вечер

Итератор здесь — анонимный класс (урок 11.4), он видит поле songs своего плейлиста. Завтра ты заменишь массив на ArrayList — и ни один цикл, который ходит по плейлисту, не заметит разницы.

Где в JDK: у каждой коллекции из модуля 13 есть iterator(), поэтому все они работают в for-each.

Mediator — посредник

Проблема. Пять участников, и каждый должен общаться с каждым. Если каждый хранит ссылки на всех остальных, получается паутина: 10 связей, а у шестерых — уже 15. Добавить нового участника — значит поправить всех старых.

Аналогия: диспетчер аэропорта

Самолёты не договариваются между собой, кто садится первым: пилоты говорят только с вышкой. Диспетчер видит всю картину и решает: «вам посадка, вам ждать». Прилетел новый самолёт — ему нужна одна связь, с вышкой.

Посредник — объект, через который другие общаются. Участники знают только его, а он знает всех. Пример — чат-комната: участник не рассылает сообщение каждому, он отдаёт его комнате, а та разносит остальным.

import java.util.ArrayList;
import java.util.List;

class ChatRoom {
    private final List<ChatMember> members = new ArrayList<>();

    void join(ChatMember member) {
        members.add(member);
    }

    void send(ChatMember from, String text) {
        for (ChatMember m : members) {
            if (m != from) {
                m.receive(from.name() + ": " + text);
            }
        }
    }
}

class ChatMember {
    private final String name;
    private final ChatRoom room;   // знает только комнату, а не других участников

    ChatMember(String name, ChatRoom room) {
        this.name = name;
        this.room = room;
    }

    String name() {
        return name;
    }

    void say(String text) {
        room.send(this, text);
    }

    void receive(String message) {
        System.out.println("[" + name + "] " + message);
    }
}
ChatRoom room = new ChatRoom();
ChatMember anna = new ChatMember("Анна", room);
ChatMember boris = new ChatMember("Борис", room);
ChatMember vika = new ChatMember("Вика", room);
room.join(anna);
room.join(boris);
room.join(vika);
anna.say("Кто идёт в кино?");
[Борис] Анна: Кто идёт в кино?
[Вика] Анна: Кто идёт в кино?

Захочешь добавить правило «не пересылать сообщения с бранью» — оно появится в одном месте, в ChatRoom, а не в каждом участнике. Обратная сторона: посредник легко разрастается в «объект, который знает всё», — за этим нужно следить.

Observer — подписчики

Проблема. Посылка поменяла статус: «Прибыла в пункт выдачи». Об этом надо сообщить по SMS, в приложении и на почту, а завтра добавится ещё канал. Если посылка будет сама дёргать каждый канал, её код придётся менять при каждом новом способе оповещения.

Аналогия: подписка на канал

Блогер не обзванивает зрителей. Он выкладывает видео, а уведомление получают все, кто нажал «Подписаться». Кто захотел — подписался, кто устал — отписался, блогер об этом даже не думает.

Наблюдатель: объект хранит список подписчиков (слушателей) и, когда что-то случилось, оповещает каждого. Подписчики — снова объекты с общим интерфейсом, а значит, их удобно передавать лямбдами:

import java.util.ArrayList;
import java.util.List;

interface ParcelListener {
    void statusChanged(String status);
}

class Parcel {
    private final List<ParcelListener> listeners = new ArrayList<>();

    void subscribe(ParcelListener listener) {
        listeners.add(listener);
    }

    void setStatus(String status) {
        for (ParcelListener l : listeners) {
            l.statusChanged(status);
        }
    }
}
Parcel parcel = new Parcel();
parcel.subscribe(status -> System.out.println("SMS: " + status));
parcel.subscribe(status -> System.out.println("Push: " + status));
parcel.setStatus("Прибыла в пункт выдачи");
SMS: Прибыла в пункт выдачи
Push: Прибыла в пункт выдачи

Где встречается. Так устроены слушатели событий в любых программах с окнами: кнопке говорят «когда тебя нажмут — вызови вот это» (в Java-окнах это метод addActionListener(…)). Это тот же обратный вызов из урока 11.4, только подписчиков может быть сколько угодно.

Проверь себя

Поговори с наставником

Спроси: «Объясни на примере из жизни, чем Декоратор отличается от Заместителя, если у обоих тот же интерфейс». Или: «Дай мне три описания ситуаций, а я угадаю паттерн и объясню почему». После задачи про доставку: «Посмотри мой DeliveryCost: где у меня ещё остался выбор по типу через if?»

Коротко

  • Адаптер — переходник: чужой интерфейс подгоняется под нужный (Arrays.asList, InputStreamReader).
  • Декоратор — обёртка с тем же интерфейсом добавляет способность; обёртки вкладываются (BufferedReader).
  • Фасад — одна простая кнопка поверх сложной системы (Files.readString).
  • Заместитель — тот же интерфейс, но управляет доступом: лениво создаёт, кеширует, защищает (Collections.unmodifiableList).
  • Стратегия — алгоритм в отдельном объекте, подменяется без if; часто это лямбда (Comparator).
  • Итератор — обход без знания устройства; любой Iterable работает в for-each.
  • Посредник — все общаются через центр: паутина связей превращается в звезду.
  • Наблюдатель — подписчики получают оповещение о событии; источник знает только интерфейс слушателя.
