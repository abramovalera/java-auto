Чистый код: стиль, DRY, KISS, YAGNI

Программа работает — это половина дела. Вторая половина — чтобы её мог прочитать и поправить человек: коллега, ревьюер или ты сам через полгода. Сведём в одно правила оформления и разберём три принципа, которые знает каждый разработчик.

Повторение

Код пишут для людей

Компьютеру всё равно, как называются переменные и сколько стоит пробелов. Ему одинаково понятны оба метода ниже — они делают одно и то же: прибавляют к сумме заказа доставку, если заказ меньше 2000 ₽.

static int calc(int s) {
    return s >= 2000 ? s : s + 199;
}🚫 так не надо — не набирай
static final int FREE_DELIVERY_FROM = 2000;
static final int DELIVERY_PRICE = 199;

static int addDelivery(int orderSum) {
    if (orderSum >= FREE_DELIVERY_FROM) {
        return orderSum;
    }
    return orderSum + DELIVERY_PRICE;
}👀 просто прочитай

Первый короче, но чтобы его понять, надо расшифровать: что такое s? что за 2000 и 199? Второй читается как текст: «добавь доставку; если сумма заказа от порога бесплатной доставки — верни как есть, иначе прибавь цену доставки».

Код читают гораздо чаще, чем пишут. Ты пишешь метод один раз, а читают его потом десятки раз: ты сам, когда ищешь баг, коллега на код-ревью (просмотр чужого кода перед тем, как его примут в общую ветку), новичок в команде через год. Роберт Мартин в книге «Чистый код» прикидывает: на чтение кода уходит больше чем в десять раз больше времени, чем на его написание. Поэтому сэкономить минуту при написании и потерять час при чтении — плохой обмен.

Аналогия: коробки при переезде

Можно подписать коробки «1», «2», «3» — ты же помнишь, что где. Через неделю на новой квартире ты открываешь шесть коробок, чтобы найти чайник. А можно написать «Кухня: чайник, кружки». Пара секунд при упаковке — и никто не роется. Хорошие имена и понятная структура — это подписи на коробках с кодом.

Мартин Фаулер, один из самых известных авторов книг о программировании, говорил примерно так: код, который понимает компьютер, напишет любой, а хороший программист пишет код, который понимают люди. Такой код называют чистым: понятные имена, единый стиль, нет повторов, нет лишнего, нет сюрпризов. Это не про красоту, а про деньги и нервы: чистый код быстрее читать, проще менять и в нём труднее спрятаться багу.

Ты уже знаешь почти всё, чтобы писать работающие программы. Сегодня — о том, как писать их так, чтобы за тебя не было стыдно на код-ревью. Хорошая новость: половину работы сделает IDEA.

Имена: все правила в одном месте

Правила имён ты встречал по кусочкам в уроках 1.6 и 2.3. Вот они вместе. Это код-стайл (code style) — договорённость, как оформлять код. Компилятор их не проверяет, но их соблюдает весь мир Java, и код с другими именами сразу выглядит «чужим».

Кроме формы имени важен смысл. Имя должно говорить, что хранит переменная или что делает метод: daysUntilDelivery лучше, чем d, days или temp. Однобуквенные имена допустимы только там, где их смысл очевиден: счётчик цикла i, параметр короткой лямбды o -> o.total().

Магические числа

Магическое число — число прямо посреди кода без объяснения, что оно значит. Помнишь 2000 и 199 из первого примера? Через месяц никто не вспомнит, что 199 — цена доставки, а не, скажем, номер склада. А если цена изменится, придётся искать все 199 по проекту и гадать, какие из них про доставку.

Лекарство — именованная константа: static final int DELIVERY_PRICE = 199;. Число записано один раз, у него есть имя, менять — в одном месте. В IDEA: поставь курсор на число и нажми Ctrl+Alt+C (Extract Constant) — IDEA сама создаст константу и подставит её вместо числа. Неудачное имя переименовывай через Shift+F6 — оно поменяется везде сразу.

В коде интернет-магазина встретилась строка if (order.status() == 3) { … }. Что делает эта проверка?

Никто не знает — и в этом проблема. 3 — это «оплачен»? «доставлен»? «отменён»? Придётся искать, где статусы раздаются. Чистый вариант — константа STATUS_DELIVERED или, ещё лучше, enum: if (order.status() == Status.DELIVERED). Тогда строка объясняет сама себя.

А комментарии?

Если код понятен из имён, комментарий «что делает строка» не нужен: // прибавляем доставку над методом addDelivery только повторяет имя. Комментарий полезен, когда объясняет почему сделано так, а не иначе: // склад закрыт по воскресеньям — переносим отправку на понедельник. Хочется написать комментарий «что тут происходит» — сначала попробуй дать переменной или методу имя получше.

Оформление и помощники: IDEA и Checkstyle

Кроме имён код-стайл договаривается о том, как код выглядит:

  • Отступ — каждый уровень вложенности сдвигается вправо (в IDEA по умолчанию — 4 пробела).
  • Открывающая фигурная скобка — на той же строке, что if, метод или класс. Закрывающая — на своей строке, под началом конструкции. else пишется сразу после закрывающей скобки: } else {.
  • Фигурные скобки — всегда, даже если внутри if одна строка. Без них легко добавить вторую строку и думать, что она тоже внутри условия.
  • Длина строки — не больше 100–120 символов (договаривается команда). Длинную строку переносят, а продолжение сдвигают дополнительным отступом. В IDEA справа в редакторе видна тонкая вертикальная линия — граница, за которую лучше не заходить.
  • Одна команда — одна строка, между методами — пустая строка.
if (orderSum >= FREE_DELIVERY_FROM)
{
    return orderSum;
}
else return orderSum + DELIVERY_PRICE;🚫 не по стилю Java
if (orderSum >= FREE_DELIVERY_FROM) {
    return orderSum;
} else {
    return orderSum + DELIVERY_PRICE;
}👀 так принято в Java

Длинная цепочка Stream переносится так, чтобы каждый шаг был на своей строке, — точка в начале строки:

List<String> bigBuyers = orders.stream()
        .filter(order -> order.total() > 10_000)
        .map(Order::customer)
        .distinct()
        .toList();👀 просто прочитай
Стилей несколько — главное, один на проект

Самые известные своды правил — Google Java Style (отступ 2 пробела, строка до 100 символов) и правила, к которым по умолчанию настроена IDEA (отступ 4 пробела, строка до 120). Они отличаются в мелочах, а совпадают в главном: имена, скобки, переносы. В команде выбирают один стиль и держатся его во всём проекте. Смешанный стиль хуже любого из двух.

Ctrl+Alt+L — форматирование одной клавишей

Расставлять пробелы и отступы руками не нужно. Ctrl+Alt+L (Code → Reformat Code) приводит весь файл к стилю проекта: отступы, пробелы вокруг = и +, скобки, переносы. Ты знаешь эту клавишу с модуля 1 — теперь сделай её привычкой: нажимай перед каждым коммитом. А Ctrl+Alt+O заодно уберёт неиспользуемые import.

Checkstyle — проверка стиля при сборке

IDEA подсказывает, но не заставляет: можно проигнорировать жёлтое и закоммитить. В команде, где десять человек, стиль поплывёт за месяц. Поэтому стиль проверяют автоматически при каждой сборке. Самый известный инструмент для Java — Checkstyle: он читает исходники и сверяет их со списком правил — имена, длина строк, скобки, магические числа и ещё сотни других.

В Gradle он подключается одной строкой — плагином checkstyle в блоке plugins. Правила лежат в XML-файле config/checkstyle/checkstyle.xml. Писать его с нуля не нужно: в проекте его обычно уже положил кто-то из команды, а за основу часто берут готовый набор правил Google Java Style. Дальше обычная задача check (а значит, и build) сама запускает проверку стиля:

Здесь замечания — предупреждения, и сборка прошла. Многие команды настраивают Checkstyle строже: есть хоть одно замечание — сборка красная, как при упавшем тесте. Тогда код «не по стилю» просто не попадёт в общую ветку. Настраивать Checkstyle самому пока не нужно: достаточно понимать, что это такое и что делать, если сборка ругается на стиль, — открыть отчёт и поправить строки. Для IDEA есть ещё плагин CheckStyle-IDEA: он показывает те же замечания прямо в редакторе.

DRY: не повторяйся

DRY — Don't Repeat Yourself, «не повторяйся». Каждое правило программы должно быть записано в одном месте. Звучит очевидно, но копипаста — самый быстрый способ написать код, и поэтому она повсюду. Вот магазин: скидка 10% на заказы от 5000 ₽ нужна в трёх местах — в чеке, в SMS и при оплате бонусами:

static void printReceipt(int sum) {
    int toPay = sum >= 5000 ? sum - sum / 10 : sum;
    System.out.println("К оплате: " + toPay);
}

static void sendSms(int sum) {
    int toPay = sum >= 5000 ? sum - sum / 10 : sum;
    System.out.println("SMS: заказ на " + toPay + " ₽");
}

static boolean canPayByBonuses(int sum, int bonuses) {
    int toPay = sum >= 5000 ? sum - sum / 10 : sum;
    return bonuses >= toPay;
}🚫 так не надо — не набирай

Пока правило не меняется, всё работает. Но правила меняются всегда.

Маркетологи снизили порог скидки до 3000 ₽. Программист поправил printReceipt и sendSms, а про canPayByBonuses забыл. У покупателя заказ на 4000 ₽ и 3700 бонусов. Что он увидит?

В чеке и в SMS — «к оплате 3600» (4000 минус 10%). А при попытке оплатить бонусами — отказ: третий метод всё ещё считает по старому правилу, скидки нет, нужно 4000, а бонусов 3700. Покупатель видит «3600», у него 3700 — и ему отказывают. Баг, жалоба в поддержку, и никакой ошибки компиляции: код же «работает».

Лечится выносом правила в отдельный метод, а чисел — в константы. Три метода теперь не считают скидку сами, а спрашивают у одного:

public class DiscountShop {
    static final int DISCOUNT_FROM = 3000;
    static final int DISCOUNT_PERCENT = 10;

    public static void main(String[] args) {
        printReceipt(4000);
        sendSms(4000);
        System.out.println(canPayByBonuses(4000, 3700));
    }

    static int priceWithDiscount(int sum) {
        if (sum >= DISCOUNT_FROM) {
            return sum - sum * DISCOUNT_PERCENT / 100;
        }
        return sum;
    }

    static void printReceipt(int sum) {
        System.out.println("К оплате: " + priceWithDiscount(sum));
    }

    static void sendSms(int sum) {
        System.out.println("SMS: заказ на " + priceWithDiscount(sum) + " ₽");
    }

    static boolean canPayByBonuses(int sum, int bonuses) {
        return bonuses >= priceWithDiscount(sum);
    }
}

Теперь порог скидки меняется в одной строке, и забыть «третье место» невозможно — его нет. Обрати внимание: метод priceWithDiscount назван не по глаголу. Так тоже можно, когда метод просто вычисляет значение и имя читается как ответ: «цена со скидкой». Главное — чтобы имя объясняло смысл.

Делать это руками не обязательно. Выдели повторяющийся кусок и нажми Ctrl+Alt+M (Refactor → Extract Method): IDEA вынесет его в новый метод, спросит имя и — что особенно приятно — сама найдёт такие же куски в классе и предложит заменить и их.

Такая переделка кода без изменения его поведения называется рефакторинг. Программа делает то же самое, но устроена лучше. Делать рефакторинг спокойно позволяют тесты из прошлых уроков: зелёные до и после — значит, ничего не сломал.

Правило трёх

Написал кусок первый раз — просто пиши. Скопировал второй раз — поморщись, но можно. Тянешься скопировать в третий — останавливайся и выноси в метод.

Не перестарайся: похожее ≠ одинаковое

DRY — про одно знание в одном месте, а не про одинаковые буквы. Два метода ниже выглядят одинаково, но это два разных правила: цена доставки за килограмм и цена коробки. Склеишь их в один multiplyBy50(int x) — а потом курьерская служба поднимет тариф до 60 ₽, упаковка останется по 50, и склеенный метод придётся расклеивать. Похожий код с разным смыслом оставляй раздельным и дай числам разные имена: PRICE_PER_KG и PRICE_PER_BOX.

static int calculateDeliveryPrice(int weightKg) {
    return weightKg * PRICE_PER_KG;      // сейчас 50, но живёт своей жизнью
}

static int calculatePackagingPrice(int boxes) {
    return boxes * PRICE_PER_BOX;        // тоже 50 — совпадение, а не правило
}👀 просто прочитай

KISS: делай проще

KISS — Keep It Simple, Stupid, «делай проще, глупыш». Из двух решений, которые одинаково работают, выбирай то, которое проще прочитать. Программисты любят хитрые однострочники: написал — чувствуешь себя гением. Но читать их будет тот, кто не был у тебя в голове в момент написания. Есть известная мысль Брайана Кернигана: отлаживать код вдвое труднее, чем писать, — так что если ты написал код на пределе своей хитрости, отладить его ты уже не сможешь.

Вложенные тернарники → if с ранним return

Метод определяет размер посылки по весу:

static String findSize(int weightKg) {
    return weightKg > 20 ? "большая"
            : weightKg > 5 ? "средняя"
            : weightKg > 0 ? "маленькая" : "ошибка";
}🚫 так не надо — не набирай

Чтобы понять, что вернётся для 5 кг, нужно мысленно пройти всю цепочку ? :. Перепишем через if — каждая ветка отдельной строкой и сразу return:

static String findSize(int weightKg) {
    if (weightKg <= 0) {
        return "ошибка";
    }
    if (weightKg <= 5) {
        return "маленькая";
    }
    if (weightKg <= 20) {
        return "средняя";
    }
    return "большая";
}👀 целиком наберёшь ниже

Строк больше, а читать проще: сверху вниз, как список правил. Тернарный оператор хорош для одного простого выбора (count == 1 ? "товар" : "товаров"), но вложенный в другой тернарник — уже ребус. Если выбор идёт по конкретным значениям (зона 1, 2, 3…), а не по диапазонам, ещё лучше подойдёт switch со стрелками: case 1 -> "центр";.

Ранний return вместо «лесенки»

Каждый вложенный if сдвигает код вправо, и скоро он превращается в лесенку, где непонятно, какой else к какому if относится:

static String checkout(String address, int items, boolean paid) {
    if (address != null) {
        if (items > 0) {
            if (paid) {
                return "Отправляем заказ";
            } else {
                return "Заказ не оплачен";
            }
        } else {
            return "Корзина пуста";
        }
    } else {
        return "Нет адреса";
    }
}🚫 так не надо — не набирай

Приём ранний return (его ещё называют guard clause — «условие-охранник»): сначала отсекаем все плохие случаи и сразу выходим из метода. Что осталось в конце — нормальный путь, без вложенности:

static String checkout(String address, int items, boolean paid) {
    if (address == null) {
        return "Нет адреса";
    }
    if (items <= 0) {
        return "Корзина пуста";
    }
    if (!paid) {
        return "Заказ не оплачен";
    }
    return "Отправляем заказ";
}👀 целиком наберёшь ниже

if, который возвращает true или false

Как записать короче, не меняя смысла?
if (age >= 18) { return true; } else { return false; }

return age >= 18; — сравнение уже даёт boolean: true или false. Обёртка из if просто переписывает этот ответ ещё раз. Это та самая серая подсветка «'if' statement can be simplified» со скрина в шаге про инспекции — Alt+Enter сделает замену сам.

Собери оба исправленных метода в один класс и проверь, что они работают так же, как старые:

public class OrderDesk {

        System.out.println(checkout("Лесная, 5", 3, true));

            return "средняя";

    static String checkout(String address, int items, boolean paid) {

}

KISS касается и Stream: цепочка из трёх шагов читается как фраза, а из десяти шагов с лямбдами внутри лямбд — уже нет. Если цепочку трудно прочитать вслух, разбей её на части с понятными именами или напиши обычный цикл. Простой цикл — не позор.

YAGNI: тебе это не понадобится

YAGNI — You Aren't Gonna Need It, «тебе это не понадобится». Не пиши код «на будущее»: классы, настройки и параметры, которые никто не просил. Задача: посчитать цену доставки курьером — 300 ₽ плюс 50 ₽ за каждый килограмм. Начитавшийся про интерфейсы программист пишет так:

// вызов: DeliveryFactory.create("courier").calculatePrice(3)

interface DeliveryStrategy {
    int calculatePrice(int weightKg);
}

class CourierDelivery implements DeliveryStrategy {
    public int calculatePrice(int weightKg) {
        return 300 + weightKg * 50;
    }
}

class DeliveryFactory {
    static DeliveryStrategy create(String type) {
        return switch (type) {
            case "courier" -> new CourierDelivery();
            // "drone", "teleport" — на будущее, вдруг пригодится
            default -> throw new IllegalArgumentException(type);
        };
    }
}🚫 так не надо — не набирай

Три типа и фабрика, чтобы умножить и сложить. А вот что действительно нужно по задаче:

static final int BASE_PRICE = 300;
static final int PRICE_PER_KG = 50;

static int calculateDeliveryPrice(int weightKg) {
    return BASE_PRICE + weightKg * PRICE_PER_KG;
}👀 просто прочитай

Почему «на будущее» — плохая идея:

  • Будущее почти никогда не наступает таким, каким его представили. Доставку дронами так и не сделают, а когда понадобится самовывоз, окажется, что заготовка под него не подходит: у самовывоза нет веса, зато есть адрес пункта выдачи.
  • Лишний код не бесплатный. Его читают, поддерживают, обновляют, в нём живут баги — хотя он не делает ничего полезного.
  • Простой код легко расширить, когда придёт время. Появится второй способ доставки по-настоящему — тогда и введёшь интерфейс. С тестами такой рефакторинг займёт полчаса.
YAGNI — не оправдание для халтуры

YAGNI про новые возможности, которые никто не просил. Проверить входные данные, обработать ошибку, написать тесты, дать нормальные имена — это не «на будущее», это нужно уже сейчас. «Вес не может быть отрицательным» — часть задачи, а «вдруг понадобится телепорт» — нет.

Коротко

  • Код читают намного чаще, чем пишут. Чистый код — понятный человеку: хорошие имена, единый стиль, ничего лишнего.
  • Имена: классы — PascalCase, переменные и методы — camelCase, методы — с глагола, константы — UPPER_SNAKE_CASE, пакеты — маленькими буквами. Магические числа — в именованные константы.
  • Оформление: скобка открывается на той же строке, закрывается на своей; строки до 100–120 символов; Ctrl+Alt+L перед коммитом.
  • Жёлтое и серое в IDEA — инспекции, их стоит убрать. Checkstyle проверяет стиль автоматически при сборке Gradle.
  • DRY — одно правило в одном месте (но похожий код с разным смыслом не склеивать). KISS — самое простое решение: ранний return вместо лесенки, if вместо вложенных тернарников. YAGNI — не писать «на будущее».
