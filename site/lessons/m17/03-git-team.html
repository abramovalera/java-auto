Удалённый репозиторий

Чтобы работать вместе, нужен общий репозиторий на сервере — удалённый (remote). Его держат на сервисах GitHub, GitLab или Bitbucket. Это не «другой Git», а такой же репозиторий, просто лежит он на сервере, и у каждого члена команды есть его полная копия на компьютере.

clone
Скачать удалённый репозиторий целиком, со всей историей. Делается один раз, в начале работы с проектом.
push
Отправить свои новые коммиты на сервер. Пока не сделал push — коммиты видишь только ты.
pull
Забрать с сервера чужие новые коммиты и влить их в свою ветку. Это fetch (скачать) + merge (влить).
origin
Обычное имя удалённого репозитория, откуда ты сделал clone.
Аналогия: общий фотоальбом в облаке

У каждого на телефоне копия альбома. Сделал фото — оно у тебя (commit). Загрузил в облако — увидели все (push). Открыл альбом — подтянулись фото друзей (pull).

Clone, pull и push в IDEA

  1. Clone: на главном экране IDEA Get from VCS (или File → New → Project from Version Control) → вставить адрес репозитория (кнопка Code на GitHub, Clone на GitLab) → Clone. IDEA скачает проект и откроет его.
  2. Pull: Ctrl+T — Update Project. Делай это каждое утро и перед тем, как начать новую задачу.
  3. Push: Ctrl+Shift+K. IDEA покажет, какие коммиты уйдут и в какую ветку. Можно сразу из окна коммита: Commit and Push…

Pull — Ctrl+T. В первый раз IDEA спросит, как вливать чужие коммиты:

Push — Ctrl+Shift+K:

git clone https://github.com/team/shop-app.git
git pull
git push -u origin feature/login
To https://github.com/team/shop-app.git

-u origin feature/login нужен один раз для новой ветки: «отправь её в origin и запомни связь». Дальше хватит просто git push.

Вход на GitHub/GitLab

Обычный пароль от сайта для push давно не принимают. IDEA сама предложит войти через браузер (Log In via GitHub) — это самый простой путь. Альтернатива — токен доступа или SSH-ключ. Никогда не вставляй токен в код и не коммить его.

Ты сделал три коммита, но не сделал push, и выключил компьютер. Коллега делает pull. Увидит ли он твои коммиты?

Нет. Коммиты живут в твоей локальной копии, на сервер они не уходили. Push — единственный способ поделиться. Поэтому в конце рабочего дня ветку принято пушить, даже если задача не закончена.

Свой проект — на GitHub

Clone — когда репозиторий на сервере уже есть. А если проект твой и живёт пока только на компьютере? Его можно выложить на GitHub в пару щелчков. Это и резервная копия, и портфолио: на собеседовании ссылка на свои проекты говорит больше любых слов.

  1. Заведи бесплатный аккаунт на github.com.
  2. Проверь .gitignore (урок 17.2): в истории не должно быть паролей, out/, build/.
  3. В IDEA: ☰ → Git → GitHub → Share Project on GitHub (если Git в проекте ещё не включён — ☰ → VCS → Share Project on GitHub).
  4. Впиши имя репозитория, реши, будет ли он приватным, → Share. В первый раз IDEA попросит войти: кнопка Log In via GitHub… откроет браузер, там подтверждаешь вход.
  5. Если в проекте ещё нет коммитов, IDEA покажет окно Add Files For Initial Commit: проверь список файлов → Add. IDEA сама создаст репозиторий на GitHub, сделает коммит и push.
  6. Дальше всё как обычно: коммит Ctrl+K, отправка Ctrl+Shift+K.

Без IDEA делают так: создают на сайте GitHub пустой репозиторий (кнопка New), копируют его адрес и связывают с ним свой проект:

git remote add origin https://github.com/misha/minibank.git
git push -u origin main

git remote add origin адрес — «запомни сервер под именем origin», дальше обычный первый push ветки.

Merge request: как код попадает в main

В командах никто не коммитит прямо в main. Каждая задача — своя ветка, а слияние идёт через запрос на слияние: в GitLab он называется Merge Request (MR), в GitHub — Pull Request (PR). Это страница, где видно все изменения ветки, коллеги оставляют комментарии, а сервер сборки (CI) автоматически прогоняет тесты.

Зачем тут тесты

Тесты проекта запускаются на каждый merge request. Красный тест — и MR не сольют, пока не разберутся: баг в коде или тест устарел. Поэтому тесты обязаны быть стабильными и понятными: на них смотрит вся команда. Писать такие тесты на JUnit ты научишься в уроках 5–7 этого модуля.

Конфликт: двое правили одно место

Обычно Git сливает ветки сам: ты менял один файл, коллега — другой, или вы правили разные места одного файла. Но если двое поменяли одни и те же строки по-разному, Git не может решить, кто прав, и останавливается: конфликт слияния (merge conflict).

Аналогия: общий документ

Вы с другом редактируете один договор оффлайн. Ты пишешь в пункте 3 «срок — 10 дней», он — «срок — 15 дней». Когда соединяете версии, кто-то должен посмотреть на оба варианта и решить. Компьютер за людей это решать не должен — и Git не решает.

Пример: в файле ShopConfig.java ветки main была строка static int deliveryDays = 4; — срок доставки в днях, объявление поля с инициализацией значением 4. Аня в своей ветке поменяла инициализирующее значение на 10, Боря в своей ветке feature/delivery — на 6. Ветку Ани уже слили в main на сервере через merge request.

Боря хочет подтянуть свежий main в свою ветку. Ловушка: его локальный main ничего не знает о слиянии на сервере. Напиши он сразу git merge main — Git ответит Already up to date, «всё и так свежее». Поэтому сначала обновляем main через pull, и только потом вливаем:

git switch main
git pull
Updating 4b7d201..e91c3a0
 src/ShopConfig.java | 2 +-
git switch feature/delivery
git merge main
CONFLICT (content): Merge conflict in src/ShopConfig.java
Automatic merge failed; fix conflicts and then commit the result.

В IDEA то же самое короче: Fetch (☰ → Git → Fetch), потом в списке веток origin/main → Merge 'origin/main' into 'feature/delivery' — сливаем сразу серверную версию (тогда в нижней метке будет написано origin/main). В файле появляются метки конфликта:

public class ShopConfig {
<<<<<<< HEAD
    static int deliveryDays = 6;
=======
    static int deliveryDays = 10;
>>>>>>> main
    static String shopName = "Ромашка";
}
<<<<<<< HEAD

Начало конфликта. Ниже — твой вариант (HEAD — текущая ветка, в которую сливаем).

=======

Разделитель между вариантами.

>>>>>>> main

Конец конфликта. Выше — вариант из вливаемой ветки.

Решить конфликт = оставить правильный вариант (или собрать из двух новый), удалить все метки и закоммитить. Файл с метками даже не скомпилируется — <<<<<<< не Java.

Аня поменяла строку 5 в LoginTest.java, Боря — строку 40 в том же файле. Будет конфликт?

Нет. Изменения в разных местах одного файла Git сливает сам. Конфликт возникает только когда правки задевают одни и те же или соседние строки. Поэтому маленькие частые коммиты и регулярный pull уменьшают конфликты.

Трёхпанельный merge в IDEA

Как только Git наткнулся на конфликт, IDEA сама открывает окно Conflicts:

Руками править метки неудобно. IDEA при конфликте показывает окно Conflicts со списком файлов. Выбери файл → Merge… — и откроется окно из трёх панелей:

  1. Для каждого конфликтного места реши: взять левый вариант (»), правый («), оба по очереди или поправить центр руками.
  2. Ненужный вариант отбрось крестиком ✕. Неконфликтные изменения IDEA уже перенесла сама — кнопка Apply non-conflicting changes вверху.
  3. Нажми Apply. Запусти тесты — убедись, что после слияния всё работает.
  4. Закоммить результат слияния (Ctrl+K) и сделай push.

Главное правило конфликта: не угадывай. Если не знаешь, почему коллега поставил 10, а не 6, — спроси его. Неправильно решённый конфликт тихо выкидывает чужую работу, и тесты потом падают «необъяснимо».

Ещё три слова из команды: fetch, rebase, stash

Их нет в «минимуме для выживания», но на работе ты услышишь их в первую же неделю. Коротко, чтобы не теряться.

fetch
«Сходить на сервер и посмотреть, что нового» — скачать чужие коммиты и ветки, ничего не вливая в твои файлы. pull = fetch + слияние. В IDEA: ☰ → Git → Fetch, после него в списке веток видны свежие origin/….
rebase
Другой способ подтянуть свежий main в свою ветку. Merge добавляет коммит «слил main в ветку», а rebase переставляет твои коммиты так, будто ты начал работу только что, от свежего main. История получается прямой линией — многие команды требуют именно так.
stash
«Карман». Ты на середине задачи, коммитить рано, а нужно срочно переключиться в другую ветку чинить баг. Stash прячет незакоммиченные правки и возвращает файлы к последнему коммиту; потом Unstash достаёт их обратно.
Аналогия: очередь в магазине

Ты встал в очередь (ответвился от main), отошёл за молоком — а за это время прошли пять человек (чужие коммиты в main). Merge — вернуться на своё старое место и сказать «я тут стоял». Rebase — честно встать в конец обновлённой очереди: твои покупки те же, но стоишь ты уже после всех.

Два правила rebase

1) Rebase меняет хеши твоих коммитов, поэтому уже запушенную ветку после него придётся отправить с перезаписью: окно Push → стрелка у кнопки → Force Push (IDEA делает это безопасным способом, --force-with-lease). 2) Так можно делать только со своей веткой. Rebase и force push общей ветки main — запрещённый приём: у коллег сломается история. Конфликты при rebase решаются в том же трёхпанельном окне, потом — Continue Rebasing.

А вот stash: ☰ → Git → Uncommitted Changes → Stash Changes…

🔎 Для любопытных: Shelve — «полка» IDEA

В окне Commit есть похожее действие Shelve Changes. Это собственный «карман» IDEA, не Git: работает так же, но хранится только в твоей IDEA. Коллеги чаще говорят «застешь», так что запомни stash.

Коротко

  • Удалённый репозиторий (GitHub/GitLab) — общий; у каждого — полная локальная копия.
  • clone — скачать, pull (Ctrl+T) — забрать чужое, push (Ctrl+Shift+K) — отдать своё.
  • Задача: ветка → коммиты → push → merge request → ревью + CI с тестами → merge.
  • Конфликт — двое правили одни строки. Решаешь в трёхпанельном окне, удаляешь метки, проверяешь тестами, коммитишь.
  • Перед слиянием main в свою ветку — сначала pull (или Fetch и merge origin/main), иначе локальный main устарел.
  • Свой проект на GitHub: ☰ → Git → GitHub → Share Project on GitHub.
  • Маленькие коммиты, частый pull и маленькие MR — меньше конфликтов и лучше ревью.
