Паттерны проектирования: как создавать объекты

Многие задачи в программировании повторяются из проекта в проект: «нужен ровно один такой объект», «у объекта двадцать необязательных настроек», «сделай такой же, только чуть другой». Для них давно есть проверенные решения с именами. Сегодня — пять решений о том, как создавать объекты.

Повторение

Что такое паттерн проектирования

Паттерн проектирования (design pattern, шаблон проектирования) — это готовое проверенное решение типичной задачи в устройстве программы. Не кусок кода, который копируют, а идея: какие классы завести, кто кого создаёт и кто кого вызывает. Под каждую программу её пишут заново своими словами.

Аналогия: кулинарные рецепты

«Бисквит», «заварной крем», «маринад» — у каждого рецепта есть имя, и повар понимает другого повара с одного слова. Рецепт не говорит, какой торт печь, — он говорит, как сделать часть, которая нужна во многих тортах. Паттерны — такие рецепты для программ: «здесь строитель», «тут одиночка» — и коллега сразу представляет, как устроен код.

Самые известные паттерны собрали в 1994 году четыре автора: Эрих Гамма, Ричард Хелм, Ральф Джонсон и Джон Влиссидес. Книга называется «Приёмы объектно-ориентированного проектирования. Паттерны проектирования», а авторов прозвали «бандой четырёх» (Gang of Four, GoF). В книге 23 паттерна, разложенных на три группы:

А ты уже пользовался паттернами, просто не знал их имён! Iterator из модуля 13 — это паттерн «Итератор». А когда ты передаёшь в sort лямбду-Comparator, ты подставляешь «Стратегию» — способ сравнения, который можно поменять.

Паттерн — не цель

Паттерны — это словарь для общения с коллегами и подсказка, когда задача похожа на типичную. Вставлять их «потому что модно» или «чтобы код выглядел профессионально» — плохая идея: простой код превращается в лабиринт из фабрик и интерфейсов. Помнишь KISS и YAGNI из урока 17.8? Сначала пиши просто. Паттерн нужен, когда без него уже больно.

Singleton — одиночка

Иногда объект должен быть ровно один на всю программу: настройки приложения, журнал (лог), подключение к общему ресурсу. Если каждый класс создаст свои «настройки» через new, один поменяет тему на тёмную, а другой об этом не узнает. Одиночка (Singleton) гарантирует: объект один, и все получают именно его.

Рецепт из трёх деталей — все они тебе знакомы по урокам про static и конструкторы:

public class AppSettings {
    private static final AppSettings INSTANCE = new AppSettings();

    private String theme = "светлая";

    private AppSettings() {
    }

    public static AppSettings getInstance() {
        return INSTANCE;
    }

    public String getTheme() {
        return theme;
    }

    public void setTheme(String theme) {
        this.theme = theme;
    }
}
private AppSettings() { }

Приватный конструктор. Снаружи класса new AppSettings() не скомпилируется — второй объект просто не создать.

private static final AppSettings INSTANCE = new AppSettings();

Единственный объект создаётся внутри класса и хранится в static-поле: оно одно на весь класс, а не своё у каждого объекта. final — подменить его нельзя.

public static AppSettings getInstance()

Статический метод — единственный вход. Кто бы его ни вызвал, получит ссылку на один и тот же объект.

AppSettings a = AppSettings.getInstance();
AppSettings b = AppSettings.getInstance();
a.setTheme("тёмная");
System.out.println(b.getTheme());
System.out.println(a == b);
Тему меняли через a, а спрашиваем у b. Что выведется?

тёмная и true. a и b — две переменные, но ссылаются они на один объект: getInstance() оба раза вернул INSTANCE. Поэтому == (сравнение ссылок) даёт true. Знакомый пример из JDK — Runtime.getRuntime(): объект «среда выполнения» на всю программу один.

Вариант через enum. Ты знаешь: у enum каждое значение существует в одном экземпляре, и JVM сама следит, чтобы не появилось второго. Значит, enum с одним значением — готовый одиночка, самый короткий и самый надёжный:

public enum Clipboard {
    INSTANCE;

    private String text = "";

    public void copy(String text) {
        this.text = text;
    }

    public String paste() {
        return text;
    }
}

Пользуются так: Clipboard.INSTANCE.copy("привет"); — и в любом другом месте программы Clipboard.INSTANCE.paste() вернёт "привет".

«Ленивый» одиночка и потоки

Иногда объект создают не сразу, а при первом вызове: if (instance == null) instance = new AppSettings();. В программе с несколькими потоками это ловушка из модуля 16: два потока одновременно увидят null — и создадут два объекта. Гонка (race condition) в чистом виде. Делать «ленивый» вариант надёжно умеют, но это отдельная тонкая тема. Тебе хватит правила: бери вариант со static final-полем (как выше) или enum — оба безопасны без лишних усилий.

Мешает тестам

Один тест поставил тёмную тему, следующий ждёт светлую — и падает, если запустить их в другом порядке. Тесты перестают быть независимыми (помнишь FIRST?).

Поэтому одиночку иногда даже называют антипаттерном. В больших программах обычно делают иначе: объект создают один раз в начале программы и передают через конструктор тем, кому он нужен. Объект по-прежнему один, но зависимость видна, а в тесте вместо него легко подставить другой.

Factory Method — фабричный метод

Начнём с простого и очень частого приёма — статического фабричного метода. Это обычный static-метод, который создаёт и возвращает объект вместо того, чтобы ты писал new сам. Ты ими давно пользуешься:

List<String> days = List.of("пн", "вт", "ср");   // а не new ArrayList<>()
Integer price = Integer.valueOf(100);             // а не new Integer(100)

Свой такой метод выглядит так. Магазину нужно уведомлять покупателя, а каналы бывают разные:

interface Notifier {
    void send(String text);
}

class SmsNotifier implements Notifier {
    public void send(String text) {
        System.out.println("SMS: " + text);
    }
}

class EmailNotifier implements Notifier {
    public void send(String text) {
        System.out.println("Письмо: " + text);
    }
}

public class Notifiers {
    static Notifier of(String channel) {
        return switch (channel) {
            case "sms" -> new SmsNotifier();
            case "email" -> new EmailNotifier();
            default -> throw new IllegalArgumentException(
                    "Нет канала: " + channel);
        };
    }
}

Тот, кто пользуется, пишет Notifier n = Notifiers.of("sms"); n.send("Заказ готов"); и знает только интерфейс. Чем это лучше new:

  • У метода есть имя. List.of, Integer.valueOf, Notifiers.of — по имени понятно, что получишь. У конструктора имя всегда одно — как у класса.
  • Можно вернуть любой подкласс. Вызывающий не знает про SmsNotifier — завтра его заменят другим классом, и чужой код не изменится.
  • Можно не создавать новый объект. new всегда создаёт новый, а фабрика может вернуть готовый.
  • Выбор класса — в одном месте. Новый канал — правка в одном методе, а не во всех местах, где были new.
Integer a = Integer.valueOf(100); Integer b = Integer.valueOf(100); — чему равно a == b? А если вместо 100 взять 1000?

Для 100 — true, для 1000 — false. Это та самая ловушка с кешем Integer от −128 до 127. Фабричный метод valueOf для маленьких чисел не создаёт новый объект, а возвращает готовый из кеша. Конструктор так бы не смог: new всегда даёт новый объект. Поэтому == с обёртками использовать нельзя — только equals.

Фабричный метод из книги GoF — шаг дальше. Там метод создания объявляет родитель, а что именно создать, решают наследники. Служба доставки: порядок доставки у всех одинаковый, а транспорт разный.

interface Transport {
    String name();
}

class Bike implements Transport {
    public String name() {
        return "Велокурьер";
    }
}

class Truck implements Transport {
    public String name() {
        return "Грузовик";
    }
}

abstract class Delivery {
    abstract Transport createTransport();      // фабричный метод

    void deliver(String parcel) {
        Transport t = createTransport();       // кого создать — решит наследник
        System.out.println(t.name() + " везёт: " + parcel);
    }
}

class CityDelivery extends Delivery {
    @Override
    Transport createTransport() {
        return new Bike();
    }
}

class CountryDelivery extends Delivery {
    @Override
    Transport createTransport() {
        return new Truck();
    }
}

public class DeliveryDemo {
    public static void main(String[] args) {
        new CityDelivery().deliver("пицца");
        new CountryDelivery().deliver("диван");
    }
}
Велокурьер везёт: пицца
Грузовик везёт: диван

Нужна доставка дронами? Новый класс DroneDelivery со своим createTransport() — и ни строчки правки в Delivery. Это принцип открытости/закрытости из SOLID в действии. Пример из JDK: метод iterator() у коллекций — фабричный метод. ArrayList создаёт свой итератор, HashSet — свой, а цикл for-each работает с любым.

Abstract Factory — абстрактная фабрика

Бывает, что объекты нужны не по одному, а семейством, и они должны подходить друг к другу. В приложении есть светлая и тёмная тема. Светлая кнопка в тёмном окне — некрасиво, значит, кнопку и окно всегда надо брать из одной темы. Абстрактная фабрика — интерфейс, который умеет создать всё семейство целиком:

interface Button { String draw(); }
interface Window { String draw(); }

class LightButton implements Button {
    public String draw() { return "[светлая кнопка]"; }
}
class LightWindow implements Window {
    public String draw() { return "светлое окно"; }
}
class DarkButton implements Button {
    public String draw() { return "[тёмная кнопка]"; }
}
class DarkWindow implements Window {
    public String draw() { return "тёмное окно"; }
}

interface ThemeFactory {                // абстрактная фабрика: всё семейство
    Button createButton();
    Window createWindow();
}

class LightTheme implements ThemeFactory {
    public Button createButton() { return new LightButton(); }
    public Window createWindow() { return new LightWindow(); }
}

class DarkTheme implements ThemeFactory {
    public Button createButton() { return new DarkButton(); }
    public Window createWindow() { return new DarkWindow(); }
}

public class ThemeDemo {
    static void showDialog(ThemeFactory theme) {
        Window w = theme.createWindow();
        Button b = theme.createButton();
        System.out.println(w.draw() + " с кнопкой " + b.draw());
    }

    public static void main(String[] args) {
        showDialog(new DarkTheme());
    }
}
тёмное окно с кнопкой [тёмная кнопка]

Метод showDialog не знает ни одного конкретного класса кнопки. Перепутать темы он не может: всё берётся из одной фабрики. Сменить тему всего приложения — значит передать другой объект-фабрику.

Фабричный методАбстрактная фабрика
Что создаётОдин объектСемейство связанных объектов
Как устроенМетод в родителе, наследник переопределяетОтдельный объект с несколькими методами createX()
Как сменитьСоздать другого наследникаПередать другую фабрику

Заметь: каждый метод абстрактной фабрики — это по сути фабричный метод. Паттерны часто живут вместе, как ингредиенты одного блюда.

Builder — строитель

Бутербродная: у бутерброда есть хлеб (обязательно), а ещё сыр, помидор, число котлет и соус — всё по желанию. Пусть сначала у класса Sandwich будет обычный конструктор на все пять полей. Вызов выглядит так:

Sandwich s = new Sandwich("ржаной", true, false, 2, "горчица");

Что значит false? Без помидора? Без лука? Через месяц не вспомнит никто. А если параметров семь и почти все необязательные, придётся писать кучу конструкторов на все сочетания — их называют «телескопическими». Сеттеры тоже не спасают: объект какое-то время живёт недособранным, и его можно поменять в любой момент.

Строитель (Builder) — отдельный объект-помощник, который собирает настройки по шагам, а в конце одним вызовом build() выдаёт готовый объект:

public class Sandwich {
    private final String bread;
    private final boolean cheese;
    private final boolean tomato;
    private final int cutlets;
    private final String sauce;

    private Sandwich(Builder b) {      // только через строителя
        this.bread = b.bread;
        this.cheese = b.cheese;
        this.tomato = b.tomato;
        this.cutlets = b.cutlets;
        this.sauce = b.sauce;
    }

    @Override
    public String toString() {
        return "Бутерброд: хлеб " + bread + ", котлет " + cutlets
                + (cheese ? ", сыр" : "") + (tomato ? ", помидор" : "")
                + ", соус " + sauce;
    }

    public static class Builder {
        private final String bread;            // обязательный — в конструкторе
        private boolean cheese = false;        // необязательные
        private boolean tomato = false;
        private int cutlets = 1;
        private String sauce = "без соуса";

        public Builder(String bread) {
            this.bread = bread;
        }

        public Builder cheese() {
            this.cheese = true;
            return this;                       // вернуть себя — секрет цепочки
        }

        public Builder tomato() {
            this.tomato = true;
            return this;
        }

        public Builder cutlets(int count) {
            this.cutlets = count;
            return this;
        }

        public Builder sauce(String sauce) {
            this.sauce = sauce;
            return this;
        }

        public Sandwich build() {
            if (cutlets < 1 || cutlets > 3) {
                throw new IllegalArgumentException(
                        "Котлет можно от 1 до 3, а не " + cutlets);
            }
            return new Sandwich(this);
        }
    }
}
Sandwich lunch = new Sandwich.Builder("ржаной")
        .cutlets(2)
        .cheese()
        .sauce("горчица")
        .build();
System.out.println(lunch);
Бутерброд: хлеб ржаной, котлет 2, сыр, соус горчица
public static class Builder

Новое для тебя: вложенный класс — класс, объявленный внутри другого. Полное имя — Sandwich.Builder. Слово static значит, что для него не нужен объект Sandwich: строитель создаётся сам по себе. Вложенный и внешний классы — одна семья: они видят private-поля друг друга, поэтому конструктор Sandwich читает b.bread.

return this;

Каждый метод настройки возвращает тот же самый строитель. Поэтому после .cutlets(2) можно сразу писать .cheese() — вызов применяется к результату предыдущего. Это и есть цепочка вызовов (fluent interface).

private Sandwich(Builder b)

Приватный конструктор: недособранный бутерброд снаружи не создать. Все поля final — готовый объект уже не меняется.

build()

Последний шаг: проверить, что набор параметров разумный, и создать объект. Все проверки — в одном месте, а не разбросаны по программе.

Что будет, если метод cheese() объявить как public void cheese() { this.cheese = true; }, а цепочку не трогать?

Не скомпилируется. .cheese() теперь возвращает void — «ничего». У «ничего» нельзя вызвать .sauce(…), и IDEA подчеркнёт следующий вызов в цепочке красным. Без return this строитель всё ещё работает, но только отдельными строками: b.cheese(); b.sauce("горчица");.

Родственник, которого ты знаешь, — StringBuilder. Его append тоже возвращает this, поэтому пишут new StringBuilder().append("Привет, ").append(name).append("!").toString(). Идея та же — собирать по шагам и в конце получить готовое. В JDK есть и «настоящие» строители, например HttpRequest.newBuilder()…build() для запросов к сайтам.

Когда строитель нужен, а когда нет

Строитель хорош, когда параметров много (примерно от четырёх) и большая часть — необязательные. Для двух-трёх обязательных полей хватит обычного конструктора или record: строитель там — лишние сорок строк. Снова KISS.

Задача

В задачах модуля тебя ждёт «Пиццерия»: заказ пиццы со строителем, проверка размера в build() и пицца дня одной цепочкой.

Prototype — прототип

Иногда проще не собирать объект заново, а взять готовый и сделать копию. Плейлист «В дорогу» уже настроен — хочется такой же, только добавить пару песен. Прототип (Prototype): объект сам умеет создавать свою копию, а тот, кто копирует, не обязан знать, как он устроен внутри.

Ещё в модуле 10 ты видел: Playlist copy = road; — это не копия, а вторая ссылка на тот же объект. Настоящую копию в Java чаще всего делают конструктором копирования:

import java.util.ArrayList;
import java.util.List;

public class Playlist {
    private final String title;
    private final List<String> songs;

    public Playlist(String title, List<String> songs) {
        this.title = title;
        this.songs = new ArrayList<>(songs);
    }

    // конструктор копирования: «сделай такой же, как этот»
    public Playlist(Playlist other) {
        this.title = other.title;                  // String не меняется
        this.songs = new ArrayList<>(other.songs); // свой новый список
    }

    public Playlist copy() {
        return new Playlist(this);
    }

    public void add(String song) {
        songs.add(song);
    }

    @Override
    public String toString() {
        return title + " " + songs;
    }
}
Playlist road = new Playlist("В дорогу", List.of("Кино"));
Playlist copy = road.copy();
copy.add("Сплин");
System.out.println(road);
System.out.println(copy);
В дорогу [Кино]
В дорогу [Кино, Сплин]

Самое важное в копировании — насколько глубоко копировать. У объекта есть поля-ссылки (у нас — список песен). Можно скопировать ссылку, а можно создать новый список:

Поверхностная копия
(shallow copy) Новый объект, но поля-ссылки скопированы как ссылки: вложенные объекты общие у оригинала и копии.
Глубокая копия
(deep copy) Вложенные изменяемые объекты тоже скопированы — копия ни с кем ничего не делит.
В конструкторе копирования поменяли строку на this.songs = other.songs;. Что теперь напечатает System.out.println(road) после copy.add("Сплин")?

В дорогу [Кино, Сплин]. Копия поверхностная: road и copy — разные объекты, но поле songs у обоих ссылается на один список. Песню добавили «в копию», а изменился общий список. Такие баги очень трудно искать: объект меняется, хотя его никто не трогал.

А как же clone()? У массивов он удобный: int[] backup = scores.clone();. Но и он поверхностный: у массива объектов скопируются ссылки, а не сами объекты. Для своих классов clone() из Object капризный: нужен интерфейс Cloneable, исключение CloneNotSupportedException, приведение типа, и копия по умолчанию поверхностная. Поэтому в Java обычно пишут конструктор копирования или метод copy(), как выше. А неизменяемые объекты (String, record с неизменяемыми полями) копировать не нужно вовсе: испортить их через общую ссылку нельзя.

Поговори с наставником

Спроси: «Объясни на примере из жизни разницу между фабричным методом и абстрактной фабрикой», «Почему одиночку называют антипаттерном и чем его заменяют в больших программах?» или «У моего класса такие поля: …. Нужен ли тут строитель или хватит конструктора?»

Коротко

  • Паттерн — проверенный рецепт для типичной задачи и общий словарь разработчиков. 23 паттерна GoF делятся на порождающие, структурные и поведенческие. Применяй, когда без него больно, а не «для красоты».
  • Singleton: приватный конструктор + static final-поле + getInstance(), или enum. Минусы: глобальное состояние, спрятанные зависимости, мешает тестам. «Ленивый» вариант в многопоточной программе — ловушка.
  • Factory Method: статическая фабрика (List.of, Integer.valueOf) прячет new; в GoF родитель объявляет createX(), наследник решает, что создать.
  • Abstract Factory: один объект создаёт целое семейство совместимых объектов.
  • Builder: обязательное — в конструктор строителя, необязательное — методами, которые возвращают this, в конце build() с проверками. Родственник — StringBuilder.
  • Prototype: копия готового объекта через конструктор копирования или copy(). Поверхностная копия делит вложенные объекты, глубокая — нет. clone() у массивов поверхностный.
