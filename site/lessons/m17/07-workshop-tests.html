Мастерская: какие тесты написать

Писать тесты ты уже умеешь. Главный вопрос теперь другой: какие именно значения проверить, чтобы тестов было немного, а баги не проскочили? У этого вопроса есть метод — как у задач на алгоритмы.

Повторение

Сколько тестов достаточно?

Задача: метод переводит баллы за экзамен в оценку. Требования от преподавателя:

Требования

Баллы — целое число от 0 до 100. 0–49 → 2, 50–69 → 3, 70–84 → 4, 85–100 → 5. Баллы меньше 0 или больше 100 — ошибка IllegalArgumentException.

Проверить все 101 значение? Здесь ещё можно, но обычно входов бесконечно много: любые строки, любые суммы. Проверить «пару случайных»? Так баги и проскакивают. Нужен метод, и он похож на шаблон Мастерской, по которому ты решал задачи на алгоритмы:

Мастерская алгоритмовМастерская тестов
1. Пойми задачу: вход и выход1. Прочитай требования: что на входе, что на выходе, что считается ошибкой
2. Реши руками на примерах2. Раздели входы на классы эквивалентности
3. Роли переменных3. Найди границы между классами
4. Псевдокод4. Таблица тестов: вход → ожидаемый результат
5. Код5. Код теста (часто параметризованный)
6. Проверь трассировкой6. Запусти; красный — разберись отладчиком
Тестируй требования, а не код

Ожидаемые значения берутся из требований, а не из того, что сейчас возвращает метод. Если подглядеть в код и написать «ожидаю то, что он вернул», тест повторит ошибку кода и будет зелёным вместе с багом.

Классы эквивалентности и границы

Класс эквивалентности — группа входов, на которых программа должна вести себя одинаково. 55 и 60 баллов — оба «тройка»: если метод правильно работает для 55, почти наверняка и для 60. Значит, из каждого класса хватит одного-двух представителей.

Аналогия: дегустация супа

Чтобы понять, посолен ли борщ, не нужно съесть всю кастрюлю — хватит ложки. Но если на плите пять разных кастрюль, ложку надо взять из каждой. Классы эквивалентности — это кастрюли.

Почему именно границы? Потому что в коде граница — это знак сравнения, а > вместо >= или 49 вместо 50 — самые частые ошибки на свете. Значение из середины класса (60) такой баг не заметит: и points > 50, и points >= 50 для 60 дают одно и то же. А 50 — заметит.

В коде написано if (points > 50) return 3; вместо >= 50. Какие из значений 49, 50, 51, 60 поймают баг?

Только 50. Для 49 оба варианта дают «не тройка», для 51 и 60 — «тройка». Отличаются они ровно в одной точке — на границе. Поэтому значение «на самой границе» обязательно.

Нет. Покрытие говорит только, какие строки выполнились, а не что их результат проверили. Тест без assert зелёный при любом баге, хоть покрытие и 100%. Покрытие помогает найти непроверенные места, но не заменяет классы, границы и честные проверки.

Хорошие привычки

Несколько правил, по которым опытные коллеги отличают хорошие тесты и хороший код. Их часто называют аббревиатурой FIRST:

⚡

Fast — быстрые

Медленные тесты перестают запускать. Юнит-тест — миллисекунды.

🧱

Independent — независимые

Любой тест можно запустить один и в любом порядке.

🔁

Repeatable — повторяемые

Сегодня, завтра, у тебя и на сервере — один результат. Никаких «упал, перезапустил — прошёл».

✅

Self-validating — сами решают

Зелёный или красный без чтения вывода глазами. Есть проверка (assert) — есть решение.

⏱️

Timely — вовремя

Тест пишут вместе с кодом или сразу после найденного бага, а не «когда-нибудь».

  • Читаемые имена — и для классов и методов, и для тестов. Через полгода ты сам будешь «коллегой», который читает этот код.
  • Нашёл баг — сначала тест, который его ловит (красный), потом исправление (зелёный). Тест и исправление — в одном коммите: Почини оценку для 85 баллов.
  • Маленькие коммиты: одна мысль — один коммит. Их легко ревьюить и легко откатить.
  • Код-ревью тестов — такое же, как кода: есть ли assert, проверены ли границы, понятно ли имя, не зависит ли тест от соседей.

Проверь себя

Мастерская с наставником

Перед задачами «Билеты в кино» и «Охота на баг» напиши: «Вот моя таблица классов и границ для задачи …, проверь план, пока я не начал писать код». Наставник оценит план, а не только зелёные тесты.

Коротко

  • Тесты строят по требованиям, а не по коду.
  • Классы эквивалентности: входы с одинаковым поведением — хватает представителя из каждого.
  • Границы: проверяй значение на стыке и рядом с ним — там живут >/>= и «плюс-минус один».
  • План — таблица «вход → ожидаем», код — параметризованный тест; красный тест разбирай отладчиком.
  • Run with Coverage показывает строки, которые тесты ни разу не выполнили (красные). 100% покрытия не значит «всё проверено».
  • FIRST: быстрые, независимые, повторяемые, с assert, написанные вовремя. Баг → красный тест → исправление → коммит.
