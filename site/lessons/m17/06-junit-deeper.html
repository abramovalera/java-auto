Повторение

@BeforeEach и @AfterEach: подготовка и уборка

Часто каждому тесту нужна одна и та же подготовка: создать корзину, положить товары, завести покупателя, подключиться к базе. Копировать её в каждый тест — плохо: поменяется подготовка — придётся править двадцать мест. Поэтому подготовку выносят в отдельный метод и помечают его аннотацией — JUnit сам вызовет этот метод в нужный момент:

АннотацияКогда выполняетсяПример из рабочих тестов
@BeforeEachперед каждым тестомсоздать новую корзину и тестовые данные
@AfterEachпосле каждого теста — даже упавшегоудалить созданные данные и временные файлы
@BeforeAllодин раз до всех тестов класса; метод staticподключиться к базе, прочитать настройки
@AfterAllодин раз после всех; метод staticотключиться от базы, удалить временную папку
Аналогия: ресторан

@BeforeAll — утром открыть ресторан и включить плиты. @BeforeEach — перед каждым гостем постелить чистую скатерть. Тест — обслужить гостя. @AfterEach — убрать со стола. @AfterAll — вечером выключить плиты и закрыть дверь.

Пройди по шагам, в каком порядке JUnit вызывает методы, — и следи за кучей: перед каждым тестовым методом JUnit создаёт новый объект тестового класса.

Вот почему тесты обязаны быть независимыми: каждый получает свежий объект и свою подготовку. Тест, который рассчитывает, что «предыдущий тест уже положил товар в корзину», сломается, как только JUnit поменяет порядок или ты запустишь его один.

Схема жизненного цикла

Что будет, если забыть static у метода с @BeforeAll?

Скомпилируется, но при запуске JUnit откажется: @BeforeAll method … must be static — и ни один тест класса не выполнится. Логика простая: метод вызывается до создания любого объекта, значит, вызвать его можно только у класса.

@DisplayName и @Disabled

@Test
@DisplayName("Заказ на 500 ₽ — доставка 199 ₽")
void smallOrderPaysFee() {
    assertEquals(199, DeliveryFee.feeFor(500));
}

@Test
@Disabled("Ждём исправления бага SHOP-123: скидка для 0 ₽")
void zeroDiscountEdgeCase() {
    // …
}
  • Аннотация @DisplayName с аргументом-строкой — человеческое имя теста в отчёте, можно по-русски, с пробелами и символами. Имя метода остаётся для кода, DisplayName — для людей, читающих отчёт.
  • Аннотация @Disabled("причина") — тестовый метод пропускается: в отчёте он жёлтый/серый (skipped), а не красный. Применяют, когда тест временно нельзя запускать — например, ждут исправления известного бага. Всегда пиши причину и номер задачи — иначе через год никто не вспомнит, можно ли его включить.

Параметризованные тесты

Проверить доставку для сумм 1, 1999, 2000 и 5000 — четыре почти одинаковых теста. Вместо копипасты — один тест и таблица данных:

import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.CsvSource;
import org.junit.jupiter.params.provider.ValueSource;

@ParameterizedTest(name = "сумма {0} → доставка {1}")
@CsvSource({
        "1, 199",
        "1999, 199",
        "2000, 0",
        "5000, 0"
})
void feeDependsOnSum(int orderSum, int expectedFee) {
    assertEquals(expectedFee, DeliveryFee.feeFor(orderSum));
}

@ParameterizedTest
@ValueSource(ints = {0, -1, -500})
void nonPositiveSumIsRejected(int orderSum) {
    assertThrows(IllegalArgumentException.class,
            () -> DeliveryFee.feeFor(orderSum));
}
@ParameterizedTest

Аннотация вместо @Test. У тестового метода появляются параметры, и JUnit вызывает его по разу на каждый набор данных, передавая значения как аргументы. В отчёте — отдельная строка на каждый запуск.

@CsvSource({"1, 199", …})

Каждая строка — один вызов; значения через запятую становятся аргументами по порядку параметров: параметр orderSum получает 1, expectedFee — 199. JUnit сам превратит текст в int.

@ValueSource(ints = {0, -1, -500})

Когда параметр один: значения перечислены массивом, по одному на вызов. Есть strings = {…}, doubles = {…} и другие.

name = "сумма {0} → доставка {1}"

Имя каждого запуска в отчёте: {0} и {1} заменятся на значения параметров.

Сколько строк-тестов появится в отчёте от этих двух методов?

7: четыре запуска feeDependsOnSum (по строке @CsvSource) и три запуска nonPositiveSumIsRejected. Упадёт одна строка — остальные всё равно выполнятся, и сразу видно, на каких данных сломалось.

🔎 Для любопытных: другие источники данных

@NullAndEmptySource подставит null и пустую строку — удобно для полей формы. @EnumSource(Color.class) — все значения enum. @MethodSource("users") — данные из static-метода, который возвращает Stream наборов: так передают сложные объекты.

AssertJ: проверки, которые читаются как фраза

AssertJ — библиотека проверок, которую любят Java-разработчики. Главная идея — fluent-стиль («текучий»): начинаешь с вызова assertThat(фактическое), ставишь точку — и IDEA подсказывает все методы-проверки, подходящие к этому типу. Проверки вызываются цепочкой: каждая возвращает тот же объект, и к нему можно дописать следующую через точку.

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;

assertThat(DeliveryFee.feeFor(500)).isEqualTo(199);

assertThat("Java").startsWith("Ja").endsWith("va").hasSize(4);

List<String> names = List.of("Аня", "Боря", "Вика");
assertThat(names).hasSize(3).contains("Боря").doesNotContain("Петя");
assertThat(names).containsExactly("Аня", "Боря", "Вика");
assertThat(names).containsExactlyInAnyOrder("Вика", "Аня", "Боря");
assertThat(new ArrayList<String>()).isEmpty();

assertThatThrownBy(() -> DeliveryFee.feeFor(0))
        .isInstanceOf(IllegalArgumentException.class)
        .hasMessageContaining("больше нуля");

assertThat(DeliveryFee.feeFor(500))
        .as("доставка для заказа на 500 ₽")
        .isEqualTo(199);

Почему AssertJ так любят в тестах

📖

Читается как текст

«Убедись, что имена содержат ровно Аня, Боря, Вика». И нельзя перепутать ожидаемое с фактическим: фактическое всегда в assertThat(…).

Сотни проверок

Для строк, списков, Map, дат, исключений, файлов. Подсказка IDEA после точки — твой справочник.

Вот настоящее сообщение AssertJ, когда containsExactly не сошёлся (автор курса сам на него наткнулся, проверяя задачу этого модуля: в слове «программирование» прячется «мир»):

Что проверяет строчка assertThat(names.contains("Боря"));?

Ничего! Вызов assertThat(…) только создаёт объект-проверку для фактического значения («берёт значение в руки»), а проверяет метод, который вызывают после точки. Без .isTrue() тест всегда зелёный. Правильно: assertThat(names).contains("Боря") — и сообщение при падении будет понятнее, чем у isTrue().

🔎 Для любопытных: мягкие проверки (soft assertions)

Обычный тест останавливается на первой упавшей проверке. А у профиля пользователя хочется проверить сразу имя, email и телефон — и увидеть все расхождения за один прогон. Для этого в AssertJ есть SoftAssertions.assertSoftly(softly -> { softly.assertThat(name).isEqualTo("Аня"); softly.assertThat(email).contains("@"); }) — все ошибки собираются и показываются вместе в конце.

Покажи наставнику

Задача: «Каталог книг: AssertJ и @BeforeEach». Задачу «Билеты в кино» оставь на после урока 17.7: там нужно уметь выбирать значения для тестов. После «Каталога» напиши: «/check m17-t06 — и спроси меня, зачем тут @BeforeEach, а не одна общая корзина на все тесты».

Коротко

  • @BeforeEach/@AfterEach — вокруг каждого теста; @BeforeAll/@AfterAll — раз на класс, static.
  • Каждый тест — новый объект тестового класса; тесты независимы, порядок не гарантирован.
  • @DisplayName — имя для отчёта, @Disabled("причина") — пропустить.
  • @ParameterizedTest + @CsvSource/@ValueSource — один тест на много данных.
  • AssertJ: assertThat(фактическое).проверка(…); containsExactly, hasSize, assertThatThrownBy, .as(…). Без метода после точки ничего не проверяется.
