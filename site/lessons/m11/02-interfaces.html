Интерфейсы: контракт «умеет делать»

Птица, самолёт и супермен — не родственники. Но все трое умеют летать. Как объяснить это Java? Знакомимся с самой важной идеей модуля.

Повторение

Общего родителя нет

Делаем игру. В ней есть птица, самолёт и супермен, и все они должны уметь летать. Попробуем через абстрактный класс Flyer с абстрактным fly()?

Не выходит. Птица уже наследуется от Animal (у неё есть имя, возраст, она ест), самолёт — от Machine (бензин, ремонт), супермен — от Hero. А родитель у класса в Java только один: class Bird extends Animal, Flyer — ошибка компиляции.

Да и по смыслу самолёт — не «разновидность летуна», как кот — разновидность животного. Полёт — это не кто он такой, а что он умеет. Для «умеет» в Java есть отдельный инструмент.

Интерфейс — список умений

Интерфейс — это контракт: набор методов, которые класс обещает уметь. Сам интерфейс ничего не делает, он только перечисляет заголовки методов — объявляет их без тела.

interface Flyable {
    void fly();                  // кто подписал контракт — обязан уметь fly()
}

class Bird extends Animal implements Flyable {
    @Override
    public void fly() {
        System.out.println("Птица машет крыльями");
    }
}

class Plane extends Machine implements Flyable {
    @Override
    public void fly() {
        System.out.println("Самолёт запускает двигатели");
    }
}
interface Flyable

Объявление интерфейса. Вместо class — слово interface. Имена часто заканчиваются на -able («способный к…»): Flyable, Runnable, Comparable.

void fly();

Абстрактный метод — без тела. В интерфейсе он автоматически public abstract — писать эти слова не нужно.

implements Flyable

Реализация интерфейса: класс реализует интерфейс — «подписывает контракт». Теперь компилятор требует реализовать (написать с телом) все абстрактные методы интерфейса. Сначала extends, потом implements.

public void fly()

public обязателен! В интерфейсе метод публичный, и в реализации нельзя сузить модификатор доступа — сделать метод «закрытее».

Писать заголовки методов интерфейса руками не обязательно. Напиши class Plane extends Machine implements Flyable { } — IDEA подчеркнёт класс красным, как абстрактный класс в уроке 1. Поставь курсор внутрь класса и нажми Ctrl+I:

Аналогия: розетка и вилка

Розетке всё равно, что в неё включают: чайник, лампу или зарядку. Ей важно одно — чтобы вилка подходила под стандарт. Интерфейс — это стандарт розетки, а классы — приборы с подходящей вилкой. Так же USB: в порт втыкается флешка, мышь, телефон — порт знает только «стандарт USB», а не марку устройства.

Забыл public — компилятор напомнит:

error: fly() in Plane cannot implement fly() in Flyable
    void fly() {
         ^
  attempting to assign weaker access privileges; was public

Полиморфизм через интерфейс

Главная сила интерфейса — переменная его типа. Она может хранить ссылку на любой объект, чей класс реализует интерфейс («подписал контракт»), даже если классы никак не связаны:

Flyable[] flyers = { new Bird(), new Plane(), new Superman() };
for (Flyable f : flyers) {
    f.fly();
}
Предскажи: что напечатает цикл, если Superman печатает «Супермен вытягивает кулак вперёд»? 
Птица машет крыльями
Самолёт запускает двигатели
Супермен вытягивает кулак вперёд

Цикл не знает, кто перед ним. Он знает только, что у каждого есть fly(), а какая реализация fly() вызовется, зависит от объекта, на который указывает ссылка f, — тот же полиморфизм, что в модуле 10.

Предскажи: у Plane есть метод refuel(). Скомпилируется ли Flyable f = new Plane(); f.refuel();?

Нет. Через переменную типа Flyable можно вызвать только методы, объявленные в интерфейсе, — fly(). Что объект «на самом деле» самолёт, компилятор не знает. Это как розетка: она даёт ток, но не умеет нажимать кнопки на чайнике.

Несколько интерфейсов сразу

Родитель у класса один, а контрактов — сколько угодно. Утка и летает, и плавает:

interface Swimmable {
    void swim();
}

class Duck extends Animal implements Flyable, Swimmable {
    @Override
    public void fly() {
        System.out.println("Утка летит на юг");
    }

    @Override
    public void swim() {
        System.out.println("Утка плывёт по пруду");
    }
}

Теперь утку можно положить и в «список летающих», и в «список плавающих»: ссылку на один объект Duck можно присвоить и переменной типа Flyable, и переменной типа Swimmable. Один объект — несколько «ролей»:

Duck duck = new Duck();
Flyable f = duck;     // смотрим на утку как на летающую — видно только fly()
Swimmable s = duck;   // смотрим как на плавающую — видно только swim()
Как запомнить

extends — один родитель: «кто я такой». implements — класс реализует много интерфейсов («контрактов») через запятую: «что я умею». Человек — один, а водительских, рыбацких и поварских удостоверений у него может быть сколько угодно.

🔎 Для любопытных: интерфейс может расширять интерфейс

Интерфейсы тоже наследуются, и тут родителей может быть несколько: interface Amphibian extends Flyable, Swimmable { }. Класс, реализующий Amphibian, обязан написать и fly(), и swim(). Для интерфейсов слово — extends, не implements: интерфейс ничего не реализует, он только дополняет список.

И instanceof работает с интерфейсами: if (obj instanceof Flyable f) { f.fly(); }.

Где это в настоящих программах

Интернет-магазин принимает деньги картой, по QR-коду, электронным кошельком. Способ оплаты описывают интерфейсом Payment: «заплати сумму», «назови себя». А классы для карты, QR-кода и кошелька — его реализации. Кассу пишут против интерфейса — и она принимает любой способ. Вот эта идея в коде:

interface Payment {
    void pay(int amount);
    String name();
}

class CardPayment implements Payment {
    public void pay(int amount) {
        System.out.println("Списываю с карты " + amount + " ₽");
    }

    public String name() { return "карта"; }
}

class QrPayment implements Payment {
    public void pay(int amount) {
        System.out.println("Оплата по QR-коду: " + amount + " ₽");
    }

    public String name() { return "QR-код"; }
}

class Checkout {
    // кассе всё равно, чем платят
    static void buy(Payment payment, int price) {
        payment.pay(price);
        System.out.println("Чек: оплачено, способ — " + payment.name());
    }
}

Поменять способ оплаты = поменять одно слово — объект какого класса создаём и передаём аргументом: buy(new CardPayment(), 500) → buy(new QrPayment(), 500). Сама касса не меняется. Именно поэтому в больших программах так много интерфейсов.

Запомни фразу, которую любят на собеседованиях: «программируй на уровне интерфейсов, а не реализаций». Это она и есть: параметр метода имеет тип интерфейса Payment, а не класса CardPayment.

Проверь себя

Поговори с наставником

Напиши: «Придумай три класса из разных “семей”, которые умеют одно и то же, а я опишу для них интерфейс и цикл по массиву».

Коротко

  • Интерфейс — контракт «умеет делать»: список абстрактных методов без тела (они автоматически public abstract).
  • implements — класс реализует интерфейс («подписывает контракт»); реализации методов — обязательно public.
  • Родитель-класс один, интерфейсов — сколько угодно: extends A implements X, Y.
  • Переменная/массив типа интерфейса хранит ссылки на объекты любых классов, реализующих интерфейс, — даже из разных «семей». Вызвать можно только методы интерфейса.
  • Код пишут против интерфейсов (Payment p = new CardPayment()), чтобы менять реализацию одной строкой.
