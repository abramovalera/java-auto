default и static в интерфейсах. Интерфейс или абстрактный класс?

Интерфейсы умеют больше, чем просто перечислять заголовки: в них бывают методы с телом и константы. Разберёмся, зачем это придумали, где ловушка «ромба» — и как выбирать между интерфейсом и абстрактным классом.

Повторение

Проблема: интерфейс уже все используют

Представь: интерфейс Flyable реализуют сто классов в десяти проектах. Однажды понадобилось, чтобы каждый летун ещё и умел приземляться. Добавляем в интерфейс void land(); — и все сто классов перестают компилироваться: никто из них не написал land().

Ровно с такой бедой столкнулись авторы самой Java, когда захотели добавить новые методы в старые интерфейсы JDK. Решение появилось в Java 8 — default-методы: метод интерфейса с телом, который наследуют все классы, реализующие интерфейс, — «по умолчанию».

interface Flyable {
    void fly();                              // обычный абстрактный метод

    default void land() {                    // метод с телом прямо в интерфейсе
        System.out.println("Мягкая посадка");
    }
}

class Bird implements Flyable {
    public void fly() { System.out.println("Птица взлетает"); }
    // land() не пишем — достанется готовый
}

class Plane implements Flyable {
    public void fly() { System.out.println("Самолёт взлетает"); }

    @Override
    public void land() {                     // а здесь своя посадка
        System.out.println("Выпускаю шасси");
    }
}
default void land() { … }

Слово default + тело. Классы-реализации могут унаследовать его как есть или переопределить (@Override), как обычный метод родителя.

public void land()

При переопределении — снова public: в интерфейсе всё публичное.

Предскажи: что напечатают new Bird().land() и new Plane().land()?

«Мягкая посадка» — у Bird вызывается унаследованный default-метод. «Выпускаю шасси» — в Plane метод переопределён. Старые классы не сломались, а новым есть что настроить.

default — не повод тащить всё в интерфейс

У интерфейса нет полей объекта, поэтому default-метод может пользоваться только другими методами интерфейса. Это «удобная надстройка над контрактом», а не замена абстрактному классу.

Вызвать default из своей реализации. И проблема ромба

Иногда хочется не заменить метод по умолчанию, а дополнить его. Для этого есть особая запись ИмяИнтерфейса.super.метод() — вызов default-версии метода из интерфейса:

class Plane implements Flyable {
    public void fly() { System.out.println("Самолёт взлетает"); }

    @Override
    public void land() {
        System.out.println("Выпускаю шасси");
        Flyable.super.land();                // и ещё посадка «по умолчанию»
    }
}
Выпускаю шасси
Мягкая посадка

А теперь ловушка, которую обожают на собеседованиях. Класс реализует два интерфейса, и в обоих есть default-метод с одинаковым заголовком:

interface Robot {
    default String hello() { return "Бип-буп"; }
}
interface Human {
    default String hello() { return "Привет"; }
}

class Android implements Robot, Human { }      // ✗ какой hello() взять?
error: types Robot and Human are incompatible;
  class Android inherits unrelated defaults for hello() from types Robot and Human

Починка — переопределить метод в классе и решить самому. Можно вызвать один из вариантов или оба через Интерфейс.super.hello():

class Android implements Robot, Human {
    @Override
    public String hello() {
        return Human.super.hello() + " / " + Robot.super.hello();
    }
}
Привет / Бип-буп

Почему «ромб» (diamond)? Название пришло из классической схемы: наверху общий предок с методом hello(), под ним два наследника, каждый переделал hello() по-своему, а внизу класс, который унаследовал обоих. Если соединить стрелками — получится ромб с четырьмя углами. В нашем примере общего предка нет, и схема похожа на треугольник, но суть та же: два разных варианта одного метода, и непонятно, какой взять. С классами Java эту проблему отрезала на корню — родитель только один. А с интерфейсами она возможна, но компилятор не даст её проглядеть.

static-методы и константы

В интерфейсе можно объявлять статические методы (static — член интерфейса, а не объекта) — помощников, связанных с контрактом. Вызываются они только через имя интерфейса: реализации их не наследуют.

interface Flyable {
    void fly();

    static int maxHeightMeters() {
        return 10000;
    }
}

// ✓ через имя интерфейса
int h = Flyable.maxHeightMeters();
// ✗ ошибка: static-методы интерфейса не наследуются
int x = Bird.maxHeightMeters();

А любое поле интерфейса — это константа. Даже если ты не написал ни одного слова, Java добавит public static final:

interface Limits {
    // на самом деле: public static final int MAX_RETRIES = 3;
    int MAX_RETRIES = 3;
}

System.out.println(Limits.MAX_RETRIES);  // 3
// ✗ cannot assign a value to final variable
Limits.MAX_RETRIES = 5;
Интерфейс — не склад констант

Раньше программисты заводили интерфейсы, в которых были только константы. Сейчас так не делают: константы объявляют в классе, а набор вариантов вроде статусов заказа NEW/PAID/DELIVERED — в enum, его разберём через урок.

🔎 Для любопытных: private-методы в интерфейсе

С Java 9 в интерфейсе можно писать и private-методы с телом. Их видят только default- и static-методы этого же интерфейса — чтобы не копировать общий кусок кода между ними. Реализации о них не знают.

В JDK default и static-методов полно. Например, у Comparator (следующий урок) есть default-метод reversed() — «тот же порядок, только наоборот». С ним мы встретимся в модуле про лямбды.

Интерфейс или абстрактный класс?

Оба — «заготовки»: создать объект ни абстрактного класса, ни интерфейса через new нельзя. Но задумывались они для разного.

  1. Нужно общее состояние (поля) и конструктор для родственных классов → абстрактный класс.
  2. Нужно умение, которое может появиться у совсем разных классов → интерфейс.
  3. Сомневаешься → начни с интерфейса: он не занимает единственное место «родителя».
  4. Часто используют оба: интерфейс как контракт + абстрактный класс, который реализует его общую часть. Как это выглядит в коде — в следующем шаге.

Потренируйся: куда бы ты отнёс каждую ситуацию?

Оба сразу: интерфейс → абстрактный класс → наследники

Самая частая связка в настоящих программах — три этажа. Наверху интерфейс: что умеет каждый. Посередине абстрактный класс: он реализует интерфейс, но пишет только общую часть — то, что у всех одинаково. Внизу конкретные наследники дописывают остальное. Пример — игрушки на батарейках:

interface Toy {
    String name();
    String sound();
    void charge(int minutes);
    int battery();                 // заряд в процентах
}

// реализует Toy, но не целиком — поэтому abstract
abstract class BatteryToy implements Toy {
    private int battery;           // общее состояние — поле

    public void charge(int minutes) {
        battery = Math.min(100, battery + minutes);
    }

    public int battery() {
        return battery;
    }
    // name() и sound() не пишем: их допишут наследники
}

class ToyCar extends BatteryToy {
    public String name() { return "Машинка"; }
    public String sound() { return "Вжж"; }
}

class ToyDuck extends BatteryToy {
    public String name() { return "Утка"; }
    public String sound() { return "Кря"; }
}

public class Toys {
    public static void main(String[] args) {
        Toy[] toys = { new ToyCar(), new ToyDuck() };
        toys[0].charge(30);
        for (Toy t : toys) {
            System.out.println(t.name() + ": " + t.battery() + "%, " + t.sound());
        }
    }
}
Машинка: 30%, Вжж
Утка: 0%, Кря
abstract class BatteryToy implements Toy

Абстрактный класс реализует интерфейс, но имеет право написать не все его методы. Недописанные (name(), sound()) остаются абстрактными — обязанность переходит к наследникам.

private int battery;

Поле можно держать только здесь: в интерфейсе полей объекта не бывает. Ради общего состояния абстрактный класс и нужен.

public void charge(…)

Методы, пришедшие из интерфейса, пишем с public — и в абстрактном классе, и в наследниках.

class ToyCar extends BatteryToy

Наследник получает готовые charge() и battery() и дописывает недостающие name() и sound(). Теперь все пять методов Toy на месте — объект создать можно.

Toy[] toys

В main работаем через интерфейс: циклу всё равно, машинка это или утка.

Предскажи: что будет, если у BatteryToy стереть слово abstract?

Ошибка компиляции: BatteryToy is not abstract and does not override abstract method sound() in Toy — «BatteryToy не абстрактный и не реализует метод sound() из Toy». Обычный (конкретный) класс обязан написать все методы интерфейса. Слово abstract как раз и разрешает оставить часть недописанной.

Где пригодится

Ровно так устроена задача практики «Умный дом»: интерфейс устройства, абстрактный класс с общим полем «включено» и три конкретных устройства.

Поговори с наставником

Напиши: «Задай мне три ситуации, а я скажу, что там лучше — интерфейс или абстрактный класс, и объясню почему».

Коротко

  • default-метод — метод интерфейса с телом; классы-реализации наследуют его готовым или переопределяют.
  • Вызвать версию по умолчанию из своей реализации: Интерфейс.super.метод().
  • Ромб: два интерфейса с одинаковым default → ошибка компиляции, пока класс не переопределит метод сам.
  • static-методы интерфейса вызываются только через его имя; поля интерфейса — всегда public static final.
  • Абстрактный класс — «кто ты» + общее состояние; интерфейс — «что умеешь», можно много. Сомневаешься — интерфейс.
  • Связка «интерфейс → абстрактный класс → наследники»: абстрактный класс реализует интерфейс частично (общее поле и общие методы), остальное дописывают наследники.
